    Long-Running Agents and Autonomy Levels: Letting an Agent Work for Hours, Safely

    Why an agent that works for hours needs memory outside its prompt, checkpoints it can resume from, and a way to recover from its own mistakes, and how to decide, task by task, how much freedom a banking agent should get.

    Contents

    The whole lesson in one sentenceA long-running agent is a process that will be interrupted, will forget, and will sometimes be wrong, so you design for resumption and for undo; and how much freedom to give it is a cost calculation on error rate, size of harm and reversibility, not a matter of trust or fashion.

    Part 1

    The intuition

    Picture a new analyst given a four-hour job: reconcile 3,000 trade-finance documents against the ledger. Halfway through, the laptop dies. A bad analyst restarts from scratch. A good one kept a running sheet of what is done, what rules were settled and what looked odd, and loses ten minutes.

    An AI agent on a long task is that analyst with two handicaps. Its working memory (the context window) is finite and gets summarised or cleared, so it forgets what was true an hour ago. And each step can go wrong: a step that is right 99.5% of the time gives a 400-step run only a 13% chance of finishing perfectly.

    The linked second question is how much may the agent do without asking? Summarising a complaint is harmless; releasing a AED 250,000 payment is not. Between them is a ladder of autonomy levels, and the right rung depends on how often the agent is wrong, how bad a wrong action is and whether it can be undone.

    Hold onto thisTreat a long-running agent like a distributed job, not a chat. State lives outside the prompt, progress is saved at checkpoints, every side effect is reversible or approved, and the autonomy level comes from risk arithmetic. The model's intelligence helps; the engineering around it makes hours-long work safe.
    Part 2

    How it really works

    Where the state lives: context, notes and the event log

    An agent loop is: read state, pick an action (tool call), see the result, repeat. Everything it "knows" is what is in its prompt right now, and on a long task the history outgrows the window. It is like working from a whiteboard that gets wiped: you need a notebook. Harnesses use four stores that differ in what they lose.

    StoreWhat it isLoses information?Use it for
    Context windowThe live prompt: instructions, recent steps, tool results.Yes, when full. Older content is dropped, cleared or summarised.What the next few steps need.
    Compaction summaryThe model rewrites its history into a shorter note and continues from it.Yes, and summaries of summaries lose more each time.Keeping the thread of reasoning. Not a record.
    Durable notes / files / databaseA progress file, task list or structured store the agent writes to and re-reads.Only what the agent forgot to write.Constraints, decisions, what is done, what is left.
    Event logAn append-only record of every action and result, kept by the harness, not the model.No.Audit, replay, resumption, "what exactly did it do?"

    The rule: anything that must survive goes into durable state, written deliberately. That means start-of-task constraints ("never contact customers flagged do-not-call"), decisions made on the way ("invoices under AED 500 are out of scope") and a list of what is finished. Anthropic's write-ups on long-running coding agents use this pattern: a setup step creates a progress file and feature list, then each fresh session reads them, does one piece of work and leaves the state tidy. A bigger window helps but does not say which information is authoritative or what survives a restart.

    Models also use long context unevenly: information buried in the middle is used less reliably than at the start or end (Liu et al., 2023). So keep a short "current state" block near the top of each step rather than rely on an ever-longer transcript.

    Checkpoints, resumption and idempotence

    A checkpoint is a saved snapshot of everything needed to continue: the plan, the notes, the position in the task and which side effects have happened. Like a video-game save point, it is keyed by a run ID so a crashed or paused run resumes, or rewinds and replays differently. Agent frameworks and durable workflow engines provide it, as database logs do.

    The catch: if the agent crashes after sending an email or posting a journal entry but before saving that it did, the resumed run does it again. The fix is idempotence: give each side-effecting action a unique key (for example a hash of run ID and step number) so the downstream system ignores the repeat, as payment systems already require. If an action cannot be made idempotent, record the intent before acting and check it on restart.

    How often to checkpoint? Saving costs time, tokens and writes; not saving means redoing work. If each step fails with probability q, a segment of c unsaved steps restarts from its start on any failure. Expected steps to finish one segment:

    E(c)=1−(1−q)cq(1−q)c

    One attempt runs until its first failure or completion; you retry until a clean pass, which takes 1 ÷ (1 − q)c attempts on average. With q = 0.5% and c = 400 that is about 1,285 steps, over three times the nominal 400. Checkpoints every 20 steps: 20 segments × 21 steps is 422 steps, plus saving costs. Long unsaved stretches and frequent saves both cost, so there is a sweet spot.

    Recovery: crashes are easy, wrong turns are hard

    Resumption handles an agent that stopped. The harder case is one that carried on confidently in the wrong direction: it misread a constraint at step 40 and has built on it for 200 steps. Four mechanisms cover this.

    • Verification gates. After each stage, a check that does not trust the agent's own report: a test, a reconciliation total, a second model or a rule. "Run the tests before marking a feature done" is this.
    • Compensating actions. Define an undo for each side effect. This is the saga pattern (Garcia-Molina and Salem, 1987): if step 7 fails, run the undos for steps 6 to 1. Reversibility is built in, not luck.
    • Stage, then commit. The agent prepares work in a draft area (a draft batch, a proposed journal) and a separate human or rule-based step commits it. Long autonomous effort, small irreversible surface.
    • Budgets and tripwires. Caps on steps, spend, records touched and wall-clock time, plus alarms on odd patterns (same call repeated, error spike). A looping or drifting agent should stop and ask.

    Runs are also getting longer. METR measures the human-expert task length a model completes with 50% reliability; its 2025 paper found this doubling roughly every seven months, and the 80% reliability horizon is much shorter. Treat any single figure with care. The point: afternoon-sized tasks are now in range, so the surrounding engineering matters more each quarter.

    Autonomy levels: a ladder, not a switch

    Autonomy is a per-task choice along a ladder, like a new driver going from instructor-in-the-car to driving alone. Each rung changes the human's role. The ladder below is a working one for a bank; it draws on automation research that separates what is automated from how much (Parasuraman, Sheridan and Wickens, 2000), and on agent-autonomy levels defined by the user's role (Feng et al., 2025).

    LevelHuman roleAgent mayTypical banking use
    L0 · SuggestDoes the work, reads suggestionsRead and recommend. No actions.Drafting a reply, highlighting clauses in a trade document.
    L1 · Approve each actionApproves every step before it runsPrepare actions and wait.Payment releases, limit changes, sending customer messages.
    L2 · Approve the exceptionsReviews flagged or high-value items onlyAct within limits; escalate on triggers.KYC document triage, alert closure under a threshold.
    L3 · Act, sample afterwardsAudits a sample, monitors dashboardsAct within a narrow scope and reversible actions.Tagging transactions, internal ticket routing.
    L4 · Act freelyWatches aggregate healthAct, log, report.Summaries, search, formatting, test-data generation.

    Three variables set the rung. Error rate e: how often the agent is wrong on realistic cases (A4). Harm h: the AED, regulatory or reputational cost of one wrong action. Reversibility ρ: the share of that harm you can undo once you notice. Human review costs money and time too. So expected cost per action = review cost + harm that slips through.     Two refinements. Dynamic autonomy: run L2 under AED 5,000 and L1 above, and drop a rung when recent errors rise or inputs look odd. Approvals degrade: a person asked to approve 400 items a day stops reading. A rubber-stamp L1 is an L4 with false comfort, so measure how often approvers change or reject items, and how long they spend.

    Part 3

    How it fails, and how to spot it

    • Constraint amnesia after compaction

      The agent obeys "never touch accounts under dispute" for two hours, then a summary drops the rule.

      Spot itAre constraints in a durable, re-read block? Force a compaction mid-run and check behaviour.
    • Double execution on resume

      A crash after a payment instruction but before the save leads to a second instruction.

      Spot itAsk how each side-effecting tool handles a repeated call with the same key. Kill the run mid-step in testing.
    • Summary drift

      "Customer verified" in one summary is copied into the next without evidence and becomes fact.

      Spot itNotes must record evidence and source; re-verify critical facts against the system of record.
    • Loops and silent spinning

      The agent retries a failing tool 300 times, or declares success without doing the work.

      Spot itStep, spend and time budgets; alerts on repeated identical calls; verification of outputs, not of the agent's claim.
    • Rubber-stamp approval

      Approvers click through hundreds of items. The control exists only on paper.

      Spot itApproval change rate, time per item, and planted known-bad items.
    • Autonomy set by one headline accuracy

      "97% accurate, so let it run." Average accuracy hides the tail and the harm size.

      Spot itAsk for error rate by case type and worst-case harm, and compare to the level table.
    • Irreversible step inside a reversible plan

      A staged workflow includes one step, such as an outbound customer message, that cannot be recalled.

      Spot itList every side effect with its undo. Any without one gets a gate.
    • Injected instructions persisted in notes

      A hostile document says "record this rule", and the notes file carries it into every later session.

      Spot itTreat the notes file as untrusted tool input; restrict who can write to it; audit it.
    • Demo horizon mistaken for reliability

      "It ran for six hours" is one trial on a tidy task.

      Spot itAsk for success rate over many runs and how often a human stepped in.
    Part 4

    Self-check

    1. An agent step succeeds 99% of the time. What is the chance a 200-step run has no failure?

    0.99200 ≈ 13.4%. Small per-step errors compound, so long runs need recovery, not just a good model.

    2. Why is a compaction summary not a safe place for a "do not contact" rule?

    Summaries are lossy, and summaries of summaries lose more. A rule kept with 85% probability per compaction survives five of them 0.855 ≈ 44% of the time. Put rules in a durable block that is re-read.

    3. A run crashes after posting a journal entry but before saving progress. What stops a duplicate on resume?

    An idempotency key on the posting (run ID plus step number), so the ledger ignores the repeat. If that is impossible, record the intent first and check the ledger on restart.

    4. What does a saga add that a plain checkpoint does not?

    A checkpoint lets you continue forward. A saga gives every completed step an undo, run when a later step fails. Resumption handles crashes; compensation handles wrong turns.

    5. An error costs AED 100 on average, the agent errs on 4% of items, and a review costs AED 25 and stops 85% of errors. Is approving each item worth it?

    No approval: 0.04 × 100 = AED 4 per item. Approval: 25 + 0.04 × 100 × 0.15 = AED 25.60. Not worth it; sample or gate instead. At AED 10,000 harm it flips: AED 400 against 25 + 60 = AED 85.

    6. Why can sampling afterwards be fine for reversible tasks and disastrous for payments?

    Auditing afterwards only removes the share of harm you can undo once you find the error (ρ). A mislabelled ticket can be re-routed; a released payment may be gone. With ρ near zero, sampling removes almost no harm.

    7. How would you tell if human approvals have become a rubber stamp?

    Check the share of items changed or rejected, time per item, and whether planted known-bad items get caught. Near-zero changes on hundreds of items a day, at seconds per item, means the control is nominal.
