    Long-Running Agents and Autonomy Levels

    Part 1

    What a long-running agent is

    In one sentenceA long-running agent is one that works for hours rather than seconds, so you run it like a background job: save its state outside the prompt, save progress at checkpoints, and decide how much it may do without asking.

    Picture an analyst reconciling 3,000 trade-finance documents over four hours. Halfway through, the laptop dies. A bad analyst starts again. A good one kept a running sheet of what is done and what rules were settled, and loses ten minutes.

    An agent is that analyst with two handicaps. Its working memory (the context window) is finite and gets summarised, so it forgets. And each step can go wrong: a step that is right 99.5% of the time gives a 400-step run only about a 13% chance of finishing perfectly.

    How it differs from a chat

    • A chat is short and a person reads every reply, so mistakes get caught at once.
    • A long run may take hundreds of steps with nobody watching, so errors compound and the history outgrows the prompt.
    Part 2

    How to keep it safe

    1. Write down what must survive. The agent only knows what is in its prompt. Anything important (constraints such as "never contact do-not-call customers", decisions made, what is finished) goes into durable notes, written deliberately.
    2. Save checkpoints. A checkpoint is a snapshot of the plan, the notes, the position in the task and which side effects have happened. Like a video-game save point, it lets a crashed run resume.
    3. Make actions idempotent. If the agent crashes after posting a journal entry but before saving that it did, the resumed run posts it again. Give each action a unique key so the receiving system ignores a repeat.
    4. Add checks and undo. A verification gate after each stage that does not trust the agent's own report. A compensating action (an undo) for each side effect, so a failure at step 7 runs the undos for steps 6 to 1. This is the saga pattern.
    5. Set budgets and tripwires. Caps on steps, spend and time, and alarms on odd patterns such as the same call repeated 300 times. A looping agent should stop and ask.
    6. Pick an autonomy level for each task, as below.
    Where state livesWhat it isLoses information?
    Context windowThe live promptYes, when full
    Compaction summaryThe model rewrites its history shorterYes, more each time
    Durable notesA file the agent writes and re-readsOnly what it forgot to write
    Event logAppend-only record kept by the harnessNo: use it for audit
    Part 3

    Autonomy levels: how much may it do alone?

    Autonomy is a ladder, not a switch, like a new driver going from instructor-in-the-car to driving alone. Each rung changes the human's role.

    LevelHuman roleBanking example
    L0 SuggestDoes the work; agent recommendsDrafting a reply
    L1 Approve eachApproves every stepPayment releases, limit changes
    L2 Approve exceptionsReviews flagged or high-value itemsKYC triage (know-your-customer checks)
    L3 Sample afterwardsAudits a sampleTicket routing, transaction tagging
    L4 Act freelyWatches aggregate healthSummaries, search

    How to pick the rung

    Three things decide it:

    • Error rate: how often the agent is wrong on realistic cases.
    • Harm: the cost of one wrong action.
    • Reversibility: how much of that harm you can undo once you notice.

    Worked reading. An error costs AED 100 and the agent errs on 4% of items, so the expected harm is about AED 4 per item. A review costs AED 25, so approving every item is not worth it: sample or gate instead. If one error cost AED 10,000, the expected harm would be AED 400 per item and reviewing everything would clearly pay.

    Checkpoint cost. With a 0.5% failure chance per step, a 400-step task with no checkpoints costs over three times its length, because every failure restarts it. Saving every 20 steps brings that to about 1.05 times. Saving too often wastes effort.

    • Strong at: dynamic rules, such as L2 under AED 5,000 and L1 above, dropping a rung when errors rise.
    • Weak at: approvals that decay. A person approving 400 items a day stops reading, so a rubber-stamp L1 is an L4 with false comfort.
    Show the formula

    P(clean run) = pn: the chance a step works (p) multiplied by itself once per step (n). At 99% per step, a 200-step run is clean only about one time in eight. Long runs need recovery, not just a good model.

    In banking, the payment never tips towards autonomy, because one error costs more than any review. Auditing afterwards only helps with harm you can undo.

    Part 4

    Common mistakes and quick check

    • Constraint amnesia after compaction

      The agent obeys "never touch accounts under dispute" for two hours, then a summary drops the rule. A rule kept 85% of the time per compaction is lost more often than not after five. Put rules in a durable block that is re-read.

    • Double execution on resume

      A crash after a payment instruction but before the save leads to a second instruction. Kill a test run mid-step and see what repeats.

    • Summary drift

      "Customer verified" is copied from summary to summary without evidence and becomes fact. Record evidence and re-verify critical facts at source.

    • Rubber-stamp approval

      Check the share of items changed, time per item, and whether planted bad items get caught.

    1. A step succeeds 99% of the time. Why is a 200-step run still unlikely to finish cleanly?

    Small errors compound: the clean-run chance is about one in eight.

    2. Why is a compaction summary not a safe place for a "do not contact" rule?

    Summaries are lossy, and summaries of summaries lose more. Use durable notes that are re-read.

    3. A run crashes after posting a journal entry but before saving. What stops a duplicate?

    An idempotency key on the posting, so the ledger ignores the repeat. Failing that, record the intent first and check the ledger on restart.

    4. What does a saga add that a plain checkpoint does not?

    A checkpoint lets you continue forward. A saga gives each completed step an undo. Resumption handles crashes; compensation handles wrong turns.

    5. Why can sampling afterwards suit reversible tasks but not payments?

    A mislabelled ticket can be re-routed. A released payment may be gone, so sampling removes almost no harm.
