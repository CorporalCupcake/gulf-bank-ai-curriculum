    Long-Running Agents and Autonomy Levels: Letting an Agent Work for Hours, Safely

    Why an agent that works for hours needs memory outside its prompt, checkpoints it can resume from, and a way to recover from its own mistakes, and how to decide, task by task, how much freedom a banking agent should get.

    Contents

    The whole lesson in one sentenceA long-running agent is a process that will be interrupted, will forget, and will sometimes be wrong, so you design for resumption and for undo; and how much freedom to give it is a cost calculation on error rate, size of harm and reversibility, not a matter of trust or fashion.

    Part 1

    The intuition

    Imagine you hand a new analyst a four-hour job: reconcile 3,000 trade-finance documents against the ledger and list the exceptions. Halfway through, the laptop dies. A bad analyst has no notes and starts again. A good one kept a running sheet: which documents are done, what rules they settled on, what looked odd. After the restart they lose ten minutes, not two hours.

    An AI agent doing a long task is that analyst, with two extra handicaps. Its working memory (the context window) is finite and gets summarised or cleared as the task grows, so it forgets things that were true an hour ago. And every step has a small chance of going wrong. Small per-step error rates add up over hundreds of steps: a step that is right 99.5% of the time gives a 400-step run with only a 13% chance of finishing perfectly.

    The second question is separate but linked: how much should the agent be allowed to do without asking? Summarising a complaint is harmless. Releasing a AED 250,000 payment is not. Between those sits a ladder of autonomy levels, and the right rung depends on how often the agent is wrong, how bad a wrong action is, and whether it can be undone.

    Hold onto thisTreat a long-running agent like a distributed job, not a chat. State lives outside the prompt, progress is saved at checkpoints, every side effect is something you can reverse or approve, and the autonomy level is set by risk arithmetic. The model's intelligence helps; the engineering around it is what makes hours-long work safe.
    Part 2

    How it really works

    Where the state lives: context, notes and the event log

    An agent loop is simple: read the state, pick an action (a tool call), see the result, repeat. Everything it "knows" is whatever is in its prompt at that moment. On a long task the history outgrows the window, so harnesses use three stores that differ in how much they lose.

    StoreWhat it isLoses information?Use it for
    Context windowThe live prompt: instructions, recent steps, tool results.Yes, when full. Older content is dropped, cleared or summarised.What the agent needs for the next few steps.
    Compaction summaryThe model rewrites its own history into a shorter note and continues from that.Yes, and repeated summaries of summaries lose more each time.Keeping the thread of reasoning. Not a record.
    Durable notes / files / databaseA progress file, a task list, a structured store the agent writes to and re-reads.Only what the agent forgot to write.Constraints, decisions, what is done, what is left.
    Event logAn append-only record of every action and result, kept by the harness, not the model.No.Audit, replay, resumption, and answering "what exactly did it do?"

    The design rule that follows: anything that must survive goes into durable state, written deliberately, not left in the prompt. Examples are the constraints given at the start ("never contact customers flagged do-not-call"), decisions made on the way ("treat invoices under AED 500 as out of scope"), and a list of what is finished. Anthropic's engineering write-ups on long-running coding agents describe this pattern: an initial setup step that creates a progress file and a feature list, then fresh sessions that each read those artifacts, do one piece of work, and leave the state tidy for the next session (check the post in Sources; I cite it from memory of its design). Longer context windows help but do not remove the need: a bigger window does not say which information is authoritative or what survives a restart.

    Models are also uneven at using what is in a long context. Information buried in the middle is used less reliably than information at the start or end (Liu et al., 2023), which is a second reason to keep a short, curated "current state" block near the top of each step rather than rely on an ever-longer transcript.

    Checkpoints, resumption and idempotence

    A checkpoint is a saved snapshot of everything needed to continue: the plan, the notes, the position in the task, and which side effects have already happened. Frameworks for agent graphs and for durable workflow engines provide this: save the state after every step, keyed by a run ID, so a crashed or paused run can be resumed or even rewound to an earlier point and replayed differently. It is the same idea as database write-ahead logs and as workflow engines used for payments.

    Checkpoints raise a subtle problem. If the agent crashes after sending an email or posting a journal entry but before saving that it did so, the resumed run will do it again. The answer is idempotence: give each side-effecting action a unique key (for example, a hash of run ID and step number) so the downstream system ignores the second attempt. Payments systems already require this. For actions that cannot be made idempotent, record the intent before acting and check it on restart.

    How often should you checkpoint? Saving costs something (time, tokens, writes). Not saving risks redoing work. If each step independently fails with probability q, a segment of c steps with no save point has to be repeated from its start whenever it fails. Expected steps to complete one segment:

    E(c)=1−(1−q)cq(1−q)c

    One attempt runs until its first failure or until it completes; you retry until a clean pass, which takes 1 ÷ (1 − q)c attempts on average. With q = 0.5% and c = 400 this is about 1,285 steps, over three times the nominal 400. With checkpoints every 20 steps, 20 segments × 21 steps each is 422 steps, plus saving costs. The total cost rises with long unsaved stretches and with frequent saves, so there is a sweet spot.

    Recovery: crashes are easy, wrong turns are hard

    Resumption handles the agent that stopped. A harder case is the agent that carried on, confidently, in the wrong direction: it misread a constraint at step 40 and has now acted on that for 200 steps. Four mechanisms cover this.

    • Verification gates. After each stage, a check that does not trust the agent's own report: a test, a reconciliation total, a second model or a rule. The coding-agent pattern of "run the tests before marking a feature done" is exactly this.
    • Compensating actions. For each side effect, define how to reverse it. This is the saga pattern from distributed systems (Garcia-Molina and Salem, 1987): a long sequence of steps, each with an undo, so a failure at step 7 triggers undos for steps 6 to 1. Reversibility is a design property you build in, not luck.
    • Stage, then commit. Let the agent prepare work in a staging area (a draft batch, a proposed journal) and have a separate step, human or rule-based, commit it. Long autonomous effort, small irreversible surface.
    • Budgets and tripwires. Caps on steps, spend, number of records touched and wall-clock time, plus alarms on odd patterns (the same call repeated, a sudden rise in error responses). Agents that loop or drift should stop and ask.

    One more thing is particular to long runs: the time horizon is growing. METR measures the length of task, in human-expert time, that a model completes with 50% reliability. Its 2025 paper found this doubling roughly every seven months; later analyses fitted shorter doubling times on recent data, and the 80% reliability horizon is much shorter than the 50% one. Treat any single figure with care (Part 4). The practical point for a bank: tasks that took a person an afternoon are now in range, so the surrounding engineering matters more each quarter.

    Autonomy levels: a ladder, not a switch

    "Should the agent be autonomous?" is the wrong question. Autonomy is a choice per task, along a ladder, and the human's role changes at each rung. Research on automation (Parasuraman, Sheridan and Wickens, 2000) separates what is automated (gathering information, analysing it, choosing, acting) from how much; recent work on agents proposes similar levels by the user's role: operator, collaborator, consultant, approver, observer (Feng et al., 2025). A usable working ladder for a bank:

    LevelHuman roleAgent mayTypical banking use
    L0 · SuggestDoes the work, reads suggestionsRead and recommend. No actions.Drafting a reply, highlighting clauses in a trade document.
    L1 · Approve each actionApproves every step before it runsPrepare actions and wait.Payment releases, limit changes, sending customer messages.
    L2 · Approve the exceptionsReviews flagged or high-value items onlyAct within limits; escalate on triggers.KYC document triage, alert closure under a threshold.
    L3 · Act, sample afterwardsAudits a sample, monitors dashboardsAct within a narrow scope and reversible actions.Tagging transactions, internal ticket routing.
    L4 · Act freelyWatches aggregate healthAct, log, report.Summaries, search, formatting, test-data generation.

    Three variables set the rung. Error rate e: how often the agent does the wrong thing, measured on realistic cases (A4). Harm h: AED, regulatory or reputational cost of one wrong action. Reversibility ρ: the share of harm you can undo if you notice. Human review has a price too, in AED per item and in delay. So the expected cost per action under a level is "review cost + the harm that slips through". The simulation below is a deliberately simple version of that sum.

    Two refinements matter in practice. First, autonomy can be dynamic: the same agent runs at L2 for amounts under AED 5,000 and at L1 above, and drops a rung when its recent error rate rises or inputs look unusual. Second, approvals degrade. A human asked to approve 400 items a day stops reading them. A rubber-stamp L1 is an L4 with a false sense of control, so measure how often approvers change or reject items, and how long they spend.

    Part 3

    How it connects

    Long-running agents sit where architecture, security, evaluation and operating risk meet.

    A1 · Know Your AgentIdentity and permission for the agent

    Autonomy levels are only enforceable if the agent has its own identity and scoped credentials. A payment limit in the policy means little if the agent holds a key without one.

    A2.1 · A2.2 · Tools and protocolsWhat the agent can touch

    Every tool the agent can call is a side effect to make idempotent, reversible or gated. Tool scope defines the maximum damage at any autonomy level.

    A3.1 · A3.2 · Prompt injectionHours of reading untrusted text

    A long run reads more documents, so it has more chances to ingest a malicious instruction. Notes files are a persistence route for injected text. Design-level defences limit what a hijacked agent can do.

    A3.4 · Agentic threatsExcessive agency

    Giving an agent more autonomy than the task needs is a named risk category. The level table is a control against it.

    A4.1 · A4.5 · EvalsMeasuring e before you pick a level

    You cannot set an autonomy level without an error rate, and a long run needs reliability across many repetitions, not one lucky pass. See also statistics for evals for how few trials you can trust.

    A5.5 · Long context, RAG, memoryMemory design choices

    Notes files, retrieval stores and long windows are three answers to the same memory problem, with different cost and failure profiles.

    B2 · Transaction monitoringAlert closure at scale

    Triage agents work through queues for hours. The rung is set by the cost of a missed suspicious case against a human review, which is the same arithmetic as the simulation.

    B7 · Document AI and copilotsBatch document processing

    Overnight jobs over thousands of trade documents are the natural first long-running agent: checkpointed, staged, with exceptions routed to people. Staff copilots mostly sit at L0 to L1.

    C3 · Managing riskSetting expectations on autonomy

    The phrase "the agent will run unattended" needs translating into a rung, a limit and an owner before it reaches a steering committee.

    Where it shows up at the bank:

    • Overnight reconciliation and exception reports. Long, structured, staged: a good first candidate.
    • Trade-finance document checking. Thousands of documents, Arabic and English, stage-and-commit with human sign-off on discrepancies.
    • AML and KYC case preparation. The agent gathers evidence for hours; the decision stays with an investigator at L1.
    • IT and operations. Incident triage and routine fixes in non-production first. Production change at L1.
    • Customer-facing actions. Messages, limit changes, card blocks: low volume per customer, high consequence, usually L1 to L2.
    Part 4

    Where the field is now

    The mechanics are stable and the open questions are about how long a run can reliably be, how to compress memory without losing commitments, and how to govern autonomy. Evidence is thinner than the marketing.

    Part 5

    How it fails, and how to spot it

    Each failure comes with the quickest check.

    • Constraint amnesia after compaction

      The agent obeyed "never touch accounts under dispute" for two hours, then, after a summary, starts touching them.

      Spot itAre constraints in a durable, re-read block, not only in the opening prompt? Test by forcing a compaction mid-run and checking behaviour.
    • Double execution on resume

      A crash after a payment instruction but before the save leads to a second instruction.

      Spot itAsk how each side-effecting tool handles a repeated call with the same key. Kill the run mid-step in testing.
    • Summary drift

      A claim in an early summary ("customer verified") is copied into the next summary without evidence and becomes a fact.

      Spot itCheck that notes record evidence and source, and that critical facts are re-verified against the system of record.
    • Loops and silent spinning

      The agent retries a failing tool 300 times, or declares success without doing the work.

      Spot itStep, spend and time budgets; alert on repeated identical calls; verification that checks outputs, not the agent's claim.
    • Rubber-stamp approval

      Approvers click through hundreds of items. The control exists on paper.

      Spot itApproval change rate, time per item, and planted known-bad items to see if they are caught.
    • Autonomy set by one headline accuracy

      "It is 97% accurate, so let it run." Accuracy on easy cases says nothing about the tail, or about harm size.

      Spot itAsk for the error rate by case type and the worst-case harm, and compare to the table, not the average.
    • Irreversible action in the middle of a reversible plan

      A staged workflow includes one step, such as an outbound customer message, that cannot be recalled.

      Spot itList every side effect with its undo. Any without one gets a gate.
    • Injected instructions persisted in notes

      A hostile document tells the agent to "record this rule", and the notes file carries it into every later session.

      Spot itTreat the notes file as untrusted input from tools; restrict who and what can write to it; review it in audits.
    • Demo horizon mistaken for production reliability

      "It ran for six hours" in a demo is one trial, on a tidy task.

      Spot itAsk for the success rate over many runs, and the rate at which a human had to step in.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “The agent can now work through a morning's job on its own, but a long job fails in small ways: it forgets, it crashes, it occasionally misreads. So we build it like a payments process, with saved progress, a full activity log, and undo for every action. How much freedom it gets depends on the task: free on drafting, approval on anything that moves money. We set that level from the error rate we measure and the size of a mistake, and we can tighten it automatically if the error rate rises.”
    To a technical interviewer or validator
    “State lives outside the context: a constraints block, progress notes and an append-only event log, with checkpoints keyed by run ID and idempotency keys on side effects. Compaction is treated as lossy. Stages end in verification gates that don't rely on the agent's self-report, and writes are staged then committed. Autonomy is per task from expected cost: review cost plus residual harm after the approval policy's catch rate, using error rates measured with repeated-trial evals, and with monitoring on approver behaviour to catch rubber-stamping.”
    “Can we just give it a bigger context window and skip all the checkpoint machinery?”

    A bigger window delays the problem and does not solve it. It still resets on a crash, it is used unevenly (middle content is used less reliably), it costs more per step, and it tells you nothing about which facts are authoritative. Durable state also gives audit and replay, which a bank needs regardless.

    “How do we decide whether this process can run without approval?”

    Estimate three numbers: the agent's error rate on realistic cases, the harm of one error, and how much of that harm is reversible. Then price each policy: review cost plus residual harm. Where one error is cheap or fully reversible, sample afterwards. Where one error is expensive or irreversible, approve each action, however good the agent looks.

    “The approvers say they're drowning. Can we remove approval?”

    First fix the design: route only flagged or high-value items to humans, batch similar items, and give approvers the evidence on one screen. If approvals are being waved through, the control is already weak, so measure it. Moving up a rung is fine if the numbers support it, and a decision to record with an owner.

    “What happens if it crashes halfway through a batch of 5,000 customer updates?”

    It resumes from the last checkpoint. Each update carries an idempotency key, so those already applied are skipped. The event log shows exactly which were done. Updates are staged and committed in small batches so the maximum in flight is bounded.

    “A vendor says its agent runs autonomously for 24 hours. Is that credible?”

    Possibly, on a suitable task, but ask: over how many runs, what success rate, what human interventions, what happens on failure, and at what harm size. Time on task is not reliability, and METR's own work shows the 80% reliability horizon is far shorter than the 50% one.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. An agent step succeeds 99% of the time. What is the chance a 200-step run has no failure?

    0.99200 ≈ 13.4%. Small per-step error rates compound quickly, which is why long runs need recovery, not just a good model.

    2. Why is a compaction summary not a safe place for a "do not contact" rule?

    Summaries are lossy and the loss compounds when a summary is summarised. A rule kept with 85% probability per compaction is kept with 0.855 ≈ 44% after five. Rules belong in a durable block that is re-read and re-checked.

    3. A run crashes after posting a journal entry but before saving progress. What stops a duplicate on resume?

    An idempotency key attached to the posting (for example run ID plus step number), so the ledger ignores the repeat. Where that is not possible, record the intent first and check the ledger on restart.

    4. What does a saga add that a plain checkpoint does not?

    A checkpoint lets you continue forward. A saga defines a compensating action for each completed step so you can undo them when a later step fails. Resumption handles crashes, compensation handles wrong turns.

    5. Task: an error costs AED 100 on average, the agent errs on 4% of items, a review costs AED 25 and stops 85% of errors. Is approving each item worth it?

    Per item, no approval costs 0.04 × 100 = AED 4. Approval costs 25 + 0.04 × 100 × 0.15 = AED 25.60. Not worth it; sample or gate instead. Approval pays when harm is large: at AED 10,000 harm, no approval is AED 400 against 25 + 60 = AED 85.

    6. Why can a sampled-afterwards policy be fine for reversible tasks and disastrous for payments?

    After-the-fact audit only helps by the share of harm you can undo once you find the error (ρ). A mislabelled ticket can be re-routed, a released payment may be gone. For ρ near zero, sampling afterwards removes almost none of the harm.

    7. How would you tell if human approvals have become a rubber stamp?

    Look at the share of items the approver changes or rejects, time per item, and whether planted known-bad items get caught. A near-zero change rate on hundreds of items a day, with seconds per item, means the control is nominal.
