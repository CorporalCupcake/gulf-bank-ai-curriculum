    Long-Running Agents and Autonomy Levels: Letting an Agent Work for Hours, Safely

    Contents
    Part 1

    The intuition

    Picture an analyst reconciling 3,000 trade-finance documents over four hours. Halfway through, the laptop dies. A bad analyst restarts from scratch. A good one kept a running sheet of what is done and what rules were settled, and loses ten minutes.

    An AI agent on a long task is that analyst with two handicaps. Its working memory (the context window) is finite and gets summarised or cleared, so it forgets. And each step can go wrong: a step that is right 99.5% of the time gives a 400-step run only a 13% chance of finishing perfectly.

    The linked question is how much may the agent do without asking? Summarising a complaint is harmless; releasing a AED 250,000 payment is not. In between is a ladder of autonomy levels, and the right rung depends on how often the agent is wrong, how bad a wrong action is and whether it can be undone.

    Hold onto thisTreat a long-running agent like a background job, not a chat. State lives outside the prompt, progress is saved at checkpoints, and every side effect is reversible or approved.
    Part 2

    How it really works

    Where the state lives: context, notes and the event log

    An agent loops: read state, act, see the result, repeat. It only "knows" what is in its prompt, and on a long task the history outgrows the window. It is a whiteboard that gets wiped; you need a notebook. There are four places to keep state.

    StoreWhat it isLoses information?
    Context windowThe live prompt: instructions, recent steps, tool results.Yes, when full.
    Compaction summaryThe model rewrites its history into a shorter note.Yes, more each time it is re-summarised.
    Durable notes / filesA progress file or task list the agent writes to and re-reads.Only what it forgot to write.
    Event logAn append-only record of every action, kept by the harness.No. Use it for audit and replay.

    The rule: anything that must survive goes into durable state, written deliberately. That means constraints ("never contact do-not-call customers"), decisions made on the way and what is finished.

    Models also use the middle of a long context less reliably, so keep a short "current state" block near the top.

    Checkpoints, resumption and idempotence

    A checkpoint is a saved snapshot of everything needed to continue: the plan, the notes, the position in the task and which side effects have happened. Like a video-game save point, it lets a crashed run resume instead of restarting.

    The catch: if the agent crashes after sending an email or posting a journal entry but before saving that it did, the resumed run does it again. The fix is idempotence: give each side-effecting action a unique key so the downstream system ignores the repeat, as payment systems already do. If that is impossible, record the intent first and check it on restart.

    How often to save? With a 0.5% failure chance per step, a 400-step task with no checkpoints costs over three times its length, because every failure restarts it. Saving every 20 steps brings that to about 1.05 times. Saving too often wastes effort, so there is a sweet spot.

    Recovery: crashes are easy, wrong turns are hard

    Resumption handles an agent that stopped. The harder case is one that carried on confidently in the wrong direction: it misread a constraint at step 40 and has built on it for 200 steps. Four mechanisms help.

    • Verification gates. After each stage, a check that does not trust the agent's own report: a test, a reconciliation total or a rule.
    • Compensating actions. Define an undo for each side effect. If step 7 fails, run the undos for steps 6 to 1 (the saga pattern).
    • Stage, then commit. The agent prepares work in a draft area and a separate human or rule commits it.
    • Budgets and tripwires. Caps on steps, spend and time, plus alarms on odd patterns such as the same call repeated. A looping agent should stop and ask.

    Autonomy levels: a ladder, not a switch

    Autonomy is a per-task choice along a ladder, like a new driver going from instructor-in-the-car to driving alone. Each rung changes the human's role.

    LevelHuman roleTypical banking use
    L0 · SuggestDoes the work; agent only recommendsDrafting a reply.
    L1 · Approve each actionApproves every step before it runsPayment releases, limit changes.
    L2 · Approve the exceptionsReviews flagged or high-value itemsKYC triage, small alert closures.
    L3 · Act, sample afterwardsAudits a sampleTagging transactions, ticket routing.
    L4 · Act freelyWatches aggregate healthSummaries, search, formatting.

    Three things set the rung. Error rate: how often the agent is wrong on realistic cases. Harm: the cost of one wrong action. Reversibility: how much of that harm you can undo once you notice. The question is whether a review costs less than the harm it prevents.

    Two refinements. Autonomy can be dynamic: L2 under AED 5,000, L1 above, and a rung down when errors rise. And approvals degrade: a person approving 400 items a day stops reading, so a rubber-stamp L1 is an L4 with false comfort.

    Part 3

    How it fails, and how to spot it

    • Constraint amnesia after compaction

      The agent obeys "never touch accounts under dispute" for two hours, then a summary drops the rule.

      Spot itForce a compaction mid-run and check behaviour.
    • Double execution on resume

      A crash after a payment instruction but before the save leads to a second instruction.

      Spot itKill the run mid-step in testing and see what repeats.
    • Summary drift

      "Customer verified" in one summary is copied into the next without evidence and becomes fact.

      Spot itNotes should record evidence; re-verify critical facts at source.
    • Loops and silent spinning

      The agent retries a failing tool 300 times, or declares success without doing the work.

      Spot itBudgets, repeated-call alerts, and checks on outputs rather than claims.
    • Rubber-stamp approval

      Approvers click through hundreds of items. The control exists only on paper.

      Spot itApproval change rate, time per item, planted known-bad items.
    • Irreversible step in a reversible plan

      A staged workflow hides one step, such as an outbound customer message, that cannot be recalled.

      Spot itList every side effect with its undo. Any without one gets a gate.
    Part 4

    Self-check

    1. An agent step succeeds 99% of the time. Why is a 200-step run still unlikely to finish cleanly?

    Small errors compound: 99% per step leaves about a one-in-eight chance of a clean 200-step run. Long runs need recovery.

    2. Why is a compaction summary not a safe place for a "do not contact" rule?

    Summaries are lossy, and summaries of summaries lose more. A rule that survives each compaction 85% of the time is gone more often than not after five. Put rules in a durable block that is re-read.

    3. A run crashes after posting a journal entry but before saving progress. What stops a duplicate on resume?

    An idempotency key on the posting, so the ledger ignores the repeat. Failing that, record the intent first and check the ledger on restart.

    4. What does a saga add that a plain checkpoint does not?

    A checkpoint lets you continue forward. A saga gives every completed step an undo. Resumption handles crashes; compensation handles wrong turns.

    5. An error costs AED 100, the agent errs on 4% of items, and a review costs AED 25. Is approving every item worth it?

    No. The expected harm is about AED 4 per item, far less than the AED 25 review, so sample or gate instead. If one error cost AED 10,000, the expected harm would be AED 400 per item and reviewing everything would clearly pay.

    6. Why can sampling afterwards be fine for reversible tasks and disastrous for payments?

    Auditing afterwards only helps with harm you can undo once you find the error. A mislabelled ticket can be re-routed; a released payment may be gone, so sampling removes almost no harm.

    7. How would you tell if human approvals have become a rubber stamp?

    Check the share of items changed, time per item, and whether planted bad items get caught. Near-zero changes at seconds per item means the control is nominal.
