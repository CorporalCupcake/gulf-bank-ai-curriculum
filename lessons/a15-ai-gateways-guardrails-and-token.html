    The AI Gateway, Token Budgets and Spec-Driven Development

    Why every model call at a bank should pass through one controlled door, what that door enforces, where the money actually goes when you pay per token, and how to let AI write the code while humans keep ownership of the spec and the tests.

    Contents

    The whole lesson in one sentenceAn AI gateway is the single place where identity, policy, logging and spend are enforced on every model call, and spec-driven development applies the same idea to code: people own the intent (the spec) and the proof (the tests), and AI fills in the middle.

    Part 1

    The intuition

    An AI gateway is the front desk of a building: visitors sign in, get a badge, and only reach approved floors. Without one, a bank ends up with the fraud team using one vendor key pasted in a notebook, operations on a second vendor, and a developer's script on a third. Nobody can say which models are in use, what customer data has left, who is spending what, or how to switch off a model the regulator questioned. One agent stuck in a retry loop quietly becomes a fifth of the invoice.

    The fix: every application calls one door; only the door calls the models. It is your bank's existing API gateway, adapted to language models: calls are priced per token, requests are free text that may hold customer data or hostile instructions, and the same prompt gives different answers.

    The second half applies the same idea to code. When AI writes most of it, the scarce skill is stating exactly what the software must do and proving it does. In spec-driven development humans write the spec and the tests, the AI writes the implementation, and the tests decide whether it is accepted.

    Shared principle: put control at a few chokepoints humans define, so everything else the AI does can stay flexible.

    Hold onto thisThe gateway does not make a model safe. It lets the bank say who called which model with what data, at what cost, under which policy, and change that centrally in an afternoon instead of across forty codebases.
    Part 2

    How it really works

    What an AI gateway does

    A gateway is a proxy with one common API (most copy the OpenAI-style chat format, whatever model sits behind). Each request passes these steps in order:

    StepWhat it doesWhy a bank wants it
    1. Authenticate and attributeEach call carries a workload identity and cost centre (a virtual key per app or team), never a shared vendor key.Who did what, who pays; basis for audit and agent identity.
    2. Authorise the modelAllow-list of approved models, versions and regions per use case and data class.Enforces the model inventory (G3) and data residency. Retire a model in one place.
    3. Rate and budget limitsRequests per minute, tokens per day, monthly team cap, alert at 80%.Stops runaway loops and surprise invoices.
    4. Input guardrailsRedact or block personal data, detect prompt injection and jailbreaks, check topic rules.Keeps customer data in; first defence against injection.
    5. Cache, then routeReturn a stored answer for repeats; otherwise pick a model by difficulty, latency or cost, with fallback if a provider is down.Cost and resilience (model choice).
    6. Output guardrailsScan the response for leaked data, policy breaches, malformed structured output.Last check before text reaches a customer or downstream system.
    7. Log and meterRecord metadata, tokens, latency, cost, policy outcomes; ship traces to observability.Audit trail, chargeback, incident reconstruction (A15.2, tracing).

    Three design questions recur.

    • Buy or build. Open-source proxies (LiteLLM), commercial gateways (Portkey, Kong) and cloud providers' own features exist. For a bank, what matters is where the proxy runs, whether prompts leave your tenancy, and who can read logs containing customer text. Vendor comparisons are often written by rival vendors.
    • What gets logged. Full prompts are the best debugging data and the riskiest. Choose per data class: hashes and metadata only, redacted text, or full text with tight access and retention.
    • Fail open or closed. If the guardrail service is down, traffic either flows unchecked or stops. An FAQ chatbot might fail open; anything touching account data fails closed.

    Guardrails: what they can and cannot promise

    A guardrail is a smoke alarm: it trades misses against false alarms, exactly as in rare-event classification. Injection attempts are rare among a million benign calls, so a detector with a 1% false-positive rate blocks thousands of legitimate requests a day, while an attacker needs only one miss.

    So gateway guardrails are a layer, not a design. Robust defences are structural: least-privilege tools, approval gates for actions that move money (M4), capability-based designs (A3). Use the gateway for what it does well: deterministic checks (allow-lists, regex for IBAN and Emirates ID formats, size and rate limits), cheap classifiers, logging and a kill switch.

    Redaction can be reversible. Swap an IBAN for [IBAN_1] before the model sees it, then restore the real value in the response. The model reasons about the structure without holding the number.

    Where the money goes: token economics

    Billing works like a taxi meter running on words in and words out, and output tokens cost several times more than input (tokenisation). One request costs:

    cost=nin·pin+nout·pout

    n is tokens, p the price per token. Monthly spend is this times the number of calls. So three levers: fewer calls, fewer or cheaper tokens per call, a cheaper model per call.

    • Prefix caching. Providers charge a fraction for input that repeats the start of a recent prompt, like a long policy text. Put stable material first and the customer's question last. Discounts differ by provider and change; check the current price sheet.
    • Response caching. Exact-match is safe but rarely hits on free text. Semantic caches match similar questions and hit more, but can answer a subtly different one ("transfer to India" versus "from India"). Use for FAQs, never personalised traffic.
    • Routing. Like sending simple tickets to a junior and hard ones to a specialist: classification, extraction and short rewrites go to a small model. The risk is mis-routing a hard case; measure on your own evals (A4), not a vendor benchmark.
    • Trimming context. Retrieve fewer, better chunks (M3), summarise long histories, cap output length. An agent re-sends its growing history every step, so cost grows faster than step count.
    • Batch and off-peak. Overnight jobs such as document classification may get cheaper asynchronous pricing. Confirm current terms.

    Three takeaways. First, output is a large share of the bill despite being short, because output tokens cost five times as much. Second, caching and routing multiply: routing saves on a bill caching already shrank. Third, calls per task is the forgotten lever: a six-step agent is six bills, each carrying the history so far.

    Layer budgets: a soft alert at 80%, a hard cap per team, and a per-request ceiling on tokens and tool steps so a stuck loop cannot burn a month's money overnight. Manage cost per resolved task, not per token (A16.1): a cheap model that fails and retries can cost more than an expensive one that works.

    Spec-driven development: humans own the spec and the proof

    Ask an AI for "a transfer-limit check" and it fills every gap with a plausible guess, like a builder given a vague sketch. Some guesses are wrong in ways that look right: rounding fils the wrong way, treating "exceeds the limit" as "reaches it", forgetting the daily limit is cumulative. The code runs and passes the tests the AI wrote for itself, yet is wrong at the edges. This is the specification problem.

    Spec-driven development gives the work a shape:

    1. Requirements. What the software must do, in plain language and examples, written by someone who knows the business rules (limits, regulatory conditions, customer segments).
    2. Design. Interfaces, data, constraints, what is out of scope. AI drafts, a human reviews.
    3. Tasks and tests. The spec becomes acceptance tests and small tasks. The tests are the spec in executable form.
    4. Implementation. AI writes code until the tests pass, within the design.
    5. Review. Humans read the diff, test results and anything untested. If behaviour is wrong, ask first "was the spec wrong or silent?" and fix the spec and tests, not only the code.

    The discipline: tests must come from the spec, not the implementation. If the same AI writes the code and the tests that confirm it, the tests inherit its misunderstandings. It is independent challenge applied to code, and the same as writing evals before a prompt (A4).

    Tools wrap the same loop: GitHub's open-source Spec Kit, AWS's Kiro IDE, or your own spec file plus test suite in Claude Code. The habit matters more than the tool. Two cautions: specs can balloon into heavy process for small changes, and a detailed but wrong spec gives false comfort. Scale ceremony to risk. A throwaway report script needs a paragraph; a limit-enforcement service needs the full chain plus the requirement-to-test-to-code traceability auditors will ask for (A15.1).

    Part 3

    How it fails, and how to spot it

    • Shadow AI around the gateway

      Teams keep direct vendor keys because the gateway is slow or lacks a model. The central view is partial and the controls are theatre.

      Spot itCompare gateway spend with vendor invoices and network egress to model providers. The gap is shadow usage.
    • Gateway as single point of failure

      One outage or bad policy push takes down every AI feature.

      Spot itAsk about redundancy, staged policy rollout, and what each app does when the gateway is unreachable.
    • Over-trusting the guardrail

      "We have an injection filter, so agents are safe." Filters miss novel phrasing and indirect injection.

      Spot itAsk what happens if the filter is bypassed. "Nothing stops it" means the design depends on the filter.
    • Logs that become the leak

      Full prompts with customer data stored widely to help debugging.

      Spot itWho can read the logs, how long are they kept, are they redacted? Sample a log line.
    • Savings that cost quality

      Aggressive routing or semantic caching saves money, quietly degrades answers, or returns another customer's context.

      Spot itRun the same eval set before and after, per route. Check cache keys include user, tenant and permission scope.
    • Forecasting from price per token alone

      The budget ignores agent loops, long histories, retries and verbose Arabic text.

      Spot itAsk for average calls per task and tokens per call from real traces, not the list price.
    • Runaway agent spend

      A tool error makes an agent retry for hours.

      Spot itLook for per-request step and token ceilings and a per-key hourly cap, not only a monthly one.
    • AI-written tests grading AI-written code

      All tests pass; the spec was never checked. Tests encode the same misreading as the code.

      Spot itAsk who wrote the acceptance tests and from what. They should trace to spec lines a person wrote or reviewed.
    • Spec rot and spec theatre

      The code changes and the spec does not, or enormous specs nobody reads.

      Spot itCompare the spec's last-updated date with the code's. Ask what changed in the spec the last time behaviour changed.
    Part 4

    Self-check

    1. Name four things a gateway enforces or records that individual vendor keys do not.

    Any four: attribution to app or team; approved-model list; budgets and rate limits; central redaction and input checks; common audit log; kill switch.

    2. A call has 3,000 input tokens and 400 output tokens. Input costs AED 11 per million, output AED 55 per million. What does one call cost, and a million calls?

    Input 3,000 × 11 ÷ 1,000,000 = AED 0.033. Output 400 × 55 ÷ 1,000,000 = AED 0.022. Total AED 0.055 per call, AED 55,000 per million. Output is 40% of cost from 12% of tokens.

    3. Why does prefix caching reward putting the system prompt first and the customer's question last?

    Prefix caches match the start of the prompt. Stable text first repeats across requests and bills at the cached rate. Variable text first means nothing repeats from the start, so the cache never hits.

    4. An agent takes 6 model calls per task, each re-sending the history. Why can cost grow faster than 6 times a single call?

    Each step's input includes all earlier inputs and outputs, so input grows every step. The total is a sum of growing amounts, not six equal calls. Caching the shared prefix softens this.

    5. Why is a semantic cache risky for account-specific questions?

    It matches by similarity, so a different customer's or subtly different question can get a stored answer that is wrong or holds someone else's details. Use it for generic content only, with user and permission scope in the cache key.

    6. In Simulation 3 you tested five of eight behaviours and the AI's bugs were in two tested and one untested behaviour. What escapes, and what should you do?

    The bug in the untested behaviour escapes, with all tests green. Add that behaviour to the spec with a test, then regenerate or fix. The two caught bugs get fixed as the AI iterates against failing tests.

    7. Which should be human-owned in spec-driven work, and why not let the AI write both?

    The spec and the acceptance tests. If the AI writes the code and its checks, one misunderstanding appears in both and green proves nothing. Independent checking, as in model validation, needs a different source.
