    The AI Gateway, Token Budgets and Spec-Driven Development

    Contents
    Part 1

    The intuition

    An AI gateway is the front desk of a building: visitors sign in, get a badge, and only reach approved floors. Without one, every team pastes its own vendor key into notebooks and scripts, and nobody can say which models are in use, what customer data has left, or who is spending what. One agent stuck in a retry loop quietly becomes a fifth of the invoice.

    The fix: every application calls one door, and only the door calls the models. It is your bank's API gateway adapted to language models, where calls are priced per token and requests are free text that may hold customer data or hostile instructions.

    Spec-driven development applies the same idea to code. When AI writes most of it, the scarce skill is stating exactly what the software must do and proving it does. Humans write the spec and the tests, AI writes the implementation, and the tests decide whether it is accepted.

    Shared principle: put control at a few chokepoints humans define, so everything else can stay flexible.

    Hold onto thisThe gateway does not make a model safe. It lets the bank say who called which model with what data and at what cost, and change policy centrally instead of across forty codebases.
    Part 2

    How it really works

    What an AI gateway does

    A gateway is a proxy with one common API, whatever model sits behind. Each request passes these steps in order.

    StepWhat it doesWhy a bank wants it
    1. Authenticate and attributeA virtual key per app or team, never a shared vendor key.Who did what, who pays (agent identity).
    2. Authorise the modelAllow-list of approved models and regions per use case.Enforces the model inventory (G3) and data residency.
    3. Rate and budget limitsPer-minute, daily and monthly caps.Stops runaway loops and surprise invoices.
    4. Input guardrailsRedact personal data, detect prompt injection.Keeps customer data in; first defence against injection.
    5. Cache, then routeReuse stored answers; otherwise pick a model by difficulty and cost, with fallback.Cost and resilience (model choice).
    6. Output guardrailsScan for leaked data and policy breaches.Last check before text reaches a customer.
    7. Log and meterRecord tokens, latency, cost and policy outcomes.Audit trail and chargeback (A15.2, tracing).

    Three design questions recur.

    • Buy or build. Open-source (LiteLLM), commercial (Portkey, Kong) and cloud options exist. What matters is where the proxy runs and whether prompts leave your tenancy.
    • What gets logged. Full prompts are the best debugging data and the riskiest. Choose per data class: metadata only, redacted text, or full text with tight access.
    • Fail open or closed. If the guardrail service is down, traffic either flows unchecked or stops. An FAQ chatbot might fail open; anything touching account data fails closed.

    Guardrails: what they can and cannot promise

    A guardrail is a smoke alarm: it trades misses against false alarms, as in rare-event classification. Attacks are rare, so even a 1% false-positive rate blocks thousands of legitimate requests a day, while an attacker needs only one miss.

    So guardrails are a layer, not a design. Robust defences are structural: least-privilege tools and approval gates for actions that move money (M4, A3). Use the gateway for deterministic checks (allow-lists, IBAN and Emirates ID patterns, rate limits), logging and a kill switch.

    Where the money goes: token economics

    Billing is a taxi meter running on words in and words out, and output tokens cost several times more than input (tokenisation). Monthly spend is the cost of one call times the number of calls, so there are three levers: fewer calls, fewer or cheaper tokens per call, a cheaper model per call.

    • Prefix caching. Providers charge a fraction for input that repeats the start of a recent prompt, like a long policy text. Put stable material first and the customer's question last.
    • Response caching. Semantic caches match similar questions but can answer a subtly different one ("transfer to India" versus "from India"). Use for FAQs, never personalised traffic.
    • Routing. Send simple tickets to a junior and hard ones to a specialist: classification and extraction go to a small model. The risk is mis-routing a hard case, so measure on your own evals (A4).

    Three takeaways. First, output is a large share of the bill despite being short, because output tokens cost five times as much. Second, caching and routing multiply: routing saves on a bill caching already shrank. Third, calls per task is the forgotten lever: a six-step agent is six bills, each carrying the history so far.

    Layer budgets: a soft alert, a hard cap per team, and a per-request ceiling on tokens and steps so a stuck loop cannot burn a month's money overnight. Judge cost per resolved task, not per token (A16.1): a cheap model that fails and retries can cost more than an expensive one that works.

    Spec-driven development: humans own the spec and the proof

    Ask an AI for "a transfer-limit check" and it fills every gap with a plausible guess, like a builder given a vague sketch. Some guesses look right but are wrong: rounding fils the wrong way, or forgetting the daily limit is cumulative. The code passes the tests the AI wrote for itself, yet is wrong at the edges.

    Spec-driven development gives the work a shape:

    1. Requirements. What the software must do, in plain language and examples, written by someone who knows the business rules.
    2. Design and tasks. Interfaces and constraints, then acceptance tests and small tasks. The tests are the spec in executable form.
    3. Implementation and review. AI writes code until the tests pass; humans read the diff. If behaviour is wrong, ask "was the spec wrong or silent?" and fix the spec and tests, not only the code.

    The discipline: tests must come from the spec, not the implementation. If the same AI writes the code and the tests that confirm it, the tests inherit its misunderstandings. It is independent challenge applied to code.

    The habit matters more than the tool (Spec Kit, Kiro, or your own spec file plus tests). Scale ceremony to risk. A throwaway report script needs a paragraph; a limit-enforcement service needs the full chain plus the requirement-to-test-to-code traceability auditors will ask for (A15.1).

    Part 3

    How it fails, and how to spot it

    • Gateway gaps: shadow AI and single point of failure

      Teams keep direct vendor keys because the gateway is slow or lacks a model, so controls are theatre. Meanwhile one outage or bad policy push takes down every AI feature.

      Spot itCompare gateway spend with vendor invoices and network egress. The gap is shadow usage. Ask what each app does when the gateway is unreachable.
    • Over-trusting the guardrail

      "We have an injection filter, so agents are safe." Filters miss novel phrasing and indirect injection.

      Spot itAsk what happens if the filter is bypassed. "Nothing stops it" means the design depends on the filter.
    • Logs that become the leak

      Full prompts with customer data stored widely to help debugging.

      Spot itWho can read the logs, how long are they kept, are they redacted? Sample a log line.
    • Savings that cost quality

      Aggressive routing or semantic caching saves money, quietly degrades answers, or returns another customer's context.

      Spot itRun the same eval set before and after, per route. Check cache keys include user, tenant and permission scope.
    • Budgets that ignore loops

      The forecast uses list price per token, but real cost comes from agent loops, long histories, retries and verbose Arabic text. A tool error can make an agent retry for hours.

      Spot itAsk for average calls per task from real traces, and look for per-request step and token ceilings and an hourly cap, not only a monthly one.
    • AI-written tests grading AI-written code

      All tests pass, but the spec was never checked. Specs also rot when code changes and the spec does not.

      Spot itAsk who wrote the acceptance tests and from what. They should trace to spec lines a person wrote or reviewed, and the spec's date should track the code's.
    Part 4

    Self-check

    1. Name four things a gateway enforces or records that individual vendor keys do not.

    Any four: attribution, approved-model list, budgets and rate limits, central redaction, a common audit log, a kill switch.

    2. A call has 3,000 input tokens and 400 output tokens, and output costs five times as much per token. Why is output still a large share of the bill, and what does that suggest for cutting cost?

    The 400 output tokens are about 12% of the tokens but around 40% of the cost, because each costs five times as much. So capping output length and avoiding chatty responses pays off, alongside caching the repeated input.

    3. Why does prefix caching reward putting the system prompt first and the customer's question last?

    Prefix caches match the start of the prompt. Stable text first repeats and bills at the cached rate; variable text first means the cache never hits.

    4. An agent takes 6 model calls per task, each re-sending the history. Why can cost grow faster than 6 times a single call?

    Each step re-sends all earlier inputs and outputs, so input grows every step. Caching the shared prefix softens this.

    5. Why is a semantic cache risky for account-specific questions?

    It matches by similarity, so a subtly different question, or another customer's, can get a stored answer that is wrong or holds someone else's details. Use it for generic content only.

    6. In Simulation 3 you tested five of eight behaviours and the AI's bugs were in two tested and one untested behaviour. What escapes, and what should you do?

    The bug in the untested behaviour escapes with all tests green. Add that behaviour to the spec with a test, then fix. The two caught bugs get fixed as the AI iterates.

    7. Which should be human-owned in spec-driven work, and why not let the AI write both?

    The spec and the acceptance tests. If the AI writes both code and checks, one misunderstanding appears in both and green proves nothing.
