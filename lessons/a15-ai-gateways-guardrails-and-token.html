    The AI Gateway, Token Budgets and Spec-Driven Development

    Why every model call at a bank should pass through one controlled door, what that door enforces, where the money actually goes when you pay per token, and how to let AI write the code while humans keep ownership of the spec and the tests.

    Contents

    The whole lesson in one sentenceAn AI gateway is the single place where identity, policy, logging and spend are enforced on every model call, and spec-driven development applies the same idea to code: people own the intent (the spec) and the proof (the tests), and AI is allowed to fill in the middle.

    Part 1

    The intuition

    Picture a bank eighteen months into adopting generative AI with no central plumbing. The fraud team calls one vendor's API with a key pasted into a notebook. Operations has a contact-centre assistant on a second vendor. A developer's test script calls a third. Nobody can say which models are in use, which customer data has left the building, who is spending what, or how to switch off a model the regulator has questioned. The monthly invoice arrives and one agent that retried in a loop accounts for a fifth of it.

    The fix is old and unglamorous: put a door in front of the models. Every application calls the door; only the door calls the models. The door is the AI gateway. It is the same idea as the API gateway your bank already runs for payments and open banking, adapted to the odd properties of language models: calls are priced by the token, the content of requests is free text that may contain customer data or hostile instructions, and the same prompt gives different answers.

    The second half of the lesson is about a different door. When AI writes much of the code, the scarce skill is no longer typing. It is saying exactly what the software must do, and proving it does. Spec-driven development makes that explicit: humans write the spec and the evaluations (tests), the AI writes the implementation, and the tests decide whether it is accepted.

    The two halves share a principle. Control belongs at a small number of chokepoints that humans define, so the large number of things the AI does can stay flexible.

    Hold onto thisThe gateway does not make a model safe. It makes the bank able to say who called which model with what data, at what cost, under which policy, and to change that centrally in an afternoon rather than across forty codebases.
    Part 2

    How it really works

    What an AI gateway does

    Technically a gateway is a proxy that speaks one common API (in practice most expose the OpenAI-style chat format, whatever model sits behind) and wraps each call in a chain of steps. In the order a request meets them:

    StepWhat it doesWhy a bank wants it
    1. Authenticate and attributeEvery call carries a workload identity and a cost centre (a virtual key per application or team), never a shared vendor key.Who did what, and who pays. Foundation for audit and for the agent-identity ideas in A1.
    2. Authorise the modelAn allow-list of approved models, versions and regions per use case and data class.Ties to the model inventory and approvals (G3), and to data residency rules. Retire a model in one place.
    3. Rate and budget limitsRequests per minute, tokens per day, a monthly cap per team, alerts at 80%.Stops runaway loops and surprise invoices.
    4. Input guardrailsRedact or block personal data, detect prompt injection and jailbreaks, check topic rules.Keeps customer data out of places it should not go; first line of defence for injection.
    5. Cache, then routeReturn a stored answer for repeats; otherwise pick a model by task difficulty, latency or cost, with fallback if a provider is down.Cost and resilience. See model choice, cost and latency.
    6. Output guardrailsScan the response for leaked data, policy breaches, malformed structured output.A last check before text reaches a customer or a downstream system.
    7. Log and meterRecord request metadata, tokens, latency, cost, policy outcomes; ship traces to your observability stack.Audit trail, chargeback, incident reconstruction. See A15.2 observability and tracing.

    Three design questions come up every time.

    • Buy or build. Open-source proxies (LiteLLM is a common one), commercial AI gateways (Portkey, Kong, and similar), and the cloud providers' own gateway features all exist. For a bank the questions are less about features than about where the proxy runs, whether prompts leave your tenancy, and who can see logs that contain customer text. Treat vendor comparison articles with care: many are written by competing vendors.
    • What gets logged. Full prompts are the best debugging data and the riskiest data. Decide per data class: store hashes and metadata only, store redacted text, or store full text with tight access and retention.
    • Fail open or closed. If the guardrail service is down, does traffic flow unchecked or stop? For a customer-facing chatbot answering FAQs you might fail open; for anything touching account data, fail closed.

    Guardrails: what they can and cannot promise

    Guardrails at the gateway are filters, and every filter trades two errors against each other: letting bad things through (a miss) and blocking good things (a false alarm). That is exactly the trade-off of rare-event classification. Prompt-injection attempts are rare among a million benign calls, so even a detector with a 1% false-positive rate blocks thousands of legitimate requests a day, and a determined attacker only needs one miss.

    This is why gateway guardrails are a layer, not a design. The more robust defences are structural: least-privilege tools, approval gates for actions that move money (M4), and capability-based designs (A3). Use the gateway for what it is good at: deterministic checks (allow-lists, regex for IBANs and Emirates ID formats, size and rate limits), cheap classifiers, logging, and a kill switch.

    One more practical point: redaction has to be reversible if the answer needs the real value. A common pattern replaces an IBAN with a token such as [IBAN_1] before the model sees it and swaps the real value back into the response afterwards, so the model reasons about the structure without holding the number.

    Where the money goes: token economics

    Language models are billed per token (tokenisation), with output tokens priced several times higher than input tokens. A request costs

    cost=nin·pin+nout·pout

    n is tokens and p the price per token for that model. Monthly spend is this, times the number of model calls. The three levers are therefore fewer calls, fewer or cheaper tokens per call, and a cheaper model per call. Gateways pull all three.

    The levers in practice:

    • Prompt (prefix) caching. Many providers charge a fraction for input tokens that repeat the start of a recent prompt, such as a long system prompt and policy text. This rewards a layout where the stable material comes first and the variable material (the customer's question) last. Discounts and rules differ by provider and change; check the current price sheet rather than trusting a number from a lesson.
    • Response caching. Exact-match caches are safe but rarely hit on free text. Semantic caches match similar questions and hit more often, at the risk of returning an answer to a question that was subtly different ("what is the fee for a transfer to India" versus "from India"). Use them for FAQ-type traffic, never for anything personalised.
    • Routing. Send easy tasks (classification, extraction, short rewriting) to a small model and keep the frontier model for hard ones. The risk is mis-routing a hard case; measure on your own evals (A4), not on a vendor benchmark.
    • Trimming context. Retrieve fewer, better chunks (M3); summarise long histories; cap output length. In an agent, every step re-sends the growing history, so cost grows faster than the number of steps.
    • Batch and off-peak. Overnight jobs such as document classification can often use cheaper asynchronous batch pricing. Confirm current terms with the provider.

    Three lessons from the simulation. First, at default settings the output side is a large share of the bill even though outputs are short, because output tokens cost five times as much. Second, caching and routing multiply: the saving from routing applies to a bill already shrunk by caching. Third, calls per task is the lever people forget. An agent that takes six steps to answer is six bills, and each step carries the history so far.

    Budgets work best as layers: a soft alert at 80%, a hard cap per team, and a per-request ceiling on tokens and tool steps so one stuck loop cannot spend a month's money overnight. Treat the cost per resolved task, not the cost per token, as the number to manage (see A16.1): a cheap model that fails and gets retried can cost more than an expensive one that works.

    Spec-driven development: humans own the spec and the proof

    When you ask an AI to "build a transfer-limit check", it fills every gap in your request with a plausible guess. Most guesses are fine. Some are wrong in ways that look right: rounding fils the wrong way, treating "exceeds the limit" as "reaches the limit", forgetting that the daily limit is cumulative. This is the specification problem: the code runs, passes the tests the AI wrote for itself, and does the wrong thing at the edges.

    Spec-driven development gives the work a shape:

    1. Requirements. What the software must do, in plain language and examples, written by someone who understands the business and the rules (for a bank: limits, regulatory conditions, customer segments).
    2. Design. Interfaces, data, constraints and what is out of scope. The AI can draft it; a human reviews.
    3. Tasks and tests. The spec is turned into acceptance tests and small tasks. The tests are the executable form of the spec.
    4. Implementation. The AI writes code until the tests pass, within the agreed design.
    5. Review. Humans read the diff, the test results and anything the tests do not cover. If behaviour is wrong, the first question is "was the spec wrong or silent?", and the fix goes into the spec and tests, not only into the code.

    The key discipline: the tests must come from the spec, not from the implementation. If the same AI writes the code and then the tests that confirm it, the tests inherit its misunderstandings. This is the same point as the validation principle of independent challenge, applied to code, and the same as writing evals before a prompt (A4).

    The real tools in this space add structure around the same loop: GitHub's open-source Spec Kit, AWS's Kiro IDE, and workflows people build directly in Claude Code with a spec file and a test suite. The tools matter less than the habit. Two cautions that practitioners raise: spec files can balloon into heavy process for small changes, and a detailed spec can give false comfort when it is wrong. Scale the ceremony to the risk. A throwaway report script needs a paragraph; a limit-enforcement service needs the full chain, and in a regulated bank it also needs the traceability from requirement to test to code that auditors will ask for (see A15.1).

    Where it shows up at the bank:

    • Staff copilots (B7): a long policy prefix makes caching valuable, and per-department chargeback matters.
    • Contact-centre assistants in Arabic and English: Arabic text usually takes more tokens than the same English text in many tokenisers, so measure your own traffic before forecasting.
    • Document AI for trade finance and KYC: high-volume, batchable, easy to route to smaller models.
    • Data residency: the gateway is where "this data class may only go to in-country or approved-region models" becomes a rule rather than a memo. Check the specific CBUAE, SAMA or central-bank requirements with your compliance team; this lesson does not state them.
    • Internal engineering: spec-driven work for limit engines, reconciliation jobs, and data pipelines, where mistakes are costly and requirements are precise.
    Part 4

    Where the field is now

    AI gateways have gone from a pattern a few platform teams built themselves to a product category. Spec-driven development has gone from a blog-post idea to named tools in about a year. Both are moving quickly, and the evidence base is mostly vendor and practitioner writing rather than controlled studies.

    Checked on 6 November 2026 with two light searches. Most results were third-party or vendor comparison articles, so claims below are kept general. Verify against official documentation before relying on any specific feature, price or date.

    1. 2023–24
      Open-source LLM proxies appear

      Unified-API proxies with virtual keys, budgets and logging (LiteLLM is a widely used one) make it routine to put one interface in front of many models.

      LiteLLM documentation
    2. 2024–25
      Commercial AI gateways and API-management vendors add LLM features

      Token-based rate limiting, semantic caching, prompt guardrails and model fallback show up in products such as Portkey and Kong's AI Gateway, and in cloud API-management offerings. Feature tiers differ; some capabilities sit in paid or hosted editions.

      Vendor documentation; comparison articles (treat as marketing)
    3. 2025
      Agent traffic changes the shape of the load

      Agents make many chained calls and call tools through protocols like MCP. Gateways extend from "model calls" to "tool and agent calls", with identity and policy for each (A2).

      See also OWASP guidance on agentic threats
    4. 2025–26
      Spec-driven tools

      GitHub released the open-source Spec Kit, AWS launched the Kiro IDE, and others (OpenSpec, Tessl) followed. All push a loop of requirements, design, tasks, implementation and validation. Adoption figures in the press conflict, so I give none.

      github.com/github/spec-kit; kiro.dev
    5. 2026
      The open questions

      How to keep specs and code in sync as both change; how much spec detail pays off; whether AI-written tests are trustworthy enough to gate AI-written code; and how to govern prompts, models, and generated code under one change process.

      Practitioner discussion; no settled evidence

    Part 5

    How it fails, and how to spot it

    • Shadow AI around the gateway

      Teams keep direct vendor keys because the gateway is slow or lacks a model. The central view is partial and the controls are theatre.

      Spot itCompare the gateway's total spend with vendor invoices and with network egress to model providers. A gap is the shadow usage.
    • Gateway as single point of failure

      One outage or bad policy push takes down every AI feature.

      Spot itAsk about redundancy, staged policy rollout, and what each application does when the gateway is unreachable.
    • Over-trusting the guardrail

      "We have an injection filter, so agents are safe." Filters miss novel phrasing and indirect injection.

      Spot itAsk what happens if the filter is bypassed. If the answer is "nothing stops it", the design depends on the filter.
    • Logs that become the leak

      Full prompts with customer data stored widely to help debugging.

      Spot itWho can read the gateway logs, how long are they kept, and are they redacted? Sample a log line.
    • Savings that cost quality

      Aggressive routing or semantic caching saves money and quietly degrades answers, or returns another customer's context.

      Spot itRun the same eval set before and after, per route. Check that cache keys include user, tenant and permission scope.
    • Forecasting from the price per token alone

      The budget ignores agent loops, long histories, retries, and verbose Arabic text.

      Spot itAsk for average calls per task and tokens per call from real traces, not the list price.
    • Runaway agent spend

      A tool error makes an agent retry for hours.

      Spot itLook for per-request step and token ceilings and a per-key hourly cap, not only a monthly one.
    • AI-written tests grading AI-written code

      All tests pass; the spec was never checked. The tests encode the same misreading as the code.

      Spot itAsk who wrote the acceptance tests and from what. Tests should trace to spec lines written or reviewed by a person.
    • Spec rot and spec theatre

      The code changes, the spec does not; or enormous specs nobody reads.

      Spot itCheck the last-updated date of the spec against the code. Ask what changed in the spec the last time behaviour changed.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “Right now each team connects to AI models its own way, so we cannot easily say what data goes where or what it costs. I'd put one controlled door in front of every model: it records who called what, applies our data rules, enforces budgets and lets us switch a model off in one place. It also lets us send routine work to cheaper models, which is where most of the savings are. It is not a safety guarantee by itself, so the high-risk actions still need approvals.”
    To a technical interviewer or architect
    “Gateway with workload-identity virtual keys, a model allow-list tied to the inventory, per-team token budgets and per-request step ceilings, deterministic PII redaction with reversible tokens, a classifier layer for injection that we treat as defence in depth, prefix-cache-friendly prompt layout, and routing validated per route on our own evals. Traces go to our observability stack with redaction by data class. For code, specs and acceptance tests are human-owned and traceable, AI implements, and CI gates on the tests.”
    “Why not let each team call the vendor directly? It's faster.”

    It is faster for the first team and slower for the bank. Without a central point we cannot enforce approved models, data residency or budgets, cannot reconstruct an incident, and every team rebuilds redaction and logging. A thin, well-run gateway keeps the speed: one endpoint, one key, same API.

    “Will the gateway stop prompt injection?”

    It reduces it. A classifier catches known patterns, and the gateway can log and rate-limit. But detection is imperfect and indirect injection arrives inside retrieved documents. The real protection is structural: least-privilege tools, no autonomous money movement without approval, and isolating untrusted content. The gateway is one layer.

    “How do we cut the AI bill by half?”

    First measure by team and by use case, in cost per resolved task. Then, in rough order of safety: put stable material first and use prefix caching; cap output length; trim retrieved context; route simple tasks to a smaller model after checking quality on our evals; batch offline work; and cap agent steps. I would not promise a number before looking at real traces.

    “Isn't spec-driven development just waterfall again?”

    The risk is real if the spec is big and frozen. The useful version is small, iterated and executable: examples and tests that run on every change. The shift is that writing the spec used to be a cost in front of coding; now implementation is cheap, so the spec and tests are where human effort pays most.

    “Can the AI write its own tests?”

    It can draft them, and often usefully, but a person must check them against the spec, because tests written from the code mirror the code's assumptions. For critical logic like limits and fees, acceptance tests come from the business rules and are reviewed by someone who owns those rules.

    Part 7

    Self-check

    1. Name four things a gateway enforces or records that individual vendor keys do not.

    Attribution to an application or team; an approved-model list; budgets and rate limits; central redaction and input checks; a common audit log and a kill switch. Any four.

    2. A call has 3,000 input tokens and 400 output tokens. Input costs AED 11 per million, output AED 55 per million. What does one call cost and what is a million calls?

    Input 3,000 × 11 ÷ 1,000,000 = AED 0.033. Output 400 × 55 ÷ 1,000,000 = AED 0.022. Total AED 0.055 per call, so AED 55,000 for a million. Output is 40% of the cost from 12% of the tokens.

    3. Why does prefix caching reward putting the system prompt first and the customer's question last?

    Prefix caches match the start of the prompt. If the stable material comes first, it matches across requests and is billed at the cheaper cached rate. If the variable text comes first, nothing repeats from the start and the cache never hits.

    4. An agent takes 6 model calls per task, each re-sending the history. Why can cost grow faster than 6 times a single call?

    Each step's input includes all earlier steps' inputs and outputs, so input tokens grow with every step. The total is closer to a sum of growing amounts than six equal calls. Caching the shared prefix softens this.

    5. Why is a semantic cache risky for account-specific questions?

    It matches by similarity, so a different customer's or a subtly different question can get a stored answer. The answer may be wrong or contain someone else's details. Use it only for generic content, and include user and permission scope in the cache key.

    6. In Simulation 3 you tested five of eight behaviours and the AI's bugs were in two tested and one untested behaviour. What escapes, and what should you do?

    One bug escapes: the one in the untested behaviour, with all tests green. Go back to the spec: add the missing behaviour and its test, then regenerate or fix. The two caught bugs are fixed by the AI iterating against failing tests.

    7. Which should be human-owned in spec-driven work, and why not let the AI write both?

    The spec and the acceptance tests. If the AI writes code and the tests that check it, a misunderstanding in one reappears in the other and the green result proves nothing. Independent checking, as in model validation, needs a different source.
