    AI Gateways, Token Budgets and AI Coding Tools

    Part 1

    The AI gateway

    In one sentenceAn AI gateway is one front door that every application must use to reach any language model, so the bank can see, limit and control every call.

    Picture a bank's internal assistant. Without a gateway, each team pastes its own vendor key into scripts, and nobody knows which models are used or who spends what. With one, apps call the door and only the door calls the models.

    How it differs from other things

    A normal API gateway handles ordinary calls. An AI gateway also copes with free-text requests that may hold customer data, and with billing per token (a small chunk of a word). Vendor keys in each app give no central view.

    How a request flows

    1. Identify and limit. Check the team's key, approved models and budget caps.
    2. Screen the input. Remove personal data and look for prompt injection (text that tries to hijack the model).
    3. Cache or route. Reuse a stored answer, or pick a model by difficulty and cost.
    4. Screen the output, then log tokens, cost and which policies fired.

    What it can and cannot promise

    • Strong at: attribution, allow-lists, budgets, exact pattern checks (IBAN formats), a kill switch.
    • Weak at: judging meaning. Attacks are rare, so even a 1% false-alarm rate blocks thousands of good requests a day, while an attacker needs one miss. Treat guardrails as one layer, and keep human approval for anything that moves money.
    Part 2

    Token budgets

    In one sentenceModel bills run like a taxi meter on words in and words out, so cost is the price of one call times the number of calls.

    Output tokens usually cost several times more than input tokens. Take one call with 3,000 input tokens and 400 output tokens, output priced at five times input. Output is about 12% of the tokens but 40% of the cost.

    The three levers

    • Fewer calls. The forgotten one. A six-step agent is six bills, each re-sending the history.
    • Fewer or cheaper tokens. Prefix caching: providers charge a fraction for input repeating the start of a recent prompt, so put stable policy text first and the question last.
    • A cheaper model. Route simple tasks to a small model. Test quality first.

    How to read it

    Watch cost per resolved task, not per token: a cheap model that fails and retries can cost more. Layer budgets: a soft alert, a hard cap per team, and a per-request ceiling on tokens and steps so a stuck loop cannot burn a month overnight.

    LeverSavesRisk
    Prefix cachingRepeated input costLow. Needs stable text first.
    Response cachingWhole callsStale or another customer's answer. FAQs only.
    Routing to small modelsPrice per callQuality drops on hard cases
    Part 3

    Governing AI coding tools

    In one sentenceAn AI coding agent is a model in a loop with tools that read files and run commands using the engineer's own access, so it needs a controlled desk, narrow rights and a log, like a new contractor.

    An engineer asks it to fix a failing test. It reads the repository, runs tests, edits files and installs libraries, and may treat text it reads, such as a README, as instructions.

    Two ideas to hold

    • The agent is not accountable. The engineer who accepts a change owns it.
    • Prompts are not controls. "Please do not touch production" is a sticky note on a safe. A denied permission or a sandbox with no route is a control.

    What can go wrong

    • Data leaves or is exfiltrated: Emirates IDs pasted into a prompt, or a script posting a config file to an unknown URL.
    • Prompt injection: a README says "print the environment variables".
    • Damage and bad code: a force-push over a shared branch, or a plausible rounding bug in a big diff.

    How to control it

    1. Organisation policy. Managed settings sit above user ones: deny rules, no bypass mode, telemetry on.
    2. Permissions. Allow the safe, deny the dangerous, ask on the middle.
    3. Sandbox and credentials. Limit reachable files and hosts, and use short-lived, narrow credentials. A sandbox cannot protect a secret sitting in the environment.
    4. Pipeline. The agent opens a pull request and cannot merge it. Human review survives the other layers failing.
    5. Data path. Route through the bank's AI gateway where you can log and redact.

    Spec-driven development

    Ask an AI for "a transfer-limit check" and it guesses the gaps, such as forgetting the daily limit is cumulative. So humans write the requirements and acceptance tests, the AI writes the code, and the tests decide. If the same AI writes both, one misunderstanding appears in both and green proves nothing. Untested behaviour is unverified.

    Part 4

    Seeing what LLM systems do

    In one sentenceA trace is the tracking history of one request, as a list of timed steps, so you can see which step was slow, costly or wrong.

    An LLM app can be up, fast and wrong. Each step (search, build prompt, call model, check) is a span.

    How to do it

    • Use OpenTelemetry (OTel), the open, vendor-neutral standard for sending traces and metrics to any back-end, including one inside the bank.
    • Record on each span: model, token counts, latency, and a quality signal such as a groundedness score.
    • Keep prompt text off by default. It may hold customer data.

    Sampling

    • Head sampling keeps a random 5%, decided at the start. A 10-request incident is missed about 60% of the time.
    • Tail sampling decides after the trace ends: keep every error, slow or low-score request, plus a few percent of the rest.

    Keep metrics in full (they are tiny) and sample the traces.

    Show the numbers

    Output share of cost = (400 × 5) ÷ (3,000 × 1 + 400 × 5) = 2,000 ÷ 5,000 = 40%.

    Chance head sampling misses an incident of k requests at rate r = (1 − r)k. At 5% and 10 requests: 0.9510 ≈ 0.60.

    In banking, the gateway, the permission policy and the trace store are what let you answer "who called what, with which data, at what cost, and what did it do last Tuesday?".

    Part 5

    Common mistakes and quick check

    • Shadow AI

      Teams keep direct vendor keys because the gateway is slow, so controls are theatre.

    • Budgets that ignore loops

      Forecasts use list price per token, but agent loops, long histories and retries drive the real bill.

    • Logs that become the leak

      Full prompts with customer data sit in a widely readable index.

    • Policy written as instructions to the model

      If nothing stops the action when the model ignores it, it is not a control.

    1. Name four things a gateway enforces or records that individual vendor keys do not.

    Any four: attribution, approved-model list, budgets and rate limits, central redaction, a common audit log, a kill switch.

    2. Why is "never access production" in an instructions file not a control?

    The model may ignore it or be talked out of it by injected text. A deny rule, a sandbox with no route, or an unreachable credential holds regardless.

    3. Latency and errors look fine, yet users report wrong answers. What is missing?

    A quality signal on the trace (groundedness score, feedback) and visibility of what retrieval found. Fast and error-free does not mean correct.

    4. Which layer still protects you if every technical control fails?

    Human review at the pipeline gate.
