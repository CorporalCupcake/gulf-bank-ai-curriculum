    SQL Thinking: Joins, Windows and Aggregation

    Part 1

    What a join does, and how it goes wrong

    In one sentenceSQL is a language for asking a table questions, and the key habit is to always know what one row of each table, and of your answer, stands for.

    Take two tables. customers has one row per person, with their monthly salary. accounts has one row per account they hold. A join glues rows together using a shared key, here the customer id.

    Now sum the salary after joining. Aisha earns 20,000 and holds three accounts, so her row is copied three times and her salary is counted three times. Yusuf earns 10,000 but holds no account, so an inner join drops him.

    Grain and fan-out

    • Grain is what one row means: salary per customer, balance per account per day.
    • Fan-out is what happens when you join a one-per-person table to a many-per-person table. The finer grain wins and the coarse columns repeat.
    Part 2

    The pieces, one at a time

    Inner join against left join

    • Inner join: keeps only rows that have a partner on both sides, like a guest list at a door.
    • Left join: keeps every row from the left table and fills the right side with NULL when there is no partner.

    For questions about "our customers", make customers the left table and left-join everything onto it. Beware: a WHERE filter on a right-hand column throws away the NULL rows, so the left join quietly becomes an inner join. Put "which partners count" in ON.

    GROUP BY and window functions

    -- one row per customer
SELECT customer_id, SUM(balance) AS total
FROM accounts GROUP BY customer_id;

-- every account row, with the customer's total beside it
SELECT *, SUM(balance) OVER (PARTITION BY customer_id) AS total
FROM accounts;
    • GROUP BY collapses many rows into one per key. The key is now the grain.
    • A window function works out the same kind of total but keeps every row, like a class report printing each mark beside the class average.

    The pattern you will write most is "latest record per customer": number each customer's rows by recency with ROW_NUMBER() and keep number 1. Add a unique tiebreaker so ties are not broken at random.

    NULL means unknown

    NULL is like a sealed envelope: it equals nothing, not even another NULL. WHERE keeps a row only if the test is true, so status = 'active' and status <> 'active' together miss every row whose status is NULL. Test with IS NULL.

    Part 3

    How to read any query

    SQL is written in one order and run in another. Read it in the order it runs.

    That order is why window functions cannot appear in WHERE, and why LIMIT without ORDER BY returns an arbitrary set. For any query, yours or an AI tool's, ask three questions.

    1. What is one row of each input, and of the output?
    2. Is each join key unique, and what happens to unmatched rows?
    3. Could a filter drop NULLs, or use information from after the event?

    The time trap

    "Latest record" suits a dashboard, but for a model it leaks the future: a March loan application would get an October credit score. Use an as-of join, which picks the most recent snapshot at or before the event.

    Part 4

    Which tool to use

    ToolOutput rowsUse it when
    Inner joinOnly matched rowsYou only want things that exist on both sides
    Left joinEvery left rowCustomers are the spine and extras are optional
    GROUP BYOne per keyYou want a summary table
    Window functionSame as inputYou want a total, rank or running figure beside each row
    • Strong at: filtering, joining and summarising big tables.
    • Weak at: statistics and models. Do those in Python once the table is right.
    Show the average-of-averages rule

    Never average averages. A branch of 100 customers and a branch of 900 cannot be weighted equally. Carry the sum and the count, and divide at the end: overall average = total sum ÷ total count.

    In banking, a doubled join can inflate exposure or income figures, so always compare row counts and totals before and after each join.

    Part 5

    Common mistakes and quick check

    • Summing a column repeated by a join

      Compare with the same sum on the source table alone. If they differ, rows were copied.

    • The left join that lost its rows

      A WHERE filter on a right-hand column removes the NULL rows. Check the row count equals the left table's.

    • Comparisons that drop NULLs

      Run a filter and its opposite. The counts should add up to the total.

    1. Customers have 3, 1, 2, 0 and 2 accounts. You join and SUM(salary). Too high, too low or right?

    Too high, because salary is copied onto each account row. An inner join also loses the customer with no account. Add up accounts per customer first.

    2. Why do status = 'active' and status <> 'active' not return every row?

    Rows with NULL status are neither true under either test, and WHERE keeps only true.

    3. You left-join customers to October transactions, then add WHERE txn_month = '2026-10'. What have you written?

    An inner join in disguise: customers with no October activity are dropped. Move the condition into ON.

    4. Why can a "latest score" join ruin a model?

    It gives past events scores from the future. Use an as-of join and the date the data was actually available.
