    F3.3 Day one About 45 minutes

    SQL Thinking: Joins, Windows and Aggregation

    Bank data lives in warehouses, and most wrong numbers in a bank are born in a query that ran without error. How to read a query by its grain, spot a join that multiplied rows, and know what a window function really does.

    Contents

    The whole lesson in one sentenceA SQL result is a claim about what one row means; nearly every wrong number comes from a join or filter that quietly changed the grain, or silently dropped the rows you meant to keep.

    Part 1

    The intuition

    A product head asks for the combined salary of salary-transfer customers who hold an account. An analyst joins customers to accounts and sums salary. It runs and returns nearly double the truth.

    Nothing failed. A customer with three accounts becomes three rows, salary copied onto each, so it is counted three times. A customer with no account vanished from the inner join. It is like splitting a restaurant bill by plates instead of by diners.

    • Every table has a grain: what one row stands for. A salary lives at the customer grain, so it is only safe to sum there.
    • A join changes the grain to the finest table it touches. After joining accounts, a row is an account and customer columns repeat.
    • The join type decides who survives. An inner join drops customers with no match. That is selection (F2.6) by accident.
    Hold onto thisBefore reading or writing a query, say in one sentence what one row of each input is, and what one row of the output is. If you can't, you can't yet trust the number.
    Part 2

    How it really works

    Grain, keys and fan-out

    The grain is what one row means. Check every column is true at that grain: salary per customer, balance per account per day, amount per transaction.

    Balances are semi-additive: add them across accounts, never across days. Summing thirty daily balances is like adding speedometer readings to get your speed. Use the closing or average value.

    Whether a join is safe depends on the keys:

    • One-to-one or many-to-one (accounts to customers): the grain is unchanged. Safe.
    • One-to-many (customers to accounts): the result takes the finer grain and left columns repeat. This is fan-out.
    • Two one-to-many joins off the same parent (accounts and cards) multiply rows rather than add them: 3 accounts and 2 cards give 6 rows. With one of each the bug hides, which is why small tests pass.

    Defences: test whether the key is unique before joining; compare row counts before and after each join (a left join returning more rows than the left table has fanned out); and aggregate the many-side first, then join. DISTINCT is a patch, not a fix: SUM(DISTINCT salary) drops two customers who happen to earn the same.

    Inner and left joins: who survives

    An inner join keeps only left rows that found a partner, like a guest list at a door: no match, no entry. A left join keeps every left row and fills the right side with NULL when nothing matches.

    If the question is "what happens to our customers", customers is the spine and everything else is left-joined onto it. An inner join to an active-customers table answers a question about a smaller population, so churn or default rates on it are skewed.

    The subtlest bug is where a filter on the right-hand table sits:

    -- A: filter in ON. Keeps every customer; October activity if any
SELECT c.customer_id, SUM(t.amount_aed)
FROM customers c
LEFT JOIN transactions t
  ON t.customer_id = c.customer_id
 AND t.txn_month = '2026-10'
GROUP BY c.customer_id;

-- B: filter in WHERE. Silently becomes an inner join
SELECT c.customer_id, SUM(t.amount_aed)
FROM customers c
LEFT JOIN transactions t ON t.customer_id = c.customer_id
WHERE t.txn_month = '2026-10'
GROUP BY c.customer_id;

    In B, a customer with no transactions has NULL in t.txn_month. NULL = '2026-10' is not true, so WHERE discards the row and the left join behaves like an inner join. The customers who did nothing in October vanish. Rule: a condition on which partners count goes in ON; a condition on which final rows to keep goes in WHERE.

    Aggregation, and the mean of means

    GROUP BY collapses rows to one per group key, so the output grain is the key. WHERE filters rows before grouping; HAVING filters groups after.

    • COUNT(*) counts rows; COUNT(col) counts non-NULL values.
    • SUM and AVG skip NULLs, so AVG(income) covers only customers with an income on file.

    Averaging averages is the classic trap. Branch A has 100 customers averaging AED 10,000; branch B has 900 averaging AED 40,000. The mean of the two is 25,000, but the true average is AED 37,000, because B is nine times bigger. Carry sums and counts, divide last: a bank-wide default rate is total defaults over total loans.

    NULL: three-valued logic

    NULL means "unknown", not empty and not zero. Think of a sealed envelope: you can't say it equals anything, even another sealed envelope. So SQL has TRUE, FALSE and UNKNOWN, and WHERE keeps a row only if the condition is TRUE.

    That means a filter and its opposite don't cover the table: rows with NULL fall into neither. KYC NULLs are rarely random, so a filter that drops them silently decides about those customers.

    • Test with IS NULL, never = NULL. For "not equal" with possible NULLs, use IS DISTINCT FROM or COALESCE.
    • Prefer NOT EXISTS to NOT IN. One NULL in the subquery makes NOT IN never true, so one missing ID can make a screening query clear everyone.

    Window functions: aggregate without collapsing

    GROUP BY turns many rows into one. A window function computes across a set of related rows and puts the answer on every row, keeping them all, like a class report that prints each pupil's mark next to the class average. Three parts define the window:

    • PARTITION BY: which rows belong together (per customer, per account).
    • ORDER BY: the order inside each group, which makes "previous", "running" and "latest" meaningful.
    • The frame: which rows feed each row's calculation. By default the frame includes all rows tied with the current one, so two same-day transactions show the same running total. Use ROWS plus a tiebreaker for one step per row.

    Windows also give running totals, ranking and LAG (the previous row, behind "days since last transaction"). The pattern you will write most is latest record per entity: ROW_NUMBER ordered by recency, keep number 1.

    WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY updated_at DESC, record_id DESC   -- tiebreaker
         ) AS rn
  FROM kyc_profile_history
)
SELECT * FROM ranked WHERE rn = 1;

    The tiebreaker matters. If two records share the latest timestamp, ROW_NUMBER picks one arbitrarily and can change between runs,, so the feature flickers day to day.

    Latest record, and as-of joins

    "Latest record" suits dashboards about today. For a model it is a trap. Attach the latest bureau score to a March loan application and it carries an October score that already reflects later missed payments. The model learns from the future: leakage (F3.2), and a join is the commonest way in.

    The fix is an as-of join: for each event, take the most recent snapshot at or before it. Some engines have a native ASOF JOIN; elsewhere use a window function.

    There is a second clock. A snapshot dated 31 October may only have reached the warehouse on 12 November, like a letter postmarked Monday and read on Thursday. Use availability time, when the bank could have known.

    Logical query order: how to read any query

    SQL is written in one order and evaluated in another. Logically, the database works like this:

    1. FROM / JOINbuild the row set; grain is fixed here
    2. WHEREfilter rows (TRUE only)
    3. GROUP BYcollapse to groups
    4. HAVINGfilter groups
    5. Window functionsrun over what survived
    6. SELECTcompute outputs and aliases
    7. DISTINCTremove duplicate rows
    8. ORDER BY, LIMITsort, then truncate
    • Window functions and SELECT aliases don't exist yet in WHERE. That is why "latest record" needs a wrapper or QUALIFY.
    • LIMIT without ORDER BY returns an arbitrary set. Never sample with it.

    Checklist for any query, yours, a colleague's or an LLM's:

    1. What is one row of each input and of the output?
    2. For each join: which key, is it unique, and what happens to unmatched rows?
    3. Where do filters sit, and could NULLs be lost? Is each value as-of the event?
    Part 3

    How it fails, and how to spot it

    • Summing a column repeated by a join

      Salary or exposure summed after joining to a finer table, or after a second one-to-many join. Often "fixed" with DISTINCT.

      Spot itCompare with the same sum on the source table alone. Larger means fan-out.
    • The left join that lost its rows

      A WHERE filter on a right-hand column removes the NULL rows, or an inner join to an activity table skews a churn rate.

      Spot itDoes the row count equal the left table's? Move right-table conditions into ON.
    • NULLs dropped by a comparison

      status <> 'closed' loses NULL-status accounts. NOT IN with a NULL returns nothing.

      Spot itRun the filter and its opposite; if counts don't sum to the total, NULLs are in the gap.
    • Aggregating the wrong way

      Branch means or monthly rates averaged, or balances summed across days.

      Spot itAVG on a column that is already a ratio. Recompute from sums and counts.
    • Latest record, carelessly

      Today's risk rating or bureau score joined to past events looks wonderful in testing and breaks live. Without a tiebreaker, "latest" also changes between runs.

      Spot itFor each feature ask: as of when? Check availability lag too.
    • AI-generated SQL that looks plausible

      Wrong but similarly named keys, history tables joined without a date condition, DISTINCT sprinkled in.

      Spot itApply the checklist and reconcile to a known figure.
    Part 4

    Self-check

    Try each before opening the answer.

    1. Five customers have 3, 1, 2, 0 and 2 accounts. You inner join customers to accounts and SUM(salary). Is the result too high, too low or right? What about a left join?

    Too high in both cases. Customers with several accounts are counted several times (AED 185,000 against a true 100,000), and the inner join also loses the customer with no account. Aggregate accounts to one row per customer first.

    2. A customer has two transactions on the same day. With SUM(amount) OVER (ORDER BY date) and no frame, do the two rows show the same running total? How do you get one step per row?

    Yes: the default frame includes all rows tied on date. Use ROWS with a unique tiebreaker.

    3. Of 10 accounts, 5 are active, 2 dormant, 1 closed and 2 have NULL status. Why don't status = 'active' and status <> 'active' together return all 10? What does status NOT IN ('closed', NULL) return?

    The two NULL rows are UNKNOWN under both, so 5 + 3 = 8. The NOT IN returns nothing: every row is either FALSE or UNKNOWN.

    4. You left-join customers to October transactions and add WHERE t.txn_month = '2026-10'. What have you written, and how do you fix it?

    An inner join in disguise: customers with no October transaction have NULL there and are dropped. Move the condition into ON.

    5. Bureau scores are dated days 10, 80 and 150 and reach the warehouse 30 days later. For an application on day 100, which score does an as-of join on snapshot date pick, and which should it pick?

    Snapshot date picks day 80, which only arrived on day 110: a leak. It should pick the day-10 score.

    6. Your "latest address" query uses ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) and next week's results differ for a few customers. Why?

    Ties on updated_at are broken arbitrarily. Add a unique tiebreaker such as the record id.

    7. A dashboard averages two branch averages, one branch with 100 customers and one with 900. Will the bank-wide figure be reliable? What should it do instead?

    No. It weights the branches equally despite a nine-to-one size difference. Carry sums and counts, and divide at the end.
