    Foundation Models for Transaction Data

    Part 1

    What it is

    In one sentenceA transaction foundation model is a model that reads millions of customers' unlabelled transaction histories to learn what normal behaviour looks like, then hands each customer a summary (a list of numbers) that other models can reuse.

    Think of a language model. It reads huge amounts of text with no labels, learning by guessing the next word. A bank has the same setup: every card swipe, transfer and salary credit is a "word", and a customer's year is a "sentence".

    To guess the next transaction well, the model must learn that this customer buys groceries on Fridays and that salary lands on the 25th. It stores what it learned as an embedding: a short list of numbers describing one customer's behaviour.

    How it differs from other models

    • A normal fraud model is trained for one task, using labelled cases (confirmed fraud or not). A foundation model needs no labels to pretrain and serves many tasks.
    • Hand-built features (average spend, number of transfers) are chosen by people. The embedding is learned from the sequence itself, including timing and order.
    Part 2

    How it works

    1. Turn each transaction into tokens. One way is to write it as text ("AED 212.40, Carrefour, Dubai, 14:05"), which costs about 15 tokens per transaction. The other is a fixed vocabulary: one token each for merchant category, amount bucket, time gap and country. That is about four tokens, so the model sees a much longer history. The price is rounding, like quoting prices to the nearest AED 10.
    2. Pretrain by guessing the next token. This is called self-supervised learning: the history supplies its own answers, so no fraud label is needed. Attention lets today's purchase link back to a pattern from three months ago.
    3. Create the embedding. Run a customer's history through the model and keep the summary vector.
    4. Reuse it. The safest route is a frozen embedding: add the vector as extra columns beside your existing features in a gradient-boosted model. The other route is fine-tuning: attach a small output layer for one task and train everything.
    5. Test it on a real task. A low pretraining loss only means the model predicts habits well. It says nothing about fraud accuracy until you test the embedding on fraud.
    Part 3

    How to read the results

    Running example: 200 confirmed fraud cases, 200 raw columns. Does the embedding help?

    Few labels (tens to a few hundred)
    Learning fraud from 200 cases across 200 columns is like learning a language from 200 sentences. The embedding has already learned which behaviours matter, so it usually helps a lot.
    Many labels (tens of thousands)
    The raw model can now learn precisely, and the signal the embedding threw away becomes the limit. The gain is often modest.
    AUC 0.5 vs 0.9
    AUC is the chance that a random fraud case scores higher than a random genuine one. 0.5 is a coin flip, 0.9 is strong.
    Nubank's 1.25% relative AUC gain
    Over a strong LightGBM baseline, that is about one AUC point. Small as a number, but large across 100 million customers. It is the company's own figure.

    One embedding, many products

    The embedding is shared infrastructure. One model feeds fraud, credit limits and offers, so a flaw or a bias reaches every product. Validate it on its own, and give it an owner.

    Part 4

    The synthetic data trap

    In one sentenceSynthetic data is made-up customer rows sampled from a model fitted to real ones, and a model that fits well can memorise real people, so "synthetic" does not mean "anonymous".

    Banks want synthetic customers to give vendors realistic data, test pipelines or add rare cases. But a generator can act like a forger who studied one painting so closely that the copy is the original. Three attacks matter:

    • Membership inference: was this person in the training data? That alone can reveal they were a customer.
    • Attribute inference: the attacker knows some fields and guesses a sensitive one, such as an arrears flag.
    • Outlier reconstruction: a client with a unique profile is often reproduced almost verbatim.
    • Utility and privacy trade off. Settings that keep rare, valuable patterns also keep the individuals behind them.
    • Simple filters leak. Dropping synthetic rows near a real record leaves a hole where each training customer stood. The hole is the signal.
    • Differential privacy is the only formal guarantee: it bounds what an attacker can learn about one record. The cost is lower fidelity on small groups.

    Whether synthetic data counts as personal data in the Gulf depends on whether people can be re-identified from it. Ask your data protection officer and legal team.

    Part 5

    Which to use, and when it breaks

    OptionLabels neededUse it when
    Hand-built featuresYes, per taskPlenty of labels, and you need a simple, explainable model
    Frozen embedding as featuresYes, smallFew labels and you want the lowest-risk upgrade
    Fine-tuned foundation modelYes, moreOne high-value task and the team to run it
    Synthetic dataNoSharing or testing, only after attack testing

    Strong at:

    • Scarce labels, because pretraining needs none.
    • Reuse across fraud, credit and offers.

    Weak at:

    • Plentiful labels, where the gain is often small.
    • Explaining decisions, because the embedding is opaque.
    • Hidden proxies: merchants and timing (prayer-time patterns, remittance corridors) can encode nationality or religion, so a credit model can discriminate with no protected column.

    In banking, one shared embedding is both the biggest opportunity and the biggest single point of failure, so validate it independently and test downstream outputs for disparity.

    Part 6

    Common mistakes and quick check

    • Weak baseline

      "Beats logistic regression by 8 points" means little if a tuned boosted model closes most of that gap. Compare against the best production model.

    • Pretraining on the future

      If the embedding was built from history that runs past the decision date, it leaks the answer. Use history up to decision time only.

    • Same customer in training and test

      The model may have memorised customers. Separate evaluation in time, the way you will deploy.

    • "Synthetic, so it's anonymous"

      Ask for a membership-inference test, reported for the rarest customers too. Averages hide the exposed few.

    1. Why can the model be pretrained with no fraud labels?

    The target is the next token in the customer's own history, so the data supplies the answer. Labels are needed only for the small final classifier.

    2. Why does the embedding help most with a few dozen fraud cases?

    A boundary across 200 raw columns is mostly noise with so few cases. With 100,000 cases the raw model learns it well, and the signal the embedding dropped becomes the limit.

    3. An embedding was built from 12 months of history, up to the day a fraud case closed. What is wrong?

    Leakage: the window runs past the decision and may include the fraud or its aftermath.

    4. Why are outlier customers exposed first by a memorising generator?

    For a typical customer many others sit nearby, so a close synthetic row says little. For an outlier it is almost certainly a copy of that person.

    5. What does differential privacy give you that attack testing does not?

    A formal bound on what any attacker can learn about one record. Attack testing covers only the attacks you tried. The cost is lower fidelity on rare groups.
