    Guardrails, Approval Gates and Choosing the Simplest Agent Design

    Which actions an agent may take alone, which need a human, why the gate must live in code and not in the prompt, why too many approvals make oversight worse, and how to pick the least autonomous design that still does the job.

    Contents

    The whole lesson in one sentenceGive an agent the least power that gets the job done, put a human only in front of actions that are hard to undo, enforce that rule in ordinary code the model cannot talk its way past, and keep the approval queue small enough that people still read it.

    Part 1

    The intuition

    A bank gives a new analyst a laptop, read access to some systems, and a list of things that need a second signature. It does not give them the ability to wire AED 2 million alone on day one, however clever they are. Cleverness is not the control. The control is the structure around them: limited access, a second pair of eyes on the risky moves, and a record of what they did.

    An AI agent (M4.1) is a new analyst that works at machine speed, never gets tired, and can be fooled by a sentence hidden in a PDF. So the same structure applies, and it matters more. Three ideas make up this lesson.

    • A guardrail is any check that sits between the model's wish and the world. It can inspect what goes in, what comes out, or, most importantly, what the agent is about to do.
    • An approval gate is the strongest guardrail: it stops the action until a person says yes. It is expensive in attention, so you spend it where a mistake cannot be taken back.
    • The simplest design that works is the safest one. A fixed workflow with a model inside one step is easier to gate, test and explain than an agent that chooses its own path, and far easier than several agents talking to each other.
    Hold onto thisTwo questions for every action an agent can take. Can it be undone, and how cheaply? and How much damage if it is wrong or hijacked? The answers, not the model's confidence, decide whether the action runs freely, runs with a log, waits for a human, or is not available at all.
    Part 2

    How it really works

    The layers of a guardrail

    "Guardrails" is used loosely. It helps to name where a check sits, because each place catches different failures and has different strengths.

    LayerWhat it checksTypical toolsStrength and weakness
    InputWhat reaches the model: prompt-injection patterns, PII, off-topic or abusive requests, out-of-scope tasks.Classifiers, regexes, allow-lists, sanitising of retrieved text.Cheap and early. Probabilistic: a clever attack can slip through, so never the only layer (see A3.1).
    Action (tool)What the agent tries to do: which tool, which arguments, on whose behalf, how large.Allow-lists, argument validation, spending limits, scope checks, approval gates.The strongest layer. Deterministic code, tested like any other code. It limits the damage even if the model is fully compromised.
    OutputWhat goes to the user or another system: leaked data, unsupported claims, tone, banned advice, format.Schema validation, groundedness checks, redaction, a second model as judge.Catches embarrassing replies. A judge model shares weaknesses with the model it judges.
    SystemEverything around the run: logging, rate limits, kill switch, budget caps, monitoring.Gateways (A15.3), tracing (P2), alerting.What lets you see a problem and stop it. Does not prevent the first bad action.

    A useful split is soft guardrails (a model or a pattern matcher decides; it can be wrong or fooled) and hard guardrails (ordinary code that either allows or refuses; it cannot be argued with). Soft ones reduce how often something bad is attempted. Only hard ones bound how bad it can get. Security people put it as: the prompt is a request, the permission system is a law.

    The broader risk has a name. OWASP lists excessive agency among its top risks for LLM applications: an agent given too many tools, too many permissions, or too much freedom to act without checks (OWASP, LLM06:2025). Guardrails are the practical answer to it.

    Tiering actions by reversibility and blast radius

    Do not decide "does this agent need a human?" for the agent as a whole. Decide it for each action. Two properties do most of the work.

    • Reversibility. Can a mistake be undone cheaply? Reading a record, drafting a reply and freezing a card (the customer can unfreeze) are reversible. Sending money, sending an email to a customer, deleting data and changing contact details are not, or only at real cost.
    • Blast radius. How much can go wrong if this one call is wrong or hijacked? One customer's balance is small. A bulk update, a rule change that affects every transaction, or a payment of AED 250,000 is large.

    Combine them into four tiers. Names vary between teams; the logic does not.

    TierReversibility and radiusWhat happensBank examples
    0 · Run freelyRead-only or purely internal; tiny radius.Runs. Still covered by system-level logging.Drafting text, summarising a document, a read on the customer in the current session.
    1 · Run and logReversible, small radius, or protective and time-critical.Runs, with a full audit record and after-the-fact sampling by a human.Temporarily blocking a card on a fraud signal, tagging a case, read-only reporting queries.
    2 · Needs approvalHard to undo, or large radius, or external.Pauses. A named human sees the exact action and approves, edits or rejects.Payments to new beneficiaries, changing a customer's phone number, sending a letter, closing an AML alert.
    3 · Not availableSevere and unneeded for the job.The tool does not exist for this agent. No prompt can call it.Editing audit logs, disabling a sanctions rule, changing the agent's own permissions.

    Notice the asymmetry in tier 1. For a fraud freeze, waiting for approval is itself the harm: the money leaves while the ticket sits in a queue. So the right control is to make the action cheap to undo and to review it afterwards. Tiers are not "more careful is always better"; they are a trade between speed, cost of error and human attention. Try sorting some yourself.

    Enforce the gate in code, not in the prompt

    The most common mistake is writing the rule into the system prompt: "Never transfer more than AED 10,000 without approval." A prompt is text the model reads and weighs with everything else. It can be overridden by a clever user, by an instruction inside a retrieved document, by a long conversation that pushes the rule out of focus, or by plain model error. Each attempt has some chance of working. Over many attempts, a small chance becomes near-certainty.

    The fix is to move the rule out of the model entirely. The model proposes a tool call. A piece of normal code, which the model cannot edit, decides whether it runs. Here is the shape, in a few lines:

    def call_tool(name, args, ctx):
    spec = REGISTRY[name]                           # allow-list: unknown tool = error
    check_scope(ctx.user, spec, args)               # least privilege, checked every call
    if spec.tier == "approve":
        tok = ctx.approvals.get(hash_call(name, args))   # approval bound to the exact arguments
        if tok is None or not tok.valid(now()):
            return pending(name, args)              # pause: do NOT execute, show a human
        if tok.approver == ctx.requester:           # four-eyes: no self-approval
            raise Denied("self-approval")
    audit.log(name, args, ctx, tok)                 # who, what, why, under which approval
    return spec.run(**args)

    Four details make this real rather than decorative.

    • Approval is bound to the exact arguments. If the human approved "pay AED 5,000 to account X", the token is valid for that call only. Otherwise the agent can get a harmless request approved and then swap the amount or beneficiary.
    • The gate sits on the only path to the side effect. If the agent can reach the payments API by another tool, a shell command or a second agent, the gate is decoration. Coverage is the whole game.
    • The agent acts with the user's permissions, not the bank's. A service account with broad rights turns a hijacked agent into a privileged insider (the "confused deputy" problem). Pass the end user's identity down and check it at the tool.
    • Approval state lives on the server. Frameworks that support pause-and-resume store the paused run and return the pending requests; the client should only be able to say yes or no to a stored request, not supply a replacement call (this is how OpenAI's Agents SDK documents it).

    Approval that works: why more gates can mean less safety

    A natural reaction is "put a human on everything". It fails for a human reason. People reviewing a long stream of mostly harmless requests stop reading. They approve in a second, because 99 out of 100 times the answer is yes. This is approval fatigue, a cousin of the alert fatigue that every transaction-monitoring team knows (B2.1). It is also automation bias: once a machine has proposed something, people tend to accept it.

    The result is a rubber stamp. The bank can say a human approved every action, and the human caught nothing. Regulators and auditors increasingly look past "a human was in the loop" to whether that human could realistically have noticed a problem (for the EU's high-risk systems, human oversight under Article 14 of the AI Act is framed around exactly that ability; check the latest application dates).

    Design for attention, not for the checkbox.

    • Gate by risk, not by volume. Only tier 2 actions reach a person. A risk score, amount limit or "first time to this beneficiary" rule decides. Everything else is logged and sampled.
    • Show the exact action, in plain words, with the evidence. "Pay AED 250,000 to a new beneficiary in another country, requested at 02:14, customer has never paid abroad" beats "Approve agent action?". A reviewer who sees the diff can catch what a reviewer who sees a button cannot.
    • Make reject easy and safe. If rejecting takes more effort than approving, approvals will win.
    • Measure the reviewers. Track time to decision, approval rate, and how often reviewers edit or reject. A 100% approval rate in two seconds is a warning, not a success. Seed the queue with known-bad test cases to check that people still catch them.
    • Keep sampled review for tier 1. Look at a random slice of what ran freely. That is how you learn the tiers are wrong.

    The next simulation models the trade. A queue of agent actions arrives each day. A few are bad (1%). Each has a risk score; bad ones score higher on average but overlap with the harmless ones, as they do in practice. You set the score above which an action goes to a human. Reviewers catch a bad action less often the faster they must work.

    The point of the curve is not the particular numbers. It is that both ends are bad and the optimum depends on things you can change: how much reviewers see, how many there are, and how well the risk score separates bad from harmless. Better scoring, better context for the reviewer and a smaller, sharper queue all push the whole curve down. This is the same threshold-and-capacity logic as alert tuning in fraud (F7), now applied to an agent's own actions.

    Two further control patterns are worth knowing. Four-eyes (maker-checker): the agent is the maker; a different, authorised human is the checker; the system forbids the same identity from being both. And pre-commit plan approval: for a long task, a person approves the plan once, then the agent runs inside narrow limits and stops for anything outside the plan. That cuts the number of prompts without removing the check (see A2.3 and A2.4 on autonomy levels).

    Workflow, single agent or multi-agent: pick the simplest that works

    Three designs, ordered by how much freedom the model has.

    • Workflow. Your code defines the steps. A model does a task inside a step, such as classify this email, extract these fields, draft this paragraph, and the code decides what comes next. Variants include a chain of steps, a router that sends each input to the right branch, parallel steps whose outputs are combined, and an evaluator that loops until a check passes.
    • Single agent. One model in a loop (M4.1) with tools. The model decides which tool to call next and when it is done. The path is not known in advance.
    • Multi-agent. Several model-driven agents, often an orchestrator that delegates sub-tasks to workers with their own context and tools, then combines the results.

    Anthropic's guidance on this (Building effective agents, 2024) is plain: find the simplest solution and only add complexity when it measurably helps, because agentic systems trade latency and cost for flexibility. The costs of moving right are real.

    • Predictability falls. A workflow has a fixed path you can test and gate step by step. An agent has a distribution of paths. A multi-agent system has a distribution of conversations.
    • Cost and latency climb. Anthropic reported that agents use around four times the tokens of a chat interaction and multi-agent systems around fifteen times (from their account of building a research system; check the source for the current figures). Each extra loop or hand-off is another model call.
    • Errors compound. If each step is right 95% of the time, ten steps in sequence are right about 60% of the time (0.9510). Free-form agents have more steps than workflows.
    • Control gets harder. More tools and more agents mean more permissions to scope, more gates to place, and more surface for injection to travel along.

    Multi-agent designs earn their cost in specific conditions: the work splits into independent pieces that can run in parallel (checking 40 related entities in a due-diligence review), the information would overflow one context, or different parts need different permissions, so that one agent reading untrusted documents is kept apart from another holding the ability to act. That last reason is a security design, not a performance one.

    Part 3

    How it connects

    Guardrails are where agent capability meets bank control. These are the neighbouring topics.

    M4.1 – M4.2 · Agent loop and tool designWhat the gate is gating

    Tool design is the first guardrail: narrow tools with typed arguments are easier to scope and approve than a general "run SQL" or "run shell" tool.

    M4.3 – M4.4 · Memory and planningWhat persists across steps

    Long-term memory can carry a poisoned instruction from one session to the next. A plan, once approved, is a natural unit for a gate.

    A3.1 – A3.2 · Prompt injection and defence by designWhy prompts cannot be the control

    Text from a document or web page can contain instructions. Design-level defences (capabilities, separating the reader from the actor) are the architectural form of the gate in this lesson.

    A3.3 – A3.4 · Tool poisoning and OWASP threatsExcessive agency, in detail

    A malicious or compromised tool server is one more way past a gate that only watches the model.

    A2.3 – A2.4 · Long-running agents and autonomy levelsAutonomy by task risk

    The tiers here become autonomy levels there: how long an agent may run and how far it may range before it must check in.

    A15.3 · AI gateways and guardrailsWhere guardrails run in the stack

    A central gateway enforces input and output checks, budgets and logging uniformly across every agent the bank builds.

    G1.1 – G1.2 · Threat modelling, access controlLeast privilege and logging

    Scoped credentials, secrets handling and audit trails are the ground the gates stand on.

    M5.5 · Evaluating agentsTesting that the gate holds

    Measure how often an agent attempts a gated action and whether any path reaches it unapproved. Adversarial runs belong in the test suite (see A4.5).

    G3 · Model governanceMonitoring and review

    Approval rates, override rates and sampled reviews are monitoring metrics for the oversight itself, which belongs in periodic review.

    A12 · Regulator expectationsWhat supervisors expect

    Accountability, human oversight and auditability are recurring supervisory themes. Check the specific current requirements rather than assuming.

    A1 · Know Your AgentIdentity and delegated authority

    Gates need to know who the agent acts for and what it is allowed to spend. That is the identity layer.

    Where it shows up at the bank:

    • Customer service assistant. Reads account context freely; sending messages and changing details needs approval or strict templates; every action logged (B7).
    • AML and KYC investigation support. An agent gathers evidence from several systems and drafts a recommendation. Closing or escalating an alert, or filing a report, remains a human decision with a named owner (B3).
    • Fraud operations. Protective, reversible actions (temporary holds) run fast and are reviewed afterwards; irreversible ones wait for an analyst.
    • Payments and treasury. Agents prepare and validate instructions; release follows the bank's existing maker-checker and limits. Most banks will keep the final payment step outside the agent.
    • Internal engineering. Coding agents in a controlled environment: read freely, write to a branch, nothing reaches production without review (A15.1).
    Part 4

    Where the field is now

    The architecture is settling: least privilege, tiered actions, deterministic enforcement, human approval for the hard-to-reverse. The live questions are how to avoid approval fatigue at scale, whether a model can be trusted to gate another model, and how many agents a task really needs.

    Part 5

    How it fails, and how to spot it

    These turn up in pilots and in design reviews. Each comes with the quickest check.

    • The rule lives in the prompt

      "The assistant is instructed never to approve refunds above AED 500." The instruction is a hope, not a control.

      Spot itAsk: if the model ignored this instruction, what would stop the action? If the answer is "nothing", there is no guardrail.
    • A gate with a side door

      Payments are gated, but a generic "call internal API" tool or a shell reaches the same endpoint.

      Spot itList every tool and every system each can reach. Try to reach the gated action by every route, as a test.
    • Approval of intent, not of the action

      A person approves "process refund", and the arguments are filled in afterwards.

      Spot itCheck that the approval record contains the exact arguments and that execution fails if they differ.
    • Rubber-stamp queues

      Everything is gated, approval rate is 99.8%, median time is two seconds.

      Spot itPull approval rate, time per decision and edit/reject rate. Slip a few known-bad items into the queue and see whether they are caught.
    • Over-privileged service account

      The agent runs with broad rights "to avoid permission errors". A hijack inherits all of them.

      Spot itCompare the agent's permissions with what its tasks need, and check whether the end user's identity is passed down.
    • Self-approval and shared identities

      The requester and the approver are the same person, or share a login.

      Spot itLook for approvals where requester equals approver, and for approvals made by service accounts.
    • A model judge as the only gate

      A second LLM "reviews" the first one's actions and is trusted to block bad ones. Both can be fooled by the same text.

      Spot itAsk what happens if the judge is wrong. Use a model judge to route to humans or to add friction, with a hard rule behind it for high-impact actions.
    • Too much architecture

      A multi-agent system with an orchestrator, critics and planners for a task that was four fixed steps.

      Spot itAsk whether a workflow, with the model only inside steps, gives the same result on a test set. If so, use it. Compare cost and latency, not just accuracy.
    • No kill switch, no log

      When something goes wrong, nobody can stop the agent quickly or reconstruct what it did.

      Spot itAsk who can disable it, in how many minutes, and where the record of every action is stored.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “We are not asking whether the assistant is smart enough to be trusted. We are limiting what it can do. It can read and draft freely, small reversible actions run with a log, and anything that moves money or contacts a customer waits for a named person to approve that exact action. These rules are built into the system, not written as instructions to the AI, so a clever request cannot talk its way past them. We keep the approvals few, so staff actually read them.”
    To a technical interviewer or validator
    “I tier tool calls by reversibility and blast radius. The model proposes; a deterministic layer enforces an allow-list, per-user scopes and, for tier-2 actions, an approval token bound to the exact arguments with no self-approval. The only path to a side effect goes through that layer. I'd start with a fixed workflow, move to a single agent only where the path can't be known in advance, and consider multiple agents only for parallel work or to separate untrusted-reader from actor permissions. I'd monitor approval rate, decision time and override rate, seed known-bad cases, and sample the free-running tier.”
    “Why not just tell the model not to do it?”

    Because an instruction is something the model weighs, and it can be overridden by a user, a poisoned document or a long conversation. Even at a 2% failure rate per attempt, a determined user gets through in a few dozen tries. The control has to be code that checks the action itself, which the model cannot edit.

    “Can't we have a human approve everything to be safe?”

    It feels safe and often isn't. With thousands of mostly harmless requests, people click through, so the real catch rate falls even as the approval count rises. Send humans only the actions that are hard to undo, show them exactly what will happen, measure their behaviour, and sample the rest afterwards.

    “Should this be a multi-agent system?”

    Only if a simpler design fails a test. Multi-agent systems cost more (reported at around fifteen times the tokens of chat), are harder to test and widen the attack surface. They are justified for work that splits into independent parallel pieces, or when I want to separate an agent reading untrusted text from one with the power to act. Otherwise a workflow or a single agent with tight tools is easier to gate and explain.

    “Could another AI model be the approver?”

    As a filter, yes: it can route routine items and flag risky ones, and that helps with volume. As the final authority for a high-impact action, I would not, because it can be fooled by the same text and cannot be held accountable. The hard limits stay in code, and a person approves what is hard to undo.

    “How do we know the guardrails work?”

    Test them like any control. Attack scripts and injected documents in the test suite; a check that every route to a gated action fails without a valid approval; approval-queue metrics in production; seeded bad cases to see if reviewers catch them; and periodic review of the free-running tier. Report rates with intervals, not a single demo.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. Name the two properties that decide whether an agent action needs a human, and give a bank action that is low on both.

    Reversibility (can it be undone cheaply) and blast radius (how much damage if wrong or hijacked). Drafting a reply that is not sent, or reading the balance of the customer in the current authenticated session, is reversible and small.

    2. Why is freezing a card on a fraud signal usually "run and log" rather than "needs approval"?

    It is protective and reversible: the customer can unfreeze it. Waiting for approval delays the very protection the action provides, so the harm of delay can exceed the harm of an occasional wrong freeze. Control it with logging, after-the-fact sampling and an easy release path.

    3. A prompt rule is beaten with probability 1% per attempt. Roughly how many independent attempts until the chance of at least one breach passes 50%?

    Solve 1 − 0.99n = 0.5: n = ln 0.5 ÷ ln 0.99 ≈ 69. A code gate that covers every dangerous path has no such curve under this model, but a gate covering 90% of paths behaves like a prompt rule with one tenth the success chance (0.1% per attempt), so about 693 attempts.

    4. Why must an approval be bound to the exact arguments of the call?

    Otherwise the agent, or an attacker steering it, can obtain approval for a harmless-looking request and then execute a different amount, beneficiary or target. Binding the token to a hash of the tool name and arguments makes any change invalidate it.

    5. Your approval queue shows 99.7% approved, median decision 1.8 seconds. Is the control working? What do you do?

    Probably not. It looks like a rubber stamp. Check volume per reviewer, whether the reviewer sees the evidence, and test with seeded bad cases. Then shrink the queue by gating on risk instead of volume, improve what is displayed, and move low-risk items to logged-and-sampled.

    6. A ten-step agent has 95% success per step. What is the chance the whole run is right, and what does it imply for design?

    0.9510 ≈ 60% (assuming independence). Long free-form chains lose reliability quickly. Prefer fewer steps, fixed workflows where the path is known, checks between steps, and approvals at the points where an error would cost most.

    7. Give two legitimate reasons to use several agents instead of one.

    Parallelism: the work splits into independent pieces (for example screening 40 related entities). And separation of permissions: one agent reads untrusted documents with no ability to act, another holds the tools to act but never sees raw untrusted text. Context size is a third. Convenience of "one agent per role" is not a reason.

    8. A colleague proposes an LLM judge to approve or block the agent's payments. What is your position?

    Use it to rank and flag, not to be the last line. It shares blind spots with the agent and cannot be accountable. Payments keep deterministic limits and a person's approval for new beneficiaries and large amounts; the judge can reduce volume and add context for that person.
