    Guardrails, Approval Gates and Choosing the Simplest Agent Design

    Contents
    Part 1

    The intuition

    A bank does not let a new analyst wire AED 2 million alone on day one, however clever they are. The control is the structure: limited access, a second signature on risky moves, a record of what they did. An AI agent (M4.1) is a new analyst at machine speed who can be fooled by a sentence hidden in a PDF, so the same structure matters more.

    • A guardrail is any check between the model's wish and the world, most importantly on what the agent is about to do.
    • An approval gate is the strongest guardrail: the action waits until a person says yes. It costs attention, so spend it where a mistake cannot be taken back.
    • The simplest design that works is the safest. A fixed workflow is easier to gate, test and explain than a free-roaming agent.
    Hold onto thisAsk two questions of every action. Can it be undone, and how cheaply? and How much damage if it is wrong or hijacked? The answers, not the model's confidence, decide whether it runs freely, runs with a log, waits for a human, or is not available at all.
    Part 2

    How it really works

    The layers of a guardrail

    A guardrail is a check; where it sits decides what it catches.

    LayerWhat it checksStrength and weakness
    InputWhat reaches the model: injection patterns, PII, out-of-scope requests.Cheap and early, but probabilistic. Never the only layer (see A3.1).
    Action (tool)What the agent tries to do: which tool, arguments, on whose behalf, how large.Strongest. Deterministic code that limits damage even if the model is fully compromised.
    OutputWhat goes to the user: leaked data, unsupported claims, banned advice.Catches embarrassing replies. A judge model shares weaknesses with the model it judges.
    SystemLogs, rate limits, kill switch, budget caps (A15.3, P2).Lets you see and stop a problem, but does not prevent the first bad action.

    Soft guardrails (a model or pattern matcher decides) can be wrong or fooled; they reduce how often something bad is attempted. Hard guardrails (ordinary code that allows or refuses) cannot be argued with; only they bound how bad it can get. The prompt is a request; the permission system is a law. OWASP lists excessive agency (too many tools, permissions or freedom to act) among its top LLM risks; guardrails are the answer.

    Tiering actions by reversibility and blast radius

    Decide per action, not per agent, with two questions.

    • Reversibility. Can a mistake be cheaply undone? Reading a record, drafting a reply and freezing a card can. Sending money, emailing a customer and deleting data cannot.
    • Blast radius. How much breaks if this call is wrong or hijacked? One customer's balance is small. A bulk update or a AED 250,000 payment is large.

    Combine them into four tiers.

    TierWhat happensBank examples
    0 · Run freelyRead-only or internal, tiny radius. Runs.Drafting text, summarising a document.
    1 · Run and logReversible, small radius, or protective and time-critical. Runs with an audit record and later sampling.Temporary card block on a fraud signal, tagging a case.
    2 · Needs approvalHard to undo, large radius, or external. Pauses; a named human approves, edits or rejects the exact action.Payment to a new beneficiary, changing a phone number, closing an AML alert.
    3 · Not availableSevere and unneeded. The tool does not exist for this agent, so no prompt can call it.Editing audit logs, disabling a sanctions rule.

    Tier 1 is the subtle one. For a fraud freeze, waiting for approval is the harm: the money leaves while the ticket sits in a queue. So make the action cheap to undo and review it afterwards. Try sorting some yourself.

    Enforce the gate in code, not in the prompt

    A rule in the prompt, such as "Never transfer more than AED 10,000 without approval", is a sign on a door, not a lock. A clever user, an instruction hidden in a retrieved document, or plain error can override it. Each attempt has a small chance; over many attempts a small chance becomes near-certainty.

    So move the rule out of the model. The model proposes a tool call; ordinary code it cannot edit decides whether it runs:

    def call_tool(name, args, ctx):
    spec = REGISTRY[name]                           # allow-list: unknown tool = error
    check_scope(ctx.user, spec, args)               # least privilege, checked every call
    if spec.tier == "approve":
        tok = ctx.approvals.get(hash_call(name, args))   # approval bound to the exact arguments
        if tok is None or not tok.valid(now()):
            return pending(name, args)              # pause: do NOT execute, show a human
        if tok.approver == ctx.requester:           # four-eyes: no self-approval
            raise Denied("self-approval")
    audit.log(name, args, ctx, tok)                 # who, what, why, under which approval
    return spec.run(**args)

    Three details make this real:

    • Approval is bound to the exact arguments. An approval for "pay AED 5,000 to X" is valid for that call only. Otherwise the agent swaps the amount or beneficiary afterwards.
    • The gate sits on the only path to the side effect. If another tool, a shell or a second agent reaches the payments API, the gate is decoration. Coverage is the whole game.
    • The agent acts with the user's permissions, not the bank's. A broad service account turns a hijacked agent into a privileged insider (the "confused deputy"). Pass the end user's identity down and check it at the tool.

    The simulation below shows why this matters: a small per-attempt chance of beating a prompt rule compounds, while a code gate blocks every dangerous action it covers.

    Approval that works: why more gates can mean less safety

    Putting a human on everything backfires. Like a smoke alarm that goes off whenever you make toast, a queue of mostly harmless requests teaches people to stop reading. This is approval fatigue, a cousin of alert fatigue in transaction monitoring (B2.1), plus automation bias: people tend to accept what a machine proposes. The result is a rubber stamp: a human approved everything and caught nothing. Regulators increasingly ask whether the human could realistically have noticed a problem (EU AI Act Article 14). Design for attention:

    • Gate by risk, not volume. Only tier 2 reaches a person; the rest is logged and sampled.
    • Show the exact action with evidence. "Pay AED 250,000 to a new overseas beneficiary at 02:14; customer has never paid abroad" beats "Approve agent action?".
    • Measure reviewers. Track decision time, approval rate and reject rate. 100% approved in two seconds is a warning. Seed the queue with known-bad cases.

    The next simulation models the trade. Each day 1% of actions are bad. Bad ones score higher on average but overlap with harmless ones. You set the score above which an action goes to a human. Reviewers catch less the faster they must work.

    Both ends of the curve are bad. Think of airport security: screen everyone hard and the queue makes screeners sloppy; screen no one and threats walk through. Better scoring, richer context and a smaller, sharper queue all push the curve down. It is the same threshold-and-capacity logic as fraud alert tuning (F7). Two more patterns help.

    • Four-eyes (maker-checker). The agent is the maker; a different authorised human is the checker; the system forbids one identity being both.
    • Pre-commit plan approval. A person approves a long task's plan once; the agent then runs inside narrow limits and stops for anything outside it (see A2.3 and A2.4).

    Workflow, single agent or multi-agent: pick the simplest that works

    Think of a kitchen. A recipe is a workflow: fixed steps, with judgement only inside a step. A single chef improvises the order. A brigade has several chefs coordinating. Use the recipe whenever it will do.

    • Workflow. Your code defines the steps; a model works inside a step (classify this email, extract these fields).
    • Single agent. One model in a loop (M4.1) with tools, choosing the next call and when to stop.
    • Multi-agent. An orchestrator delegates sub-tasks to workers with their own context and tools.

    Add complexity only when it measurably helps (Anthropic's Building effective agents). Moving right costs you predictability (a workflow has one testable path; an agent has many), cost and latency (Anthropic reported roughly four times the tokens of chat for agents and fifteen times for multi-agent), and control (more tools mean more permissions to scope and more routes for injection). Errors also compound: at 95% per step, ten steps are right about 60% of the time.

    Multi-agent earns its cost when work splits into independent parallel pieces (checking 40 related entities), would overflow one context, or needs different permissions: an agent reading untrusted documents kept apart from one that can act. The last is a security design, not a performance one.

    Part 3

    How it fails, and how to spot it

    • A soft rule as the only gate

      "The assistant is instructed never to approve refunds above AED 500", or a second LLM reviews the first one's actions. Both can be fooled by the same text. That is a hope, not a control.

      Spot itAsk: if the model ignored this, what would stop the action? If "nothing", there is no guardrail. Use a judge to route to humans, with a hard rule behind it.
    • A gate with a side door

      Payments are gated, but a generic "call internal API" tool or a shell reaches the same endpoint.

      Spot itList every tool and what it can reach. Test every route to the gated action.
    • Approval of intent, not of the action

      A person approves "process refund" and the arguments are filled in afterwards, or requester and approver are the same person.

      Spot itCheck the approval record holds the exact arguments, execution fails if they differ, and requester never equals approver.
    • Rubber-stamp queues

      Everything is gated, approval rate 99.8%, median time two seconds.

      Spot itPull approval rate, time per decision and reject rate. Slip in known-bad items and see if they are caught.
    • Over-privileged service account

      The agent has broad rights "to avoid permission errors". A hijack inherits all of them.

      Spot itCompare its permissions with what its tasks need, and check the end user's identity is passed down.
    • Too much architecture

      An orchestrator, critics and planners for a task that was four fixed steps, with no kill switch or log when it goes wrong.

      Spot itCheck whether a workflow gives the same result on a test set. Ask who can stop the agent, in how many minutes, and where every action is recorded.
    Part 4

    Self-check

    1. Name the two properties that decide whether an agent action needs a human, and give a bank action that is low on both.

    Reversibility (can it be undone cheaply) and blast radius (damage if wrong or hijacked). Reading the current customer's balance, or drafting an unsent reply, is reversible and small.

    2. Why is freezing a card on a fraud signal usually "run and log" rather than "needs approval"?

    It is protective and reversible: the customer can unfreeze. Waiting for approval delays the very protection the action gives. Control it with logging, sampling and an easy release path.

    3. A prompt rule is beaten only 1% of the time per attempt. Why is that still not safe, and what does a code gate change?

    Small chances compound: after roughly 70 attempts a breach is more likely than not. A gate covering every dangerous path takes the model out of the decision. A gate covering 90% only cuts the odds tenfold, and the attacker needs just the one path you missed.

    4. Why must an approval be bound to the exact arguments of the call?

    Otherwise an agent, or an attacker steering it, gets a harmless-looking request approved and then runs a different amount or beneficiary. Tying the approval to the tool name plus arguments makes any change invalidate it.

    5. Your approval queue shows 99.7% approved, median decision 1.8 seconds. Is the control working? What do you do?

    Probably not: it looks like a rubber stamp. Check volume per reviewer, whether they see the evidence, and test with seeded bad cases. Then gate on risk, improve what is displayed, and move low-risk items to logged-and-sampled.

    6. Why do long free-form agent runs lose reliability, and what does that imply for design?

    Each step has a small chance of error and they compound: 95% per step over ten steps is right only about 60% of the time. Prefer fewer steps, fixed workflows where the path is known, checks between steps, and approvals where an error costs most.

    7. Give two legitimate reasons to use several agents instead of one.

    Parallelism (independent pieces, such as screening 40 related entities) and separation of permissions (one agent reads untrusted documents with no power to act; another holds the tools but never sees raw untrusted text). "One agent per role" for convenience is not a reason.

    8. A colleague proposes an LLM judge to approve or block the agent's payments. What is your position?

    Use it to rank and flag, not as the last line. It shares blind spots with the agent and cannot be accountable. Payments keep deterministic limits and a person's approval for new beneficiaries and large amounts; the judge can cut volume and add context for that person.
