    Guardrails, Approval Gates and Simple Agent Designs

    Part 1

    What a guardrail is

    In one sentenceA guardrail is a check between what the model wants to do and what actually happens, and the strongest ones are ordinary code the model cannot talk its way past.

    A bank does not let a new analyst wire AED 2 million alone on day one. The control is the structure: limited access, a second signature, a record. An AI agent is a new analyst at machine speed who can be fooled by a sentence hidden in a PDF, so the structure matters more.

    Running example. A payments-support agent can read accounts, draft replies, freeze cards and send payments. Which of those should just run, and which should wait for a person?

    • Guardrail: any check on input, action, output or the system around the agent.
    • Approval gate: the strongest kind. The action waits until a named person says yes.
    Part 2

    Where guardrails sit, and how they differ

    LayerChecksStrong at / weak at
    InputWhat reaches the model: injection patterns, personal data, off-topic requestsCheap and early. Probabilistic, so never the only layer.
    Action (tool)Which tool, which arguments, for whom, how largeStrongest. Plain code that limits damage even if the model is fully fooled.
    OutputLeaked data, unsupported claims, banned adviceCatches embarrassing replies. A judge model shares the blind spots of the model it judges.
    SystemLogs, rate limits, budget caps, kill switchLets you see and stop a problem, but does not prevent the first bad action.
    • Soft guardrails (a model or pattern matcher decides) can be wrong or fooled. They reduce how often something bad is attempted.
    • Hard guardrails (code that allows or refuses) cannot be argued with. Only they cap how bad it can get.

    The prompt is a request. The permission system is a law.

    Part 3

    How to decide what needs a human

    Decide per action, not per agent.

    1. Can it be undone, and how cheaply? Reading a record, drafting a reply and freezing a card can. Sending money, emailing a customer and deleting data cannot.
    2. How much breaks if it is wrong or hijacked? One customer's balance is small. A bulk update or a AED 250,000 payment is large.
    3. Pick the tier from the answers, as below.
    4. Enforce it in code, never only in the prompt (Part 4).

    Tier 1 is the subtle one. For a fraud freeze, waiting for approval is the harm: the money leaves while the ticket sits in a queue. So make it cheap to undo and review it afterwards. In tier 3 the tool does not exist for this agent.

    Part 4

    Enforce the gate in code

    A prompt rule such as "never transfer more than AED 10,000 without approval" is a sign on a door, not a lock. A clever user or a hidden instruction in a document can override it. Over many attempts, a small chance becomes near-certainty.

    So move the rule out of the model. The model proposes a tool call; code it cannot edit decides.

    1. Allow-list. An unknown tool is an error.
    2. Check scope on every call, using the end user's permissions, not a broad service account.
    3. If the tier needs approval, pause and show a person the exact action. Do not run it.
    4. Check the approval matches the exact arguments, is still valid, and was not given by the requester.
    5. Log who, what, why and under which approval, then run.

    Three details make it real:

    • Bound to the arguments. An approval for "pay AED 5,000 to X" covers that call only. Otherwise the agent swaps the amount afterwards.
    • The only path. If a shell or another tool reaches the payments system, the gate is decoration.
    • The user's identity. A broad service account turns a hijacked agent into a privileged insider.
    Show the formula

    Chance of at least one breach = 1 − (1 − p)n, where p is the chance one attempt beats the rule and n is the number of attempts. At p = 2%, 35 attempts give 1 − 0.9835 ≈ 50%. A gate covering 90% of paths only cuts the odds tenfold: the attacker needs just the path you missed.

    Part 5

    Approval that works

    Putting a human on everything backfires. Like a smoke alarm that goes off whenever you make toast, a queue of mostly harmless requests teaches people to stop reading. The result is a rubber stamp: a human approved everything and caught nothing.

    • Gate by risk, not volume. Only tier 2 reaches a person.
    • Show the exact action with evidence. "Pay AED 250,000 to a new overseas beneficiary at 02:14; customer has never paid abroad" beats "Approve agent action?".
    • Measure reviewers. Track decision time, approval rate and reject rate. 100% approved in two seconds is a warning. Slip known-bad cases into the queue.
    • Four-eyes. The requester and the approver must be different people.
    Part 6

    Pick the simplest agent design

    Think of a kitchen: a recipe (workflow), one improvising chef (single agent), or a brigade (multi-agent). Use the recipe whenever it will do.

    DesignWho decides the stepsUse it when
    WorkflowYour code. A model works inside a step.Steps are known: extract fields from a KYC document
    Single agentOne model in a loop with toolsOpen-ended: investigate a complaint across systems
    Multi-agentAn orchestrator hands work to workersIndependent parallel pieces, overflowing context, or different permissions
    • Moving right costs you predictability (a workflow has one testable path), cost and latency, and control (more tools, more permissions to scope).
    • Add complexity only when it measurably helps. Anthropic reported roughly four times the tokens of chat for agents and fifteen times for multi-agent systems.
    • Multi-agent for security: keep the agent that reads untrusted documents apart from the one that can act.

    In banking, start from the action tiers, put the hard gates in code on the only path to money and customer data, and review a sample of what ran freely.

    Part 7

    Common mistakes and quick check

    • A soft rule as the only gate

      "The assistant is told never to approve refunds above AED 500", or a second model reviews the first. Ask: if the model ignored this, what would stop the action? If nothing, there is no guardrail.

    • A gate with a side door

      Payments are gated, but a generic "call internal API" tool reaches the same endpoint. List every tool and what it can reach.

    • Approving intent, not the action

      A person approves "process refund" and the arguments are filled in later.

    • Too much architecture

      An orchestrator and planners for a task that was four fixed steps.

    • Rubber-stamp queues

      99.7% approved in two seconds means nobody is reading. Gate only risky actions and test with known-bad cases.

    1. Which two properties decide whether an action needs a human? Give a low-on-both example.

    Reversibility and blast radius. Reading the current customer's balance, or drafting an unsent reply, is reversible and small.

    2. Why is a fraud-signal card freeze usually "run and log"?

    It is protective and reversible, and waiting for approval delays the protection. Control it with logging, sampling and an easy release path.

    3. A prompt rule is beaten 1% of the time per attempt. Why is that still unsafe?

    Small chances compound: after about 70 attempts a breach is more likely than not. A code gate removes the model from the decision.

    4. Why must approval be bound to the exact arguments?

    Otherwise a harmless-looking request gets approved and a different amount or beneficiary is run. Any change should invalidate the approval.
