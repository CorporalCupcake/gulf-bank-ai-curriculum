    Know Your Agent: How AI Agents Get Permission to Pay

    How AI agents get permission to buy things for your customers, how each layer of trust works, and what an issuing bank has to decide.

    Contents

    The whole lesson in one sentenceBefore an AI agent spends a customer's money, everyone must know who the agent is, who it acts for, what it may do, and how to prove afterwards what happened. Know Your Agent (KYA) answers those four questions.

    Status checked on 26 October 2026. Tags: Live in real use, Pilot testing, Proposed draft, Inferred my reading.

    Part 1

    The intuition

    Card payments assume a person, and fraud systems look for human signs such as typing rhythm. Now a customer tells an assistant, “Book me a flight to Muscat next Thursday, under AED 1,500,” and the agent pays. To the merchant and bank this looks like a bot, and bots have always been treated as fraud.

    Think of a valet key: it starts the car but doesn't open the boot. Agents need the same for money, a credential tied to a known agent and customer, with limits built in.

    Question 1Who is this agent?Which software, run by which accountable business?
    Question 2Who is it acting for?Is a verified customer behind it?
    Question 3What may it do?Which amounts, merchants and dates did the customer allow?
    Question 4Can we prove it?Is there signed evidence of what was asked and done?

    A different technology answers each question. See which attack each layer stops.

    Hold onto thisIdentity is not authority. Proving an agent is genuine tells you who is asking, not whether the customer wanted this purchase.
    Part 2

    How it really works

    Agent identity: signed requests and directories

    Layer one answers who is this agent? Think of a wax seal: only the sender can make it, and anyone can check it. The standard is Web Bot Auth.

    • The operator keeps a private key. The public key goes into a network directory only after the network vets the business (“know your business”, KYB).
    • Each request is signed, with a short expiry and a one-off random nonce. A pass means it came from that registered agent, unaltered.

    Visa's version is the Trusted Agent Protocol Live. Signatures last at most 8 minutes, and merchants block any nonce already seen, which stops replays.

    Binding the agent to the customer and the card

    Layer two answers who is it acting for? It builds on network tokenisation, as in Apple Pay: the merchant sees a substitute token, not the real card number, plus a one-time cryptogram per payment. A stolen token is nearly useless elsewhere.

    For agents, the token is tied to that agent and that card (Mastercard's Agentic Tokens; Visa Intelligent Commerce). The customer sets it up with a passkey, the phone's fingerprint or face check, so nobody can enrol a stolen card. The issuing bank still approves each token request, as for phone wallets.

    Delegated authority: mandates and limits

    Layer three answers what may it do? Every protocol writes down the customer's permission so a machine can enforce it and nobody can quietly change it. Only the vocabulary differs.

    • Visa Intelligent Commerce: the agent submits a purchase instruction carrying the customer's limits, and credentials are released only against it. Live
    • Mastercard: from August 2026 issuers attach spend controls to a token (amount limits, single use, allow or block lists), and Mastercard declines rule-breakers before the bank sees them. Live
    • Google AP2: signed mandates, each “open” (customer constraints) or “closed” (one specific purchase). Proposed

    One distinction matters everywhere: human present or not present. If the customer approves the exact basket, the agent is a fast shopping assistant. If they said “buy the tickets when they go on sale, up to AED 400” and left, the pre-signed limits are all that stands between them and a mistake.

    The flows, end to end

    Set-up happens once. Every purchase then follows the same short loop.

    What the issuing bank decides

    In every design the issuer approves the token, honours the limits, and makes the final authorisation call, now with a “token assurance” signal showing an agent is involved.

    The trade-off is familiar from fraud work: tight limits stop bad purchases and good ones; loose limits let the agent work and let a manipulated agent spend.

    Liability and disputes

    Disputes used to be “I didn't do this” (fraud) or “it wasn't what I paid for” (merchant). Agents add a third: “I authorised the agent, but not this purchase.”

    The first kind is covered by tokens and passkeys under existing rules. The third is unsettled: as of October 2026 no network has published an agent-specific liability shift.

    So evidence decides: the signed mandate, agent identity and transaction events. A bank that stores these wins disputes it would lose relying on the agent company's logs.

    Fraud in agentic commerce

    Agents move fraud rather than remove it. Three attacks to know by name:

    • Prompt injection. Hidden text on a page tells the agent to buy something else. The agent and signature are genuine, so only limits and monitoring help.
    • Agent account takeover. An attacker steals the customer's agent account, which already holds an approved token.
    • Rogue or front agents. A business registers an agent to launder stolen cards. KYB and passkey binding defend.

    For fraud models, the old signals vanish. Agents have no typing or mouse behaviour, so a model trained on humans scores good agent traffic as risky. Useful new features: agent track record, human present or not, and headroom under the mandate. Labels start scarce, so begin with rules and anomaly detection.

    Watch outAgent fraud rates differ from card-not-present traffic, so set thresholds and calibration separately (F7).
    Part 3

    How it fails, and how to spot it

    • Treating a verified agent as an authorised purchase

      A prompt-injected agent passes identity checks.

      Spot it“It's verified, so we approve.”
    • Blocking all bot traffic as fraud

      Legacy rules decline good agent transactions for looking automated.

      Spot itCompare agent and human decline rates.
    • Reusing the human fraud model unchanged

      Behavioural features mislead for agents, so scores are miscalibrated.

      Spot itDoes the model have agent features and its own calibration?
    • Mandates so broad they mean nothing

      “Up to AED 50,000, any merchant, no expiry” still counts as a mandate.

      Spot itCheck the limits customers actually set.
    • Relying on the agent company's logs for disputes

      Unsigned third-party logs are weak evidence.

      Spot itWhat signed evidence does the bank itself store?
    • No way for customers to see and revoke agents

      Customers forget which agents hold their card.

      Spot itCan a customer cut an agent off in two taps?
    • Confident claims built on stale or vendor sources

      For example, a liability shift that hasn't been published.

      Spot itEvery claim needs a date and a primary source.
    Part 4

    Self-check

    1. What four questions does Know Your Agent answer, and which technology answers each?

    Who: operator vetting plus signed requests. Acting for: an agent-scoped token after a passkey check. May do: mandates and spend controls. Proof: signed intent and transaction events. Monitoring and revocation span all four.

    2. A merchant receives a request with a valid signature from a registered agent, but the nonce was seen three minutes ago. What should it do?

    Block it. It is a replay of a genuine request. The signature is valid because the content is identical, so only the nonce check catches it.

    3. A genuine, verified agent reads a web page with hidden instructions and tries to buy AED 1,000 of gift cards. Which layer stops it?

    Not identity, which passes. The mandate stops it, because gift cards or that amount are outside the limits. Monitoring is the backstop.

    4. In AP2, what's the difference between human-present and human-not-present purchases?

    Human present: the customer approves the exact basket. Human not present: the customer signs limits in advance, and the agent completes the purchase later within them.

    5. Where do the spending limits live in Visa's design compared with Mastercard's?

    Visa: in the agent's purchase instruction, which credentials are released against. Mastercard: on the token itself, and Mastercard declines violations before the issuer sees them.

    6. Your bank's fraud model declines 8% of agent transactions against 1% of human ones, but confirmed fraud is similar. What's likely happening?

    The model leans on behavioural features agents lack, so they look like bots. Segment agent traffic, add agent features, and calibrate separately (F7 methods).
