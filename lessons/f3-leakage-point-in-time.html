    F3.1 Day one ★ Priority About 40 minutes

    Point-in-Time Correctness and Leakage

    Contents
    Part 1

    The intuition

    A risk team builds a model to predict 90-days-past-due. Test AUC is 0.98; a quarter live, it is 0.60. The culprit was "average balance over the last 30 days", computed from the extract date, not each application date. For a customer who defaulted, it included the weeks when the balance collapsed.

    It is like sitting an exam with the answer key in your bag. That is leakage: information in the data that was not available when the real decision was made. It is about when, not what. The leaked value is a correct number for the wrong dates, so staring at it will not reveal it.

    Hold onto thisFor every number the model sees, ask: when did the bank first know this, and was that before the decision? If you cannot answer, do not use it.
    Part 2

    How it really works

    Three clocks: event, knowledge and decision time

    Every warehouse row has three times, like a letter that is written, posted and read. Event time is when it happened (a raise on 1 March). Knowledge time is when the bank's systems first held it (the HR letter uploaded 22 April). Decision time is when the bank had to act.

    The rule: a value may feed a decision only if its knowledge time is on or before the decision time, not its event time. Define each feature by when it is available, not when it is true.

    What leakage looks like

    Four forms cause most damage. Target leakage: a feature set because of the outcome, such as "collections stage" on a default model or "SAR filed" on an AML model. Temporal leakage: a window running past the decision (Simulation 1). Restated data: a bureau score corrected months later (Simulation 2). Contamination: the same customer or fraud ring on both sides of a split, or selection fitted before splitting (Simulations 3 and 4).

    The damage is large because a leaky feature looks stronger than any honest one, so the model leans on it. Live, that weight is wasted, and the model can be worse than a clean one while its test score says the opposite.

    As-of joins and restated data

    An as-of join asks "what did the bank's file say on 15 April?" and attaches the latest value known at that timestamp, not today's. A naive join to a table overwritten in place gives every old row today's segment, rating and corrected score.

    You need history: a table keeping every version with dates, or a snapshot at each decision. Treat any table overwritten in place as unusable for training until someone shows its history.

    Splits: random, temporal, grouped and embargoed

    A random split is like testing yourself on shuffled questions from last year's papers. A temporal split trains on an earlier period and tests on a later one, which is how the bank uses the model: on customers who have not happened yet.

    Also group splits by the unit that is new in production (customer, device), so the model cannot memorise entities. Embargo a gap at least as long as the label window. Then walk forward: the out-of-time score is the estimate, and the drop from random shows how perishable the pattern is.

    Preprocessing, selection and tuning on the whole dataset

    The subtlest leak involves no time. Any step that learns from data (selection, target encoding, resampling, tuning) must learn from training rows only. Picking the best 20 of 2,000 features using every row, then cross-validating, is like picking winning horses after the race.

    Use a pipeline that fits every step inside each fold (F11). Tuning is selection too: try 200 settings and report the best test AUC and you have picked the luckiest noise (F2.4).

    The "too good to be true" AUC: a detection routine

    Application scorecards typically reach AUC 0.70 to 0.80. Attack anything far above that. Score each feature alone: one at 0.9 on a hard problem is a leak or a join mistake. Compare a time-shifted test with the random split. Rebuild with a cut-off a month earlier, and if the score collapses, check the last weeks. A shadow run on real incoming cases is the only fully convincing test.

    Part 3

    How it fails, and how to spot it

    The leaks you will meet most, each with its quickest check.

    • Windows anchored to the extract date

      "Last 30 days" computed once on build day.

      Spot itSearch the SQL for CURRENT_DATE or NOW().
    • Outcome fields and text used as inputs

      Collections stage, block reason, or notes written after resolution.

      Spot itAsk who sets a high-importance field and when.
    • Overwritten or restated data

      Segment or bureau score overwritten in place.

      Spot itAsk if the table keeps history.
    • Random split on time-ordered or grouped data

      Same customer on both sides, or months shuffled.

      Spot itCount test customers also in training.
    • Immature labels in the newest cohort

      Last month's loans look excellent because none have had time to default.

      Spot itPlot default rate by origination month; a sharp recent fall is immaturity.
    Part 4

    Self-check

    1. A single feature available at application time gives an AUC of 0.92 for default. Plausible?

    No. Whole scorecards reach 0.70 to 0.80. Treat it as a leak until its knowledge time is verified.

    2. Why can a model with a strong leaky feature score worse live than one using only the honest feature?

    It leans on the leaky feature in training because it looks strongest. Live, that weight goes to noise.

    3. An application is decided on 15 April. A raise to AED 24,000, effective 1 March, was uploaded on 22 April. Which salary does the training row use?

    The earlier one. The raise preceded the decision, but the bank knew it only on 22 April. Filter on recording date.

    4. Why can a random 80/20 split of card transactions overstate fraud performance even without time leakage?

    Fraud comes in bursts on one card, so the model recognises the card. Split by card and by time.

    5. You pick the best 30 of 1,500 features on the full data, then cross-validate and get 0.74. Trustworthy?

    No. Selection used the labels of later validation rows. Redo it inside each fold; the honest number may be far lower.
