    Data Leakage: When the Model Sees the Future

    Part 1

    What leakage is

    In one sentenceData leakage is when your model is trained or tested using information it would not have had at the moment of the real decision, so its scores look great and then collapse live.

    Running example: a university predicts which students will fail a course. On test data the model scores an AUC of 0.98. (AUC ranks how well a model separates the two groups: 0.5 is a coin flip, 1.0 is perfect.) A term later, live, it scores 0.60.

    The culprit was "average attendance over the last 30 days", worked out on the day the data was pulled, not on each student's prediction date. Students who dropped out had attendance falling to zero, because they had already left. The model was reading the answer.

    It is like sitting an exam with the answer key in your bag. The leaked number is correct, just for the wrong dates, so staring at it will not reveal the problem.

    Hold onto thisFor every number the model sees, ask: when did we first know this, and was that before the decision? If you cannot answer, do not use it.
    Part 2

    How leakage happens and how to avoid it

    How it differs from overfitting

    • Overfitting: the model memorises noise in the training data. A proper test on fresh data reveals it.
    • Leakage: the test itself is contaminated, so even a proper-looking test is too kind. Nothing in the numbers warns you.

    Three clocks on every row

    Think of a letter: written, posted, read. Every stored fact has three times.

    • Event time: when it happened (a student's grade was earned on 1 March).
    • Knowledge time: when our systems first held it (the grade was entered on 22 April).
    • Decision time: when we had to act.

    The rule: a value may feed a decision only if its knowledge time is on or before the decision time. Event time is not enough.

    Four common kinds

    • Target leakage: a feature that exists because of the outcome. "Number of reminder emails sent" predicts late payment perfectly, because reminders only go out after a payment is late.
    • Time leakage: a window that runs past the decision date, like the attendance example.
    • Restated data: a value corrected months later, then joined to old rows as if it had always been that.
    • Contamination: the same person (or group) in both training and test data, so the model recognises them.

    The damage is large because a leaky feature looks stronger than any honest one, so the model leans on it. Live, that weight is wasted. The model can end up worse than a clean one while its test score says the opposite.

    Fix: look up what was on file that day

    An as-of join asks "what did our records say on 15 April?" and attaches the latest value known by then, not today's. A normal join to a table overwritten in place gives every old row today's values.

    This needs history: a table that keeps every version with dates, or a snapshot taken at each decision. Treat any table overwritten in place as unusable for training until someone shows its history.

    Splitting the data

    • Random split: like testing yourself on shuffled questions from last year's papers. Fine only if rows are independent and nothing drifts.
    • Temporal split: train on an earlier period, test on a later one. Use it whenever time matters.
    • Grouped split: keep each person (or device) wholly on one side, so the model cannot memorise them.
    • Embargo: leave a gap between train and test at least as long as the label window (how long you wait to see the outcome).

    The leak that involves no time

    Any step that learns from data (picking features, target encoding, scaling, tuning) must learn from training rows only. Picking the best 20 of 2,000 features using every row, then cross-validating, is like picking winning horses after the race.

    With pure-noise features and coin-flip labels, selecting on all rows can score far above the true 0.5. Selecting inside the training rows does not. Put every step inside a pipeline that refits it within each fold. Tuning counts as selection too: try 200 settings and report the best, and you have picked the luckiest noise.

    Part 3

    How to spot it

    Hard human-behaviour problems, such as loan-default scorecards, typically reach an AUC of 0.70 to 0.80. Treat anything far above that as a leak until proved otherwise.

    CheckWhat it tells you
    Score each feature aloneOne feature at 0.9 on a hard problem is a leak or a join mistake
    Random vs time-shifted testA big drop when you test on a later period shows time leakage or drift
    Rebuild with an earlier cut-offIf the score collapses, look hard at the last weeks of data
    Search the SQL for CURRENT_DATE or NOW()Windows anchored to the day the data was pulled
    Count test people also in trainingAny overlap means contamination
    Shadow run on real incoming casesThe honest score, with nothing to leak

    Strong at catching leaks: the time-shifted test, because it copies how the model is really used.

    Weak at catching them: staring at feature values or importance charts. A leaked feature looks like a great feature.

    In banking, the classic cases are a credit score corrected months later, collections-stage fields used to predict default, and last month's loans looking excellent only because none have had time to default yet.

    Part 4

    Common mistakes and quick check

    • Windows anchored to the extract date

      "Last 30 days" computed once on build day. Compute it per row, from that row's decision date.

    • Using outcome fields as inputs

      Notes, status codes or block reasons written after the case was resolved. Ask who sets the field and when.

    • Random split on time-ordered or grouped data

      The same person on both sides, or months shuffled together. Split by time and by person.

    • Immature labels in the newest group

      Recent cases look good because the outcome has not had time to happen. Plot the outcome rate by start month: a sharp recent fall means immaturity.

    1. A single feature, available at decision time, gives an AUC of 0.92 for predicting loan default. Plausible?

    No. Whole scorecards reach 0.70 to 0.80. Treat it as a leak until its knowledge time is checked.

    2. Why can a model with a strong leaky feature do worse live than one with only the honest feature?

    It leans on the leaky feature in training because it looks strongest. Live, that weight goes to noise.

    3. A decision is made on 15 April. A raise, effective 1 March, was entered on 22 April. Does the training row use it?

    No. The raise happened earlier, but we only knew it on 22 April. Filter on knowledge time.

    4. Why can a random split of card transactions overstate fraud performance even without time leakage?

    Fraud comes in bursts on one card, so the model learns to recognise the card. Split by card and by time.

    5. You pick the best 30 of 1,500 features on all the data, then cross-validate and get 0.74. Trustworthy?

    No. Selection used the labels of the rows later used to validate. Redo it inside each fold; the honest number may be far lower.
