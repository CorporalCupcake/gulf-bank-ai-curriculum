    NumPy and pandas: Thinking in Arrays and Tables

    Why one array operation beats a loop over a million rows by a factor of fifty, how broadcasting decides what can be combined with what, and the pandas traps that return a plausible wrong answer: silent index alignment, join row explosion, copies, and dtypes.

    Contents

    The whole lesson in one sentenceNumPy is fast because it moves the loop out of Python into compiled code that works on whole arrays at once, and pandas is the same idea with labels attached, so most of its errors come from labels, shapes and types quietly doing something other than what you meant, and the cure is to check row counts, indexes and dtypes after every step.

    Part 1

    The intuition

    Picture a back-office clerk who has to convert a million card transactions from dollars to dirhams. She can pick up each slip, multiply by 3.6725, write the answer, and move on. Or the bank can hand the whole stack to a machine built for one job: multiply every number by the same constant. The clerk is a Python for loop. The machine is a NumPy array operation. The arithmetic is identical. What differs is how much work surrounds each multiplication. For the clerk, most of the time goes on looking at the slip, checking what kind of thing it is, and picking up the pen. For the machine, almost all of it goes on multiplying.

    That is the first half of the lesson, and it is what people mean by vectorisation: express the computation as operations on whole arrays, so the per-element loop runs in compiled code.

    The second half is that real data has labels. A column of balances means nothing unless you know whose balance each one is. pandas glues labels (an index and column names) onto NumPy arrays. That is enormously convenient, and it is also where the danger lives. When you add two columns, pandas matches them by label, not by position. When you join two tables, it matches rows by key, and if a key appears twice it multiplies the rows. When you assign to a slice, it may or may not change the original. None of these raise an error. They produce a number, and the number is wrong.

    Hold onto thisEvery pandas step has a silent contract: which labels line up, how many rows come out, what type each column now has. Experienced people write the contract down as a check (an assertion on row count, a uniqueness check on a key, a look at dtypes) so that a broken one fails loudly instead of feeding a wrong figure into a report.

    pandas is also the same questions as SQL (F3.3) in a different dress. If you can say it in SQL, you can say it in pandas. The reason to learn both is that SQL runs where the data lives and pandas runs where you explore, test and build models. Part 2 puts the two side by side.

    Part 2

    How it really works

    What an array actually is

    A Python list of a million numbers is a million separate objects, each with its own header saying what type it is, plus a list of pointers to them. A NumPy ndarray is different: one contiguous block of memory holding the raw numbers, side by side, all of the same type, plus a small description of how to read the block. That description has three parts you should know by name.

    • dtype: the type of every element, such as float64 (8 bytes), int64, float32 (4 bytes), bool. One dtype for the whole array.
    • shape: the sizes along each axis. A table of 1,000 customers by 12 months has shape (1000, 12). A single column of 1,000 values has shape (1000,), which is neither a row nor a column, just a one-dimensional run. This distinction causes real bugs, as the broadcasting section shows.
    • strides: how many bytes to jump to reach the next element along each axis. This is what makes a transpose or a slice free: NumPy changes the description and leaves the bytes alone.

    The last point has a consequence worth knowing. Slicing with a[:, 3] returns a view: a new description of the same memory. Write into the view and you change the original. Fancy indexing with a list or a boolean mask (a[a > 0]) returns a copy. NumPy does not warn you which you got. The rule of thumb: basic slices are views, anything chosen by values or lists is a copy, and .copy() makes your intent explicit.

    import numpy as np

amounts = np.array([120.0, 45.5, 8300.0, 15.0])   # dtype float64, shape (4,)
amounts.shape, amounts.dtype, amounts.nbytes       # ((4,), float64, 32)

big = amounts[amounts > 100]    # boolean mask -> a COPY: [120., 8300.]
head = amounts[:2]              # basic slice  -> a VIEW of the same memory
head[0] = 0.0                   # amounts is now [0., 45.5, 8300., 15.]

    Because the type is fixed, so is the memory cost, and you can compute it in your head. A column of n float64 values takes 8n bytes. A table of 50 million transactions with 40 numeric columns is 50,000,000 × 40 × 8 = 16 GB before you have done anything. Dropping to float32 halves it. Using int32 or category for codes and labels can shrink it far more. Knowing this arithmetic is how you tell a colleague "that will not fit on the laptop" before the laptop freezes.

    Two dtype facts that bite in banking. First, floating point cannot represent most decimals exactly: 0.1 + 0.2 is 0.30000000000000004. For analysis that is fine, but for anything that must reconcile to the fils (ledger totals, fee calculations), keep amounts as integers of the smallest unit, or use decimal, and compare with a tolerance, not ==. Second, np.nan is a float, so a column of integers that contains one missing value silently becomes float64, and nan == nan is False. Use np.isnan, never equality.

    Why a loop is slow and an array operation is not

    When Python runs total += a[i] * b[i], the interpreter does a lot per element: it fetches a[i] as a full Python object, looks up what * means for that type, allocates a new object for the result, and repeats for the addition. Each step is small, but together they cost tens of nanoseconds on every pass. A NumPy operation like (a * b).sum() pays the interpreter's overhead once, then hands the contiguous block to a compiled routine that streams through memory, often using the processor's SIMD instructions to do several numbers per cycle.

    So the cost model is roughly two lines. A Python loop costs n × (some tens of nanoseconds of overhead + the work). A NumPy call costs a fixed few microseconds to start + n × (about a nanosecond of work). The fixed start-up cost is why vectorising a 20-element array gains almost nothing, and the per-element gap is why a million elements gains fifty-fold or more.

    What does "vectorise" mean in practice? Replace the loop with the operation the loop was computing.

    # Slow: a Python loop over a million rows
fees = []
for amt, is_intl in zip(amounts, intl_flags):
    fees.append(amt * 0.0275 if is_intl else amt * 0.01)

# Fast: the whole thing as array operations
fees = np.where(intl_flags, amounts * 0.0275, amounts * 0.01)

    The vectorised form has three useful building blocks. Ufuncs (+, *, np.log, np.sqrt) apply an operation to every element. Boolean masks (amounts[amounts > 5000]) replace if. Reductions (sum, mean, max with an axis argument) collapse a dimension and replace accumulator loops. np.where(cond, x, y) is the vector form of if/else.

    Honest limits: a loop is not always wrong. If each step depends on the previous one (a running balance with an overdraft rule, a state machine), it may not vectorise cleanly; then use a library function like cumsum where it fits, or reach for Numba or a compiled tool. And vectorising creates temporary arrays: a*b + c*d makes three temporaries of full size, which matters when the array is already a few gigabytes. For a team at a bank the practical rule is simpler: if you wrote a for loop over rows of a DataFrame, there is almost always a one-line version, and it is almost always 10 to 100 times faster.

    Broadcasting: how arrays of different shapes combine

    What should balances - column_means do when balances has shape (1000, 12) and column_means has shape (12,)? You want each month's average subtracted from that month's column. NumPy does this without copying the means 1,000 times, through broadcasting. The rule has three steps:

    1. Right-align the shapes, so the last axes line up. Pad the shorter shape with 1s on the left.
    2. Go axis by axis. Two sizes are compatible if they are equal, or one of them is 1.
    3. The result size on each axis is the larger one. An axis of size 1 is stretched (virtually, with stride zero) to match.

    If any axis fails step 2, NumPy raises an error. That is the good outcome. The dangerous case is a shape that broadcasts when you did not intend it to. Try the common ones.

    Two idioms to remember. x[:, None] (or x.reshape(-1, 1)) turns a (1000,) run into a (1000, 1) column. And reductions take keepdims=True so the collapsed axis stays as size 1 and broadcasts back correctly:

    row_means = balances.mean(axis=1, keepdims=True)    # shape (1000, 1)
centred   = balances - row_means                    # each customer minus their own mean
z = (balances - balances.mean(axis=0)) / balances.std(axis=0)   # standardise each month

    Notice the opposite danger: if a table happens to be square, say (12, 12), then a (12,) vector broadcasts along the last axis without complaint, and if you meant the other axis, the answer is wrong with no error. When shapes are square, or when you are unsure, print .shape at each step and test on a tiny array where you can verify the answer by hand. This is the habit in F10.2 (the testing mindset) applied to arrays. Broadcasting is also the same mechanism behind matrix operations in F1.1, and every neural-network layer in F5 uses it to add a bias to a whole batch.

    pandas in one picture: arrays with labels

    A Series is a NumPy array plus an index (the row labels). A DataFrame is a set of Series sharing one index, with column names. Each column has its own dtype, which is the big difference from a single NumPy array. The mental model: a dictionary of columns, aligned by row label.

    Copies, views and the warning everyone ignores

    Historically pandas would sometimes give you a view and sometimes a copy of a slice, and the only sign was a SettingWithCopyWarning when you assigned to it. The line df[df.amount > 5000]["flag"] = 1 (two steps chained: first select, then assign) assigns to a temporary copy and leaves df untouched. Pandas 3.0, released in January 2026, makes copy-on-write the only mode: any object derived from another behaves as a copy, and chained assignment of this kind never updates the original. The rule is now clean, and the working version is one step: df.loc[df.amount > 5000, "flag"] = 1. If your bank pins an older pandas (2.x), the same line still works but may warn, so write it the one-step way regardless.

    big = df.loc[df["amount"] > 5000].copy()    # an explicit copy you may modify freely
df.loc[df["amount"] > 5000, "flag"] = 1      # modify the original, one step

    Index alignment: the silent matcher

    When you combine two Series or DataFrames with an operator (a - b), pandas first aligns them on the index: it takes the union of the labels and matches values with the same label. Labels present in only one side produce NaN. This is correct and useful when the labels mean something. It becomes a trap in two situations. When the indexes are not what you think (one is a default 0,1,2,... and the other is customer IDs), the result is mostly NaN. Worse, when you filter or sort one side, then add a plain column or .values from the other, you either get alignment you did not expect or you bypass alignment and pair wrong rows with no warning.

    The working habits: give frames a meaningful index (set_index("cust_id")) or none you rely on, call reset_index(drop=True) when you truly want positional behaviour, assert that the indexes match when you expect them to (assert a.index.equals(b.index)), and prefer an explicit merge on a key to relying on index magic between two tables. And note that fill_value=0 answers a different question from the one you asked: a missing fee being 0 is plausible, a missing balance being 0 usually is not.

    Grouping: split, apply, combine

    groupby is SQL's GROUP BY with three flavours, and choosing the right one is most of the skill. Each does the same first step (split rows into groups by key) and differs in what comes back.

    This is the shape of nearly every customer-level feature table (F3.4). Three details to know. Missing keys disappear by default: rows whose group key is NaN are dropped from groupby unless you pass dropna=False, so a customer segment with blanks quietly loses those customers from the totals. count counts non-missing values; size counts rows, and the difference is the number of missing values. And pandas skips NaN in sum and mean while plain np.mean returns NaN. The pandas default is convenient and also hides missing data; use .isna().sum() to see how much is hiding. Group by what happened before the prediction date only, or you have built a leakage feature (F3.1).

    Joining: how rows multiply

    merge is SQL's JOIN. The how argument picks inner (only keys in both), left (every left row, matching right where present), or outer (everything). The rule that causes real damage is about duplicate keys: if a key appears m times on the left and n times on the right, the output has m × n rows for it. A transactions table joined to a customer table should have one row per transaction out. If the customer table has two rows for one customer (an address history, a re-issued ID, a slowly changing dimension), every transaction of that customer is doubled, and so is every total you compute afterwards.

    Four defences, in order of how often they save you. Check uniqueness of the key on the side that should be unique before merging (assert customers["cust_id"].is_unique). Pass validate="m:1" so the merge raises MergeError if that assumption fails. Compare row counts before and after, and compare the total of an additive column. And use indicator=True to add a column showing which rows matched, so you can count the unmatched ones rather than guessing. Also watch the key's type: customer IDs read as integers in one file and strings in another simply fail to match, and an account number like 00123 read as a number loses its leading zeros. Read identifiers with dtype=str.

    The join type is a statement about your data. A left join says "keep every transaction, whether or not I know the customer". An inner join says "only analyse transactions with a known customer", which silently removes rows, and removal is rarely random: in the simulation it is the AED 700 transaction. For point-in-time work (F3.1), joins on a key alone are not enough, because you also need the customer record as it stood on the transaction date. pandas has merge_asof for that, which joins each row to the most recent earlier record.

    Reshaping: wide, long, and the dtype checks that go with them

    The same data can be long (one row per customer per month: cust_id, month, balance) or wide (one row per customer, a column per month). Models, SQL aggregates and plotting libraries mostly want long or tidy data; reports and matrix operations mostly want wide. Two functions convert: pivot_table goes long to wide, melt goes wide to long, and stack/unstack do the same using the index.

    wide = long.pivot_table(index="cust_id", columns="month",
                        values="balance", aggfunc="sum")        # one row per customer
long_again = wide.reset_index().melt(id_vars="cust_id",
                                     var_name="month", value_name="balance")

    Pivoting makes a hole wherever a customer has no row for a month, and that hole is a NaN. Whether it should become 0 (no activity) or stay missing (we do not know) is a modelling decision, not a formatting one (F3.4). Do it deliberately.

    Finally, a short list of dtype checks to run after loading any file: df.dtypes, df.isna().sum(), df.describe(include="all"), and df.memory_usage(deep=True).sum(). A date column left as text sorts alphabetically and cannot be subtracted (dates get their own lesson, F11.3). A numeric column read as object because one cell said "N/A" will not sum. Low-cardinality strings such as segment, branch or currency are far smaller as category. And pandas 3.0 changes the default string type, so any code that tested for dtype == object to find text columns needs updating (Part 4).

    F4.3 · Cross-validationSplits are index operations

    Temporal and grouped splits are boolean masks and group keys over a frame. A split done by shuffling rows is one line, and the wrong one.

    F5 · F1.3 · Neural networks and gradientsBatches are arrays

    A layer's bias is added to a whole batch by broadcasting. Deep-learning frameworks copy NumPy's shapes, dtypes and broadcasting rules almost exactly, so this lesson transfers.

    P1 · Data platformsWhen pandas stops being the tool

    When data exceeds one machine's memory, the same ideas move to warehouse SQL and distributed engines. The vocabulary carries over; the memory arithmetic tells you when to move.

    Where it shows up at the bank:

    • Fraud and transaction features. Velocity counts, rolling sums and "spend relative to the customer's usual" are groupby and transform over tens of millions of rows. The loop-versus-vector gap decides whether feature building takes minutes or an afternoon.
    • Reconciliation and reporting. Joins between ledgers, with duplicate keys and unmatched rows as the main source of discrepancies. Row counts and totals before and after every join are the audit trail.
    • Credit and risk. Monthly snapshots as long tables pivoted to wide for modelling; staging and provisioning calculations that are broadcasts of rates across portfolios.
    • AML and KYC. Entity matching across customer, account and counterparty tables, where a duplicated customer record multiplies alerts. Identifiers must stay strings.
    • Arabic and English text. Name fields in two scripts stored in one column; string comparison and normalisation done with vectorised .str methods rather than loops.

    Part 5

    How it fails, and how to spot it

    These appear in human-written and AI-written analyses alike. Each comes with the quickest check.

    • Row-by-row loops on a DataFrame

      for i, row in df.iterrows() or df.apply(f, axis=1) over millions of rows. It runs, slowly, and someone concludes "Python is too slow for this".

      Spot itSearch the code for iterrows, apply(..., axis=1) and explicit for loops over rows. Ask what whole-column expression would do the same.
    • Silent index alignment

      Adding a column or Series whose index differs: NaNs appear, or values attach to the wrong customers after a sort or filter.

      Spot itCheck result.isna().sum() after every combination, and a.index.equals(b.index) where it should hold. If the output has more rows than either input, the indexes did not match.
    • Join row explosion

      A key that should be unique is not, and rows and totals inflate with no error.

      Spot itCompare rows and an additive total before and after. Use validate="m:1" and indicator=True. A customer count that suddenly exceeds the bank's customer base is the classic red flag.
    • Inner joins that drop the awkward rows

      Unmatched transactions vanish, and they are often the interesting ones (new customers, closed accounts, bad data).

      Spot itDo a left join with indicator=True and count left_only before deciding to drop anything.
    • Chained assignment and unintended copies

      df[mask]["x"] = 1 changes nothing (pandas 3.0) or something unpredictable (older versions).

      Spot itLook for two sets of brackets before an assignment. Replace with df.loc[mask, "x"] = 1. Run the code on a tiny frame and print it.
    • Numpy views mutated by accident

      A slice is passed to a function that modifies it in place, and the original data changes.

      Spot itKeep a pristine copy and compare, or use np.shares_memory(a, b). Call .copy() when you intend to modify.
    • Wrong axis or accidental broadcasting

      Standardising rows instead of columns, or a square table hiding a transposed vector.

      Spot itPrint .shape at each step and test on a 3 by 4 array where the answer can be checked by hand. Prefer keepdims=True.
    • Missing values handled by default behaviour

      NaN skipped in mean, dropped in groupby keys, turning integers into floats, compared with ==.

      Spot itReport isna().sum() per column before any aggregate. Check that group counts add up to the row count.
    • Floats for money, text for identifiers read as numbers

      Totals that differ from the ledger by a few fils; account numbers that lost their leading zeros; IDs that fail to join because one side is int and the other str.

      Spot itRead identifiers with dtype=str; keep money as integer fils or decimal; compare with a tolerance; look at df.dtypes right after loading.
    Part 6

    What to say in the room

    To a manager who asks why a job is slow · 30 seconds
    “The job loops over the rows one at a time in Python, which pays interpreter overhead on every row. The same arithmetic written as whole-column operations runs in compiled code and is typically tens of times faster. I'd rewrite the hot step that way and measure on the real table. If it still doesn't fit in memory, we move the aggregation into the warehouse rather than buy a bigger machine.”
    To a technical interviewer or reviewer
    “Most of my pandas defects have been silent ones: index alignment, duplicate join keys, dtype changes. So I build in checks: unique keys asserted and validate on merges, row counts and an additive total compared across each join, isna counts before aggregates, identifiers read as strings, and one-step .loc assignment. Heavy aggregation goes to SQL; pandas gets the reduced table. I know pandas 3 made copy-on-write the default and changed the string dtype, so I check the pinned version before reusing old code.”
    “Why not just use a loop? It's clearer.”

    For a few hundred rows, a loop is fine. At millions of rows it costs tens to hundreds of times more, because every step goes through the Python interpreter. The vectorised form is usually shorter and has fewer places for off-by-one errors. Where the logic is truly sequential, I'd use a cumulative function or a compiled helper, and say so.

    “The join gave us more customers than we have. What happened?”

    Almost certainly a duplicate key on one side, most often a customer table with several records per customer (history rows or re-issued IDs). Each match multiplies rows. I'd check key uniqueness, count rows before and after, and look at the duplicated keys. Then fix at source or deduplicate deliberately, and add validate="m:1" so it cannot recur silently.

    “Why is my column all NaN after adding two Series?”

    pandas aligns on the index before adding. If the two indexes share no labels (for example, one is customer IDs and the other a default 0..n), every result is NaN. Decide whether they should align by label, and if so set the right index; if you truly want position, reset the index on both or work with arrays. Don't reach for .values to make the NaN go away, because that hides a mismatch.

    “Should we move off pandas to Polars or Spark?”

    It depends on where it hurts. If extracts fit in memory and runtime is acceptable, there is no reason to. If preparation is the bottleneck on large tables, DuckDB or Polars on one machine is a lighter step than a cluster; if the data lives in the warehouse, push the heavy work there. The ideas transfer, so learning pandas semantics is not wasted. I'd benchmark on our real table, not on a vendor's.

    “How do you know your feature table is right?”

    I check it against something independent. Row counts and totals tie to the source. A handful of customers are recomputed by hand or in SQL and compared. Keys are unique, missing counts are expected, dtypes are what I declared, and the code has a few tests on a tiny hand-made frame. And I confirm every feature uses only data available at the prediction date.

    Self-check

    Try each one before opening the answer. The numeric ones need only the arithmetic in Part 2.

    1. You have balances of shape (1000, 12) and cust_mean of shape (1000,), and balances - cust_mean raises an error. Why, and what is the fix?

    Broadcasting aligns shapes from the right: 12 is compared with 1000, which are neither equal nor 1, so it fails. Make the means a column of shape (1000, 1) with cust_mean[:, None], or compute them with mean(axis=1, keepdims=True). Then 1000 matches 1000 and 12 stretches against 1.

    2. A table of 50 million transactions has 40 numeric columns, all float64. How much memory? What if you can use float32 for 30 of them?

    50,000,000 × 40 × 8 bytes = 16 billion bytes, about 16 GB. With 30 columns at 4 bytes and 10 at 8: 50,000,000 × (30×4 + 10×8) = 50,000,000 × 200 = 10 GB. Before checking precision needs: float32 keeps roughly seven significant digits, which is too little for exact money.

    3. 1,000 transactions, AED 2,000,000 in total, are joined to a customer table. Fifty customers appear twice in that table and each has 10 transactions. How many rows come out of a left join, and what happens to the total?

    Each of those 50 customers' 10 transactions is matched twice, adding 50 × 10 = 500 rows, for 1,500 rows. The total rises by the amount of those 500 extra rows, so it is above AED 2,000,000. Nothing errors. validate="m:1" would have raised an error.

    4. Series a has index {1, 2, 3} and b has index {2, 3, 4}. What does a + b return, and what does a.add(b, fill_value=0) return?

    a + b has index {1, 2, 3, 4} with NaN at 1 and at 4 (two NaNs), and sums at 2 and 3. With fill_value=0 the missing side counts as 0, so label 1 gives a's value and label 4 gives b's value, and no NaN remains. That may or may not be sensible for your data.

    5. What is the difference between groupby(...).agg("sum") and groupby(...).transform("sum"), and when do you want the second?

    agg returns one row per group. transform returns a result the same length as the original, with each group's sum repeated on every row of that group. You want it when each row needs its group's statistic, for example a transaction's share of its customer's total, or an amount minus the customer's mean. It is the pandas form of a SQL window function.

    6. df[df.amount > 5000]["flag"] = 1 leaves df unchanged. Why, and what do you write instead?

    The first bracket produces a new object (a copy under pandas 3 copy-on-write, and unpredictably a copy or a view in older versions), and the assignment goes to that. The original is never touched. Use one step: df.loc[df.amount > 5000, "flag"] = 1.

    7. A pipeline reads cust_id as integers from a CSV, but the customer table stores it as text like "00417". What happens at the join, and what do you do?

    Either the merge fails on mismatched types, or (if both are coerced) 417 does not equal "00417" and nothing matches, so a left join gives NaNs everywhere. The leading zeros are lost the moment the column is read as a number. Read identifiers with dtype=str on both sides, strip whitespace, and check the unmatched count with indicator=True.
