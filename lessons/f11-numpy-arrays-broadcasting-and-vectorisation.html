    NumPy and pandas: Thinking in Arrays and Tables

    Why one array operation beats a loop over a million rows by a factor of fifty, how broadcasting decides what can be combined with what, and the pandas traps that return a plausible wrong answer: silent index alignment, join row explosion, copies, and dtypes.

    Contents

    The whole lesson in one sentenceNumPy is fast because the loop runs in compiled code over whole arrays; pandas adds labels, so its errors come from labels, shapes and types quietly doing something you did not mean, and the cure is to check row counts, indexes and dtypes after every step.

    Part 1

    The intuition

    A clerk converts a million card slips from dollars to dirhams. She can pick up each slip, multiply, write the answer and move on. Or a machine built for one job multiplies the whole stack at once. The clerk is a Python for loop; the machine is a NumPy array operation. Same arithmetic, but the clerk spends most of her time handling slips. That is vectorisation: describe the computation on whole arrays, so the loop runs in compiled code.

    Real data also has labels: a balance means nothing without knowing whose it is. pandas glues labels (an index and column names) onto NumPy arrays. That is convenient and dangerous, because three things happen without any error:

    • Adding two columns matches them by label, not position.
    • Joining two tables multiplies rows when a key repeats.
    • Assigning to a slice may or may not change the original.

    Each gives a number, and the number is wrong.

    Part 2

    How it really works

    What an array actually is

    A Python list is a shelf of separate boxes. A NumPy array is one tray of identical items laid side by side. Three properties describe it:

    • dtype: the type of every element (float64 uses 8 bytes, float32 4).
    • shape: size per axis. 1,000 customers by 12 months is (1000, 12). A bare column of 1,000 values is (1000,): neither row nor column, just a run. This distinction causes real bugs (see broadcasting).
    • strides: how NumPy steps through memory. It is why transposes and slices are free.

    A basic slice such as a[:, 3] is a view: same memory, so writing to it changes the original. Selecting by mask (a[a > 0]) gives a copy. NumPy does not tell you which you got, so use .copy() to state your intent.

    import numpy as np

amounts = np.array([120.0, 45.5, 8300.0, 15.0])   # dtype float64, shape (4,)
amounts.shape, amounts.dtype, amounts.nbytes       # ((4,), float64, 32)

big = amounts[amounts > 100]    # boolean mask -> a COPY: [120., 8300.]
head = amounts[:2]              # basic slice  -> a VIEW of the same memory
head[0] = 0.0                   # amounts is now [0., 45.5, 8300., 15.]

    Memory is simple arithmetic: rows × columns × bytes per value. 50 million transactions with 40 float64 columns is about 16 GB. Smaller dtypes (float32, category for labels) shrink that, which is how you say "that will not fit on the laptop" before it freezes.

    Two dtype traps in banking:

    • Floats are inexact. 0.1 + 0.2 is 0.30000000000000004. Fine for analysis. For anything that must reconcile to the fils, keep integers of the smallest unit or use decimal, and compare with a tolerance, not ==.
    • NaN is a float. One missing value silently turns an integer column into float64, and nan == nan is False. Use np.isnan.

    Why a loop is slow and an array operation is not

    Python looks up the type of every element and builds a new result object each time round, tens of nanoseconds per pass. NumPy pays a small fixed cost once, then hands the whole block to compiled code that streams through memory. So 20 elements gain almost nothing, while a million gain fifty-fold or more. Like a taxi against a train: not worth it for one street, decisive across the country.

    To vectorise, replace the loop with the operation it was computing:

    # Slow: a Python loop over a million rows
fees = []
for amt, is_intl in zip(amounts, intl_flags):
    fees.append(amt * 0.0275 if is_intl else amt * 0.01)

# Fast: the whole thing as array operations
fees = np.where(intl_flags, amounts * 0.0275, amounts * 0.01)

    Three building blocks cover most cases: ufuncs (+, np.log) apply an operation to every element; boolean masks (amounts[amounts > 5000]) replace if; reductions (sum, mean, with axis) replace accumulator loops.

    If each step depends on the previous one (a running balance with an overdraft rule), it may not vectorise. The practical rule: a for loop over DataFrame rows almost always has a one-line version that is 10 to 100 times faster.

    Broadcasting: how arrays of different shapes combine

    To subtract each month's average from balances of shape (1000, 12) using column_means of shape (12,), NumPy stretches the means down all 1,000 rows without copying them, like a stencil pressed down the page. The rule: line the shapes up from the right; on each axis the sizes must be equal or one of them must be 1. A size-1 axis is stretched to fit.

    An axis that fails raises an error, which is the good outcome. The dangerous case is a shape that broadcasts when you did not intend it.

    Two idioms fix most shape problems: x[:, None] turns (1000,) into a (1000, 1) column, and keepdims=True keeps a collapsed axis as size 1 so it broadcasts back:

    row_means = balances.mean(axis=1, keepdims=True)    # shape (1000, 1)
centred   = balances - row_means                    # each customer minus their own mean

    The opposite danger: for a square table like (12, 12), a (12,) vector broadcasts without complaint, and if you meant the other axis the answer is wrong with no error. When unsure, print .shape at each step and test on a tiny array you can check by hand.

    pandas in one picture: arrays with labels

    A Series is a NumPy array plus an index (row labels). A DataFrame is Series sharing one index, each column with its own dtype. Mental model: a dictionary of columns, aligned by row label. Three selection forms matter:

    You wantpandasSQL equivalentWatch for
    Rows by conditiondf[df.amount > 5000]WHERE amount > 5000Combine with & and |, brackets around each, not and/or.
    Rows and columns by labeldf.loc[mask, "amount"]both of the above.loc slices include the end label.
    By positiondf.iloc[0:10, 2]none (SQL has no row order)After sorting or filtering, position and label differ.

    Copies, views and the warning everyone ignores

    df[df.amount > 5000]["flag"] = 1 is two steps (select, then assign), so it assigns to a temporary copy and df is untouched. Older pandas sometimes returned a view and warned with SettingWithCopyWarning. Pandas 3.0 makes copy-on-write the only mode, so chained assignment never updates the original. Write it in one step: df.loc[df.amount > 5000, "flag"] = 1.

    Index alignment: the silent matcher

    For a - b, pandas aligns on the index first: it matches equal labels, like matching exam scores to students by name rather than seat number. Labels on only one side give NaN. That is right when labels mean something, and a trap when:

    • The indexes are not what you think (one is 0,1,2,..., the other customer IDs): the result is mostly NaN.
    • You filter or sort one side, then use .values from the other: you bypass alignment and pair the wrong rows with no warning.

    Habits: give frames a meaningful index (set_index("cust_id")), assert a.index.equals(b.index) where it should hold, and prefer an explicit merge on a key between tables. fill_value=0 answers a different question: a missing fee as 0 is plausible, a missing balance as 0 usually is not.

    Grouping: split, apply, combine

    groupby is SQL's GROUP BY. Every flavour splits rows by key first; they differ in what comes back.

    FlavourReturnspandasSQL analogue
    AggregateOne row per groupdf.groupby("cust_id")["amount"].agg(["sum","mean","count"])GROUP BY cust_id
    TransformOne value per original row, group statistic repeateddf.groupby("cust_id")["amount"].transform("sum")SUM(amount) OVER (PARTITION BY cust_id)

    Aggregating by customer is the shape of nearly every feature table (F3.4). Three details:

    • Missing keys disappear. Rows with a NaN group key are dropped unless you pass dropna=False.
    • count counts non-missing values; size counts rows. The gap is the number of missing values.
    • pandas skips NaN in sum and mean. Convenient, but it hides missing data: check .isna().sum().

    Group only by what happened before the prediction date, or the feature leaks (F3.1).

    Joining: how rows multiply

    merge is SQL's JOIN; how is inner (keys in both), left (every left row) or outer (everything). The damaging rule is about duplicate keys: a key appearing twice on one side matches every row on the other side twice. Like a wedding where a double guest-list entry gets two full sets of place settings. If the customer table has two rows for one customer, every one of that customer's transactions is doubled, and so is every total afterwards.

    Three defences, by how often they save you:

    1. Pass validate="m:1" so the merge raises MergeError if the right side has duplicate keys.
    2. Compare row counts and an additive total before and after.
    3. Use indicator=True to count unmatched rows instead of guessing.

    Also watch key types: IDs read as integers in one file and strings in another fail to match, and an account number like 00123 read as a number loses its leading zeros. Read identifiers with dtype=str.

    The join type is a statement about your data. left says "keep every transaction, known customer or not". inner says "only analyse known customers", which silently removes rows, and removal is rarely random (in the simulation it is the AED 700 transaction). For point-in-time work (F3.1), merge_asof joins each row to the most recent earlier record.

    Reshaping: wide, long, and the dtype checks that go with them

    Long data has one row per customer per month; wide has one row per customer and a column per month. Models, SQL aggregates and plotting want long; reports and matrix operations want wide. pivot_table goes long to wide, melt goes wide to long.

    Pivoting leaves a NaN wherever a customer has no row for a month. Whether it becomes 0 (no activity) or stays missing (unknown) is a modelling decision (F3.4), so make it deliberately.

    After loading any file, run df.dtypes, df.isna().sum() and df.describe(include="all"). They catch the usual three problems:

    • A date left as text sorts alphabetically and cannot be subtracted (see F11.3).
    • A numeric column read as object because one cell said "N/A" will not sum.
    • Low-cardinality strings (segment, branch, currency) are far smaller as category.
    Part 3

    How it fails, and how to spot it

    Each comes with the quickest check.

    • Row-by-row loops on a DataFrame

      for i, row in df.iterrows() or df.apply(f, axis=1) over millions of rows. It runs, slowly, and someone concludes "Python is too slow for this".

      Spot itSearch for iterrows and apply(..., axis=1). Ask what whole-column expression would do the same.
    • Silent index alignment

      Adding a column or Series whose index differs: NaNs appear, or values attach to the wrong customers after a sort or filter.

      Spot itCheck result.isna().sum() after every combination, and a.index.equals(b.index) where it should hold.
    • Join row explosion, or inner joins that drop rows

      A key that should be unique is not, and rows and totals inflate with no error. Or an inner join drops the unmatched transactions, which are often the interesting ones (new customers, closed accounts, bad data).

      Spot itCompare rows and an additive total before and after. Use validate="m:1" and indicator=True, and count left_only before dropping anything.
    • Chained assignment and views mutated by accident

      df[mask]["x"] = 1 changes nothing (pandas 3.0) or something unpredictable (older versions). A NumPy slice passed to a function that edits it in place changes the original data.

      Spot itLook for two sets of brackets before an assignment and use df.loc[mask, "x"] = 1. Call .copy() when you intend to modify.
    • Wrong axis or accidental broadcasting

      Standardising rows instead of columns, or a square table hiding a transposed vector.

      Spot itPrint .shape at each step and test on a 3 by 4 array you can check by hand. Prefer keepdims=True.
    • Missing values and dtypes left to defaults

      NaN skipped in mean, dropped in groupby keys, integers turned into floats; floats for money; account numbers that lost leading zeros or fail to join because one side is int and the other str.

      Spot itCheck df.dtypes right after loading and report isna().sum() before any aggregate. Read identifiers with dtype=str; keep money as integer fils or decimal.
    Part 4

    Self-check

    Try each one before opening the answer.

    1. You have balances of shape (1000, 12) and cust_mean of shape (1000,), and balances - cust_mean raises an error. Why, and what is the fix?

    Shapes line up from the right: 12 meets 1000, neither equal nor 1, so it fails. Make the means a column with cust_mean[:, None], or use mean(axis=1, keepdims=True).

    2. A table of 50 million transactions has 40 float64 columns and will not fit on your laptop. How do you think about what is using the memory, and what can you do?

    Memory is rows × columns × bytes per value, so about 16 GB here. Cut the bytes per value: float32 where precision allows (not for exact money), category for labels. Or cut the rows and columns you load.

    3. A thousand transactions are joined to a customer table in which fifty customers appear twice. What happens to the row count and the total, and what would have caught it?

    Each of those customers' transactions is matched twice, so rows and the total both inflate, with no error. validate="m:1" would have failed the merge, and comparing the total before and after would have shown the jump.

    4. Series a has index {1, 2, 3} and b has index {2, 3, 4}. What does a + b return, and what changes with a.add(b, fill_value=0)?

    a + b has index {1, 2, 3, 4}: NaN at 1 and 4, sums at 2 and 3. With fill_value=0 a missing side counts as 0, so no NaN remains. Whether that is sensible depends on the data.

    5. What is the difference between groupby(...).agg("sum") and groupby(...).transform("sum"), and when do you want the second?

    agg returns one row per group. transform returns the original length, with each group's sum repeated on every row. Use it when each row needs its group's statistic, such as a transaction's share of its customer's total.

    6. df[df.amount > 5000]["flag"] = 1 leaves df unchanged. Why, and what do you write instead?

    The first bracket makes a new object and the assignment goes to that. Write one step: df.loc[df.amount > 5000, "flag"] = 1.

    7. A pipeline reads cust_id as integers from a CSV, but the customer table stores it as text like "00417". What happens at the join, and what do you do?

    Either the merge fails on mismatched types, or 417 does not equal "00417" and nothing matches. Read identifiers with dtype=str on both sides, and count unmatched rows with indicator=True.
