    Releasing and Watching Models: Batch, Real-Time, Shadow, Canary and Monitoring

    How to choose when a model runs, how to put a new one in front of customers without betting the bank on it, and how to notice, before a customer or a regulator does, that it has quietly stopped working.

    Contents

    The whole lesson in one sentenceRun the model as rarely as the decision allows, release it in stages that limit how much damage a mistake can do, and watch four layers (system, data, predictions, outcomes) knowing that outcomes, the layer you trust most, arrive last.

    Part 1

    The intuition

    A model that scores well in a notebook has done about a third of the job. The rest is two questions the notebook never asked.

    When does it run? A card-fraud model must answer in the 100 milliseconds between a customer tapping a terminal and the bank replying. A propensity model that picks who gets a personal-finance offer can run overnight. A provisioning model can run once a month. Running faster than the decision needs costs real money and adds failure modes. Running slower than the decision needs makes the answer stale before anyone acts on it.

    How do we change it safely? A new fraud model that is 2 points worse on recall will not announce itself. Nothing crashes. The dashboards stay green. A few weeks later the chargebacks come in. So you never switch a bank's decisions to a new model in one move. You let it watch first (shadow), then let it act on a small slice (canary), then widen, with a way back at every step.

    After release the model still decays, because the world it learned from moves. Customers change, fraudsters adapt, a data pipeline gets renamed, a rule upstream changes its output. Monitoring is the discipline of noticing that early. The hard part is that the clean signal, whether the model was right, comes late: a default takes 90 days, a chargeback weeks. So you need earlier, weaker signals as well, and you need to know what each one can and cannot tell you.

    Hold onto thisThe question is never "can we do real-time?". It is "how fast does the value of this decision fade, and what is each extra speed worth?" Match the pattern to the decision, then choose a release method that limits the damage of being wrong.
    Part 2

    How it really works

    Batch, real-time and the middle ground

    Three serving patterns cover almost everything. They differ in when features are computed, when the model runs and where the answer is stored or sent.

    PatternHow it worksBank examplesCosts and risks
    BatchA scheduled job reads a table, scores everyone, writes the scores to another table. Downstream systems read the stored score.Next-best-product lists, churn scores, early-warning for credit, IFRS 9 stage and expected-loss runs, AML customer risk ratings.Cheap, easy to test and replay. Scores are as old as the last run. A job that silently fails leaves yesterday's scores in use.
    Real-time (online)A service receives one request, assembles features, runs the model and answers within a latency budget, often tens to a few hundred milliseconds.Card authorisation, instant-payment screening, login risk, chatbot or copilot replies.Needs always-on infrastructure, a latency budget, and the same features at serving time as in training (see feature stores). Failure is immediate and visible.
    Streaming / near-real-timeEvents flow through a pipeline that updates features or scores within seconds to minutes, without a caller waiting.Velocity features ("transactions in the last hour"), mule-account alerts, transaction monitoring queues.The hardest to get right: ordering, late events, exactly-once counting. Worth it only if value fades in minutes.

    Two practical rules come from Simulation 1.

    • Half-life sets the pattern. If the decision loses most of its value within minutes, you need online scoring. If it loses value over days, a daily batch captures almost everything, and real-time is an expensive way to be a little less stale. Many good designs are hybrid: a batch model produces a rich customer profile overnight, and a light real-time model combines it with the live transaction.
    • The pattern constrains the model. A real-time model that needs 300 features from five systems will blow its latency budget. Teams often train a smaller model for serving than the one they explored with, or precompute the expensive features in batch and look them up. Latency is a modelling constraint, not an afterthought. The real-time fraud design lesson and its batch counterpart walk through both end to end.

    Batch has a failure that real-time doesn't: it fails quietly. When a real-time service dies, calls fail and someone is paged. When a nightly job dies, the stale scores sit in the table looking perfectly normal. Every batch output needs a freshness check ("scored today? how many rows? how many nulls?") as part of the job, not a person's memory.

    Shadow, canary and the other ways to release

    The release patterns differ in two things: whether the new model's decision affects customers, and what you can learn from it.

    PatternWhat happensWhat you learnWhat you can't learn
    ShadowThe new model (challenger) gets a copy of live traffic and scores it. Its output is logged, never acted on. The old model (champion) still decides.Latency, errors, missing features, score distribution, agreement with the champion. Zero customer risk.Whether its decisions would have been better. Customers it would have declined never reached the outcome, so you never see if they were fraud.
    CanaryA small share of traffic is decided by the new model. The rest stays on the champion. You widen in steps (1%, 5%, 25%, 100%) if guardrail metrics hold.Real outcomes for the new model's own decisions, with a live control group to compare against.Anything rare or slow, quickly. Detection needs enough events and, for fraud, enough label maturity.
    Blue-greenTwo complete environments. Traffic flips from blue (old) to green (new) at once, with an instant switch back.Infrastructure correctness. Fast rollback.Nothing about model quality before the flip. All customers are exposed at once.
    A/B testRandom assignment to old or new, held for a planned period, analysed once.A causal answer on a business metric (F3.6, F2.7).Slow by design; not a safety mechanism if you wait for the end.
    Champion / challengerThe standing arrangement: one model decides, one or more challengers run in shadow or on a small slice, ready to replace it.Continuous evidence that a better model exists.Needs a policy for who decides and on what evidence.

    The usual path is offline evaluation, then shadow, then canary, then full release, and each step answers a different question. Offline asks "is it good on history?". Shadow asks "does it run, and does it behave sensibly on live data?". Canary asks "does it do no harm when it actually decides?". Skipping shadow means finding infrastructure bugs on real customers. Skipping canary means finding out about quality bugs the same way.

    How a canary assigns traffic matters more than it looks. Assign by a hash of the customer or card, not per transaction, so one customer sees one model consistently and their history stays coherent:

    def use_challenger(customer_id: str, canary_share: float, salt: str = "fraud-v7") -> bool:
    # stable bucket in [0, 1): same customer, same arm, every time
    h = int(hashlib.sha256(f"{salt}:{customer_id}".encode()).hexdigest(), 16)
    return (h % 10_000) / 10_000 < canary_share

    Changing the salt re-randomises the split for the next experiment, and widening the share only adds customers, never swaps them. In practice this lives in a feature-flag or traffic-routing service, not in model code.

    A canary is only as good as its guardrails: metrics with limits agreed beforehand, such as latency, error rate, the fraction of requests with missing features, approval rate, alert volume, and, once labels arrive, precision and recall against the control. Breach a limit and the system rolls back automatically, without a meeting. Write the limits down before the canary starts, not after you see the numbers.

    Three things the simulation teaches, and a practitioner will recognise.

    • Label delay, not traffic, usually sets the pace. Even a canary that collects enough events in two days cannot say anything about fraud outcomes until chargebacks land. That is why canaries also watch fast proxies: approval rate, alert volume, score distribution, analyst override rate. They are weaker evidence, but they arrive today. See delayed labels and feedback loops and label delay in the imbalanced-data lesson.
    • Rare events make small canaries slow. The relevant sample size is the number of positives in each arm, not the number of transactions, the same logic as in imbalanced data. For an AML model with 40 cases a month, a canary cannot prove superiority in any sensible time. You rely on shadow comparison, expert review of disagreements, and a pre-agreed rollback plan.
    • Shadow comparison is not outcome comparison. If the challenger would have blocked a transaction the champion approved, you don't know whether it was fraud. Review a sample of disagreements by hand, and read the shadow results as "where do they differ, and does it look sensible?", not as accuracy.

    Rollback, versions and what a release must carry

    A release is more than a model file. To roll back, and to answer an auditor six months later, you must be able to say exactly what was running. A model release should be an immutable bundle: the model artefact, the feature definitions and code version, the training data snapshot or its query, the threshold and cost assumptions, the evaluation report, the approval, and the container or environment. The model lifecycle lesson covers registries and promotion; here the point is that rolling back means moving a pointer to the previous bundle, not retraining under pressure.

    Rollback has traps. If the new model changed a feature definition or a table schema, the old model may not run on today's features. If decisions were made and acted on (accounts blocked, customers called), rolling back the model does not undo them; you may need a list of decisions made by the bad version to review. And in a bank, a model that influences a regulated decision usually needs the validation and sign-off described in independent validation before a canary starts, not after it succeeds.

    What to monitor: four layers

    "Monitoring" means four different things, and mixing them up causes most arguments. Think of a chain from the machine to the money.

    LayerExamplesSpeedWhat it tells you
    1. SystemLatency p50 / p99, error rate, timeouts, throughput, batch job success and duration, freshness of scores.SecondsThe service is up and fast. Says nothing about whether answers are right.
    2. Data qualityNull rate per feature, out-of-range values, new categories, row counts, schema changes, duplicated keys, a feature that suddenly equals its default.Minutes to hoursInputs are well-formed. The most common real cause of a sudden model failure.
    3. Data and prediction driftPopulation Stability Index (PSI) per feature and for the score, Kolmogorov-Smirnov (KS) distance, share of alerts, approval rate.Daily to weeklyThe world or the pipeline looks different from training. Early, but cannot say the model is worse.
    4. PerformancePrecision, recall, calibration, gain or loss against actual outcomes, cut by segment.Delayed by the label lagWhether the model is actually right. The only layer that proves harm, and the slowest.

    Layers 1 and 2 are cheap and should be near-complete. Layer 3 gives early warning. Layer 4 is the truth but arrives late. A healthy monitoring design wires all four, with an owner and an action for each alarm. An alert that nobody is responsible for is decoration.

    Add a fifth habit for any model that is used by a human: track what people do with it. Analyst override rate, queue age and the fraction of alerts closed in under 30 seconds tell you whether the model has lost trust, long before its metrics move.

    Drift: four ways the world moves, and the numbers that catch them

    "Drift" is a family. The differences decide which monitor can see it.

    • Covariate drift (data drift): the inputs P(X) change; the rule linking inputs to outcomes P(Y|X) doesn't. Example: a new salary-transfer partnership brings younger, lower-income customers. Input monitors see it. Performance may or may not suffer.
    • Prior or label shift: the outcome rate P(Y) changes, with P(X|Y) the same. Example: a fraud wave doubles the fraud rate. Scores shift upward, calibration breaks (the prior-shift correction in the imbalanced data lesson is the quick fix).
    • Concept drift: the rule P(Y|X) itself changes. Example: fraudsters learn what the model flags and change tactics; a regulation changes who defaults. The inputs may look unchanged. Input monitors are blind to it; only outcomes reveal it.
    • Pipeline faults: not a change in the world but a break in the plumbing: a column renamed, a unit changed from fils to dirhams, a join that starts dropping rows. They look like drift and are far more common and abrupt. Check them first.

    The workhorse statistic is the Population Stability Index, long used in credit scorecards. Cut the reference (training) distribution into bins, usually deciles, then compare the share of the current population in each bin:

    PSI=∑i=1B(ai−ei)·lnaiei

    ei is the expected share in bin i (10% for deciles of the reference), ai the actual share now. Each term is positive, so PSI is zero only when nothing moved and grows with every bin that does. It is a symmetric version of the Kullback-Leibler divergence (F1.7). The common rule of thumb, from scorecard practice rather than a theorem, reads under 0.1 as stable, 0.1 to 0.25 as worth a look, above 0.25 as a real shift. Treat those cut-offs as starting points: they depend on sample size and the number of bins.

    Alternatives: the KS statistic (largest gap between the two cumulative distributions, no binning), the Wasserstein distance (how far the mass has to move, in the feature's own units), a chi-squared test or Jensen-Shannon distance for categories, and a domain classifier: train a model to tell reference rows from current rows, and if it can (AUC well above 0.5) then something moved, and its feature importances say what. F7 covers PSI and KS in more depth: drift monitoring. Two cautions apply to all of them. With huge samples, p-value tests flag trivial shifts, so use effect sizes. And a drifting feature is a hypothesis, not a diagnosis: check it against the business story and the performance layer before retraining.

    Performance monitoring when the truth arrives late

    Performance is the only layer that proves a model is worse, and it is the slowest. A fraud model's recall for transactions in March can only be measured once March's chargebacks are in, which may be May. A default model's accuracy for loans issued this quarter is unknown for another year. Four tactics help.

    • Measure by cohort and by label age. Report recall for the cohort of transactions made in week w, evaluated once its labels are mature. Never mix young and old cohorts in one number, or recent fraud counts as legitimate and recall appears to collapse (the trap from the imbalanced-data lesson).
    • Use fast proxies. Alert rate, approval rate, score distribution, analyst confirmation rate on reviewed alerts (labels in hours), and early labels such as customer disputes within 48 hours. They are weaker, but they move first.
    • Keep a random review sample. If you only learn the outcomes of what you flagged, monitoring is blind to what you miss. A small random sample of unflagged cases, reviewed independently, gives an unbiased recall estimate (F2.6).
    • Estimate performance without labels, carefully. Research methods try to predict the metric from score and input shifts (for example confidence-based estimators). They help as an extra signal but fail under concept drift, so do not let them replace real labels.

    Link all four layers to actions. A good alert says what it means and what to do: "null rate of salary_credit_3m 38% since 02:10; fall back to the previous feature snapshot and page data engineering". An alert that says "PSI 0.27" teaches nobody anything. Thresholds, owners and the response should be agreed beforehand and revisited after each incident. Over-alerting kills monitoring as surely as no alerting; fewer, better-tuned alerts get read.

    Monitoring is therefore an exercise in combining weak, fast signals with strong, slow ones. Fast monitors raise suspicion; slow ones confirm it. And some faults (concept drift) can only be caught by the slow one, which is why a periodic challenger retrain-and-compare, with a random labelled sample, belongs in the design even when everything looks quiet.

The live arguments are about how much monitoring can be automated, and how to monitor systems whose output is text.

    Part 5

    How it fails, and how to spot it

    Most production incidents are boring. Each of these has a quick check.

    • Training-serving skew

      The feature is computed one way in training (a SQL window over history) and another online (a cache with different rounding or time zone). Offline AUC is 0.93; live it behaves like 0.80.

      Spot itLog the served features for a sample of requests and compare them with the offline recomputation for the same requests. Differences are skew.
    • Silent batch failure

      The nightly job fails or runs on yesterday's data. Downstream systems keep using stale scores that look normal.

      Spot itCheck the score table's maximum scoring date, row count against yesterday and the null share, as a hard step in the job.
    • Skipping shadow

      The first live traffic the model sees is in a canary. A missing feature makes it return a default score for 20% of customers.

      Spot itAsk for the shadow report: share of requests with missing features, latency percentiles, score distribution against the champion.
    • A canary that is too small or too short to say anything

      "The 2% canary showed no difference" after three days and 6 frauds.

      Spot itAsk how many positives were in each arm and what size of loss the test could have detected (power).
    • Judging a canary on immature labels

      The new model looks better because its frauds haven't been reported yet, as are the champion's.

      Spot itCompare cohorts of equal label age only. Check that both arms had the same time to mature.
    • Treating shadow disagreement as accuracy

      "The challenger flagged 30% more cases, so it finds more fraud."

      Spot itAsk whether any outcome is known for the extra cases. If none, it is an unlabelled difference, not a gain.
    • Rollback that doesn't work

      The previous model needs a feature the pipeline no longer produces.

      Spot itRehearse a rollback in a staging environment before the release, not during the incident.
    • Monitoring only the inputs, or only the outputs

      PSI is green for months while the fraud tactic changes (concept drift). Or recall is watched but null rates are not, and a bad join runs for weeks.

      Spot itFor each of the four layers, ask what alarm covers it, who owns it and what they do.
    • Alert fatigue and one-number thresholds

      Forty features each alert at PSI 0.1 every week. People mute the channel. The real incident is buried.

      Spot itCount alerts per month and the share acted on. If under about 20% led to action, retune.
    • Retraining on contaminated data

      Drift triggers an automatic retrain on the last month, which includes the faulty period, so the new model learns the bug.

      Spot itCheck the retraining window against known incidents, and apply the label-maturity embargo.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “We won't switch the new fraud model on for everyone at once. It runs silently alongside the current one first, to prove it works on live traffic. Then it makes decisions for a small slice of customers, with limits agreed in advance, and switches itself off if it breaches them. Once it's live we watch the system, the data, the model's outputs and the real outcomes. The outcomes arrive weeks late, so we also watch earlier warning signs. The cost of caution is a few weeks; the cost of a bad release is real money and a conversation with the regulator.”
    To a technical interviewer or validator
    “Serving pattern follows the half-life of the decision: online for authorisation, batch for propensity and provisioning. Release is offline evaluation, shadow with disagreement review, hashed-by-customer canary with pre-registered guardrails and automatic rollback, then ramp. Monitoring covers four layers: system, data quality, input and score drift with PSI and KS, and performance by cohort at matured label age, with a random review sample so recall is unbiased. Concept drift is invisible to input monitors, so outcome monitoring and periodic challenger comparison remain essential.”
    “Why not just go real-time for everything?”

    Because it costs more, fails louder and constrains the model, and only pays if the decision loses value within minutes. A nightly batch captures nearly all the value of a marketing or provisioning model. I'd ask how quickly the benefit of acting fades, and choose the slowest pattern that still captures most of it.

    “What is the difference between shadow and canary?”

    In shadow the new model scores live traffic but nothing acts on it, so there is no customer risk, but also no outcomes for its own decisions. In a canary it makes real decisions for a small slice, so we get real outcomes and a control group, at the price of limited exposure. Shadow checks that it runs; canary checks it does no harm.

    “PSI is 0.3 on the income feature. Do we retrain?”

    Not yet. First check whether it's a pipeline fault (nulls, units, a changed source), then whether the population really changed, for example a new customer segment. Then look at the performance layer and the score distribution: has the model's behaviour actually changed? Retraining on a faulty window would bake the fault in. Drift is a prompt to investigate, not a diagnosis.

    “Our inputs look stable but fraud losses are creeping up.”

    That pattern suggests concept drift: the relationship between inputs and fraud has changed, for example because fraudsters adapted. Input monitors can't see that. I'd look at recall by cohort at matured label age, review a random sample of unflagged transactions, and see what the challenger finds. The fix is usually retraining on recent labelled data, plus new features that capture the new tactic.

    “How do you know a rollback will work?”

    By rehearsing it. Each release is an immutable bundle, with model, feature code, threshold and environment, and rollback is repointing to the previous bundle. I'd test that in staging on today's features before the release, because the usual trap is that the old model needs a feature or schema that has moved on.

    “Does the regulator require specific monitoring?”

    I'd say: banks in the UAE have model management standards from the central bank, and there is recent AI and ML guidance, but I'd confirm the exact requirements and any Saudi equivalent with our model risk team rather than quote from memory. In practice, expect independent validation before use, documented ongoing monitoring with thresholds and owners, and periodic review.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. An alert is worth AED 100,000 a day if acted on instantly, but its value halves every 6 hours. Roughly what share does a nightly (24-hour) batch capture?

    τ = half-life ÷ ln 2 = 6 ÷ 0.693 = 8.66 hours. Share = (τ/H)(1 − e−H/τ) = (8.66/24)(1 − e−2.77) = 0.361 × 0.937 ≈ 34%, about AED 34,000 a day. A 6-hour batch would capture (8.66/6)(1 − e−0.693) = 1.443 × 0.5 ≈ 72%.

    2. Why can't shadow mode tell you whether the challenger is more accurate?

    Its decisions aren't acted on, so the cases where it disagrees with the champion never play out under its policy. If it would have declined a transaction the champion approved, we don't learn whether it was fraud (the champion's approval produced the label only for the champion's decisions). We can compare scores, latency and agreement, and have people review samples of disagreements.

    3. Why assign canary traffic by customer hash, not per transaction?

    So a customer is consistently on one model, and their history and features stay coherent. Per-transaction assignment mixes models inside one customer's sequence, contaminates velocity features and makes customers' experience erratic. Hashing also gives a stable split that only grows as you widen the share.

    4. A canary has 80 frauds a day, the control 720. Why does a longer label delay not reduce the number of traffic days needed, but still delays the decision?

    Statistical power depends on how many labelled positives you gather per arm, which depends on traffic and time, not on when labels arrive. But you can only count a transaction once its label has matured, so the whole observation window is shifted by the delay. Total wait is traffic days needed plus label delay, and exposure runs the whole time.

    5. Name the four layers of monitoring and say which one can't be fooled by a pipeline bug, and which is slowest.

    System, data quality, data and prediction drift, performance. Performance monitoring measures against real outcomes, so a pipeline bug can't hide there; but it's the slowest, because it waits for labels. A pipeline bug is caught fastest by data quality checks.

    6. Which kind of drift will an input-feature PSI monitor miss entirely, and what would catch it?

    Concept drift, where P(Y|X) changes while inputs look the same. It needs outcome monitoring: recall or calibration by cohort at matured label age, a random review sample, or a challenger trained on recent data compared against the champion.

    7. Weekly recall for the newest 3 weeks looks very low. List two non-model explanations.

    First, label immaturity: those weeks' frauds haven't been reported yet, so they count as legitimate. Second, a change in how or when labels are produced, for example a backlog in the investigation team, or a changed chargeback process. Compare cohorts at equal label age before concluding the model has decayed.
