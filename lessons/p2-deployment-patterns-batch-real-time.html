    Releasing and Watching Models: Batch, Real-Time, Shadow, Canary and Monitoring

    How to choose when a model runs, how to put a new one in front of customers without betting the bank on it, and how to notice, before a customer or a regulator does, that it has quietly stopped working.

    Contents

    The whole lesson in one sentenceRun the model as rarely as the decision allows, release it in stages that limit how much damage a mistake can do, and watch four layers (system, data, predictions, outcomes) knowing that outcomes, the layer you trust most, arrive last.

    Part 1

    The intuition

    A good notebook score is about a third of the job. Production adds two questions.

    When does it run? Think of weather warnings: a storm alert is checked every minute, a seasonal forecast once a month. Card fraud must be scored in the 100 ms between tap and reply. A personal-finance offer can be scored overnight. Provisioning can run monthly. Running faster than the decision needs costs money and adds failure modes. Running slower makes the answer stale before anyone acts.

    How do we change it safely? A new fraud model with 2 points worse recall crashes nothing. Dashboards stay green and the chargebacks arrive weeks later. So it is introduced like a trainee driver: it rides along first (shadow), then drives a quiet road (canary), then widens, with a way back at every step.

    After release the model decays: customers change, fraudsters adapt, a pipeline column is renamed. Monitoring catches that early. The clean signal, whether the model was right, comes late (a default takes 90 days, a chargeback weeks). So you also need earlier, weaker signals, and you must know what each can and cannot tell you.

    Hold onto thisAsk "how fast does this decision's value fade, and what is each extra speed worth?", not "can we do real-time?". Match the pattern to the decision, then release in a way that limits the damage of being wrong.
    Part 2

    How it really works

    Batch, real-time and the middle ground

    Batch is a printed timetable. Real-time is asking the driver now. Streaming is a live departures board. They differ in when features are computed, when the model runs and where the answer goes.

    PatternHow it worksBank examplesCosts and risks
    BatchA scheduled job scores everyone and writes scores to a table. Downstream systems read the stored score.Next-best-product, churn, credit early-warning, IFRS 9 runs, AML risk ratings.Cheap, easy to test and replay. Scores are as old as the last run. A silently failed job leaves yesterday's scores in use.
    Real-time (online)A service takes one request, assembles features, scores and answers within a latency budget (tens to a few hundred ms).Card authorisation, instant-payment screening, login risk, chatbot replies.Always-on infrastructure, a latency budget, and the same features at serving as in training (see feature stores). Failure is immediate and visible.
    Streaming / near-real-timeEvents flow through a pipeline that updates features or scores within seconds to minutes, with no caller waiting.Velocity features ("transactions in the last hour"), mule-account alerts, monitoring queues.Hardest to get right: ordering, late events, exactly-once counting. Worth it only if value fades in minutes.
    • Half-life sets the pattern. If a decision loses most of its value in minutes, score online. If it loses value over days, a daily batch captures almost all of it. Hybrids are common: batch builds a rich customer profile overnight, and a light real-time model combines it with the live transaction.
    • The pattern constrains the model. A real-time model needing 300 features from five systems will blow its latency budget, like a sat-nav that takes ten minutes to plan a turn. Teams train a smaller serving model, or precompute the expensive features in batch and look them up. See the real-time fraud design and its batch counterpart.
    • Batch fails quietly. A dead real-time service pages someone. A dead nightly job leaves stale scores that look normal. Build a freshness check into the job ("scored today? how many rows? how many nulls?"), not into someone's memory.

    Shadow, canary and the other ways to release

    Release patterns differ in two ways: whether the new model's decisions affect customers, and what you can learn from it.

    PatternWhat happensWhat you learnWhat you can't learn
    ShadowThe new model (challenger) scores a copy of live traffic. Output is logged, never acted on. The old model (champion) still decides.Latency, errors, missing features, score distribution, agreement with the champion. Zero customer risk.Whether its decisions would have been better. Customers it would have declined never reached an outcome.
    CanaryA small share of traffic is decided by the new model, the rest by the champion. Widen (1%, 5%, 25%, 100%) while guardrail metrics hold.Real outcomes for its own decisions, with a live control group.Anything rare or slow, quickly. Needs enough events and mature labels.
    Blue-greenTwo full environments. Traffic flips from blue (old) to green (new) at once, with an instant switch back.Infrastructure correctness. Fast rollback.Model quality before the flip. Everyone is exposed at once.
    A/B testRandom assignment to old or new, held for a planned period, analysed once.A causal answer on a business metric (F3.6, F2.7).Slow by design. Not a safety mechanism if you wait for the end.
    Champion / challengerThe standing arrangement: one model decides, challengers run in shadow or on a slice, ready to replace it.Continuous evidence that a better model exists.Needs a policy on who decides, on what evidence.

    The usual path is offline evaluation, shadow, canary, full release. Each answers a different question: is it good on history, does it run sensibly on live data, does it do no harm when it decides. Skip shadow and infrastructure bugs hit real customers. Skip canary and quality bugs do.

    Assign canary traffic by a hash of the customer or card, not per transaction, so one customer always sees one model and their history stays coherent:

    def use_challenger(customer_id: str, canary_share: float, salt: str = "fraud-v7") -> bool:
    # stable bucket in [0, 1): same customer, same arm, every time
    h = int(hashlib.sha256(f"{salt}:{customer_id}".encode()).hexdigest(), 16)
    return (h % 10_000) / 10_000 < canary_share

    A new salt re-randomises the split for the next experiment. Widening the share only adds customers, never swaps them. In practice this sits in a feature-flag or routing service, not model code.

    A canary is only as good as its guardrails: limits agreed beforehand on latency, error rate, missing-feature share, approval rate, alert volume and, once labels arrive, precision and recall against the control. Breach one and the system rolls back automatically, without a meeting. Write the limits down before you see the numbers.

    • Label delay, not traffic, usually sets the pace. A canary can have enough events in two days and still say nothing about fraud outcomes until chargebacks land. So canaries also watch fast proxies: approval rate, alert volume, score distribution, analyst override rate. Weaker, but available today. See delayed labels and feedback loops and label delay.
    • Rare events make small canaries slow. What counts is positives per arm, not transactions. With 40 AML cases a month, a canary can't prove superiority in any sensible time. Rely on shadow comparison, expert review of disagreements and a pre-agreed rollback plan.
    • Shadow comparison is not accuracy. If the challenger would have blocked something the champion approved, you don't know if it was fraud. Review a sample of disagreements by hand and read shadow results as "where do they differ, and does it look sensible?".

    Rollback, versions and what a release must carry

    A release is more than a model file. To roll back, or to answer an auditor six months on, you must know exactly what was running. Ship an immutable bundle, like a sealed recipe box: model artefact, feature definitions and code version, training data snapshot or query, threshold and cost assumptions, evaluation report, approval and environment. See the model lifecycle lesson. Rolling back means moving a pointer to the previous bundle, not retraining under pressure.

    Three traps:

    • If the release changed a feature definition or table schema, the old model may not run on today's features.
    • Decisions already acted on (accounts blocked, customers called) are not undone. Keep a list of decisions made by the bad version for review.
    • A model influencing a regulated decision needs validation and sign-off (independent validation) before the canary starts, not after it succeeds.

    What to monitor: four layers

    "Monitoring" means four things, and mixing them up causes most arguments. Think of a chain from the engine to the road: the car runs, the fuel is clean, the dashboard looks normal, and you actually arrive.

    LayerExamplesSpeedWhat it tells you
    1. SystemLatency p50 / p99, error rate, timeouts, throughput, batch success and duration, score freshness.SecondsThe service is up and fast. Nothing about whether answers are right.
    2. Data qualityNull rate per feature, out-of-range values, new categories, row counts, schema changes, duplicate keys, a feature stuck at its default.Minutes to hoursInputs are well-formed. The most common real cause of sudden failure.
    3. Data and prediction driftPopulation Stability Index (PSI) per feature and for the score, Kolmogorov-Smirnov (KS) distance, alert share, approval rate.Daily to weeklyThe world or pipeline looks different from training. Early, but can't say the model is worse.
    4. PerformancePrecision, recall, calibration, gain or loss against actual outcomes, by segment.Delayed by label lagWhether the model is right. The only layer that proves harm, and the slowest.

    Layers 1 and 2 are cheap and should be near-complete. Layer 3 warns early. Layer 4 is the truth but late. Wire all four, with an owner and an action per alarm. An alert nobody owns is decoration.

    For any model used by a human, add a fifth habit: track what people do with it. Analyst override rate, queue age and share of alerts closed in under 30 seconds show lost trust long before metrics move.

    Drift: four ways the world moves, and the numbers that catch them

    "Drift" is a family, and which monitor can see it depends on the member. Each below has an example.

    • Covariate drift (data drift): the inputs P(X) change, the rule P(Y|X) doesn't. A salary-transfer partnership brings younger, lower-income customers. Input monitors see it. Performance may or may not suffer.
    • Prior (label) shift: the outcome rate P(Y) changes. A fraud wave doubles the fraud rate. Scores shift up and calibration breaks (the prior-shift correction in imbalanced data is the quick fix).
    • Concept drift: the rule P(Y|X) itself changes. Fraudsters learn what the model flags and switch tactics. Inputs may look unchanged, so input monitors are blind to it. Only outcomes reveal it.
    • Pipeline faults: a broken plumbing, not a changed world: a renamed column, fils turned into dirhams, a join dropping rows. They look like drift, are far more common and abrupt. Check them first.

    The workhorse statistic is the Population Stability Index (PSI), long used in credit scorecards. It asks: if I cut the training distribution into ten equal slices, is today's population still spread evenly across them? Like checking whether a class that used to be evenly split by height still is.

    PSI=∑i=1B(ai−ei)·lnaiei

    ei is the expected share in bin i (10% for deciles), ai the actual share now. Each term is positive, so PSI is zero only when nothing moved and grows with every bin that does. It is a symmetric version of Kullback-Leibler divergence (F1.7). Rule of thumb from scorecard practice, not a theorem: under 0.1 stable, 0.1 to 0.25 worth a look, above 0.25 a real shift. Depends on sample size and bin count. PSI measures how far the shape moved, not whether the model got worse: going from 0.05 to 0.3 says the population changed, not by how much accuracy fell.

    Alternatives:

    • KS statistic: the largest gap between the two cumulative curves. No binning.
    • Wasserstein distance: how far the mass must move, in the feature's own units.
    • Chi-squared or Jensen-Shannon: for categories.
    • Domain classifier: train a model to tell reference rows from current ones. AUC well above 0.5 means something moved, and feature importances say what.

    More in drift monitoring. Two cautions. With huge samples, p-value tests flag trivial shifts, so use effect sizes. And a drifting feature is a hypothesis, not a diagnosis: check it against the business story and the performance layer before retraining.

    Performance monitoring when the truth arrives late

    Performance is the only layer that proves a model is worse, and the slowest. March recall can be measured only once March's chargebacks are in, perhaps in May. A loan default model's accuracy for this quarter is unknown for a year. Four tactics help.

    • Measure by cohort and label age. Report recall for transactions from week w, once its labels are mature. Mixing young and old cohorts makes recent fraud count as legitimate, so recall seems to collapse (see imbalanced data).
    • Use fast proxies. Alert rate, approval rate, score distribution, analyst confirmation rate (labels in hours) and early labels like disputes within 48 hours. Weaker, but they move first.
    • Keep a random review sample. If you learn outcomes only for what you flagged, you're blind to what you miss. A small independent review of unflagged cases gives an unbiased recall estimate (F2.6).
    • Estimate performance without labels, carefully. Research methods predict the metric from score and input shifts. Useful as an extra signal, but they fail under concept drift. They don't replace labels.

    Tie every layer to an action. A good alert says what it means and what to do: "null rate of salary_credit_3m 38% since 02:10; fall back to the previous snapshot and page data engineering". "PSI 0.27" teaches nobody anything. Agree thresholds, owners and responses beforehand and revisit after each incident. Too many alerts kill monitoring as surely as none.

    Monitoring combines weak, fast signals with strong, slow ones. Fast monitors raise suspicion, slow ones confirm. Some faults (concept drift) only the slow one catches, so a periodic challenger retrain-and-compare, with a random labelled sample, belongs in the design even when all is quiet.

    Part 3

    How it fails, and how to spot it

    Most production incidents are boring. Each has a quick check.

    • Training-serving skew

      A feature is computed one way in training (SQL window over history) and another online (a cache with different rounding or time zone). Offline AUC 0.93, live it behaves like 0.80.

      Spot itLog served features for a sample of requests and compare with the offline recomputation for the same requests.
    • Silent batch failure

      The nightly job fails or runs on yesterday's data. Stale scores look normal.

      Spot itMake max scoring date, row count against yesterday and null share a hard step in the job.
    • Skipping shadow

      First live traffic is in a canary. A missing feature gives a default score to 20% of customers.

      Spot itAsk for the shadow report: missing-feature share, latency percentiles, score distribution against the champion.
    • A canary too small or short to say anything

      "The 2% canary showed no difference" after three days and 6 frauds.

      Spot itAsk how many positives each arm had and what loss the test could detect (power).
    • Judging a canary on immature labels

      The new model looks better because its frauds haven't been reported yet (nor the champion's).

      Spot itCompare cohorts of equal label age only, with the same time to mature in both arms.
    • Treating shadow disagreement as accuracy

      "The challenger flagged 30% more cases, so it finds more fraud."

      Spot itAsk if any outcome is known for the extra cases. If not, it's an unlabelled difference, not a gain.
    • Rollback that doesn't work

      The previous model needs a feature the pipeline no longer produces.

      Spot itRehearse rollback in staging before release, not during the incident.
    • Monitoring only inputs, or only outputs

      PSI is green for months while the fraud tactic changes (concept drift). Or recall is watched but not null rates, and a bad join runs for weeks.

      Spot itFor each of the four layers, ask which alarm covers it, who owns it and what they do.
    • Alert fatigue and one-number thresholds

      Forty features each alert at PSI 0.1 every week. People mute the channel and the real incident is buried.

      Spot itCount alerts per month and the share acted on. Under about 20% means retune.
    • Retraining on contaminated data

      Drift triggers an automatic retrain on the last month, which includes the faulty period. The new model learns the bug.

      Spot itCheck the retraining window against known incidents and apply the label-maturity embargo.
    Part 4

    Self-check

    Try each one before opening the answer.

    1. An alert is worth AED 100,000 a day if acted on instantly, but its value halves every 6 hours. Roughly what share does a nightly (24-hour) batch capture?

    τ = 6 ÷ 0.693 = 8.66 hours. Share = (τ/H)(1 − e−H/τ) = (8.66/24)(1 − e−2.77) = 0.361 × 0.937 ≈ 34%, about AED 34,000 a day. A 6-hour batch captures (8.66/6)(1 − e−0.693) = 1.443 × 0.5 ≈ 72%.

    2. Why can't shadow mode tell you whether the challenger is more accurate?

    Its decisions aren't acted on, so cases where it disagrees with the champion never play out under its policy. If it would have declined a transaction the champion approved, we never learn if it was fraud. We can compare scores, latency and agreement, and review samples of disagreements.

    3. Why assign canary traffic by customer hash, not per transaction?

    So a customer stays on one model and their history and features stay coherent. Per-transaction assignment mixes models in one customer's sequence, contaminates velocity features and makes the experience erratic. Hashing also gives a stable split that only grows as you widen the share.

    4. A canary has 80 frauds a day, the control 720. Why does a longer label delay not reduce the traffic days needed, but still delays the decision?

    Power depends on labelled positives gathered per arm, which depends on traffic and time, not on when labels arrive. But a transaction counts only once its label matures, so the whole window shifts by the delay. Total wait is traffic days plus label delay, and exposure runs throughout.

    5. Name the four layers of monitoring. Which can't be fooled by a pipeline bug, and which is slowest?

    System, data quality, data and prediction drift, performance. Performance uses real outcomes so a pipeline bug can't hide there, but it is the slowest because it waits for labels. Data quality checks catch a pipeline bug fastest.

    6. Which drift will an input-feature PSI monitor miss entirely, and what catches it?

    Concept drift, where P(Y|X) changes while inputs look the same. Catch it with outcome monitoring: recall or calibration by cohort at matured label age, a random review sample, or a challenger trained on recent data compared with the champion.

    7. Weekly recall for the newest 3 weeks looks very low. List two non-model explanations.

    Label immaturity: those weeks' frauds aren't reported yet, so they count as legitimate. Or a change in how labels are produced, such as an investigation backlog or a changed chargeback process. Compare cohorts at equal label age before concluding the model has decayed.
