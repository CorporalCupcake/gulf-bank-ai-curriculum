    Searching Document Images: ColPali, Late Interaction and Contextual Retrieval

    How to retrieve a scanned letter of credit without ever running OCR on it, why keeping many small vectors per page beats one big vector, what that costs in storage, and how a sentence of added context rescues text chunks that have lost their owner.

    Contents

    The whole lesson in one sentenceInstead of squeezing a page into one vector, keep one small vector per patch (or per token) and let each query word find its own best match, so a tiny stamp or a table cell is not averaged away; this is more accurate on scans and layouts, costs one to two orders of magnitude more storage, and a cheaper cousin for plain text is to prepend a line of context to each chunk before indexing it.

    Part 1

    The intuition

    A trade-finance operations team has two million scanned pages: letters of credit, bills of lading, invoices, amendment letters, KYC packs. Some are Arabic, some English, many are both, with stamps, handwriting, tables and skewed photocopies. An officer asks: "Which credit carried the amendment stamp about the shipment date?"

    The standard pipeline from M3 is: run OCR and layout parsing, cut the text into chunks, embed each chunk into one vector, search. It works when every step works. On a scan, every step is a chance to lose something. OCR garbles an Arabic stamp. The table loses its row structure. The chunker cuts a clause away from its heading. By the time you search, the thing the officer is asking about may no longer exist in the index.

    ColPali's idea is to skip the pipeline. Show the page to a vision-language model as an image, and let it produce a small vector for each patch of the page, roughly a 32 by 32 grid of them. Do the same to the query, one vector per word-piece. Then score a page by asking, for each query word, "what is the best-matching patch on this page?", and adding those answers up. That scoring rule is called late interaction, borrowed from a text model called ColBERT.

    The word "late" means query and page are encoded separately and only meet at the end, in a cheap comparison. So the page vectors can be computed once, offline. The word "interaction" means the comparison is fine-grained, token against patch, rather than one summary against one summary.

    Hold onto thisA single-vector embedding is a summary, and summaries lose the rare detail. Late interaction keeps the detail and pays for it in storage and compute. Almost everything in this lesson is a consequence of that one trade.

    The second topic, contextual retrieval, attacks a different loss in the same spirit. A chunk such as "Revenue grew 3% over the previous quarter" is meaningless on its own: whose revenue, which quarter? Embedding it as is gives a vector for a sentence that fits a thousand companies. The fix is to ask an LLM to write one sentence of situating context per chunk and index the two together. Part 2 shows both ideas with numbers you can move.

    Part 2

    How it really works

    Page image to patch vectors, and MaxSim scoring (A6.1)

    The recipe, as published by Faysse and colleagues (ICLR 2025):

    1. Start with a vision-language model (VLM). ColPali uses PaliGemma-3B: an image encoder that cuts the page into patches and turns each into a vector, feeding them into a language model (F5.3, attention; F5.4, self-supervised learning). The language model's job is to let patches see each other, so a patch containing "5,000" knows it sits under the heading "Amount".
    2. Add a small linear layer that projects each patch's output to 128 dimensions. Roughly 1,000 patches per page, so about 1,000 vectors of 128 numbers each. This is the "bag of embeddings".
    3. Encode the query the same way, as text through the same model: one 128-dimensional vector per query token.
    4. Score with MaxSim. For every query token, take its similarity (dot product of normalised vectors, so cosine) with every patch, keep the maximum, and sum over query tokens.
    S(q,d)=∑i∈qmaxj∈d⟨qi,dj⟩

    qi is the vector of query token i; dj is the vector of page patch j. The inner max says "find the one patch that best answers this word". The outer sum says "a good page answers all the words". Nothing is averaged across the page, so a small region can score fully.

    Training uses the contrastive idea from F5.4: given a query and its page, push the MaxSim score up relative to the other pages in the batch. ColPali was trained on about 120,000 query-page pairs, a mix of public document question sets and synthetic queries that a language model wrote about web-crawled PDF pages. The authors also released ViDoRe, a benchmark of page-retrieval tasks across domains, and showed that the model beat pipelines built on OCR plus captioning plus text embeddings, while indexing faster, because there is no OCR or layout stage to run.

    Try the scoring rule yourself. The page below is a toy: 48 patches, each carrying a hidden topic (amount, goods, stamp, and some others). A "query token" is a vector pointing at one topic. The brightness of each cell is its cosine similarity to the chosen token, and the ringed cell is the maximum.

    Two practical details. First, the query is short and the page is long, so the work at search time is: for each of about 10–20 query tokens, compare with each of about 1,000 patches of each candidate page. That is cheap per page but not free across millions, which is why systems retrieve candidates first (next topic) and run MaxSim as a second stage. Second, ColPali comes with a family: ColQwen2 and later models swap in other VLMs, and the open-source colpali-engine library and the Vespa, Qdrant, Weaviate and Elastic style vector stores now support multi-vector fields. Check the current model card for your language and licence needs.

    Why late interaction beats one vector per page (A6.2)

    The usual dense retriever ("bi-encoder", F1.1) squeezes a page into one vector and compares by one dot product. Think of it as a page's average meaning. Averages are good at gist and bad at needles. If the answer is a stamp covering 3% of the page, it contributes 3% of the average and is easily outvoted by a distractor page that talks about amounts and goods at length.

    The opposite end is a cross-encoder, which reads query and page together and is far more accurate but must be rerun for every pair, so it can only rerank a short list. Late interaction sits between: representations are precomputed (fast, indexable) but the comparison is fine-grained. ColBERT (Khattab and Zaharia, 2020) introduced it for text, getting close to cross-encoder quality at a fraction of the cost.

    The simulation below makes the difference visible. There are 24 toy pages. A query asks for three things: an amount, goods and a stamp. The 23 distractors each mention amounts and goods heavily (7–14 patches each) but contain no stamp. The one correct page is ordinary on amounts and goods (5–7 patches each) and has the stamp. Slide the stamp's size and watch where the correct page ranks under each scoring rule.

    The failure of the single vector is not a bug in any one model. It is arithmetic: the mean of many patches is dominated by whatever occupies most of the page. Better training helps, and so does making the single vector bigger, but the information bottleneck remains. This is the same pressure behind hybrid search (M3.2): different scoring rules catch different needles. Late interaction is the dense version of what BM25 does with exact words (M3.1): every query term gets to find its own match.

    The price: storage, and how people shrink it

    One vector per patch is the cost. ColPali stores about 1,030 vectors of 128 numbers for each page. In 16-bit floats that is 1,030 × 128 × 2 bytes ≈ 264 kB per page, against 2 kB for a single 1,024-dimension vector. That is about 130 times more, before any index overhead. For two million pages: about 0.5 TB for ColPali against 4 GB for one vector each. For a hundred million pages it is a different conversation.

    The standard ways to shrink it, all of which trade a little accuracy for a lot of space:

    • Pool the patches. Average neighbouring patches (for example merge 2 to 3 together) before storing. Fewer vectors per page, coarser detail. Reported results show a large storage saving for a modest quality drop on typical documents; a tiny stamp may be the thing that suffers, so test on your own needles.
    • Quantise the numbers. 8-bit integers halve the size; binary vectors (one bit per dimension) cut it by 16, with a rescoring pass using the full-precision vectors on a short list. Same idea as P3.1 for model weights, applied to the index.
    • Shrink the dimension. Matryoshka-style embeddings (R10.1) let you truncate vectors with graceful loss. Some newer multi-vector models are trained to do this.
    • Two-stage retrieval. Use a cheap first stage (a single vector, BM25, or a compressed form) to find a few hundred candidates, then rescore only those with exact MaxSim. ColBERTv2 and PLAID (2021–22) did this for text with residual compression of token vectors and centroid-based candidate pruning. MUVERA (Google, NeurIPS 2024) turns a set of vectors into one fixed-size vector whose dot product approximates MaxSim, so ordinary single-vector search can do the candidate stage, reporting that it retrieves several times fewer candidates for the same recall.

    Contextual retrieval: giving a chunk its owner back (A6.2)

    Everything above was about image pages. Plain text pipelines have a neighbouring problem. Chunking (M3.3) slices a long report into passages, and each passage loses the identity of the document it came from. "The provision charge rose to AED 95 million." Which bank, which period? Both the embedding and the keyword index see only the sentence.

    Anthropic's contextual retrieval (September 2024) fixes this at indexing time: for every chunk, give an LLM the whole document plus the chunk and ask for a sentence or two that situates the chunk ("This is from Gulf Mercantile Bank's Q2 2025 results; it discusses group revenue growth"). Prepend that to the chunk, then embed it and build the BM25 index from the enriched text. Anthropic reported that this cut failed top-20 retrievals by about 49% on their test sets, and by about 67% when combined with a reranker (figures from memory of their post, internal benchmarks; verify before quoting). A related idea, late chunking (Jina, 2024), gets context a different way: run a long-context embedding model over the whole document first, then pool the token vectors into chunk vectors, so each chunk vector has already "seen" the rest of the document.

    This is where the two topics meet. ColBERT-style token vectors are also contextual: each token's vector depends on its neighbours. The difference is where you keep the context: in extra words (contextual retrieval), in the vector (late chunking), or in many vectors (late interaction).

    Costs to be honest about: one LLM call per chunk at indexing time (made cheap by prompt caching, because the whole document is repeated for each chunk), longer chunks to embed, and a new failure mode, which is that the generated context can be wrong. A wrong "this is from Q2 2025" is now an index-level fact. Validate a sample, and log the model and prompt version (P2.3), because re-running the generator changes your index.

    Where it shows up at the bank:

    • Trade finance. Finding the amendment, the matching bill of lading or the prior presentation across thousands of scans, without waiting for a perfect OCR of Arabic and English side by side.
    • KYC and onboarding packs. Passport pages, trade licences, board resolutions, with stamps, seals and photographs that carry meaning text does not.
    • Policy and regulatory libraries. Circulars, with tables of limits and ratios that parsers flatten. Contextual retrieval helps when a clause only makes sense under its heading.
    • Credit files and statements. Financial statements in PDF with multi-column tables, where "which year does this column belong to?" is the whole question.
    • Internal copilots. Slides and diagrams in staff knowledge bases, which text-only retrieval ignores.

    Visual document retrieval has moved from a single paper to a benchmark-and-model ecosystem in about two years. The live arguments: how much of the OCR pipeline is really redundant, how to make multi-vector indexes affordable, and how to evaluate on realistic, multilingual enterprise documents.

    Part 5

    How it fails, and how to spot it

    Each failure comes with its quickest check.

    • Benchmark scores taken as bank scores

      ViDoRe-style benchmarks use public, mostly English and French documents. Your Arabic bill of lading with a handwritten annotation is out of distribution.

      Spot itBuild 100–200 real queries with known right pages and measure recall at 5 and 20 before choosing a model. Report it per language and per document type.
    • Retrieval without reading

      Visual retrieval finds the page. It does not extract the amount. Feeding the page to a generator that misreads a digit moves the error downstream.

      Spot itFor any number that drives a decision, require a second path: field extraction with checks, or a human view of the highlighted region.
    • Storage and latency surprise

      A pilot on 5,000 pages works; the full archive does not fit in memory.

      Spot itDo the arithmetic in Simulation 3 before the pilot, and test pooled or binary variants for recall loss.
    • Pooling erases the needle

      Merging patches saves space and quietly blurs small stamps, digits and signatures, the exact things KYC cares about.

      Spot itInclude "small feature" queries in the test set and compare recall before and after pooling.
    • Images carry instructions

      A page can contain hidden or tiny text such as "ignore previous instructions". Once a VLM reads the retrieved page, that is a prompt injection (A3.1).

      Spot itTreat retrieved pages as untrusted input; keep tool permissions narrow for the generating step.
    • Wrong context baked into the index

      The LLM that writes chunk context guesses the period or the entity wrongly. Every retrieval of that chunk is now misdirected, consistently.

      Spot itSample 100 enriched chunks and have a person check the context line. Store the prompt and model version alongside the index.
    • No audit trail from an image embedding

      A vector cannot explain why a page was returned. A reviewer asks "why did it surface this one?"

      Spot itShow the best-matching patches for each query token (as in Simulation 1). It is a built-in, if rough, explanation.
    • Near-duplicate pages

      Template letters differ in one number. Both pages score almost the same and the system picks one.

      Spot itLook at retrieved results at rank 1–5 for near-identical pairs; add metadata filters (customer, date, reference) before the vector search.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “Today our document search depends on reading each scan correctly first, and Arabic scans with stamps and tables often are not read correctly. A newer approach searches the page as an image, so a stamp or a table cell can be found even when text extraction fails. It costs more storage, so I would try it on one use case, trade-finance amendments, against a test set of real questions and compare it with what we run now before we commit.”
    To a technical interviewer or validator
    “I'd keep the OCR-and-text pipeline as the baseline and add a ColPali-family late-interaction index for scans and layout-heavy pages, scored by MaxSim on patch embeddings, with a cheap first stage and exact rescoring on the shortlist. I'd budget storage at around 260 kB per page unquantised and test pooling and binarisation for recall loss on small features. On the text side I'd add LLM-generated chunk context to both BM25 and embeddings, then rerank. Everything is judged on recall at k over our own bilingual queries.”
    “Why not just OCR everything better?”

    We should, and the text is needed anyway for extraction and audit. But retrieval over OCR inherits every OCR error and every loss of layout. A visual index gives a second path that does not depend on OCR succeeding. Whether it pays for itself is measured, not assumed: recall at k on our scans with and without it.

    “What does late interaction actually mean?”

    The query and the page are encoded separately, so page vectors are precomputed. They meet late, in a cheap comparison where each query token takes the best match over the page's patches or tokens, and the matches are added up. It keeps fine detail that a single summary vector averages away.

    “The storage looks huge. Is this practical?”

    Unquantised, about 130 times a single-vector index. In practice you pool patches, quantise to 8-bit or binary, and use a cheap candidate stage so only a few hundred pages get exact scoring. Each step costs some accuracy, so we measure it, and we only apply it to the collections that need layout awareness.

    “Does it work for Arabic?”

    I would not assume. The underlying VLMs are multilingual to varying degrees and public benchmarks are mostly English and French plus a few other languages. I'd test candidate models on our own Arabic and mixed-language pages, including right-to-left tables and stamps, and report recall by language before choosing.

    “How is contextual retrieval different from just bigger chunks?”

    Bigger chunks bring context but dilute the match and cost more at query time. Contextual retrieval keeps the chunk small and adds a short, targeted description of where it comes from, so both the keyword index and the embedding know whose revenue and which quarter. The costs are one LLM call per chunk at indexing and the risk of wrong context lines, so we audit a sample.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. A query has 12 tokens; a page has 1,030 patch vectors. How many dot products does one MaxSim score need, and which operations are max and which are sum?

    12 × 1,030 = 12,360 dot products. For each of the 12 query tokens, take the max over the 1,030 patches; then sum the 12 maxima. Across 1,000 candidate pages that is about 12 million dot products of 128-d vectors, trivial for a GPU but not for a naive scan of 100 million pages, hence the candidate stage.

    2. Compute the storage for 5 million pages at 1,030 vectors × 128 dims in 16-bit, and after pooling by 4 and binarising.

    Per page: 1,030 × 128 × 2 = 263,680 bytes; × 5 million ≈ 1.32 TB. Pooling by 4 gives about 258 vectors; binary is 1 bit per number so 258 × 128 / 8 = 4,128 bytes per page; × 5 million ≈ 20.6 GB. A reduction by a factor of 64.

    3. Why does a single mean vector lose a stamp that covers 3 patches of 48?

    The mean gives it weight 3/48 ≈ 6% of the page vector, while amounts and goods that cover many patches dominate the direction. A distractor with strong amounts and goods scores higher against a query mixing all three. MaxSim lets the stamp token match its patch at full strength.

    4. What is the difference between a bi-encoder, a cross-encoder and a late-interaction model?

    Bi-encoder: one vector per item, precomputed, one dot product; fast, coarse. Cross-encoder: reads query and item together; accurate, but must run per pair, so used for reranking. Late interaction: many vectors per item, precomputed, compared token against token at query time; in between on both accuracy and cost.

    5. Name two ways contextual retrieval can make results worse.

    The generated context can be wrong (wrong entity or period), which misdirects every query that reaches that chunk; and the added text can pull in generic words that make many chunks look alike for the query. Also, it raises indexing cost, and regenerating the context changes the index, so version it.

    6. A vendor says their visual retriever "scores 90% on ViDoRe". What do you ask?

    Which version and which subsets and languages; the metric (nDCG@5 or recall@k); how the corpus size compares with ours; whether the model saw similar data in training; what the storage per page is; and the result on a sample of our own Arabic and English documents.

    7. When would you still prefer the OCR text pipeline?

    When the documents are born-digital PDFs with a clean text layer, when you need exact quotes, filters, field extraction or audit trails, or when storage and latency budgets are tight. Often the answer is both: text as the backbone, visual retrieval as a second index for the hard pages.
