    Attacks on the Model Itself: Poisoning, Evasion and Extraction

    Contents
    Part 1

    The intuition

    Picture a new fraud analyst. Three people could defeat her.

    • The trainer who lies. Early on, someone teaches her "this pattern is fine". Later she waves it through. This is data poisoning: damage at training time, living inside the model.
    • The customer who tests the rules. A fraudster sends AED 5,000, then 12,000, then 19,000, noting which are stopped, and stays just under the line. This is evasion: the model is fine, the input is crafted.
    • The competitor who keeps asking. A fintech calls your scoring API 200,000 times and trains its own model on your answers. This is extraction (stealing the function). Coaxing a chatbot into reciting a customer's name is inversion (recovering the data).

    Banks are targets because the decision is worth money: a fraud model is a lock, a credit model is a price, a sanctions screener is a gate.

    Hold onto thisAsk of any model: who can influence what it learns from, who can submit inputs, and what do its answers reveal? The threat model (G1.1 – G1.2) should name an owner for each.
    Part 2

    How it really works

    Data poisoning (G1.3)

    Poisoning places examples in the training set to change what the model learns, like slipping wrong answers into a student's textbook. It can make the model worse overall, or change it in just one place. The sharpest form is a backdoor: normal behaviour until an input contains an attacker-chosen trigger, then the attacker's behaviour.

    Realistic routes into a bank are mundane:

    • Labels people control. Fraud labels come from disputes, chargebacks and analyst decisions. A ring can file disputes that teach the model "this device pattern is a genuine customer".
    • Scraped or purchased data. Buying expired domains that a web-scale dataset points to gives control of a small slice (Carlini et al., 2023).
    • Downloaded models and retrieval stores. A poisoned document in a RAG knowledge base needs no training and is close to indirect prompt injection.

    Simulation 1 uses label flipping on a fraud model. The attacker gets fraud-like records labelled legitimate, so the model learns that this region is safer than it is. Measure the damage against the positives, not all rows (see imbalanced data). "0.1% of rows" can mean 10% of the fraud labels, and once poison outweighs the real fraud in a region, the model stops alerting there.

    A model with 800 fraud labels is more fragile than one with 8 million. Backdoors worry people most for large language models: the attacker inserts documents with a rare trigger phrase followed by the wanted behaviour, and the model is normal otherwise, so clean tests pass.

    The 2025 surprise was scale. Souly et al. pretrained models from 600M to 13B parameters. About 250 poisoned documents installed a deliberately narrow backdoor at every size, though larger models saw about 20 times more clean data. The absolute count mattered, not the percentage.

    Defences against poisoning are mostly process, because detection is hard:

    • Provenance and access control. Know where each row and label came from and who can write it (lineage and metadata).
    • Label audits and a trusted hold-out set. Re-review samples. Keep a small curated test set attackers never touched; worse results there than on pipeline data means investigate.
    • Supply chain hygiene. Pin and hash-check downloaded models and datasets; treat third-party fine-tunes as untrusted code.

    Adversarial examples and evasion (G1.4)

    An adversarial example is an input changed slightly so the model errs while a human sees no difference, such as an image nudged by invisible noise. At a bank the usual case is black-box: the attacker only submits inputs, sees decisions, and feels along the decision boundary.

    In banking data the features are things attackers can choose: amount, timing, device, destination. A fraudster cannot set account age, but can split a payment or use a fresh device. Test with perturbations that cost the attacker something. Text and documents have versions too: transliteration against sanctions screening, altered scans, and synthetic faces and voices (deepfakes).

    Mental model: the attacker is running an experiment against your decision boundary, like a burglar rattling every window. The simulation lets you be the attacker, then the defender.

    Jitter only blurs the attacker's estimate: some land under the line, some over. Rate-limiting and treating probing as a signal removes the search itself, because each probe above the line is a declined payment from the same device or account family. A clear reason code ("declined: amount over limit for this profile") helps attackers more than a silent challenge.

    Defences for evasion accept that no model is immune:

    • Hide the boundary. Rate-limit, return decisions not scores, give uninformative errors.
    • Features that cost the attacker. Prefer hard-to-fake signals (device history, network position) over freely set ones (amount, text fields).
    • Layers, plus monitoring. Add rules, velocity limits and human review. Evasion looks like drift with an adversary behind it (drift monitoring, feedback loops).

    Model extraction and inversion (G1.5)

    Extraction is stealing the function. It is like solving for x: if every answer is a clean equation, a few answers pin everything down. APIs that return confidence scores leak simple models from very few queries (Tramèr et al., 2016). The attacker's reasons: skip the build cost, probe for blind spots offline (unlimited private probes for Simulation 3), or see your credit policy. The near case is a scoring endpoint exposed to partners.

    For a deep model the attacker trains their own model on your outputs, which is distillation without permission. An approximate copy is enough for planning evasion.

    Inversion and membership inference go after the data. Models are slightly more confident on records they trained on, so an attacker can sometimes tell whether a person was in the training set. Models that memorise can repeat personal information verbatim (memorisation and private training). This is a data-protection issue as well as security: "was this customer in the training data?" can itself be a disclosure. Check the local data-protection rules.

    Defences for extraction and inversion:

    • Less in the answer. Return a decision or coarse band, not a six-decimal probability. Give customer-level reason codes, not every feature's contribution (local explanations are a known leak).
    • Query controls. Authentication, per-client rate limits, and anomaly detection (near-identical inputs varying one feature at a time is a signature).
    • Reduce memorisation, and test it. Deduplicate, avoid raw identifiers (privacy basics), and run a membership-inference test before release.
    Part 3

    How it fails, and how to spot it

    • "Our training data is internal, so it cannot be poisoned"

      Labels come from customers, staff, vendors and past model decisions. Any can be bent.

      Spot itList every source of rows and labels and who can write to each.
    • Poisoning judged by percentage of rows

      "Only 0.1% is affected." For a rare class or a backdoor, that can be most of the positives.

      Spot itRe-express the share against the positives or one trigger, not all rows.
    • Clean test accuracy taken as proof of integrity

      A backdoored model passes clean tests by design.

      Spot itAsk for a test set the attacker could not reach, plus trigger-style tests.
    • Retraining on the model's own decisions

      If declined customers get no labels, a blind spot reinforces itself, and an approved attacker looks like a good customer.

      Spot itCheck for labels on declined and challenged cases and a random review sample (feedback loops).
    • Verbose APIs and explanations

      Exact probability, every feature contribution and errors naming the failed rule, for every caller.

      Spot itRead a response as an attacker. Could you fit a model from it? Does a decline reveal which rule fired?
    • Robustness and privacy claims without a test

      "The model is robust" (to which attack?) or "the data is locked down" (while the model trained on it is widely shared and can leak it). Random noise is a weak test.

      Spot itAsk for the threat model, an optimised attack under realistic constraints, and a membership-inference test on the released model.
    Part 4

    Self-check

    1. Name the three attack types and say, for each, when it happens and what the attacker needs.

    Poisoning: training time; influence over data, labels or a pretrained artefact. Evasion: run time; ability to submit inputs and see outcomes. Extraction: run time; query access, easier with informative outputs. Inversion and membership inference target the training data, not the function.

    2. A fraud model is trained on 1,000 fraud records and 99,000 legitimate ones. An attacker gets 100 fraud-like records labelled legitimate. Why is that worse than "0.1% of the data" suggests?

    It is 0.1% of rows but 10% of the fraud labels. What the model learns about fraud depends on the positives, so damage scales with that smaller base (Simulation 1). At 500 records, half the fraud labels are corrupted.

    3. What did the 2025 poisoning study find about dataset size, and what does it not show?

    From 600M to 13B parameters, about 250 poisoned documents installed the backdoor regardless of size, though larger models saw far more clean data. It tested one narrow backdoor, in pretraining, at modest scale. It does not show the same for larger models, more harmful behaviours or other training methods.

    4. Why can a backdoored model pass your normal test set?

    The test set lacks the trigger, so the model behaves normally. Defence needs a trusted hold-out, trigger-oriented tests and provenance, not just average accuracy.

    5. In Simulation 3, why did blocking after a few flagged probes beat adding jitter?

    Jitter blurs the line, but the attacker's estimate stays centred on the true limit. Blocking stops the search: each probe above the line is flagged, and the attacker runs out of safe attempts while still far from the limit.

    6. A scoring API returns exact probabilities. Another returns only approve or decline. Which is easier to copy, and does the second protect you?

    The exact probabilities: every score is a clean clue, so a simple model can be recovered from roughly one query per feature. With decisions only, the attacker needs many more queries, a few hundred for a 40-feature model, still easy for a script. Returning less raises the cost without stopping a determined attacker; rate limits and monitoring do the rest.

    7. Why is membership inference a concern even when the raw training data is well protected?

    The model leaks: it is more confident on records it trained on, so a querying attacker can sometimes tell if a person was in the training set, and memorising models can repeat records. Test the released model and reduce memorisation.

    8. You can pick one control for a partner-facing credit-scoring API. Which, and why?

    Authentication with per-partner rate limits and query-pattern monitoring, plus a coarse band instead of an exact score. It cuts extraction, boundary-finding and leakage at once using controls the bank already runs. Pair it with contract terms and logs.
