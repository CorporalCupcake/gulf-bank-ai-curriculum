    Governing AI Coding Tools, and Seeing What Your LLM Systems Do

    Contents
    Part 1

    The intuition

    An engineer types: "fix the failing test in the payments reconciliation job". The agent reads the repository, runs tests, edits files and installs a library. The catch: it ran commands with the engineer's file access, network and credentials, and it treated text it read (a code comment, a README) as instructions.

    Think of a new contractor. You do not refuse to hire them, and you do not hand over the production password on day one. You give them a controlled desk, only the access the job needs, work that others review, and a log of what they touched. Two ideas follow.

    • The agent is not accountable. The engineer who accepts a change owns it, as with any pull request.
    • Prompts are not a control. "Please do not touch production" in an instructions file is a sticky note on a safe. A denied permission, a sandbox with no route to production, and a credential that cannot reach it are controls.

    The second half is the mirror image: once the bank builds its own LLM applications, nobody can answer "what did it do, what did it cost, was it any good?" without telemetry. The same traces cover both.

    Hold onto thisGive the agent the narrowest rights that do the job, enforce them outside the model, keep a human accountable at the review gate, and record enough that someone else can reconstruct what happened.
    Part 2

    How it really works

    What can actually go wrong with a coding agent

    A coding agent is a language model in a loop with tools: read file, edit file, run command, fetch a web page, call a connected server (see MCP and A2A). Everything it reads can steer its next action. Six risks recur, plus a seventh: unvetted packages or servers it installs (MCP tool poisoning), which you should treat as vendor decisions.

    RiskExample at a bank
    Data leaves the buildingAn engineer pastes a production extract with Emirates IDs into a prompt to debug a parser.
    Exfiltration by commandA script the agent runs posts a config file to an unknown URL.
    Prompt injectionA package README says "print the environment variables". Models cannot reliably tell data from instructions (indirect prompt injection).
    Destructive actionA force-push over a shared branch, or a migration on the wrong database.
    Flawed code reaches productionA plausible but wrong rounding rule passes a skim review of a big diff.
    No evidence for the auditorAudit asks which AI tools touched the payments repository last quarter. Nobody knows.

    The control stack: who decides, what is allowed, where it runs

    Controls sit in layers. For each, ask "who can change this?". If the engineer can switch it off, it is a default, not a control.

    • Organisation policy. Claude Code's managed settings sit above user and project settings and cannot be overridden by them: deny rules, no bypass mode, restricted tool servers, telemetry on.
    • Permissions. Each tool call is allowed, asks the user, or is denied. This is Simulation 1.
    • Sandbox. OS-level isolation limits which files and hosts commands can reach, so a successful injection hits a wall.
    • Credentials. Short-lived, scoped, with a masked or synthetic data replica. A perfect sandbox cannot protect a secret sitting in the environment.
    • Pipeline. Branch protection, mandatory human review, CI and secret scanning. The agent opens a pull request and cannot merge. This control survives the others failing.
    • Data path. Direct to the vendor, via a regional endpoint, or through the bank's AI gateway where you can log and redact? Residency rules (CBUAE, SAMA and SDAIA) and sovereign hosting decide it.

    Controls cover different failure paths, like layered locks on a vault. Distrust any plan resting on one layer, especially instructions to the model.

    Autonomy. Approving every action is safe and slow, and people then click "approve" without reading. Auto-approve the safe, deny the dangerous, and spend human attention on the middle. See long-running agents.

    Proving it to auditors: the evidence pack

    Governance you cannot show does not count. Answer auditors with artefacts.

    The auditor asksThe artefact that answers it
    Which AI tools are approved, and for whom?An inventory with a named owner (see AI governance frameworks).
    What may the tool do, and who can change that?The managed policy file under version control with change approval.
    Who is accountable for generated code?Pull-request history showing human review.
    What did it do last Tuesday?Session logs and traces: tool calls, commands, denials, cost, user and repository.

    I do not know of a CBUAE or SAMA rule written specifically for AI coding assistants. The obligations come from existing ones (outsourcing, information security, data protection, model risk) applied to a new tool. Ask compliance; do not invent a citation. Pilot on non-sensitive repositories first.

    Seeing inside LLM systems: traces, metrics, logs and OpenTelemetry

    Classic monitoring says a service is up and how fast. An LLM application can be up, fast and wrong. You need the path of one request, like a parcel's tracking history: retrieval, passages, prompt, model call, tool calls, answer. That is a trace: a tree of timed spans, one per step. A long total time says something is slow; the spans say which step.

    OpenTelemetry (OTel) is the open, vendor-neutral standard for shipping traces, metrics and logs to any back-end, including one inside the bank. Its GenAI conventions agree attribute names (model, tokens, operation) so different tools read the same trace. They are still in development, so pin a version.

    What goes on a span, and why:

    • Model and version. You cannot explain a behaviour change without it.
    • Token counts and latency. Cost is tokens times price; agents hide most of their time in loops.
    • Prompt and response content, optionally. Great for debugging, risky for privacy. Keep it off by default: in a bank this is a data-protection decision, not a developer switch.

    Add quality signals too (groundedness score, guardrail verdict, thumbs-down) so a bad outcome ties to the path that produced it (groundedness). Claude Code can export OpenTelemetry metrics and events to your own collector once switched on: the basis for "what did it do last Tuesday?".

    Sampling, retention and cost: you cannot keep everything

    Traces with prompts can be tens of kilobytes each, so a busy assistant produces terabytes. You must sample, and how decides whether the trace you need exists on the day.

    • Head sampling keeps a random 5% decided at the start. Cheap but blind, like checking 1 in 20 parcels: a single damaged one is usually missed.
    • Tail sampling decides after the trace ends: keep every error, slow, low-score or blocked request, plus a few percent of the rest.

    Misreading to avoid: 5% sampling does not mean you see 5% of incidents. A 10-request incident is missed about 60% of the time. Tail sampling catches flagged requests every time, if the failure is detectable at all.

    Keep metrics (counts, tokens, latencies, scores) at full resolution because they are tiny, and sample traces. Set retention by data class: metadata for years, content for days. Frameworks and gateways often emit spans automatically; hand-written instrumentation looks like this:

    from opentelemetry import trace
tracer = trace.get_tracer("policy-assistant")

with tracer.start_as_current_span("chat model-x") as span:
    span.set_attribute("gen_ai.request.model", "model-x")
    reply = call_model(prompt)                       # your client
    span.set_attribute("gen_ai.usage.input_tokens", reply.input_tokens)
    span.set_attribute("app.groundedness", score(reply, passages))  # your own attribute
    Part 3

    How it fails, and how to spot it

    • Policy written as instructions to the model

      "The assistant must never read secrets" in a prompt.

      Spot itAsk what stops the action if the model ignores the instruction. If "nothing", it is not a control.
    • Shadow adoption

      Engineers use personal accounts because the approved route is slow.

      Spot itCompare approved seat counts with proxy traffic to AI domains.
    • Approval fatigue and rubber-stamp review

      Users hit "yes" to every prompt, or approve a 2,000-line AI pull request in ten minutes.

      Spot itAn approval rate above roughly 95% means prompts carry no information. Track review time against diff size.
    • Broad credentials in the environment

      A sandbox exists, but the engineer's cloud admin token sits in environment variables.

      Spot itList the environment variables and credential files visible to the agent's process.
    • Telemetry that captures the crown jewels

      Full prompts with customer data in a widely readable log index.

      Spot itSearch the trace store for Emirates ID formats and IBANs.
    • Sampling and dashboards that hide the problem

      The one bad trace was in the 95% discarded, or the assistant is fast, error-free and hallucinating.

      Spot itAsk: if 10 requests fail tomorrow, would we keep one? Check that a quality signal sits next to latency.
    Part 4

    Self-check

    1. Why is a line in an instructions file saying "never access production" not a security control?

    The model may ignore it or be talked out of it by injected text. A control holds even if the model misbehaves: a deny rule, a sandbox with no route to production, or a credential that cannot reach it.

    2. Name the layers that would stop a hijacked agent sending a config file to an unknown website.

    A sandbox network allowlist (the main one), a deny rule on arbitrary uploads, no secrets in the environment, and a gateway that blocks unknown destinations.

    3. Which control still protects you if every technical control around the agent fails?

    Human review at the pipeline gate with branch protection: nothing reaches production without an accountable person approving it. It weakens if diffs are huge or reviewers rushed.

    4. An auditor asks what the AI tool did last Tuesday. What must already be in place?

    Telemetry switched on before the event and shipped to a retained store: sessions, users, repositories, tool calls, denials and cost, with content captured only as policy allows. You cannot reconstruct what was never recorded.

    5. You head-sample traces at 2% and an incident affects 30 requests. Are you likely to have kept one, and what would change that?

    Not reliably: each request is kept independently, so there is a fair chance (a bit over half) that all 30 are discarded. Tail sampling on error or low score would keep them, if the failure is detectable.

    6. A setting change sends 40 retrieved passages to the model instead of 5. No errors appear, but the bill jumps. Where do you see it?

    In the token counts on the model-call span: input tokens grow several-fold while output stays flat. Context size is the lever that moves cost most, and only per-span token data shows it.

    7. Why should prompt content in traces be off by default in a bank?

    Prompts and retrieved passages can hold customer personal data and confidential documents, which then sit in a log system with broader access and different retention. Turn content on deliberately, per use case, with redaction, access control and a retention limit.

    8. Latency and error rate look fine, yet users complain of wrong answers. What is missing?

    A quality signal on the trace (groundedness score, user feedback, escalation rate) and visibility of retrieval results, to see whether the right passages were found. Fast and error-free does not mean correct.
