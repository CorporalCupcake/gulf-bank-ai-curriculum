    Agent Memory and Planning

    Part 1

    What agent memory is

    In one sentenceAn LLM agent remembers nothing by itself: before every step, the surrounding code rebuilds one page of text for it to read, and "memory" is everything that decides what goes on that page.

    Picture a capable contractor who wakes with amnesia every few minutes. All they have is one sheet of paper slid under the door. If the sheet says what the job is, what is done and the customer's hard conditions, they carry on smoothly. If it is cluttered, or a condition has fallen off, they do competent work on the wrong job.

    That sheet is the context window: the text the model reads on a single call. Planning is the same problem from the other side: how the agent splits a big job into steps it can check.

    Running example. An agent refreshes a customer's KYC file ("know your customer" records) over 40 tool calls. At step 1 the relationship manager says: "do not phone the owner." By step 40 that sentence is buried under pages of tool output.

    Only the sheet is "in" the model. Everything else is a database or file plus a write path (what decides to save) and a read path (what decides to fetch). Most memory failures are failures of one of those two paths, not of storage.

    Part 2

    How it differs from other things

    • Not the model's training. The model's built-in knowledge is frozen. Memory is text you hand it each time.
    • Not a bigger window. A larger window delays the clutter problem. Every step still resends everything, costs grow, and models use the middle of a long context less reliably than the start and end.
    • Not the system of record. Core banking and the KYC system own the truth. Agent memory is a sticky note, not the ledger.

    Four kinds of memory are worth naming.

    Part 3

    How the sheet is kept useful

    Every step adds text, so the sheet fills up. Teams manage it in four steps.

    1. Pin the hard rules. Put must-keep rules ("do not phone the owner") in the system prompt, in code, or in a fixed note that is on every sheet.
    2. Trim what is old. A sliding window keeps only the last few steps. Cheap, but it silently drops early instructions.
    3. Compact when full. A model summarises the history and the run restarts from the summary. Lossy, and nobody sees what was dropped.
    4. Write notes outside the window. The agent saves key facts to a file as they appear and re-reads it. Only as good as what it writes.

    Notes beat summaries for facts that must survive: a note is written when the fact appears, a summary is written later, in a hurry. Compaction also compounds: if a summary keeps a fact 85% of the time, after four rounds about half the facts are gone.

    Long-term memory: write, fetch, forget

    • Write short, dated items ("card blocked abroad, fixed by travel notice", with source and a link to the full record), not raw transcripts.
    • Fetch by search, usually embeddings, plus hard filters such as customer ID. Filter first, then search.
    • Decide what wins. Addresses change. An append-only store contradicts itself, so set rules for which version is used and when items expire.
    • Rank by three signals: how recent, how relevant to now, how important. Any one alone fails: recency finds chit-chat, relevance finds similar words about the wrong point, importance floods the sheet with old drama.
    Part 4

    Planning: splitting a job into steps

    In one sentenceA plan is a list of steps from here to done, and it only makes a long task reliable if you check between the steps.

    There are three common styles, often mixed.

    • No explicit plan. Think, act, read the result, repeat. Flexible, but can wander or lose the goal.
    • Plan first, then execute. Easy to review and approve, but brittle if the real data differs from what the plan assumed.
    • Plan, act, replan. Revise when a result contradicts the plan. The usual choice for real work.

    A convincing plan is not evidence that it works. The case for steps is that each one can be checked, gets a small clean sheet, and is a place for a human approval. Good steps have a testable "done" condition, and irreversible actions come last.

    Errors multiply along a chain. If each step is right 98% of the time, 40 steps in a row are all right only about 45% of the time. Splitting a job into more steps does not change that. Checks at the boundaries do.

    A check can be code (the total reconciles, the IBAN is valid), a lookup against the source, a second model, or a person. Code checks are cheap and trustworthy. A model checking its own work tends to repeat its own misreading.

    Part 5

    How to read a design, and what to use

    Ask of any agent: what is on the sheet at step 40, what decides what is saved, and what happens if the agent's copy is wrong?

    • Rule at step 1, trap at step 40. If the agent still honours the rule, memory works. Losing it raises no error: the agent acts as if it was never told.
    • Escalated versus silently wrong. "Stopped and asked for help" is good. "Finished, wrongly" is the outcome to measure and minimise.
    • Replan triggers. A step fails twice, a tool returns something unexpected, or a budget is exceeded.

    Show the formula

    P(all steps right) = cn, where c is the chance each step is right and n is the number of steps. At c = 0.98 and n = 40: 0.9840 ≈ 0.45. The chance falls fast because each step multiplies in another small risk.

    In banking, every memory item is customer data with retention and deletion duties, and a false statement the agent read in an email can be saved as "something the bank knows". Record the source, time and writer of each memory, and read regulated facts from the system of record at the time of use.

    Part 6

    Common mistakes and quick check

    • Hard rules living only in the chat history

      They drop out when the window slides or is summarised. Pin them in the system prompt, in code or in a fixed note.

    • Mixing customers' memories

      Searching by similarity before filtering can surface one customer's details in another's conversation. Filter by customer ID first. Treat leakage as a privacy incident.

    • Keeping a copy of regulated facts as truth

      A stored risk rating goes stale. Read it from the owning system when needed.

    • Splitting into steps with no checks

      A 24-step plan without checks is exactly as unreliable as one big step, and now it is slower.

    1. Why does an agent's bill grow faster than its number of steps?

    Each step re-reads the whole history so far, so later steps cost more than earlier ones.

    2. A summary keeps each fact 85% of the time. Why is that not reassuring?

    The risk compounds across rounds: after four compactions about half the facts are gone, with no warning. Put must-keep facts in a note or store.

    3. Which belongs in agent memory: a customer's current risk rating, or "prefers WhatsApp"?

    The preference, with source and date. The risk rating is owned by another system, so read it through a tool instead of copying it.

    4. A job has 24 actions, each 98% reliable. You split it into 24 steps with no checks. What changed?

    Nothing: it is still right about 62% of the time (0.9824). Splitting helps only when the boundaries are used for checks, retries or approval.

    5. Why prefer an escalation to a finished-but-wrong result?

    An escalation costs a person's time. A silent error reaches a customer, a filing or a ledger.
