    Feature Stores and Data Contracts

    Part 1

    What a feature store is

    In one sentenceA feature store defines each model input once, keeps it in two places (full history for training, latest value for live scoring), and a data contract is the written promise from the team that supplies the raw data.

    A feature is one input to a model, such as "transactions on this card in the last 24 hours". Say a fraud model's top feature is built in the warehouse with SQL and scores AUC 0.98. Live scoring must answer in under 50 milliseconds, so engineers rewrite the feature in Java.

    It looks the same, but it is not. The SQL excluded the current transaction and the Java includes it. One uses Gulf time and the other UTC. Nobody wrote a bug, and the model quietly performs worse. This is training-serving skew: the model sees different inputs live than it learned from.

    How it differs from other things

    • A feature table is one team's table plus shared code. That is enough for a few batch models.
    • A feature store adds a catalogue, two stores and automatic point-in-time joins. It pays off when many models share features, decisions are real time, or audit must show what any past score used.
    • Data quality checks catch bad data after it arrives. A data contract is agreed before it ships.
    Part 2

    How it works

    1. Register the feature: name, entity (customer or card), logic, owner and how fresh it promises to be.
    2. Materialise it. Jobs write the same definition to the offline and online stores.
    3. Build training sets with a point-in-time join (below).
    4. Serve the latest value from the online store at decision time.
    5. Check the data on the way in, and pin the feature version in the model's metadata.

    The as-of join

    For each training row, use the feature value the live system would have returned at that moment. The key is availability time: when you could use the value, not the time it describes. A nightly job summarising Tuesday finishes at 02:00 on Wednesday, so it was not usable on Tuesday evening.

    • Latest would pick C, which already contains the fraud burst. That is leakage.
    • Nearest can also pick a snapshot taken after the event.
    • As-of matches what the online store would have said, staleness included. That is the point: the model should learn from inputs it will really get. In pandas the tool is merge_asof.

    Part 3

    How to read freshness and checks

    Matching training is not the same as being fresh. A feature can match perfectly and still be uselessly stale, like an accurate newspaper from last week. A value refreshed every Δ minutes is on average half of Δ old when read, up to Δ at worst, plus pipeline delay.

    Salary-credit average, refreshed daily
    Fine. It changes monthly.
    "Card used in three countries in an hour", refreshed every 15 minutes
    About 7 minutes old on average, up to 15. A rule that must react within 5 minutes cannot rely on it. It needs a streaming feature.

    Data quality checks

    Upstream data is often wrong: a core-banking release changes a column, or a vendor feed stalls. The model does not crash. It just consumes garbage. Run these cheap checks on each batch:

    • Schema: are the columns and types as agreed?
    • Completeness: is the missing share under, say, 1%?
    • Range: is 0 < amount ≤ 200,000 AED?
    • Uniqueness: are keys unique, so a replayed message cannot double a count?
    • Accepted values: is every channel one we know?
    • Freshness: is the newest event under 15 minutes old?
    • Distribution: does the shape match a reference? A population stability index below 0.2 is a common threshold.

    Give every check an action: block the load and keep yesterday's values, warn and continue, or quarantine bad rows. A check nobody acts on is noise. If amounts suddenly arrive in fils instead of dirhams, the range and distribution checks fire. Null, uniqueness and freshness checks do not, because the values are present, unique and recent.

    Data contracts

    A data contract is a machine-readable promise the producing team publishes and your pipelines depend on, like a delivery service agreement. It covers three things.

    • Schema and meaning: columns, types, units (AED or fils?), time zone, how reversals appear.
    • Quality and service levels: maximum null share, freshness, delivery time.
    • Ownership and change rules: a named owner, how breaking changes are announced, how long the old version keeps running.

    The contract lives in a repository and is tested against the producer's code, so a release that renames a column fails its own tests, not your model at 3am.

    Part 4

    Which to use

    ToolStopsMisses
    Feature storeSkew and leakage from different code or joinsBad upstream data
    Quality checksBroken or impossible dataPlausible shifts, such as 15% drift
    Data contractSurprise upstream changesTeams that never signed it
    Drift monitoringSlow, plausible changeNothing instant
    • Strong at: removing a whole class of silent failure by design, and answering audit questions about past scores.
    • Weak at: cost and effort. Buying a platform while definitions are still copied by hand fixes nothing.

    In banking, a regulator may ask exactly which inputs produced a past decision, so each feature needs an owner, a version and an availability time.

    Part 5

    Common mistakes and quick check

    • Two implementations of one feature

      SQL in training and Java in serving differ in rounding, time zones and null handling. Log served features and recompute them offline to compare.

    • Joining on the wrong time

      Joining on the latest value, or on when a value describes rather than when it arrived, leaks the future. AUC looks great and live results do not.

    • A stale online store

      A stream stalls and the last value sits there for hours, looking normal. Alert when a served value's age exceeds its promise.

    • Passing checks that pass nonsense

      A 15% drift in amounts passes every rule. Add drift monitoring and reconcile against an independent source such as the general ledger.

    1. What is training-serving skew, and why does it raise no error?

    The model sees live features that differ from its training features. Every value is still valid, so nothing fails; the model just gets worse.

    2. A nightly job finishes Tuesday's totals at 02:00 Wednesday. A fraud label is at Tuesday 20:00. Which time does the as-of join use?

    Availability time (Wednesday 02:00). The label then gets Monday's totals, which is what the live system had. Using the date the totals describe would leak.

    3. Why is the online store not just the offline store with a cache?

    Online holds only the latest value per entity for millisecond lookups. Offline holds full history for big scans. A cache over a warehouse is still slow on a miss.

    4. All checks pass, yet fraud losses rise. What else do you need?

    Drift monitoring on features and scores, reconciliation against an independent source, and performance monitoring once labels mature. Checks catch breaks, not plausible shifts.

    5. What goes in a data contract for a customer-income feed?

    Currency and period (monthly or annual, gross or net), what null means, the income definition, freshness, accepted ranges, owner, change policy and personal-data classification.
