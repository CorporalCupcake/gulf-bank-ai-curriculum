    Same Features Live as in Training: Feature Stores, Consistency and Data Contracts

    Why a model that scored 0.98 AUC in the notebook can quietly drop to 0.85 in production, how feature stores and as-of joins prevent it, and how checks and contracts stop broken upstream data from ever reaching a model.

    Contents

    The whole lesson in one sentenceA model is only as good as the match between the features it learned from and the features it is fed live, so define each feature once, compute it point-in-time correctly, serve it fresh enough for the decision, and make the data's producers promise (and be checked on) what they deliver.

    Part 1

    The intuition

    A data scientist builds a card-fraud model. A top feature is transactions on this card in the last 24 hours, computed in the warehouse with a SQL window. AUC is 0.98. Engineers must score each transaction in under 50 ms, and a warehouse query takes seconds, so they rewrite the feature in Java over a cache refreshed every few minutes. It looks the same. It is not:

    • The SQL window excluded the current transaction; the Java one includes it.
    • The SQL used Gulf Standard Time midnight; the cache uses UTC.
    • The SQL saw late-arriving records; the cache never does.

    Nobody wrote a bug. Two implementations of one idea drifted apart, like two cooks following the "same" recipe from memory. Live inputs are shaped slightly differently from training, and the model quietly performs worse. This is training-serving skew.

    The mirror image is a wrongly built training table. If last Tuesday's fraud label is joined to the latest feature value, the feature includes the fraud burst itself. The model learns a signal that will not exist at decision time. This is the leakage of F3.1, seen as plumbing.

    A feature store answers both: each feature is defined once, computed one way, stored twice (big history for training, fast copy for serving), and joined to labels as of each decision. Data contracts and quality checks answer a third failure: an upstream system changes something and the feature silently turns to garbage. All three keep one promise: the numbers in front of the model mean what the model thinks they mean.

    Nothing here is "broken": no error, no failed job, and the model still returns numbers between 0 and 1. That is why skew is dangerous, and why design that makes skew impossible beats debugging it later.

    Hold onto thisThree promises make a model trustworthy in production: the feature is computed the same way in training and serving (consistency); it uses only what was known at decision time (point-in-time correctness); and upstream data is what you expected (quality and contracts). A feature store enforces the first two. Checks and contracts enforce the third.
    Part 2

    How it really works

    What a feature store is made of

    A feature store is a shared pantry: each ingredient is defined once and both kitchens (training and live) use it. It has five parts.

    • Registry. Catalogue of definitions: name, entity (customer, card, merchant), logic or source, type, owner, freshness promise, description. One definition feeds training and serving, which ends the "two implementations" problem.
    • Offline store. Full history, in warehouse or lakehouse tables (P1.1 – P1.2). Big, cheap, slow. Builds training sets and backfills.
    • Online store. Latest value per entity, in a key-value database (Redis, DynamoDB, Cassandra) with single-digit-millisecond lookups. Small, fast, costly per gigabyte. Used at decision time.
    • Materialisation. Batch jobs (hourly or nightly) and streaming jobs (per event) that write the same definition to both stores. This produces consistency.
    • Point-in-time retrieval API. "For each (entity, timestamp, label) row, give the feature values known at that timestamp." The store does the as-of join so no analyst reinvents it wrongly.

    How a feature is produced decides how hard consistency is.

    Feature kindExampleHow it is computedConsistency risk
    BatchAverage monthly salary credit, last 6 monthsNightly job on the warehouse, pushed to the online storeLow. Staleness of up to a day is acceptable for slow-moving facts.
    Streaming / windowedCard transactions in the last 10 minutesStream processor updates on every eventMedium. Training must replay the same window logic over history.
    On-demand (request-time)This amount ÷ customer's usual amount; distance from homeComputed inside the request from the request plus stored valuesHigh unless the same code runs in training. Best handled by one shared function.
    EmbeddingsMerchant vector, document vectorProduced by a model, stored like any featureHigh. If the embedding model changes, old and new vectors are not comparable. Version them.

    Not every bank needs a feature-store product. A few batch models get most of the value from a disciplined feature table, a shared transformation library and as-of joins. A product pays off when many models share features, real-time decisions need fresh values, or audit needs to show exactly what any past score used.

    Point-in-time correctness: the as-of join

    Think of a school report written on Friday: it must not be used to predict Monday's mark. For each training row (a label at time e, the transaction being scored), take the feature value the live system would have returned at e. Features are stored as snapshots: entity, value, event time, and the time the value became available. Join each entity to the latest snapshot whose availability time is at or before e:

    SELECT l.txn_id, l.card_id, l.event_ts, l.is_fraud,
       f.txn_count_24h
FROM labels l
LEFT JOIN LATERAL (
    SELECT txn_count_24h
    FROM card_features f
    WHERE f.card_id = l.card_id
      AND f.available_ts <= l.event_ts   -- not event_ts of the feature, when it arrived
    ORDER BY f.available_ts DESC
    LIMIT 1
) f ON TRUE;

    The key is available_ts: when you could use the value, not the time it describes. A nightly job summarising Tuesday finishes at 02:00 Wednesday, so it was not usable Tuesday evening. In pandas use merge_asof (F11.2). The failure is joining on the latest row, or on date alone.

    As-of equals serving: if the join takes the latest usable snapshot, the training row is what the online store would have said, staleness included. That is intended; a model should learn from the inputs it will really get, not idealised fresh ones. Also, late corrections (a backdated chargeback, a restated balance) make offline history cleaner than anything live ever saw. "Bitemporal" tables, which keep both event time and recorded time, let you reproduce what was known then.

    Freshness, latency and how fresh is fresh enough

    Consistency is not freshness: a feature can match perfectly and still be uselessly stale, like a perfectly accurate newspaper from last week. Freshness should match how fast the thing you detect moves.

    • Salary-credit average changes monthly. Daily batch is plenty.
    • "Card used in three countries in an hour" changes in minutes. With a 15-minute refresh, the attacker has finished.
    • Credit-limit utilisation for an overnight collections list: hours are fine.

    A feature materialised every Δ minutes is on average Δ/2 old when read, up to Δ at worst, plus pipeline delay. Streaming everything costs complexity and money, so choose per feature. The lookup itself also has a budget: with 100 ms available, 40 serial reads at 5 ms each take 200 ms. Stores therefore fetch a whole feature set per entity in one call and keep vectors small.

    age of value when read≈Δ2+ℓ

    Δ is the materialisation interval, ℓ the pipeline delay between event and write. A 15-minute batch with a 2-minute delay averages 9.5 minutes old when read and reaches 17 at worst. Read it as a bound on how early any rule on that feature can fire.

    Data quality checks: what to test and where

    Upstream data is often wrong: a core-banking release changes a column, a vendor feed stalls, a join silently drops customers. The model does not crash; it consumes garbage. Quality checks are cheap tests, like a smoke alarm, run on each batch or stream window before features are used. The families below come from Great Expectations, Soda, Deequ and Google's data validation work.

    FamilyQuestionExample for a transactions table
    SchemaAre the columns and types as agreed?amount is decimal, channel exists, no new columns unannounced
    CompletenessHow much is missing?Null share of amount ≤ 1%; row count within ±30% of the same weekday last month
    Validity / rangeAre values possible?0 < amount ≤ 200,000 AED; currency code in the ISO list
    UniquenessAre keys unique?txn_id has no duplicates (a replayed message would double a feature)
    Accepted valuesAre categories known?channel in {POS, ECOM, ATM, APP}; a new "WALLET" must be reviewed
    FreshnessIs the data current?Newest event is under 15 minutes old
    DistributionDoes the shape match what we know?Population stability index of amount below 0.2 against a reference (F7.7)
    ReferentialDo joins find their partners?99.5% of transactions match a known customer

    Checks sit at three points: ingestion (stops bad raw data cheaply), after transformation (catches your own join bugs) and at feature-serving time (catches an out-of-range value in one request; use a safe default or fallback). Each check needs a decision attached: block the load and keep yesterday's values, warn and continue, or quarantine the bad rows. A check nobody acts on is noise.

    Thresholds are the hard part. Too tight and the team ignores alerts; too loose and nothing is caught. Start from history, flag a high percentile of usual variation, and treat each false alarm as a chance to improve the check.

    Data contracts: moving the promise upstream

    A data contract is the agreement made before the data ships. Checks catch problems after the producer ships them; a contract is a machine-readable promise the producer publishes and your pipelines depend on. Think of a delivery service-level agreement: the supplier states what arrives, in what shape, by when. It covers:

    • Schema: columns, types, nullability, units (AED or fils?), time zone.
    • Semantics: what each field means, how a transaction is defined, how reversals appear.
    • Quality and service levels: maximum null share, freshness, delivery time, retention.
    • Ownership and change rules: a named owner, how breaking changes are announced and versioned, how long the old version runs.
    • Classification: personal data, residency limits, who may access (G2).
    dataset: core_banking.card_transactions
version: 2.1
owner: payments-data@bank.example
schema:
  - name: txn_id        type: string   required: true   unique: true
  - name: amount        type: decimal  unit: AED        required: true
  - name: event_ts      type: timestamp tz: UTC
  - name: channel       type: string   allowed: [POS, ECOM, ATM, APP]
quality:
  - freshness: event_ts within 15 minutes
  - null_share(amount) <= 0.01
change_policy: breaking changes announced 30 days ahead, two versions run in parallel

    The point is the process: the contract sits in a repository and is validated in CI against the producer's code, so a release that renames a column fails its own tests, not your model at 3 a.m. Open specifications exist (the Open Data Contract Standard from the Bitol project), and quality tools can turn contract clauses into executable checks. Limit: a contract binds only the teams that sign it, and needs a producer who treats it as part of the job. At many banks the hard part is organisational.

    Part 3

    How it fails, and how to spot it

    • Two implementations of one feature

      SQL in training, Java in serving. Rounding, time zones, window edges and null handling all differ.

      Spot itLog serving-time features and recompute them offline for the same transactions. The difference should be zero or explained.
    • Joining on the latest value

      Training rows get feature values from after the label. AUC is gorgeous, live performance is not.

      Spot itAny join on customer ID alone, or on date without time, is suspect. Compare offline AUC with a forward-in-time test.
    • Joining on when a value describes, not when it arrived

      A nightly job writes Tuesday's totals at 02:00 Wednesday, but the training set treats them as available Tuesday.

      Spot itAsk for each feature's availability timestamp. If only an event timestamp exists, assume leakage.
    • Silent defaults

      A missing feature becomes 0 online and NaN offline (or the reverse). The model learned that NaN means something.

      Spot itCompare missing rates per feature, offline and live. Never missing online but often missing in training is a warning.
    • Stale online store

      A stream stalls; the last value sits there for hours, looking normal.

      Spot itTrack the age of each served value and alert when it exceeds the promise.
    • Upstream change nobody told you about

      A core system release switches amounts to fils, adds a currency, renames a code.

      Spot itRange and accepted-value checks at ingestion, a contract with a change policy, an on-call owner.
    • Checks with no owner or no action

      Hundreds of alerts, all muted.

      Spot itFor every check, name who is paged and whether the pipeline blocks. Review which fired last quarter.
    • A check suite that passes plausible nonsense

      A slowly drifting definition or a 15% shift in amounts passes every rule.

      Spot itAdd distribution monitoring on features and outputs (F7.7), and reconcile against an independent source such as the general ledger.
    • Feature versions that change under a model

      Someone fixes a definition; the model, trained on the old version, now receives the new one.

      Spot itPin feature versions in the model's metadata. A change means a new version and a retraining plan.
    • Buying a platform to fix a process

      The store goes live but definitions are still copied by hand and nobody owns them.

      Spot itAsk how many models share each feature, who approves a change, and how it is rolled out.
    Part 4

    Self-check

    1. What is training-serving skew, and why does it not raise an error?

    The model sees live features that differ from its training features (different code, data or timing). Every value is still valid and in range, so nothing fails; the model just gets worse. You find it only by comparing live inputs with offline recomputation, or by watching performance.

    2. A nightly job finishes writing Tuesday's customer totals at 02:00 on Wednesday. A fraud label occurred Tuesday 20:00. Which timestamp should the as-of join use, and what goes wrong otherwise?

    Availability time (Wednesday 02:00). The Tuesday 20:00 row then gets Monday's totals, which is what the live system had. Joining on the date the totals describe gives values not yet available: a leak.

    3. A feature is refreshed every 30 minutes with a 3-minute pipeline delay. How old is it when read, on average and at worst?

    Average Δ/2 + ℓ = 15 + 3 = 18 minutes. Worst case 30 + 3 = 33. A rule needing a signal within 5 minutes cannot rely on it.

    4. Why is the online store not just the offline store with a cache in front?

    Online holds only the latest value per entity in a key-value system built for millisecond lookups. Offline holds full history in analytical tables built for large scans. The same definitions fill both, but the access patterns are opposite. A cache over a warehouse is still slow on a miss and cannot do windowed updates.

    5. Name two checks that would catch amounts suddenly arriving in fils instead of dirhams, and one that would not.

    The range check (maximum amount) and the distribution check (PSI against a reference) fire. Null-rate, uniqueness and freshness checks do not: values are present, unique and recent.

    6. Your quality checks all pass, yet fraud losses rise and the model's average score has changed. What other safeguards should you have?

    Drift monitoring on features and scores (F7.7), reconciliation against an independent source, logged served features compared with offline, and performance monitoring once labels mature. Checks catch breaks, not slow or plausible shifts.

    7. A colleague proposes recomputing training features from the freshest, corrected history. What is the risk?

    The model trains on inputs cleaner than anything it will get live (late data included, corrections applied), so training looks better than serving. Use what was known at the time, or log served values for later training.

    8. What goes in a data contract for a customer-income feed used by a credit model?

    Schema and units (currency, monthly or annual, gross or net), nullability and what null means, source and definition of income, update frequency and freshness, accepted ranges, owner, change policy (notice period, versioning), personal-data classification and access rules.
