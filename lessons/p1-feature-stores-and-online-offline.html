    Same Features Live as in Training: Feature Stores, Consistency and Data Contracts

    Why a model that scored 0.98 AUC in the notebook can quietly drop to 0.85 in production, how feature stores and as-of joins prevent it, and how checks and contracts stop broken upstream data from ever reaching a model.

    Contents

    The whole lesson in one sentenceA model is only as good as the match between the features it learned from and the features it is fed live, so define each feature once, compute it point-in-time correctly, serve it fresh enough for the decision, and make the data's producers promise (and be checked on) what they deliver.

    Part 1

    The intuition

    A data scientist builds a card-fraud model. One of her best features is number of transactions on this card in the last 24 hours. She computes it in the data warehouse with a SQL window function over a training table. AUC is 0.98. The model is handed to engineers, who must score each transaction in under 50 milliseconds. A warehouse query takes seconds, so they rewrite the feature in the payments service, in Java, counting from a cache that is updated every few minutes. It looks the same. It is not.

    The SQL window ended at the transaction time, exclusive of the transaction itself. The Java version includes the current transaction. The SQL treated midnight in Gulf Standard Time; the cache uses UTC. The SQL saw late-arriving records; the cache never does. Nobody wrote a bug. Two implementations of one idea drifted apart. Live, the model sees inputs shaped slightly differently from anything it trained on, and quietly performs worse. This failure has a name: training-serving skew.

    Its mirror image happens when the training table is built wrongly. If the label for last Tuesday's fraud is joined to the latest value of the feature, the feature includes what happened after the fraud, including the fraud burst itself. The model "learns" a signal that will not exist at the moment of the decision. That is the leakage of F3.1, now seen as a plumbing problem.

    A feature store is the platform answer to both. It is a place where each feature is defined once, computed one way, stored twice (a big history for training and a fast copy for serving), and joined to labels as of the moment of each decision. A data contract and data quality checks are the answer to a third failure: the upstream system changes something, and the feature silently turns to garbage. Both are about the same promise: the numbers in front of the model mean what the model thinks they mean.

    Note what did not change: nothing is "broken". No error is raised, no job fails. The model still returns numbers between 0 and 1. That is why skew is dangerous, and why this lesson cares more about design that makes skew impossible than about debugging it afterwards.

    Hold onto thisThree promises make a model trustworthy in production: the feature is computed the same way in training and serving (consistency); it uses only what was known at decision time (point-in-time correctness); and what arrives upstream is what you expected (quality and contracts). A feature store is one way to enforce the first two. Checks and contracts enforce the third.
    Part 2

    How it really works

    What a feature store is made of

    Strip away the product names and a feature store has five parts.

    • A registry. A catalogue of feature definitions: name, entity (customer, card, merchant), the logic or source, the data type, the owner, the freshness promise, a description a human can read. The same definition feeds training and serving. This is what ends the "two implementations" problem.
    • An offline store. The full history, usually tables in the warehouse or lakehouse (P1.1 – P1.2). Big, cheap, slow. Used to build training sets and to backfill.
    • An online store. The latest value per entity, in a key-value database built for single-digit-millisecond lookups (Redis, DynamoDB, Cassandra and similar). Small, fast, expensive per gigabyte. Used when a decision is made.
    • Materialisation (the pipes). Jobs that compute features and write them to both stores: batch jobs that run every hour or night, and streaming jobs that update on every event. Materialising the same definition to both sides is what produces consistency.
    • A point-in-time retrieval API. "Give me, for each (entity, timestamp, label) row, the feature values as they were known at that timestamp." The store does the as-of join so each data scientist does not reinvent it, wrongly.

    Feature types differ in how they are produced, and that decides how hard consistency is.

    Feature kindExampleHow it is computedConsistency risk
    BatchAverage monthly salary credit, last 6 monthsNightly job on the warehouse, pushed to the online storeLow. Staleness of up to a day is acceptable for slow-moving facts.
    Streaming / windowedCard transactions in the last 10 minutesStream processor updates on every eventMedium. Training must replay the same window logic over history.
    On-demand (request-time)This amount ÷ customer's usual amount; distance from homeComputed inside the request from the request plus stored valuesHigh unless the same code runs in training. Best handled by one shared function.
    EmbeddingsMerchant vector, document vectorProduced by a model, stored like any featureHigh. If the embedding model changes, old and new vectors are not comparable. Version them.

    Not every bank needs a product called a feature store. A team with a handful of batch models can get 80% of the value with a disciplined feature table in the warehouse, a shared transformation library, and as-of joins. The product earns its cost when many models share features, when real-time decisions need fresh values, and when audit demands that you can show exactly what any past score was based on.

    Point-in-time correctness: the as-of join

    For each training row, a label at time e (the transaction being scored), you want the feature value that the live system would have returned at e. Features are stored as snapshots: (entity, value, event time, and the time the value became available). The right join takes, per entity, the most recent snapshot whose availability time is at or before e:

    SELECT l.txn_id, l.card_id, l.event_ts, l.is_fraud,
       f.txn_count_24h
FROM labels l
LEFT JOIN LATERAL (
    SELECT txn_count_24h
    FROM card_features f
    WHERE f.card_id = l.card_id
      AND f.available_ts <= l.event_ts   -- not event_ts of the feature, when it arrived
    ORDER BY f.available_ts DESC
    LIMIT 1
) f ON TRUE;

    The key word is available_ts: the time you could use the value, not the time it describes. A nightly job that summarises Tuesday finishes at 02:00 on Wednesday; it was not usable on Tuesday evening. The pandas version is merge_asof (see F11.2). The failure is joining on the latest row, or on the date alone.

    Two details worth remembering. First, as-of equals serving: if the join takes the latest usable snapshot, the training row is what the online store would have said, staleness included. That is the point. A model should learn from the inputs it will really get, not from idealised fresh ones. Second, when late data is corrected after the fact (a backdated chargeback, a restated balance), the offline history may be cleaner than anything live ever saw. Stores that keep both the event time and the time the value was recorded ("bitemporal" tables) let you reproduce what was known then.

    Freshness, latency and how fresh is fresh enough

    Consistency is not freshness. A feature can be perfectly consistent and uselessly stale. The right freshness depends on how fast the thing you detect moves.

    • A salary-credit average changes monthly. Daily batch is plenty.
    • "Card used in three countries in an hour" changes in minutes. If the online store updates every 15 minutes, the attacker has already finished.
    • Credit limit utilisation for an overnight collections list: hours are fine.

    On average a feature materialised every Δ minutes is Δ/2 minutes old when read, and up to Δ old at worst, plus pipeline delay. The cost of streaming everything is complexity and money, so you choose per feature. The second constraint is the lookup itself: if a decision has a 100 ms budget, reading 40 features from the online store at 5 ms each, serially, is already 200 ms. Stores fetch a whole feature set for an entity in one call, and keep feature vectors small, for this reason.

    age of value when read≈Δ2+ℓ

    Δ is the materialisation interval and ℓ the pipeline delay between the event and the write. A 15-minute batch with a 2-minute delay has values that are on average 9.5 minutes old when read, and up to 17 minutes. Read it as a bound on how early any rule built on that feature can possibly fire.

    Data quality checks: what to test and where

    Everything above assumes the raw data is right. Upstream it often is not: a core-banking release changes a column, a vendor feed stalls, a join silently drops customers. The model does not crash; it consumes garbage. Quality checks are cheap tests run on each batch (or window of a stream) before the features are used. They fall into a few families, taken from the tooling in Great Expectations, Soda, Deequ and the Google data validation work.

    FamilyQuestionExample for a transactions table
    SchemaAre the columns and types as agreed?amount is decimal, channel exists, no new columns unannounced
    CompletenessHow much is missing?Null share of amount ≤ 1%; row count within ±30% of the same weekday last month
    Validity / rangeAre values possible?0 < amount ≤ 200,000 AED; currency code in the ISO list
    UniquenessAre keys unique?txn_id has no duplicates (a replayed message would double a feature)
    Accepted valuesAre categories known?channel in {POS, ECOM, ATM, APP}; a new "WALLET" must be reviewed
    FreshnessIs the data current?Newest event is under 15 minutes old
    DistributionDoes the shape match what we know?Population stability index of amount below 0.2 against a reference (F7.7)
    ReferentialDo joins find their partners?99.5% of transactions match a known customer

    Checks sit at several points: at ingestion (cheap, stops bad raw data), after transformation (catches your own join bugs) and at feature-serving time (catches a feature out of range in a single request, with a safe default or a fallback). Each check needs a decision attached: block the load and keep yesterday's values, warn and continue, or quarantine the offending rows. A check that nobody acts on is noise.

    Thresholds are the hard part. Too tight and the team learns to ignore alerts; too loose and nothing is caught. Start from history, flag on a high percentile of the usual variation, and review every false alarm as a chance to improve the check.

    Data contracts: moving the promise upstream

    Checks catch problems after the producer ships them. A data contract is the agreement made before: the team that owns a dataset publishes a machine-readable statement of what it delivers, and consumers (your feature pipelines) depend on that statement. It usually covers:

    • Schema: columns, types, which are nullable, units (AED, or fils?), time zone.
    • Semantics: what each field means, how a transaction is defined, how reversals are represented.
    • Quality and service levels: maximum null share, freshness, delivery time, retention.
    • Ownership and change rules: a named owner, how breaking changes are announced and versioned, how long the old version continues.
    • Classification: contains personal data, residency constraints, who may access (links to G2).
    dataset: core_banking.card_transactions
version: 2.1
owner: payments-data@bank.example
schema:
  - name: txn_id        type: string   required: true   unique: true
  - name: amount        type: decimal  unit: AED        required: true
  - name: event_ts      type: timestamp tz: UTC
  - name: channel       type: string   allowed: [POS, ECOM, ATM, APP]
quality:
  - freshness: event_ts within 15 minutes
  - null_share(amount) <= 0.01
change_policy: breaking changes announced 30 days ahead, two versions run in parallel

    The point is the process: a contract in a repository, validated in CI against the producer's code, so a release that renames a column fails its own tests, not your model at 3 a.m. Open specifications exist (the Open Data Contract Standard from the Bitol project is one), and quality tools can turn the contract's clauses into executable checks. The honest limitation: a contract binds only the teams that sign it, and it needs a producer who accepts it as part of their job. At many banks the hard part is organisational, not technical.

    How it connects

    This lesson is where the modelling topics meet the plumbing. These are the connections to keep.

    Behavioural aggregates and encodings are the content of a feature store. Their definitions (windows, units, missing-value rules) are exactly what must stay identical in training and serving.

    The PSI check in Simulation 4 is the same statistic. Quality checks catch sudden breaks; drift monitoring catches the slow slide the checks pass.

    The offline side of a feature store is tables in the warehouse or lakehouse. Table formats with time travel help you reproduce training sets.

    When a producer wants to change a column, lineage tells you which features and models break. Contracts name the owner; lineage shows the consumers.

    P2 · Model lifecycle and deploymentBatch versus real-time serving

    Whether you need an online store at all depends on the deployment pattern. See also the model lifecycle, where feature versions are recorded with the model version.

    P5 · System designReal-time fraud architecture

    The worked design case uses these building blocks, with latency budgets. The batch counterpart is propensity and campaign scoring.

    B1 · Fraud detectionVelocity features, in anger

    Counts and sums over short windows are the textbook online-offline consistency problem. Labels arriving late (B1.2) add a second time axis.

    F10.2 · Testing mindsetTests for data, not just code

    A quality check is a unit test on data. The habits transfer: small, named, run automatically, failing loudly.

    Where it shows up at the bank:

    • Card and payment fraud. Velocity, device and merchant features with sub-second budgets; streaming windows; consistency between replayed history and live.
    • Credit decisioning. Bureau pulls, income and balance aggregates used in both a batch scorecard and an application-time decision. The scorecard and the live decision must read the same definition of "average monthly salary".
    • Marketing and churn. Mostly batch features and a daily list; consistency problems are quieter but still real, for instance different definitions of "active customer" in two teams' tables.
    • Regulatory and risk data. The principles for risk data aggregation and reporting from the Basel Committee (BCBS 239) ask banks for accuracy, completeness, timeliness and clear ownership of risk data. Contracts and checks are a practical way to evidence those. Check with the bank's own data governance team how its regulator (CBUAE or SAMA) frames this; I have not cited any specific local rule.
    • LLM and RAG systems. The same idea in a different form: an index of documents and embeddings must be versioned and fresh, and a changed embedding model silently breaks retrieval.
    Part 4

    Where the field is now

    The concepts are settled and the product landscape is still moving. The main shifts: feature stores are folding into data platforms, real-time features have become a mainstream expectation, and data contracts have moved from a blog idea to a standardised, tool-supported practice.

    Research checked on 6 November 2026 with light web searches. Much of what I found was blogs and comparison sites, so market claims below are marked as reported rather than confirmed.

    1. 2015
      ML debt is mostly data and plumbing

      A widely cited Google paper argued that real ML systems are mostly glue code and data dependencies, naming undeclared consumers, unstable data and entanglement as sources of hidden cost.

      Sculley et al., NeurIPS 2015
    2. 2017
      Feature stores arrive in industry

      Uber described the idea of a shared feature store in its Michelangelo platform; the pattern of one definition feeding offline and online use spread from there.

    3. 2018–19
      Automated data validation

      Amazon's Deequ and Google's TFX data validation made "unit tests for data" a library: constraints and schema suggested from data, with checks on every batch and drift between batches.

    4. 2019–22
      Open-source stores and the data contract idea

      Feast became the best-known open-source feature store; Hopsworks and others followed. In parallel the "data contract" idea spread from data-engineering practice as a response to upstream breakage.

    5. 2025–26

    Part 5

    How it fails, and how to spot it

    Each failure comes with the quickest check.

    • Two implementations of one feature

      SQL in training, Java or Python in serving. Rounding, time zones, window edges and null handling all differ.

      Spot itLog the features used at serving time and recompute them offline for the same transactions. The difference should be zero or explained.
    • Joining on the latest value

      Training rows get feature values from after the label. AUC is gorgeous, live performance is not.

      Spot itCheck the join key and timestamp. Any join on customer ID alone, or on date without time, is suspect. Compare offline AUC with a forward-in-time test.
    • Joining on the time a value describes, not when it arrived

      A nightly job writes Tuesday's totals at 02:00 Wednesday, but the training set treats them as available Tuesday.

      Spot itAsk for the availability timestamp of each feature. If only an event timestamp exists, assume leakage until shown otherwise.
    • Silent defaults

      A missing feature becomes 0 online and NaN offline (or the reverse). The model has learned that NaN means something.

      Spot itCompare missing-value rates per feature, offline and live. A feature that is never missing online but often missing in training is a warning.
    • Stale online store

      A stream stalls; the last value sits there for hours, looking normal.

      Spot itTrack the age of each served value and alert when it exceeds the promise. A freshness check on the online store is as important as on the source.
    • Upstream change nobody told you about

      A core system release switches amounts to fils, adds a currency, renames a code.

      Spot itRange and accepted-value checks on ingestion, a contract with a change policy, and an on-call owner.
    • Checks with no owner or no action

      Hundreds of alerts, all muted.

      Spot itFor every check, name who is paged and whether the pipeline blocks. Review which checks have fired in the last quarter.
    • A check suite that passes plausible nonsense

      A slowly drifting definition or a 15% shift in an amount passes every rule.

      Spot itAdd distribution monitoring on features and outputs (F7.7), and reconcile against an independent source such as the general ledger.
    • Feature versions that change under a model

      Someone fixes a definition; the registered model, trained on the old version, now receives the new one.

      Spot itPin feature versions in the model's metadata. A change creates a new feature version and a retraining plan.
    • Buying a platform to fix a process

      The store goes live but definitions are still copied by hand, and nobody owns them.

      Spot itAsk how many models share each feature, who approves a change, and how a change is rolled out.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “A model can pass every test and still underperform live if it is fed slightly different numbers than it learned from. That is the most common reason good models disappoint in production, and it makes no noise. The fix is not a bigger model: it is defining each input once, using it the same way in training and live, and checking what arrives from upstream systems. I'd start with the few inputs behind fraud and credit decisions, put owners and automatic checks on them, and expand from there.”
    To an engineer or validator
    “Features are defined once in a registry and materialised to an offline store for training and an online store for serving. Training sets are built with as-of joins on availability time, so each row equals what the online store would have returned. We log served feature vectors and compare them to offline recomputation to detect skew. Upstream datasets have contracts covering schema, units, freshness and change policy, with checks in CI and at ingestion; drift monitoring covers what checks can't.”
    “Do we really need a feature store?”

    Maybe not yet. The value is in shared definitions, point-in-time joins and a low-latency read path. With a few batch models, a well-governed feature table and shared transformation code may be enough. A store pays off when several models share features, when sub-second features matter, or when audit needs exact reproduction of past scores. Buy or build for the problems we actually have, and avoid adding a platform to cover a process gap.

    “The model scored well offline and is poor live. Where do you start?”

    With the inputs, before the model. Log the live feature values and recompute them offline for the same transactions; check missing rates and distributions; check that the training join used availability time; compare against a forward-in-time test to rule out leakage. Only then look at drift in the world or label delay.

    “How fresh do the features need to be?”

    As fresh as the behaviour we are trying to catch moves. An attack that completes in minutes needs minutes; a salary pattern needs a day. I'd set a freshness promise per feature, measure the age of served values, and spend streaming money only where the loss from delay justifies it.

    “Why do data contracts matter if we already have quality checks?”

    Checks find problems after the producer ships them; a contract makes the producer responsible beforehand and fails their release, not our model. It also records meaning and units, which checks can't, and names an owner. We need both, and neither replaces drift monitoring.

    “Is the online store the source of truth?”

    No. It holds the latest values for fast reads, rebuilt from the same definitions as the offline history. The offline store, plus the logged served values, is the record. If the two disagree, the offline recomputation is the thing to debug against, and the disagreement is the finding.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. In your own words: what is training-serving skew, and why does it not raise an error?

    The features the model sees live differ from the ones it trained on, because they were computed by different code, from different data, or at a different time. Every value is still valid and in range, so nothing fails; the model just gets less accurate. You find it only by comparing live inputs to offline recomputation or by watching performance.

    2. A nightly job finishes writing Tuesday's customer totals at 02:00 on Wednesday. A fraud label occurred Tuesday 20:00. Which timestamp should the as-of join use and what goes wrong otherwise?

    The availability time (Wednesday 02:00), so the Tuesday-20:00 row gets Monday's totals, which is what the live system would have had. Joining on the date or event time the totals describe gives the row values that were not available yet: a leak.

    3. A feature is refreshed every 30 minutes with a 3-minute pipeline delay. How old is it when read, on average and at worst?

    Average Δ/2 + ℓ = 15 + 3 = 18 minutes. Worst case 30 + 3 = 33 minutes. A rule needing a signal within 5 minutes cannot rely on it.

    4. Why is the online store not the same as the offline store with a cache in front of it?

    The online store holds only the latest value per entity in a key-value system built for millisecond lookups; the offline store holds full history in analytical tables for large scans. They are populated by the same definitions, but they are designed for opposite access patterns. A cache in front of a warehouse would still be too slow on a miss and cannot do windowed updates.

    5. Name two checks that would catch amounts suddenly arriving in fils instead of dirhams, and one that would not.

    The range check (maximum amount) and the distribution check (PSI against a reference) would both fire. A null-rate, uniqueness or freshness check would not, since values are present, unique and recent.

    6. Your quality checks all pass, yet fraud losses rise and the model's average score has changed. What other safeguards should you have?

    Drift monitoring on features and on scores (F7.7), reconciliation against an independent source, logged served features compared to offline, and monitoring of model performance once labels mature. Checks catch breaks, not slow or plausible shifts.

    7. A colleague proposes recomputing features in training using only the freshest, cleanest corrected history. What is the risk?

    The model learns from inputs cleaner than anything it will receive live (late data included, corrections applied), so training is optimistic compared with serving. Prefer what was known at the time, or log the actual served values for later training.

    8. Sketch what would go in a data contract for a customer-income feed used by a credit model.

    Schema and units (currency, monthly or annual, gross or net), nullability and what null means, source and definition of income, update frequency and freshness, accepted ranges, owner, change policy with notice period and versioning, personal-data classification and access rules.
