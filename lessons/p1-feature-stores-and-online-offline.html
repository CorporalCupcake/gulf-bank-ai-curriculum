    Same Features Live as in Training: Feature Stores, Consistency and Data Contracts

    Why a model that scored 0.98 AUC in the notebook can quietly drop to 0.85 in production, how feature stores and as-of joins prevent it, and how checks and contracts stop broken upstream data from ever reaching a model.

    Contents

    The whole lesson in one sentenceA model is only as good as the match between the features it learned from and the features it is fed live, so define each feature once, compute it as of the decision time, serve it fresh enough, and make data producers promise what they deliver.

    Part 1

    The intuition

    A fraud model has a top feature: transactions on this card in the last 24 hours, built in the warehouse with SQL. AUC is 0.98. But live scoring must take under 50 ms, so engineers rewrite the feature in Java over a cache. It looks the same. It is not: the SQL excluded the current transaction and the Java includes it; one uses Gulf time, the other UTC; one sees late records, the other never does.

    Nobody wrote a bug. Two implementations of one idea drifted apart, like two cooks following the "same" recipe from memory, and the model quietly performs worse. This is training-serving skew.

    The mirror image is a wrongly built training table. Join last Tuesday's fraud label to the latest feature value and the feature already contains the fraud burst. That is leakage (F3.1), seen as plumbing.

    A feature store answers both: define each feature once, store it twice (full history for training, a fast latest copy for serving), and join to labels as of each decision. Data contracts and quality checks answer a third failure: an upstream system changes something and the feature silently turns to garbage.

    Nothing is "broken": no error, no failed job, and the model still returns numbers between 0 and 1. That is why skew is dangerous, and why a design that makes skew impossible beats debugging it later.

    Hold onto thisThree promises make a model trustworthy in production: the feature is computed the same way in training and serving; it uses only what was known at decision time; and upstream data is what you expected. A feature store enforces the first two. Checks and contracts enforce the third.
    Part 2

    How it really works

    What a feature store is made of

    A feature store is a shared pantry: each ingredient is defined once and both kitchens (training and live) use it.

    • Registry. The catalogue of definitions: name, entity (customer, card), logic, owner, freshness promise. One definition feeds training and serving.
    • Offline store. Full history in warehouse tables (P1.1 – P1.2). Big, cheap, slow. Builds training sets.
    • Online store. Latest value per entity in a key-value database such as Redis. Small, fast, millisecond lookups. Used at decision time.
    • Materialisation and point-in-time retrieval. Jobs write the same definition to both stores, and the store does the as-of join so no analyst reinvents it wrongly.

    How a feature is produced decides how hard consistency is.

    Feature kindExampleConsistency risk
    BatchAverage salary credit, last 6 monthsLow. A day of staleness is fine for slow facts.
    StreamingCard transactions in the last 10 minutesMedium. Training must replay the same window logic.
    On-demandThis amount vs the customer's usual amountHigh unless the same code runs in training.
    EmbeddingsMerchant vectorHigh. If the embedding model changes, old and new vectors are not comparable. Version them.

    You do not always need a product. A few batch models do well with a disciplined feature table, shared transformation code and as-of joins. A product pays off when many models share features, decisions are real time, or audit must show what any past score used.

    Point-in-time correctness: the as-of join

    Think of a school report written on Friday: it must not be used to predict Monday's mark. For each training row, use the feature value the live system would have returned at that moment. The key is the availability time: when you could use the value, not the time it describes. A nightly job summarising Tuesday finishes at 02:00 Wednesday, so it was not usable on Tuesday evening. Join each label to the latest snapshot available at or before the event (in pandas, merge_asof, F11.2). The failure is joining on the latest row, or on date alone.

    As-of equals serving: the training row is what the online store would have said, staleness included. That is intended, because a model should learn from the inputs it will really get. Beware late corrections (a backdated chargeback, a restated balance): they make offline history cleaner than anything live ever saw.

    Freshness, latency and how fresh is fresh enough

    Consistency is not freshness: a feature can match perfectly and still be uselessly stale, like an accurate newspaper from last week. Match freshness to how fast the thing you detect moves.

    • Salary-credit average changes monthly. A daily batch is plenty.
    • "Card used in three countries in an hour" changes in minutes. With a 15-minute refresh, the attacker has finished.
    • Utilisation for an overnight collections list: hours are fine.

    A value refreshed every Δ minutes is on average half of Δ old when read, and up to Δ at worst, plus pipeline delay. That bounds how early any rule on it can fire. Streaming everything costs complexity and money, so choose per feature.

    Data quality checks: what to test and where

    Upstream data is often wrong: a core-banking release changes a column, a vendor feed stalls, a join silently drops customers. The model does not crash; it consumes garbage. Quality checks are cheap smoke alarms, run on each batch before features are used.

    CheckQuestion and example
    SchemaAre columns and types as agreed? amount is still a decimal.
    CompletenessHow much is missing? Null share of amount at most 1%.
    RangeAre values possible? 0 < amount ≤ 200,000 AED.
    UniquenessAre keys unique? A replayed message would double a feature.
    Accepted valuesAre categories known? A new "WALLET" channel must be reviewed.
    FreshnessIs the newest event under 15 minutes old?
    DistributionDoes the shape match a reference? Population stability index (F7.7) below 0.2.

    Run checks at ingestion, after transformation (your own join bugs) and at serving time. Each check needs an action attached: block the load and keep yesterday's values, warn and continue, or quarantine the bad rows. A check nobody acts on is noise. Thresholds are the hard part: too tight and the team ignores alerts, too loose and nothing is caught. Start from history.

    Data contracts: moving the promise upstream

    A data contract is the agreement made before the data ships. Checks catch problems after the producer ships them; a contract is a machine-readable promise the producer publishes and your pipelines depend on, like a delivery service-level agreement. It covers:

    • Schema and meaning: columns, types, units (AED or fils?), time zone, what a transaction is, how reversals appear.
    • Quality and service levels: maximum null share, freshness, delivery time.
    • Ownership and change rules: a named owner, how breaking changes are announced, how long the old version runs.
    dataset: core_banking.card_transactions
version: 2.1
owner: payments-data@bank.example
schema:
  - name: amount   type: decimal  unit: AED   required: true
  - name: channel  type: string   allowed: [POS, ECOM, ATM, APP]
quality:
  - freshness: event_ts within 15 minutes
change_policy: breaking changes announced 30 days ahead

    The point is the process: the contract lives in a repository and is validated in CI against the producer's code, so a release that renames a column fails its own tests, not your model at 3 a.m. It binds only the teams that sign it, so at many banks the hard part is organisational.

    Part 3

    How it fails, and how to spot it

    • Two implementations of one feature

      SQL in training, Java in serving. Rounding, time zones, window edges and null handling (0 online, NaN offline) all differ.

      Spot itLog serving-time features and recompute them offline for the same transactions. Compare missing rates too. Differences should be zero or explained.
    • Joining on the wrong time

      Joining on the latest value, on date alone, or on when a value describes rather than when it arrived. Training rows get information from after the decision, so AUC is gorgeous and live performance is not.

      Spot itAsk for each feature's availability timestamp. If only an event timestamp exists, assume leakage.
    • Stale online store

      A stream stalls; the last value sits there for hours, looking normal.

      Spot itTrack the age of each served value and alert when it exceeds the promise.
    • Upstream change nobody told you about

      A core system release switches amounts to fils, adds a currency, renames a code.

      Spot itRange and accepted-value checks at ingestion, a contract with a change policy, an on-call owner.
    • Checks that pass nonsense, or nobody acts on

      A 15% drift in amounts passes every rule, or hundreds of alerts are all muted.

      Spot itAdd distribution monitoring (F7.7) and reconcile against an independent source such as the general ledger. For every check, name who is paged and whether the pipeline blocks.
    • Feature versions that change under a model

      Someone fixes a definition; the model, trained on the old version, now receives the new one. Related trap: buying a platform while definitions are still copied by hand.

      Spot itPin feature versions in the model's metadata. A change means a new version and a retraining plan.
    Part 4

    Self-check

    1. What is training-serving skew, and why does it not raise an error?

    The model sees live features that differ from its training features (different code, data or timing). Every value is still valid, so nothing fails; the model just gets worse. You find it by comparing live inputs with offline recomputation, or by watching performance.

    2. A nightly job finishes writing Tuesday's customer totals at 02:00 on Wednesday. A fraud label occurred Tuesday 20:00. Which timestamp should the as-of join use, and what goes wrong otherwise?

    Availability time (Wednesday 02:00). The Tuesday 20:00 row then gets Monday's totals, which is what the live system had. Joining on the date the totals describe gives values not yet available: a leak.

    3. A feature refreshes every 30 minutes. A rule needs to react within 5 minutes of an attack starting. Can it rely on this feature?

    No. The value is on average about 15 minutes old when read, plus pipeline delay, and up to 30 at worst. Such a rule needs a streaming feature.

    4. Why is the online store not just the offline store with a cache in front?

    Online holds only the latest value per entity, built for millisecond lookups. Offline holds full history, built for large scans. The same definitions fill both, but the access patterns are opposite. A cache over a warehouse is still slow on a miss.

    5. Name two checks that would catch amounts suddenly arriving in fils instead of dirhams, and one that would not.

    The range check and the distribution check fire. Null-rate, uniqueness and freshness checks do not: values are present, unique and recent.

    6. Your quality checks all pass, yet fraud losses rise and the model's average score has changed. What other safeguards should you have?

    Drift monitoring on features and scores (F7.7), reconciliation against an independent source, logged served features compared with offline, and performance monitoring once labels mature. Checks catch breaks, not plausible shifts.

    7. A colleague proposes recomputing training features from the freshest, corrected history. What is the risk?

    The model trains on inputs cleaner than anything it will get live, so training looks better than serving. Use what was known at the time, or log served values for later training.

    8. What goes in a data contract for a customer-income feed used by a credit model?

    Schema and units (currency, monthly or annual, gross or net), what null means, the definition of income, freshness, accepted ranges, owner, change policy (notice period, versioning), and personal-data classification.
