    The Testing Mindset, and Being Able to Rebuild Any Number You Reported

    What a good test actually checks, why a green tick proves much less than it seems (especially on AI-written tests), and how version control, pinned environments and recorded seeds let you reproduce a figure months later when an auditor asks.

    Contents

    The whole lesson in one sentenceA passing test only proves the claims it makes, so ask what bug would have made it fail; then keep code, data, settings and seeds recorded so any number you reported can be rebuilt on demand.

    Part 1

    The intuition

    A smoke alarm that never goes off proves nothing until you press the test button. Tests are the same. AI-generated code arrives with fourteen green tests and 100% coverage. Now plant one bug: a customer exactly 30 days overdue lands in the wrong collections bucket. If the tests stay green, the tick never meant "this works". It meant "nothing I thought to check has broken".

    The second half applies the idea to time. Six months on, an auditor asks: "You told the committee the AUC was 0.87. Show me." If you cannot rebuild that number, it is an anecdote. Version control and reproducibility turn a result into evidence.

    Hold onto thisCoverage says which lines ran, not whether the result was right. A test with no assertion earns full coverage and checks nothing. Ask of every test: what bug would make this fail?
    Part 2

    How it really works

    F10.3 What a good test checks, and what a passing test does not prove

    A test sets up an input, runs the code and asserts something about the output. The assertion is where the value lives. Good tests share four habits.

    • Behaviour, not implementation. "30 days overdue lands in 30-59" survives a rewrite. "The function calls round() twice" breaks on every tidy-up.
    • Placed where bugs live. Like a bridge inspector checking the joints, not the flat road: defects hide at boundaries (0, 29/30, 89/90, empty input, missing values, month-end dates).
    • An independent oracle. The expected value comes from outside the code: a hand calculation, a ledger figure, a worked example in the policy. A test that uses the formula it is testing can never fail.
    • Tolerances for floats. 0.1 + 0.2 == 0.3 is false. Use pytest.approx.
    @pytest.mark.parametrize("days, expected", [
    (-5, "current"), (0, "current"),     # paid early, due today
    (29, "1-29"), (30, "30-59"),         # edges of a bucket
    (89, "60-89"), (90, "90+"),
])
def test_bucket_edges(days, expected):
    assert bucket(days) == expected

    Mutation: how to test the tests

    Like a fire drill for your suite: break the code on purpose and see if anyone notices. Make one small change (a "mutant"), such as flipping <= to <. If a test fails, the mutant is killed; if all stay green, the suite is blind to that bug. The mutation score is the share of mutants killed. In Simulation 1, 1 of 6 (17%) means the suite runs all the code and judges almost none of it.

    Properties, data and models

    A property must hold for every input, like "a lift never goes up when you press down". A library such as Hypothesis generates hundreds of inputs and shrinks any failure to the smallest example. Example: more days overdue never gives a lower bucket.

    Most wrong numbers come from data, not functions. Run checks on every refresh, like airport security with several scanners: unique keys, no dates after the as-of date (F3.1), one currency per column, row count unchanged by a join, total reconciles to the ledger. Each catches faults the others miss (Simulation 2).

    For models, test that an obviously fraudulent case scores high, that Mohammed vs Mohamed does not move the score, and that more missed payments never lower the risk.

    What a passing test does not prove

    • That the requirement was right. The code can implement "90+ means default" perfectly while policy says 90 days past due and over a materiality amount. Tests check the code against the spec, not the spec.
    • That the data resembles production. Ten tidy rows say nothing about Arabic name variants, null IDs or a salary column half in AED, half in USD. Unit tests also miss leakage and drift (F3.1, F7.7).
    • That the tests are not the problem. An assistant asked for tests often reads the function and mirrors it, copying expected values from the code's output, so a bug gets enshrined. Warning signs: no assert, only is not None, everything mocked. Review by hiding the implementation and asking if you would have chosen those values.

    F10.4 Version control: a history you can return to

    Git is a ledger of snapshots. Each commit is a snapshot of the files plus a message, author and time, and its hash is computed from its contents, so the same hash always means the same code. A branch is a movable label on a commit; a tag is a fixed one ("model-v3-validated").

    • Commit small, say why. "Exclude dormant accounts from the base population (ticket 4821)" is worth ten "fix".
    • One branch per change; merge through review. Never rewrite shared history; fix mistakes with a new commit.
    • Never commit secrets or customer data. Once in history, it is in every clone.
    git tag -a pd-model-v3-committee -m "Numbers in committee paper of 12 March"
git bisect start; git bisect bad; git bisect good v2.4   # find the breaking commit

    git bisect finds what broke a number by halving, like guessing a number between 1 and 24: mark one commit good and one bad, git checks out the middle, you test, and it halves again (Simulation 4). It needs an automatic good/bad test.

    Notebooks are a trap: out-of-order cells mean results depend on hidden state. "Restart and run all" is the honest test.

    Reproducibility: what must be frozen to rebuild a number

    A number is reproducible if someone else can follow the recipe card and get the same dish. The bank's bar: given a number in a report, rebuild it. A number is a function of five inputs, and any can change silently.

    InputHow it driftsWhat to record
    CodeEdits after the run.The commit hash; report only from a clean tree.
    DataTables are overwritten; late labels arrive.An as-of date, an immutable snapshot, a row count and a checksum.
    EnvironmentA library update changes a default.A lock file with exact versions, or a container image digest.
    RandomnessSplit, initial weights, sampling.Every seed, and the splitting code.
    ConfigurationThresholds and hyperparameters set in a notebook cell or in someone's head.A config file committed with the code.

  "data_snapshot": "txn_2026-03-31", "rows": 4812030, "data_sha256": "9be1…",
  "env_lock_sha256": "c41d…", "python": "3.12.4",

}

    Experiment trackers (see the model lifecycle) write this for you. The rule: no number leaves without the identifiers to regenerate it.

    Seeds are necessary, not sufficient. A fixed seed repeats one run; it does not make it trustworthy. Different seeds give different splits, and the spread is the honest uncertainty. Reporting the best of fifty seeds is cherry-picking (Simulation 3).

    Reproducibility when the model is an LLM

    Three things can change under you: the model (a provider can update what a name points to, so pin a dated identifier), the prompt (it is code, so version and review it) and sampling (temperature zero lowers variation but does not guarantee identical output). So an LLM regression test is a frozen evaluation set scored against a tolerance, run several times, not one exact-match string. See prompt versioning and tracing and statistics for evals.

    Part 3

    How it fails, and how to spot it

    • Coverage as the goal

      "95% coverage" offered as proof of quality. Assertion-free tests reach it easily.

      Spot itDelete one condition in the code; if nothing fails, the suite is decoration.
    • Tests that mirror the code

      The expected value uses the same formula, or is copied from the output, so a bug passes its own test.

      Spot itAsk where the expected number came from: policy, ledger or hand calculation.
    • Happy path only, or over-mocked

      Typical values only, or every external call stubbed to return what the code wants.

      Spot itLook for 0, exact thresholds, empty tables and missing values. Break the real query; if the test still passes, it tests nothing.
    • Flaky tests tolerated

      "Just re-run it." Real failures get ignored.

      Spot itRun the suite five times. Fix the seed, clock or ordering that varies.
    • Reporting from an uncommitted notebook

      A figure from a notebook with unsaved edits, out-of-order cells and a CSV on a desktop. A silent library update can also change the number.

      Spot itAsk for the commit hash, data snapshot and lock file; "restart and run all" should match.
    • Best-seed reporting

      Seeds tried until the metric looks good; only that run saved.

      Spot itAsk how many seeds were tried. Report mean and range.
    • Secrets, data or rewritten history in git

      An API key or customer extract committed "just for now", or a force-push that makes the tagged commit disappear.

      Spot itScan the repo before sharing and rotate exposed credentials. Protect main branches; confirm the tag still resolves to the same hash.
    Part 4

    Self-check

    1. A test suite has 100% line coverage and a mutation score of 4%. What does that tell you?

    Lines run, but almost no code change makes a test fail: assertions are weak or missing.

    2. Which inputs would you test for a function that assigns an arrears bucket from days overdue?

    Both sides of every boundary, a negative (paid early), a very large value and missing input. Expected values come from policy.

    3. An AI assistant writes a test whose expected value is assert result == calculate_fee(1000). What is wrong?

    It compares the function with itself, so it cannot fail. Take the expected value from outside, such as the tariff table.

    4. After a merge, the row count after joining customers rises from 600 to 648 and the sum of amounts rises too. Which check catches it and what is the likely cause?

    The post-join row-count check and the ledger reconciliation. Likely cause: duplicate keys in the customer table fan out the join and duplicate transactions.

    5. List the five things you must record to rebuild a reported AUC.

    Code, data, environment, seeds and configuration.

    6. You run 40 seeds and the AUCs range from 0.84 to 0.90. A teammate reports 0.90. What is the fair statement?

    AUC is around 0.87 and varies by about 0.06 with the split. 0.90 is the best draw. Report the mean with the spread.

    7. You know commit 1 is good and commit 24 is bad. Roughly how many pipeline runs does git bisect need, and when does it not work?

    About five, because each run halves the suspects. It fails without a reliable automatic good/bad verdict: a noisy metric or an old commit that will not run misleads it, and one giant commit hides the cause.
