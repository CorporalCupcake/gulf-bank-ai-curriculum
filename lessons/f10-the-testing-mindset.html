    The Testing Mindset, and Being Able to Rebuild Any Number You Reported

    What a good test actually checks, why a green tick proves much less than it seems (especially on AI-written tests), and how version control, pinned environments and recorded seeds let you reproduce a figure months later when an auditor asks.

    Contents

    The whole lesson in one sentenceA test is a claim about behaviour that could have turned out false; a passing test only proves the claims it makes, so ask what bug would have made it fail, and then keep code, data, settings and seeds under version control so any number you ever reported can be rebuilt on demand.

    Part 1

    The intuition

    A colleague pastes AI-generated code into your repository. It comes with fourteen tests, all green, and the coverage report says 100%. It is tempting to relax.

    Now picture the same function with one bug introduced on purpose: a customer exactly 30 days overdue is put in the wrong collections bucket. Do the fourteen tests turn red? If they do not, the green tick never meant "this works". It meant "nothing I thought to check has broken". That gap is the whole subject of the first half of this lesson.

    The second half is the same idea applied to time. Six months from now a validator, an auditor or your own manager asks: "You told the committee the model's AUC was 0.87. Show me." If you cannot rebuild that exact number, from that exact data, with that exact code, the number is an anecdote. Version control and reproducibility are how you turn a result into evidence.

    Both halves share one attitude. Assume your work is wrong in some way you have not found yet, and arrange things so the error gets caught cheaply. A test catches it when the code changes. A reproducible run catches it when someone else, or you later, re-does the work.

    Hold onto thisCoverage tells you which lines ran. A test tells you whether the result was right. A smoke test with no assertion earns full coverage and checks nothing. The question that separates a good test from decoration is: what bug would make this fail?
    Part 2

    How it really works

    F10.3 What a good test checks, and what a passing test does not prove

    A test has three parts: set up an input, run the code, assert something about the output. The assertion is where the value lives. A good test has these habits.

    • It checks behaviour, not implementation. "30 days overdue lands in the 30-59 bucket" survives a rewrite. "The function calls round() twice" breaks every time you tidy up and tells you nothing about customers.
    • It sits where bugs live. Most defects hide at boundaries (0, 29/30, 89/90, empty input, one row, a missing value, a date at month end, a negative amount) and in rare branches. Typical-case tests are easy to write and rarely fail.
    • It has an independent oracle. The expected value must come from somewhere other than the code under test: a hand calculation, a known figure from the ledger, a regulation's worked example, a simple slow version of the same logic. A test that computes its expected value with the same formula it is testing can never fail.
    • It uses tolerances for floats. 0.1 + 0.2 == 0.3 is false in floating point. Use pytest.approx or numpy.testing.assert_allclose, and state the tolerance in business terms (within AED 0.01).
    • It is small, fast and isolated. One idea per test, no dependence on the order of other tests, no live database. Slow or flaky tests get switched off, and then you have none.
    import pytest
from collections_buckets import bucket

@pytest.mark.parametrize("days, expected", [
    (-5, "current"), (0, "current"),     # paid early, due today
    (1, "1-29"), (29, "1-29"),           # edges of a bucket
    (30, "30-59"), (59, "30-59"),
    (60, "60-89"), (89, "60-89"),
    (90, "90+"), (400, "90+"),
])
def test_bucket_edges(days, expected):
    assert bucket(days) == expected

    The expected values come from the policy document, not from running the function. That is the oracle.

    Mutation: how to test the tests

    Simulation 1 used the trick that measures a test suite honestly. Take the correct code, make one small deliberate change (a "mutant"): flip <= to <, shift a constant by one, swap a label. Run the tests. If something fails, the mutant is killed. If everything stays green, the suite could not see that bug.

    mutation score=mutants killedmutants created

    A suite with 100% line coverage and a 17% mutation score (one of six bugs caught, as with "Typical cases" in Simulation 1) runs all the code and judges almost none of it. Real tools generate hundreds of mutants and are slow, so teams run them on the critical modules, not everything.

    Tests for properties, not just examples

    Examples check the cases you thought of. A property says something that must hold for every input, and a library generates hundreds of inputs, including nasty ones, and shrinks any failure to the smallest example. For data science the useful properties are plain:

    • Bucketing is monotonic: more days overdue never gives a lower bucket.
    • Splitting then concatenating the data gives back the same rows; no row is in both train and test.
    • Converting AED to USD and back returns the amount within a cent.
    • Scores stay in [0, 1], and permuting the row order does not change any customer's score.
    from hypothesis import given, strategies as st

@given(a=st.integers(-1000, 1000), b=st.integers(-1000, 1000))
def test_more_overdue_never_lowers_bucket(a, b):
    order = ["current", "1-29", "30-59", "60-89", "90+"]
    lo, hi = sorted([a, b])
    assert order.index(bucket(lo)) <= order.index(bucket(hi))

    Testing data, and testing models

    In this job most wrong numbers come from the data, not from a function. So the tests that matter most are often checks that run on every refresh: keys are unique, dates are not after the as-of date (F3.1), one currency per column, null rates within bounds, the row count after a join equals the row count before it, and the total reconciles to the ledger. Simulation 2 shows why you need several, because each catches faults the others miss.

    For models the idea extends. Minimum functionality: an obviously fraudulent synthetic case must score high. Invariance: changing a customer's name from Mohammed to Mohamed, or the order of rows, should not move the score. Directional: raising the number of missed payments should not lower the risk. Regression (golden) test: on a frozen sample, scores stay within a stated tolerance of last release unless you meant to change them. This style is the CheckList approach for language models (Ribeiro et al., 2020), and it applies to any scorer.

    What a passing test does not prove

    • That the requirement was right. The code can implement "90+ means default" perfectly while the policy says 90 days past due and over a materiality amount. Tests verify the spec, not the spec.
    • That the data resembles production. A test on ten tidy rows says nothing about Arabic name variants, null customer IDs or a salary column that is half in AED and half in USD.
    • That there is no leakage or drift. Unit tests pass on a model that leaks the label. Those need data and evaluation checks (F3.1, F7.7).
    • That the model is good. Software tests say the pipeline does what you wrote. Whether the model generalises is a statistics question (F4.5).
    • That the tests are not the problem. This is the AI-specific one. A coding assistant asked for "tests for this function" often reads the function and writes tests that mirror it, with the expected values copied from whatever the code returns. If the code has a bug, the test enshrines it. Warning signs are tests with no assert, asserts on is not None only, everything mocked, and expected values that look like the output of the code rather than of the policy. A fair review of AI-written tests starts by hiding the implementation and asking whether you would have chosen those expected values.

    Last, a note on randomness. A test that depends on an unseeded random number will pass on Tuesday and fail on Wednesday, and people learn to re-run until green. Seed everything in tests (np.random.default_rng(0)), and for stochastic code assert statistical bounds, not exact values.

    F10.4 Version control: a history you can return to

    Git stores a project as a chain of commits. Each commit is a complete snapshot of the tracked files plus a message, an author, a time and a pointer to its parent. It is identified by a hash computed from its contents, so the same hash always means the same code, and altering history changes every hash after it. A branch is just a movable label pointing at a commit; a tag is a fixed label ("model-v3-validated"). A pull request is a proposal to merge one branch into another, and it is the place where a second person reads the diff. Reading and approving diffs (F10.1, F10.2) is how most errors get caught before they reach a number.

    For a data scientist the working rules are short.

    • Commit small, with a message that says why. "Exclude dormant accounts from the base population (per credit risk, ticket 4821)" is worth ten "fix".
    • One branch per change; merge through review. Do not edit the validated branch directly.
    • Never rewrite history that others have pulled. No force-pushes to shared branches. If you made a mistake, add a new commit that reverses it; the record stays honest.
    • Never commit secrets or customer data. Passwords, API keys, a CSV of real customers. Once in history it is in every clone. Keep a .gitignore and check before your first push. Whether data may leave the bank's environment at all is a policy question, not a git one.
    • Tag what you reported. The commit behind the committee paper gets a tag. That one habit rescues you later.
    git switch -c fix/dormant-accounts      # new branch for one change
git add src/population.py tests/test_population.py
git commit -m "Exclude dormant accounts from base population (ticket 4821)"
git log --oneline -5                    # what happened recently
git diff main..HEAD                     # exactly what a reviewer will read
git tag -a pd-model-v3-committee -m "Numbers in committee paper of 12 March"
git bisect start; git bisect bad; git bisect good v2.4   # find the breaking commit

    Git can also find who broke a number. git bisect does a binary search through history: you say one commit is good and one is bad, git checks out the middle, you run your test, and it halves the range again. Twenty-four suspects take at most five runs. Simulation 4 lets you try it. This works only if you have a test or a metric that says good or bad automatically, which is another reason to write one.

    Notebooks deserve a warning. A notebook's saved file includes its outputs and a cell order that can differ from the run order, so diffs are unreadable and results can depend on hidden state ("restart and run all" is the only honest test). Teams commonly strip outputs before committing (nbstripout), pair the notebook with a plain script, or move the logic into modules that notebooks import.

    Reproducibility: what must be frozen to rebuild a number

    "Reproducible" is used loosely, so separate three levels.

    • Rerunnable: you, today, same machine, can run it again. Low bar, often failed by notebooks.
    • Reproducible: someone else, with your code, data and instructions, gets the same numbers.
    • Replicable: an independent team, with new data and their own code, finds the same conclusion. That is science's bar, and it matters for claims like "this feature improves fraud detection".

    For a bank the working target is the middle one: given a number in a report, rebuild it. A number is the output of a function of five inputs, and any one of them can change silently.

    Experiment trackers (MLflow, Weights and Biases, or your platform's equivalent, see the model lifecycle) write this manifest for you. The point is not the tool but the discipline: no number leaves the building without the identifiers needed to regenerate it.

    Seeds are necessary and not sufficient. A fixed seed makes one run repeatable; it does not make the answer trustworthy. Different seeds give different splits and different results, and the spread is the honest uncertainty. Reporting the best of fifty seeds is cherry-picking with extra steps. Simulation 3 shows both effects.

    Reproducibility when the model is an LLM

    Language-model systems add three sources of change. The model behind a name can be updated by the provider, so pin a dated or versioned model identifier and record it. The prompt is code: version it, review it, tag it. And sampling is random: setting temperature to zero lowers variation but does not guarantee identical output, because served inference can differ with server load and batch size (He and Thinking Machines Lab, 2025, give a detailed explanation and a deterministic-kernel fix at a speed cost). So for an LLM component, a regression test is a frozen evaluation set scored with a stated tolerance, run several times, not one exact-match string. See prompt versioning and tracing and statistics for evals.

    How it connects

    You cannot write good tests for code you cannot read. The hollow-analysis patterns there (silent filters, leakage, wrong joins) are exactly what the checks in Simulation 2 turn into automatic alarms.

    A 600-line notebook cell cannot be unit-tested. Pure functions with clear inputs and outputs can, which is the practical reason for modules and interfaces.

    F3.1 · Leakage and point-in-timeTests that guard the as-of date

    "No feature dated after the label date" can be written as a test that runs on every refresh. Leakage is the fault no row-level check sees.

    An analysis that survives review states its data snapshot, commit and seeds, so a reviewer can rerun it.

    F4.5 · Cross-validationSeeds, folds and spread

    Repeated splits are the honest way to show the spread that one seed hides, as in Simulation 3.

    F7.7 · Drift monitoringTests after release

    Data checks are tests at the door; drift monitoring is the same idea running continuously after deployment.

    P1 · Lineage and feature storesWhere did this column come from?

    Lineage tools record data provenance automatically. Your manifest is the model-level equivalent.

    P2 · Model lifecycleCI, registries and promotion

    Continuous integration runs your tests on every pull request; a model registry stores the commit, data and metrics for each version you release.

    G3 · Independent validation, ongoing monitoringValidators will try to rebuild it

    Independent validation includes re-performing the developer's results. A manifest that works makes validation days faster and findings fewer.

    Where it shows up at the bank:

    • Regulatory and committee numbers. Provisioning, stress tests and model-performance reports get challenged months later. Rebuildable figures end arguments quickly. I have not verified what CBUAE or SAMA require specifically on model documentation or reproducibility; ask your model risk and compliance teams for the internal standard.
    • Credit and collections logic. Bucketing, staging and exposure rules are full of thresholds, which makes them ideal boundary tests (Simulation 1).
    • Fraud and AML pipelines. Late labels, restated data and daily refreshes make the data checks of Simulation 2 and snapshots essential.
    • AI-assisted coding. The faster code is produced, the more the safety rests on tests you trust and diffs you read.

    Where the field is now

    The practices are mature. What is changing is who writes the tests (increasingly an AI), how we judge them, and how reproducible AI systems can be at all.

    Part 5

    How it fails, and how to spot it

    Each failure comes with the quickest check.

    • Coverage as the goal

      "We have 95% coverage" is offered as proof of quality. Tests with no assertions reach it easily.

      Spot itCount asserts per test. Delete one condition in the code and see whether anything fails. If not, the suite is decoration.
    • Tests that mirror the code

      The expected value is computed with the same formula, or copied from the output. A bug passes its own test.

      Spot itAsk where the expected number came from. It should trace to policy, a ledger figure or a hand calculation.
    • Only the happy path

      Typical values, no boundaries, no empty or null input.

      Spot itLook for 0, the thresholds exactly, one row, empty table, negative amounts and missing values in the test list.
    • Over-mocking

      Everything external is replaced with a stub that returns what the code wants, so the test checks only the stubs.

      Spot itIf the test still passes after you break the real database query or API call, it is not testing it. Keep at least one test on real or realistic data.
    • Flaky tests tolerated

      "Just re-run it." The suite loses authority and real failures get ignored.

      Spot itRun the suite five times in a row. Fix the seed, the clock or the ordering that makes it vary.
    • Reporting from an uncommitted notebook

      The figure came from a notebook with unsaved edits, out-of-order cells and a CSV on someone's desktop.

      Spot itAsk for the commit hash and data snapshot. "Restart and run all" should give the same number.
    • Silent environment change

      A library update changes a default and the same code gives a different AUC.

      Spot itCompare lock files between the old and new run. Compare numbers on a frozen sample.
    • Best-seed reporting

      The notebook tries seeds until the metric looks good, and only that run is saved.

      Spot itAsk how many seeds were tried and for the spread. Several seeds with a mean and range is the honest figure.
    • Secrets and data in git

      An API key or a customer extract is committed "just for now".

      Spot itCheck the repository before sharing it; rotate any exposed credential even after deleting the file, because history keeps it. Tell your security team.
    • Force-pushed history

      Someone rewrites a shared branch and the tagged commit disappears.

      Spot itProtect main and release branches; confirm the reported tag still resolves to the same hash.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “Every figure I give you will come with a reference: the exact version of the code, the exact data extract and the settings used. If someone asks in a year why the model said 0.87, we can rebuild it in an afternoon rather than argue from memory. And the code that calculates our arrears buckets has automatic checks at every threshold, so a change that moves a customer from 59 to 60 days cannot slip through unnoticed.”
    To a technical interviewer or validator
    “I test at boundaries and with properties, with expected values from policy, not from the code. I judge a suite by its mutation score on critical modules, not line coverage, and I read AI-generated tests for assertion strength before trusting them. Each run writes a manifest: commit, data snapshot and checksum, lock-file hash, seeds, config. I report a mean and range over seeds, not the best one, and I use data checks on every refresh for keys, dates, units, join counts and ledger reconciliation.”
    “The tests all pass. Can we ship?”

    They show the checks I wrote still hold. I would also ask what bugs they would catch: do they cover boundaries and the data assumptions, is there at least a reconciliation to the source, and has a reviewer read the diff? If the tests were generated, I would plant two or three deliberate bugs and see whether any test fails.

    “Is 80% test coverage enough?”

    The number does not measure what we need. Coverage says lines ran, not that results were checked. I would put the effort into boundary and property tests on the logic that moves money or risk, and use mutation testing there. A lower coverage with strong assertions beats high coverage with weak ones.

    “Why can't you just set the random seed and call it reproducible?”

    The seed fixes one run, but data, library versions and configuration can also change the answer, so I record all of them. And a seed is not evidence of quality: different seeds give different splits, so I show results across several seeds. A single lucky seed overstates performance.

    “Do we really need to version data? It is huge.”

    We do not copy everything into git. We keep an immutable snapshot or table version in the data platform, and record its identifier, row count and checksum in the manifest. What matters is that the same query tomorrow cannot silently return different rows. How long snapshots are retained is a question for the data owners and the model-risk policy.

    “Our LLM assistant gave a different answer this morning. Is it broken?”

    Not necessarily. Outputs vary with sampling, and even at temperature zero served models can differ run to run, and providers update models. I would check that we pinned the model version and prompt, then compare on a frozen evaluation set across several runs against a tolerance. A change in that score is a regression; a single different sentence is not.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. A test suite has 100% line coverage and a mutation score of 4%. What does that tell you?

    Nearly every line executes under test, but almost no change to the code makes a test fail. The assertions are weak or missing. Coverage measures execution, mutation score measures detection.

    2. Which inputs would you test for a function that assigns an arrears bucket from days overdue?

    Each side of every boundary (0 and 1, 29 and 30, 59 and 60, 89 and 90), a negative value (paid early), a very large value, and missing input if it can occur. Expected values come from the policy.

    3. An AI assistant writes a test whose expected value is assert result == calculate_fee(1000). What is wrong?

    It compares the function with itself, so it can never fail. The expected value should come from outside: a hand calculation or the tariff table, such as assert fee(1000) == 25.0.

    4. After a merge, the row count after joining customers rises from 600 to 648 and the sum of amounts rises too. Which check catches it and what is the likely cause?

    The row-count check after the join, and the reconciliation to the ledger. Likely cause: the customer table has duplicate keys, so a join fans out and duplicates transactions. A unique-ID check on the raw transactions would not catch it, because the duplication happens at the join.

    5. List the five things you must record to rebuild a reported AUC.

    The code (commit hash, clean tree), the data (snapshot id, row count, checksum), the environment (lock file or image digest), the random seeds, and the configuration (thresholds, hyperparameters, features).

    6. You run 40 seeds and the AUCs range from 0.84 to 0.90. A teammate reports 0.90. What is the fair statement?

    The model's AUC is around the middle of the range (for example 0.87) and varies by about 0.06 depending on the split. The 0.90 is the best draw. Report the mean or median with the spread, and use a held-out period for the final figure.

    7. You know commit 1 is good and commit 24 is bad. How many pipeline runs does git bisect need at most, and when does it not work?

    22 unknown commits between them need at most 5 runs (25 = 32 ≥ 22). It needs a reliable automatic good/bad verdict. If the metric is noisy, or an old commit does not run at all, the search misleads or stalls. Also, the history must contain small commits; one giant commit hides the cause.
