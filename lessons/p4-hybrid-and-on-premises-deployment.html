    Hybrid and On-Premises Deployment

    Part 1

    Where should the model run?

    In one sentenceWhere a model runs (inside the bank's own data centre, in a rented cloud, or split between the two) is a design decision made early, and usually forced by rules about the data, not by cost.

    Say a data scientist wants to fine-tune a language model on call-centre transcripts. Before any modelling, three people she has not met ask questions. Information security: do the transcripts hold names, account numbers or voices, and where would the GPUs sit? Compliance: is the provider approved, and may the data leave the country? Infrastructure: the bank's four on-premises GPUs are shared with fraud, so which week do you want them?

    None of these is about model quality, and all of them decide whether the project happens.

    The three options

    • On-premises: your own servers, in your own data centre or a rented room in someone else's. Full control, fixed capacity.
    • Public cloud: rented, elastic capacity, ideally in a region inside your country (see the previous lesson).
    • Hybrid: both, with a clear rule for which workload goes where.

    How it differs from the usual cost question

    Most teams ask "which is cheaper?" first. In a bank that is the wrong order. Data classification, law and latency are constraints: a pass or a fail, like a visa check. Only cost is a trade-off. A spreadsheet that says cloud is 30% cheaper is meaningless for a workload that may not legally run there.

    Part 2

    What forces a workload to stay put

    1. Data classification. Banks label data (public, internal, confidential, restricted). Policy ties each label to allowed environments. This is the first filter.
    2. Residency and outsourcing rules. Personal-data laws and financial regulators set conditions on moving data abroad. Using a cloud provider is usually treated as outsourcing, which needs approval, an exit plan and audit rights. Get the current wording from compliance or legal.
    3. Speed and coupling. A fraud score inside a card payment has tens of milliseconds. A trip to a distant region uses up that budget and adds a way to fail.
    4. Cost and supply. GPUs are scarce, power and cooling are real, and the bank may already own spare capacity.

    What running on-premises takes

    On-premises, you assemble what the cloud gives you for free.

    • A GPU scheduler (Kubernetes or Slurm) with quotas, so a student's experiment never starves fraud scoring.
    • Internal mirrors. Production networks often have no internet, so packages, images and model weights come from scanned internal copies. This stalls new teams first.
    • A model registry and serving, with rollback, plus data that arrives through paths with lineage.
    • Keys held in the bank's hardware security modules.

    Open-weight models make on-premises language-model work possible. Compressing the model (see the earlier lesson) is a direct lever: 4-bit can fit on one GPU what full precision needed four for.

    Part 3

    Hybrid: what makes it work and what makes it hurt

    Hybrid gives a clean rule per workload. The hard part is everything that crosses the boundary.

    • Data gravity. Moving terabytes is slow, costs fees, and every copy is one more thing to secure and delete. Move the code to the data. What must cross is usually aggregated, masked or synthetic.
    • Environments drifting apart. If you train in the cloud and serve on-premises, different library versions give slightly different predictions. Fix: build one container image and promote it through stages.
    • Failure paths. If real-time scoring needs a cloud link, a link outage becomes a fraud-control outage. Keep a local fallback, even a simpler model.

    The common pattern is a split by phase. Training is bursty and tolerates delay, so it goes where compute is elastic and the data allows. Serving is steady and speed-bound, so it sits inside the bank beside the systems that call it.

    Own or rent? Utilisation decides

    A car you own costs the same parked or driven. A taxi costs only per ride. A GPU server is the same: its cost is fixed (purchase, power, cooling, space, staff), so the cost per useful hour depends on how busy it is. Break-even is the busyness at which owning matches the rented price. Below it, rent. Above it, own.

    Owned GPUs busy 30% of the time
    Each useful hour costs about double what it would at 60%. Owning is probably dearer than renting.
    Owned GPUs busy 60 to 70%
    Good for a real cluster, and often past break-even. Ask for measured utilisation before buying more.
    Rented price drops by a big committed discount
    Break-even can move past 100%, meaning owning never wins on cost alone.
    Part 4

    Which to use

    OptionStrong atWeak at
    On-premisesControl of data, keys and speed; can be air-gappedUpfront cost, GPU lead times, fixed capacity, you run it
    In-country cloudElastic capacity, managed servicesNeeds approval; support may sit abroad; GPUs can be tight
    Local sovereign cloudBuilt for residency questionsSmaller catalogue; check contract and certifications
    HybridCheapest allowed place per workloadTwo platforms to secure; identity and data movement are hard
    External API or foreign regionBest models, no infrastructureUsually not allowed for restricted data

    Many bank models need no GPU at all: tabular fraud and credit models train on CPUs in minutes. Check the need first.

    Show the break-even formula

    Cost per useful hour (owned) = yearly cost of the server ÷ (hours in a year × utilisation × GPUs per server). Break-even is where this equals the rented price per GPU-hour. Doubling utilisation roughly halves the owned cost per useful hour.

    Part 5

    Common mistakes and quick check

    • Costing before checking constraints

      Ask who classified the data and who approved the provider. If the answer is "not yet", the comparison is premature.

    • Treating pseudonymised data as safe to export

      Hashed customer IDs can be reversed by trying every possibility, and linking datasets can re-identify people. It is still personal data under most regimes.

    • Real-time scoring over a distant link

      A network blip becomes declined cards or missed fraud. Look for a timeout and a local fallback.

    • Assuming high utilisation

      Clusters sit idle at night, between projects and while waiting for data. Ask for the measured figure, not the plan.

    1. Why can a cost model alone give the wrong answer in a bank?

    Classification, law and latency are pass-or-fail constraints. Cost only matters among the options that pass.

    2. A fraud model scores card payments in tens of milliseconds. Where does serving go?

    Inside the bank, beside the calling systems, with training placed wherever data rules and capacity allow.

    3. Owned GPUs run at 20% utilisation. Rent or own?

    Probably rent, unless the data cannot legally leave. Fixed costs spread over few useful hours make each one dear.

    4. You train in the cloud and serve on-premises, and scores differ slightly. Likely cause and fix?

    Mismatched libraries or feature code. Build one container image and promote it through stages.

    5. What should cross the hybrid boundary?

    As little as possible, and in reduced form: aggregated, masked or synthetic. Move code to the data, not data to the code.
