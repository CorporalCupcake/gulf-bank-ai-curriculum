    P6.3 Edge About 10 minutes

    Privacy-Enhancing Technologies

    Part 1

    What they are

    In one sentencePrivacy-enhancing technologies are tools that let you use or share data while limiting what anyone can learn about individuals. Each protects something different and costs something different.

    Running example: a bank group operates in several countries, and a mule-account ring (accounts used to pass stolen money along) moves money through all of them. Each subsidiary sees only a slice. A group model would see far more, but customer data is personal data and each country restricts moving it.

    Four tool families answer four different questions. Most confusion comes from treating them as one thing.

    QuestionToolPlain idea
    Can a published answer give away a person?Differential privacyAdd random noise so the answer is almost the same with or without any one person
    Can two parties join data without seeing each other's?Clean rooms, private set intersectionA controlled space where only approved, aggregated results leave
    Can someone compute on data they cannot read?Homomorphic encryption, secret sharingMaths that lets a server add numbers it cannot see
    Can I train a model without moving the data?Federated learningSend the model to the data, send back only updates, average them

    Each leaves a gap. Differential privacy protects the output, not the raw data. A clean room is mostly governance. Encryption is slow. Federated updates can leak. The skill is knowing which gap you can live with.

    Part 2

    Differential privacy: noise that hides one person

    Think of a fogged window: you see the shape of the crowd, not one face. A branch publishes how many customers hold a product. We add random noise to that count. Now ask: was Hessa in the data? The noisy answer is almost equally likely either way.

    How to read it

    • The dial is epsilon (ε). Small ε means strong privacy and noisy answers. Large ε means accurate answers and little protection. Roughly, ε near 1 is strong and above 10 is largely symbolic.
    • Noise is fixed in size. A count changes by at most 1 per person, so the noise is about 1/ε counts whatever the dataset size. An error of 10 on a 1,200-customer segment is under 1%. On a group of 15 customers it ruins the answer, and small groups are the ones you most want to protect.
    • Privacy is a budget. Every query spends some ε. Ten queries sharing ε = 1 get 0.1 each, so ten times the noise each. When the budget is gone, the data is closed.
    • Averages need a cap. One customer with AED 80 million can swing a mean balance, so each value is clipped at a limit. Too high adds needless noise; too low biases the answer down.
    • Check the unit. A customer with 4,000 transactions is 4,000 rows. A guarantee per row says little about the customer.
    Part 3

    The other three, in plain steps

    Clean rooms and private set intersection

    A clean room holds data from two parties joined on a shared key. Analysts can run only approved analyses, with no row-level output, a minimum group size and an audit log. In most products this is access control and contract, not cryptography. The operator, or a bug, could in principle see the joined data.

    Private set intersection is the cryptographic cousin: two parties learn which identifiers they share and nothing about the rest. Use it for shared watch-lists, or to check whether an account on a mule list appears at a counterparty.

    Encryption and secret sharing

    Homomorphic encryption lets a server compute on data it cannot read and return a result only the owner can open. Like a locked glovebox, the server works the gloves without seeing inside. The catch is cost: computation is orders of magnitude slower. Training large networks under encryption is out of reach today. Private lookups and sums work.

    Secret sharing is simpler and does more practical work. How it works:

    1. Each entity splits its number into random-looking shares.
    2. It gives one share to each party.
    3. Any incomplete set of shares is pure randomness.
    4. Adding everyone's shares gives the exact total.

    Used across several entities, this is called secure aggregation. Its limit: it hides individual inputs, not what the total reveals. With three entities, two can subtract their own figures from the total and recover the third.

    Federated learning

    The model goes to the data, not the data to the model.

    1. A server sends the current model to each entity.
    2. Each entity trains it locally for a few steps.
    3. Each returns only the change (the update).
    4. The server averages the updates. Repeat.

    The usual difficulty is that countries have different customers and fraud patterns, so each entity pulls the model its own way and the average can suit nobody. Federated learning is also not a privacy guarantee. Updates are computed from the data, and attacks can reconstruct inputs from them. Serious designs stack the tools: secure aggregation so the server sees only the sum, and differential privacy on the updates so the sum leaks little.

    Part 4

    Which to use

    ToolProtectsCosts youReady today?
    Differential privacyPublished resultsAccuracy, esp. small groupsYes, for statistics on large groups
    Clean roomJoined data, by rulesTrust in the operatorYes, widely sold
    Encryption / secret sharingInputs during computationSpeed, complexitySums and lookups only
    Federated learningRaw data locationCoordination, driftPilots across a few entities
    • Strong at: letting groups collaborate when data cannot move, with a clear statement of what is protected.
    • Weak at: none is a legal basis on its own, and most failed projects fail on agreements (one label definition, one feature schema, one model owner) rather than maths.
    Show the formula

    Noise size for a count ≈ 1 ÷ ε. Halving ε doubles the typical error. With a budget split over q queries, each query gets ε ÷ q, so its noise is q times bigger.

    In banking, start with the question (publish, join, compute or train), pick the tool for that gap, and ask what it protects, from whom, and at what cost.

    Part 5

    Common mistakes and quick check

    • "It is differentially private" with no ε

      Ask for ε, what one unit protects (row, customer, account) and how many releases share the budget.

    • Small cells in a clean room

      A query returning 3 people, plus one with an extra filter, isolates someone. Check minimum group sizes and query logs.

    • "The data never leaves, so it is anonymous"

      Federated updates can be inverted. Ask who sees individual updates.

    • Encryption oversold

      A demo on 1,000 rows is not production. Ask for speed on real-sized data.

    1. You halve ε from 1 to 0.5 on a count. What happens?

    The typical noise doubles, and an attacker learns less from one answer.

    2. A quarterly budget of ε = 1 is shared by 25 dashboard counts. What is the cost?

    Each gets about 25 times the noise of a single count. Small cells become unusable.

    3. What does a clean room not guarantee?

    It is mostly rules and contract, so the operator might still see the joined rows. Ask who operates it.

    4. Two of three entities pool their figures with the published total. What do they learn?

    They recover the third entity's figure exactly. Add noise to the total or use more participants.

    5. Why is federated learning alone not private?

    Updates are computed from the data and can be inverted. Add secure aggregation and differential privacy.
