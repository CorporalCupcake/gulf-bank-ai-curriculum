    The Model Lifecycle, and Knowing Exactly Which Model Is Running

    The stages a bank model passes through, why review cadence matters, how experiment tracking stops you fooling yourself, and what a registry must answer when an auditor asks.

    Contents

    The whole lesson in one sentenceA model is a controlled asset with a life: stages, owners, gates and decay. At every moment the bank must say which version is running, what built it, who approved it, and how to go back.

    Part 1

    The intuition

    A data scientist builds a card-fraud model in a notebook, and someone copies its output into a scoring service. Nine months later a regulator asks: which model is this, who approved it, what data trained it? Nobody can say. The model may be fine. The bank cannot show it.

    The lifecycle is the fix. Treat a model like an aircraft part, not a document: design, tests, certificate, serial number, scheduled inspections, retirement date. None of this adds accuracy. It makes the model trustworthy, reproducible and reversible.

    • Models decay, so the work is never finished. They drift from right to wrong silently, so the lifecycle builds in a monitoring and review loop.
    • Identity is the foundation. You cannot audit, roll back or retire "the model" unless it is a precise versioned thing: this code, this data snapshot, these parameters, this approval.
    Hold onto thisEvery question about a production model is one of four: what is it exactly, how was it made, who allowed it, how do we undo it.
    Part 2

    How it really works

    The model lifecycle, stage by stage

    Model-risk policies worldwide (US SR 11-7, the CBUAE Model Management Standards, SAMA's expectations) share the same nine stages. Step through them: what happens, what artefact it leaves, who signs, and what breaks if it is skipped.

    • It is a loop. Monitoring feeds change, and a recalibration is a new version needing its own approval, scaled to how material it is.
    • Tiering sets effort. A fraud model that can block thousands of customers gets full independent validation and frequent review. A model that routes internal emails does not.
    • Independence is structural. Builders cannot validate their own model, like marking your own exam.

    Decay and review cadence

    Models go stale like milk, not like a light bulb: quality slides slowly (new fraud tactics, a changed customer mix) or drops suddenly when an upstream feed breaks. The lifecycle question is: how often do you look, and how stale is the answer?

    A breach of the agreed quality floor is only found at the next scheduled review, and only once labels have matured (F3.5, B1.2). On average you wait about half a review interval plus the label delay; at worst a full interval plus the delay. Every month below the floor is harm: missed fraud, wrong provisions, mispriced loans.

    Review cadence is a risk decision with a price. A quarterly review is the interval at which you accept being wrong. And automation shrinks the interval, not the label delay. A weekly dashboard cannot see true performance if fraud labels take eight weeks, so input-drift monitors (PSI, KS, F7.7) run alongside: earlier warning, weaker evidence.

    Experiment tracking: counting what you tried

    Development is hundreds of runs, not one model. An experiment tracker (MLflow, Weights & Biases, or a bank-built tool) records for each run:

    • Code and data version: git commit, and a snapshot ID or hash of the exact training table (F3.1).
    • Parameters and environment: hyperparameters, seed, feature list, library versions.
    • Metrics and artefacts: validation scores, plots, the fitted model file.

    It is a lab notebook that cannot be edited afterwards. Its first use is reproduction (F10.4). Its second is honesty about selection. Roll a die 100 times and report only the highest roll: it looks lucky because you chose it. The best of N similar configurations is likewise biased upward, because the winner was partly lucky. More tries, noisier scores and smaller real differences all widen the gap between reported and true quality. Only the tracker tells you N.

    The remedy is not fewer experiments. Keep a test set that selection never touched, report N beside the best score, and use nested validation when it matters (F4.5, F4.9).

    The model registry: what is live, and why

    The tracker records attempts. The model registry records decisions, like a car registration tying a plate to one vehicle, its owner and its inspections. It holds named models with numbered versions, each linked to the run that made it, plus:

    • Alias or stage: a movable label such as champion or challenger. Serving code asks for "the champion of fraud-card", never a file path, so promotion and rollback are label moves.
    • Metadata: owner, risk tier, validation and approval status, model card, data snapshot, code commit.
    • History: an append-only log of who moved which label, when, under what ticket.

    The rule that makes it a control: a label moves only if the evidence is attached. A version without independent validation and approval cannot become champion. Only the release process may write the alias.

    Registries expose the traps: a model whose training data was overwritten is a name without an identity, and a rollback target whose libraries no longer install is not a rollback. Good practice: immutable versions, pinned environments (an image digest, not "latest"), data snapshots by reference (P1.5), and a retention policy. For generative models the "model" also includes the prompt, retrieval index, tools and guardrails (P2.5).

    Part 3

    How it fails, and how to spot it

    • The notebook that became production

      Hand-set paths, no environment spec. Nobody can rebuild it.

      Spot itAsk for the command that retrains the live model from scratch. Run it on a clean machine.
    • The unlogged winner

      A headline score is the best of many runs and the count is never reported.

      Spot itAsk how many configurations were tried and whether the test set helped choose.
    • An identity that is only a name

      The data version is a table that refreshes nightly, or the approval names "the fraud model", not a version ID.

      Spot itCheck that data references are immutable snapshots and each approval names an exact version.
    • Promotion or rollback outside the registry

      A file is copied to the serving host by hand, or the rollback target no longer installs.

      Spot itCompare the production hash with the champion's, and ask when the last rollback drill ran.
    • Review cadence set by habit, not risk

      Every model is reviewed annually, even a fast-decaying fraud model.

      Spot itCompare the review interval with the decay rate and label delay.
    • Shadow models and zombies

      Old models still scoring unmonitored, or retired ones still read downstream.

      Spot itReconcile the inventory against what is running.
    Part 4

    Self-check

    1. Name the four questions a lifecycle and registry should answer about any production model.

    What is it exactly? How was it made? Who allowed it? How do we undo it?

    2. A model breaches its quality floor at month 8.75. Reviews are every 6 months and labels take 3 months to mature. Roughly when is it detected, and why?

    At month 12: labels only mature around month 11.75, and the next review falls at 12. It ran below the floor for about 3 months.

    3. Why does weekly automated monitoring not remove the label delay?

    Outcome-based metrics need outcomes. Drift and proxy metrics warn earlier but are weaker evidence, so they trigger a review rather than replace it.

    4. You tried 200 near-identical configurations and the best has validation AUC 0.84 on 200 positives. Is that a better model?

    Probably not. With that many tries and few positives, chance alone can lift the best score several points. Confirm on a test set selection never touched.

    5. What is the difference between an experiment tracker and a model registry?

    The tracker records every attempt. The registry records decisions: which versions exist, who approved them, which is live.

    6. Why should a registry store a data snapshot ID, not a table name?

    A table name points at whatever the table holds today. A snapshot ID points at exactly the rows the model saw.

    7. A recalibration of a live credit model is proposed. Is it a new model version?

    Yes. It changes predictions, so it gets a new version and validation and approval in proportion to materiality.
