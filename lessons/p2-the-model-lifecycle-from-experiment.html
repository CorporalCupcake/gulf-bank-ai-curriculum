    The Model Lifecycle and Versioning

    Part 1

    What the model lifecycle is

    In one sentenceThe model lifecycle is the set of stages a model passes through from first experiment to retirement, and versioning is the practice of giving every model an exact, unchangeable identity so you can always say which one is live and why.

    The running example is a card-fraud model. At any moment, a bank must be able to answer four questions about it: what is it exactly, how was it made, who allowed it, and how do we undo it?

    Model-risk rules around the world (the US SR 11-7 guidance, the CBUAE Model Management Standards, SAMA's expectations) share this idea. Each stage leaves evidence, called an artefact, such as a report, a signature or a log entry.

    Part 2

    How it differs from other things you know

    • Lifecycle vs a software release. Code either works or it does not. A model can work perfectly in testing and slowly go stale, so it needs ongoing review.
    • Experiment tracker vs registry. The tracker (MLflow, Weights & Biases) records every attempt. The registry records decisions: which versions exist, who approved them, which is live.
    • Version vs file name. "model_final_v2.pkl" says nothing about data or code. A proper version points to the exact training data, code commit and settings.
    Part 3

    How it works

    1. Experiment and log. Developers run many trials. The tracker records, for each run, the code commit, the data snapshot, the settings and the scores.
    2. Validate independently. A separate team reviews the model. Builders cannot mark their own exam.
    3. Approve. A named person or committee signs off for a stated use. How much scrutiny depends on the model's tier: a fraud model that can block thousands of customers gets the full process, a model that routes internal emails does not.
    4. Register. The approved model becomes a numbered version in the registry. The version is immutable, which means it never changes once saved.
    5. Deploy by label. The registry holds movable labels such as champion (live) and challenger (being tested). Serving code asks for "the champion of fraud-card", never a file path.
    6. Monitor, then retrain or retire. Quality is tracked. A retrained or recalibrated model is a new version that goes round the loop again.

    The rule that makes a registry a control, not just a list: a label moves only if the evidence is attached. A version without validation and approval cannot become champion, and only the release process may move a label.

    Part 4

    How to think about it

    Models go stale like milk

    Quality usually slides slowly (new fraud tactics, a changed customer mix) or drops suddenly when an input feed breaks. The question is how often you look and how long the answer takes to arrive.

    • Label delay. You only know a fraud prediction was right once the outcome is confirmed. If labels take 3 months, a breach is invisible for at least 3 months.
    • Review interval. A model that falls below its agreed quality floor at month 8.75, with reviews every 6 months and a 3-month label delay, is detected around month 12. It ran below the floor for about 3 months.
    • Automation shrinks the interval, not the label delay. Weekly dashboards help, and drift monitors give earlier but weaker warning. They trigger a review rather than replace it.

    The best of many tries looks better than it is

    Roll a die 100 times and report only the highest roll: it looks lucky because you chose it. The best of 200 similar model configurations is likewise biased upward, because the winner was partly lucky. Keep a test set that selection never touched, and report how many tries you made beside the best score.

    Part 6

    Common mistakes and quick check

    • The notebook that became production

      Hand-set paths and no environment record mean nobody can rebuild it. Ask for the command that retrains the live model from scratch.

    • An identity that is only a name

      An approval for "the fraud model" names nothing. Approve an exact version ID.

    • Copying files by hand

      Promotion outside the registry breaks the audit trail. Compare the production hash with the champion's.

    • One review cycle for every model

      A fast-decaying fraud model needs more frequent review than a stable one. Set cadence by risk.

    1. Name the four questions a lifecycle and registry should answer.

    What is it exactly, how was it made, who allowed it, and how do we undo it?

    2. What is the difference between a tracker and a registry?

    The tracker records every attempt. The registry records decisions: versions, approvals and which is live.

    3. Why store a data snapshot ID, not a table name?

    A table name points at whatever it holds today. A snapshot ID points at exactly the rows the model saw.

    4. A recalibration of a live credit model is proposed. Is it a new version?

    Yes. It changes predictions, so it gets a new version and validation and approval in proportion to how material it is.

    5. Why does weekly monitoring not remove the label delay?

    Outcome-based metrics need outcomes. Drift metrics warn earlier but are weaker evidence.
