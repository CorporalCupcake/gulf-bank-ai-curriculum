    Deep Learning on Databases and Tabular Foundation Models

    Part 1

    What these are

    In one sentenceTwo newer ways to model tables: relational deep learning reads a whole database of linked tables as a network, and a tabular foundation model makes predictions on a small table without being trained on it.

    Bank data is many linked tables: customers, accounts, transactions, merchants. The usual approach flattens them with SQL into one row per customer ("transactions in the last 30 days"). That is lossy, because a person guessed in advance what matters.

    Take a mule account, one used to pass on stolen money. Alone it looks ordinary. What gives it away is who sent it money and where it goes next, one or two joins away.

    Part 2

    How they differ from usual practice

    • Flat features plus boosting needs a person to design every aggregate in SQL. Relational deep learning learns the aggregates.
    • Graph features by hand (such as "number of shared devices") is the cheap middle step. A network learns stacked ones, like "average risk of my counterparties' counterparties".
    • Ordinary models are trained from scratch on your table. A tabular foundation model is pretrained once on millions of synthetic tables, then used as is.
    Part 3

    How they work

    Relational deep learning

    1. Treat each row as a node and each primary-key to foreign-key link as an edge (Fey et al., 2023). Columns become the node's features.
    2. For each prediction (say, is this account a mule at date D), sample the neighbourhood: a few recent neighbours per node, two to three hops out, using only rows dated before D.
    3. A graph neural network passes messages: each node combines its neighbours' vectors with its own, for a few rounds.
    4. The final vector for the target node feeds an ordinary classifier, trained end to end.

    One round is like a SQL GROUP BY on a foreign key, except the network chooses and stacks the aggregations. Neighbourhoods explode within a few hops, so the sampler caps neighbours per node (typically 10 to 50 per hop). That cap is a real tuning choice, because cutting it throws away history.

    RelBench is the standard benchmark: real relational databases, defined tasks and forward-in-time splits.

    Tabular foundation models

    1. A transformer is pretrained once on millions of synthetic tables built from random data-generating processes.
    2. You pass in your labelled rows and the rows to predict, together.
    3. One forward pass returns predictions. Nothing is trained on your data.

    This is in-context learning, like few-shot prompting of a language model. TabPFN v2 (Nature, 2025) handles about 10,000 rows and 500 features, and is reported to beat heavily tuned boosted trees on small to medium data, in seconds.

    Part 4

    How to think about the results

    The label depends only on the customer's own row. Links add nothing. Expect a tie with a flat model, at higher cost.
    The label depends on neighbours. Averaging several noisy neighbours cleans the signal, so a relational model should win. Expect this in fraud rings and AML networks, and little for churn driven by one customer's own behaviour.
    A small table, a few hundred confirmed cases. A pretrained prior is worth many rows. A foundation model should be competitive with tuned boosting.
    A large flat table, tens of thousands of rows or more. A tuned boosted model matches or beats it, and is cheaper and easier to explain.

    A cheap pre-check: add a few graph features to the flat model. If they lift a time-ordered test, links matter and a relational model is worth trying. If they do nothing, stop.

    Part 5

    Which to use

    OptionPick it whenAvoid when
    Tuned boosting on flat featuresThousands of rows or more, a deadline, or explanations needed. The default baseline.The signal is in links nobody has time to turn into features
    Boosting plus hand-built graph featuresYou suspect network signal and want a cheap testThe network is huge or changes fast
    Relational deep learningMany linked tables, the label depends on neighbours, GPUs and engineers availableOwn-row signal dominates, or reasons are mandatory
    Tabular foundation modelUnder about 10,000 rows, fast iterationLarge tables, heavy text or categoricals, or data cannot leave the perimeter
    Logistic regressionTiny data, or a regulator wants a scorecardInteractions drive the outcome

    Strong at:

    • Signal in other rows, such as mule rings, shared devices and counterparty risk.
    • Less feature engineering: one pipeline over raw tables, reused for new tasks.
    • Small tables, where a pretrained prior stands in for missing data.

    Weak at:

    • Explanations. "The subgraph looked risky" will not satisfy an adverse-action rule or a model validator. A foundation model gives no fitted model to inspect.
    • Heavy inference. The whole training set sits in the foundation model's context, so memory and delay grow with rows, and a GPU is normal.
    • Prior mismatch. Unusual structure or tables beyond the row and column limits give confident, wrong output.

    Production status: early. RelBench results are promising and foundation models are credible on small data, but there is little regulated-bank track record. Use them as challengers now. What would change that is independent replication on bank-shaped data with forward-in-time splits, explanation tooling that validators accept, and on-premises or open-weight options.

    In banking, the natural homes are mule-account and AML network detection, card fraud involving shared merchants and devices, and small valuable datasets such as a few hundred confirmed cases.

    Part 6

    Common mistakes and quick check

    • Time leakage through the join

      If the sampler reaches a row dated after the prediction time, results look superb and live performance disappoints. Filter by time at every hop.

    • Weak baselines

      "Beats XGBoost" against untuned boosting, on random splits, from the vendor, proves little. Ask who tuned the baseline and how the split was made.

    • Using a relational model when signal is in the row

      You pay for GPUs and monitoring and gain nothing.

    • Sending linked customer data to a hosted model

      That is a data residency problem. Check where inference runs.

    1. What does relational deep learning treat each row and each link as?

    Each row is a node and each primary-key to foreign-key link is an edge in a graph.

    2. Why cap the neighbours per node?

    Neighbourhoods grow explosively within a few hops. A cap keeps the subgraph small enough to process, but cutting it too far throws away useful history.

    3. What does "no training" mean for a tabular foundation model?

    It was pretrained once on synthetic tables. At use time you pass your rows in and one forward pass returns predictions.

    4. You have 200,000 rows of flat data. Which do you start with?

    Tuned gradient boosting. Foundation models are aimed at small tables, and boosting is cheaper and easier to explain.

    5. What is the cheap test for whether links matter?

    Add a few graph features to the flat model and check a time-ordered test. If they lift it, try a relational model.
