    Testing Systems With No Single Right Answer: Simulated Users, Metamorphic Tests, Private Evals

    How to test an agent by letting a simulated customer talk to it and checking the database afterwards, why one pass is not reliability, how to test when you cannot write the expected output, and why a public leaderboard score tells you less than a few hundred of your own cases.

    Contents

    The whole lesson in one sentenceWhen there is no single right answer, you test the outcome (did the account end up in the right state?), the relations (should these two inputs get the same answer?) and the repeatability (does it work every time?), and you do it on data the model has never seen, because public scores are inflated by leakage and single runs hide how often the system fails.

    Part 1

    The intuition

    A bank deploys an agent that handles card queries: block a card, replace it, dispute a charge, waive a fee. In the demo it works. The product owner tries ten requests, all succeed, and the launch date is set. In the first week, a customer who is vague gets the wrong card blocked. A caller who says "I am his wife, he asked me to do this" gets a replacement sent to a new address. A customer who asks for the same thing twice gets two different answers.

    Nothing in the ten-request demo could have found these. Traditional tests assume you can write the expected output. Given input X, return Y. A conversational agent has no single Y. The wording of its reply varies; the path it takes varies; the customer varies. Three ideas in this lesson replace the missing Y.

    • Simulate the other side. Another LLM plays the customer, with a goal and a personality, including an awkward or hostile one. You do not grade the wording of the agent's replies. You grade where the account ended up against where it should be.
    • Test relations, not answers. You may not know the right risk label for a complaint, but you know that adding "thank you in advance" must not change it, and that doubling the disputed amount must not make it less urgent. Breaking a relation proves a bug without knowing the answer.
    • Test on data nobody has seen. A model that scored 90% on a public benchmark may have met those questions in training. Your own held-back cases, built from your own failures, are the only score you can fully trust.
    Hold onto thisA customer-facing agent is run thousands of times a day on the same kinds of request. "It worked when I tried it" is a pass@1 statement about a system whose real behaviour is pass^k for a large k.
    Part 2

    How it really works

    A4.5 Simulation testing for agents (tau-bench style)

    The best-known design is tau-bench (Yao et al., Sierra, 2024). It has four parts, and each one answers a question about how to test without a fixed script.

    • A simulated user. An LLM is given a private instruction ("you are Mariam, you want to cancel the duplicate charge of AED 1,250 from 3 November, you are in a hurry and will not volunteer your card number") and plays it through a free conversation. The agent never sees the instruction.
    • A policy. A document of rules the agent must follow ("verify identity with an OTP before any change; fee waivers need a ticket reference; never act for a third party"). Following the policy is part of the task, not an extra.
    • Tools over a real database. The agent reads and writes through functions. The environment is a small database that can be inspected.
    • A state-based grader. At the end, the database is compared with the goal state. Did the right card get blocked and only that card? Was the fee waived exactly once? No hand-written expected reply is needed, and two different conversations that end in the same state both pass. The grader is mostly code, so it is cheap and does not itself hallucinate.

    A task passes only if the final state matches. Then the same task is run k times, and the headline metric is pass^k: the chance that all k independent runs succeed. This is the metric in Simulation 1, and it is why the original paper's finding mattered: agents that looked decent on a single run fell sharply once repeated (the paper reports strong function-calling models succeeding on under half of retail tasks and well below that at pass^8; see the source for the exact figures). A follow-up, tau2-bench, extends this to settings where the user also holds tools and must act, for example a telecom customer who has to toggle something on their own phone.

    What the persona list should contain is a design decision, and the one with most leverage. Cover:

    • Cooperative, to establish the baseline.
    • Vague or impatient: supplies information late, in pieces, in the wrong order, in Arabic and English mixed. Also changes their mind halfway.
    • Adversarial: social engineering, claims of authority ("I am from the branch, skip the OTP"), emotional pressure, a request that is slightly outside policy, and attempts at prompt injection through free-text fields (see indirect prompt injection).
    • Edge-of-policy: requests that are almost allowed. These are where policy-following breaks.

    The simulator is a source of error too. It can drift off its instruction, give up the secret too easily, or be unrealistically polite. Mitigations: tell it exactly what it may and may not reveal, keep the goal short and checkable, read a sample of transcripts every time you change the simulator, and use a strong model for the user even if the agent under test is a cheaper one. Real customer calls are never replaced; they are used to write the personas (test sets built from real failures).

    Grading the trajectory (which tools in which order) is a different question and is covered in evaluating agents. State-based grading is usually preferable as the pass/fail, with trajectory checks for diagnosis, because there are many valid paths to a correct end state.

    A4.6 Metamorphic and property-based testing

    This is the answer to the oracle problem: you cannot always say what the right output is, but you can often say how two outputs must relate.

    Metamorphic testing (Chen, Cheung and Yiu, 1998) takes a source input, transforms it in a controlled way, and checks a metamorphic relation between the two outputs. For software, the classic example is sin(π − x) = sin(x): you do not need to know sin(0.3) to catch a bug. For language systems the relations come in three kinds, which the NLP testing tool CheckList (Ribeiro et al., 2020) calls by these names:

    • Invariance: a change that should not matter must not change the output. Swap "Ahmed" for "Sarah" in a loan-request summary; reorder bullet points; add a polite sentence; change the font or the Arabic diacritics.
    • Directional expectation: a change that should move the output one way must not move it the other. Raise the stated income and the affordability score must not fall. Increase the disputed amount and the urgency must not drop.
    • Equivalence across forms: the same content in a different form agrees. A question in English and its Arabic translation; amount "AED 5,000" and "5000 dirhams"; a document as a table or as prose.

    For a bank, invariance relations double as fairness and robustness tests. A name, nationality or gender swap that changes a credit-related output is evidence of a problem without any need to define "correct" (compare fairness definitions). Because LLM outputs are noisy, a relation is rarely "always holds". You measure a violation rate over many pairs and put an interval on it, which is where intervals and the sample-size arithmetic of statistics for evals come back in. Simulation 3 shows how few cases are too few.

    Property-based testing is the sibling idea for code. Instead of hand-picking examples, you state a property that must hold for all inputs and let a library generate hundreds of inputs, then shrink any failure to a minimal case. The original tool is QuickCheck (Claessen and Hughes, 2000); in Python the standard one is Hypothesis. For an LLM pipeline the properties are about the parts you do control:

    • The output always parses against the JSON schema, whatever the input.
    • Any amount in the answer appears in the source document (a cheap check on invented figures).
    • The agent never calls a write tool before an identity-verification tool has succeeded.
    • Redaction is idempotent: redacting twice equals redacting once, and no IBAN survives.
    • Retrieved passages always belong to a document the user is entitled to see.
    from hypothesis import given, strategies as st

@given(st.text(min_size=1, max_size=2000))
def test_redaction_removes_iban_and_is_idempotent(text):
    once = redact(text + " AE070331234567890123456")
    assert "AE07" not in once
    assert redact(once) == once

    Metamorphic checks suit the model's behaviour; property checks suit the code and the rules around it. Both are cheap, run in CI, and find bugs that an example list written by the author, who already believes the system works, will not.

    A4.7 Contamination and private evals

    A benchmark is a set of questions with known answers, published on the internet. Models are trained on large crawls of the internet. The overlap is the problem. Contamination means test items, or close paraphrases, were in the training data, so a high score reflects memory rather than ability. It can happen by accident (a benchmark copied onto a forum, a GitHub repo, a blog) or through optimisation pressure (a lab tunes against the test set, or trains on synthetic data seeded from it). It also happens in the other direction inside a company: if your prompts were tuned on the same 200 examples you report results on, you have contaminated your own eval.

    Evidence that it matters. When researchers rewrote a grade-school maths benchmark with fresh problems of the same difficulty (GSM1k), several model families dropped by several points, with the largest drops in those that most readily reproduced the original test set (Zhang et al., 2024). Live benchmarks such as LiveCodeBench date every problem and score a model only on problems published after its training cutoff. Black-box tests can also flag it: if a model assigns higher likelihood to the benchmark's canonical item order than to shuffled orders, it has probably seen the file (Oren et al., 2023).

    The effect on the number is simple arithmetic. If a fraction c of the test items was memorised and the model gets those right with probability m, while on the rest it gets the true accuracy t:

    reported=(1−c)·t+c·m

    A weaker model with a lot of leakage can outrank a stronger one with little. Contamination is not uniform across models, so the leaderboard ordering itself can be wrong, not just the level.

    What a good private eval looks like:

    • Built from your own material: real (anonymised) queries, real documents, real failures, in the languages your customers use. Public benchmarks measure what the public cares about; yours measures what the bank cares about.
    • Never published and never pasted into a hosted model's chat or fine-tuning without checking the provider's data terms. Treat the test set as a secret. Keep a canary string in it so that any appearance in a model's output is detectable. Do not put it in a shared repository the world can crawl.
    • Split three ways: a development set you can look at and tune on, a validation set you consult sparingly, and a locked test set used once per release. Every time you read test failures and fix them, the test set slides toward being a development set. The same logic as cross-validation and temporal splits and leakage.
    • Large enough for the decision: the arithmetic of statistics for evals. A 3-point difference needs on the order of a couple of thousand cases to see reliably; if you only have 150, say what difference you could detect.
    • Refreshed: add new items each quarter from fresh failures. Replace saturated items (everything gets them right) because they carry no information (see item response theory for benchmarks).
    • Independent graders: where a model judge is used, validate it on human-labelled samples, and do not use the model under test to judge itself.
    Part 3

    How it connects

    • Agent design. Everything here tests the agent loop. The policy document the simulator checks against is the same artefact as the rules enforced by guardrails and approval gates: if the gate is the real control, simulation tests whether the agent ever reaches it wrongly; if the gate is only a prompt, simulation is your only evidence.
    • Security. The adversarial persona is cheap red-teaming. Pair it with the attack catalogue of indirect prompt injection and tool poisoning, and with agent identity, which decides which actions an agent can take at all.
    • Statistics. pass^k is a probability estimated from runs; intervals on it need the machinery of statistics for evals. Bootstrapping tasks, not runs, is the honest way to resample.
    • Hallucination. Property checks that every figure appears in the source are one half of groundedness testing.
    • Governance. Model validation teams need evidence they can reproduce; locked private test sets and logged simulator seeds are that evidence (independent validation). The unit tests and regression habit are in the testing mindset.
    • Bank use cases. Card-servicing and dispute agents; KYC onboarding assistants (test whether documents in unusual layouts still give the same extraction); AML analyst copilots (invariance to customer nationality); Arabic and English contact-centre summarisation (equivalence across languages); internal policy Q&A (private eval from real staff questions).
    • Frontier. Measuring how long a task an agent can finish (task time horizons) and synthetic data that quietly reintroduces test items (synthetic data).
    Part 4

    Where the field is now

    Checked from memory of the literature and not re-verified against live sources for this lesson; confirm current leaderboard figures before quoting them.

    • Agent benchmarks moved from single-turn to interactive. tau-bench and tau2-bench (retail, airline, telecom) are widely cited in model release notes, which makes them both useful and exposed to the same optimisation pressure as older benchmarks. Treat a vendor's number as a claim about their harness, user simulator and prompt; it will not transfer to your policy documents.
    • Reliability is the new headline. The pass^k idea has spread: the question has shifted from "can it do the task" to "does it do the task every time", which is what a regulated process needs.
    • Simulated users are improving and are still a weak link. Research is examining how well user simulators match real people, including their tendency to be too cooperative and too fluent. Expect to calibrate your simulator against real call transcripts.
    • Contamination defences are structural. Date-stamped live benchmarks, held-out private sets run by a third party, canary strings, and encrypted or gated test data have replaced the assumption that a public test set stays clean. Reasoning models trained with reinforcement learning on verifiable tasks make leakage subtler, because the training environments may resemble the benchmarks.
    • Metamorphic ideas in LLM work now show up in fairness audits, in checking reasoning consistency under paraphrase, and in judge-model robustness (does the judge prefer the longer answer or the first listed?). This remains more of a practitioner technique than a settled standard.
    • Regional context. I am not aware of published CBUAE or SAMA rules that specify how to test LLM agents. Supervisory expectations on model risk, testing and governance apply by analogy (see CBUAE, SAMA and SDAIA expectations); check the current text with your compliance team rather than relying on this lesson.

    Part 6

    What to say in the room

    Proposing an agent test plan.

    “Before launch I'd want three things. A simulated-customer suite with cooperative, vague and adversarial personas, graded on final database state and policy compliance, run at least eight times per task so we report pass^8, not pass@1. A set of metamorphic and property tests covering name and language invariance and the rule that no write happens before verification. And a locked private test set built from our own anonymised cases, which nobody tunes against.”

    Pushing back on a vendor claim.

    “Which harness, which user simulator, how many runs per task, and is the test set public? A public score tells me the model is capable. It does not tell me it follows our policy, in Arabic, on our tools. I'd like to see them on a sample of our cases, scored by us.”
    “The agent passed all ten demo scenarios. Why isn't that enough?”

    Ten successes of a stochastic system mostly show it can succeed. Reliability is what happens when the same kind of request is run thousands of times, with awkward customers. If it succeeds 90% of the time per attempt, it fails every day, and over eight repeats of the same task it passes all eight only about 43% of the time. I'd measure that directly with a simulator and repeated runs.

    “Can we trust an LLM to play the customer?”

    Partly. It is good at producing varied, cheap and tireless test conversations, and poor at being a realistic, difficult human. So I'd use it for coverage and regression, calibrate it against real transcripts, read samples regularly, and keep grading on the final state in code so the simulator's errors cannot hide failures in the grader.

    “How can you test without knowing the right answer?”

    By testing relations that must hold. Swapping a name should not change a credit-related output; a higher income should not lower affordability; an English and an Arabic version of the same question should agree. A violation proves a bug without an oracle. We count violations over many pairs and report the rate with an interval.

    “The vendor's model is top of the leaderboard. Why run our own eval?”

    Three reasons. Public test sets may be in the training data, and leakage differs by model so rankings can be wrong. The benchmark does not use our tasks, languages or policies. And only a locked set of our own cases lets us show a validator a reproducible number. A few hundred well-chosen cases will tell us more about our use case than any leaderboard.

    “How big does our private set need to be?”

    It depends on the difference that matters. Distinguishing 70% from 73% needs a couple of thousand items; with 200 we can only see differences of about ten points. I'd start with a few hundred for smoke testing, state the detectable difference honestly, and grow it from production failures.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. An agent has a per-attempt success rate of 85% on every task. What is pass^4 and pass@4?

    pass^4 = 0.854 ≈ 52%. pass@4 = 1 − 0.154 ≈ 99.95%. The first answers "will it work every time"; the second "will it work if we retry and can tell which worked". Customers experience the first.

    2. Why grade an agent on the final database state rather than on its replies?

    Many different conversations are valid; there is no single correct reply to compare with. The state is what actually matters (the right card blocked, the fee waived once), is checked in code, and cannot be flattered by fluent wording. It misses unsafe behaviour along the way, so add policy checks on the tool log.

    3. Give one invariance, one directional and one equivalence relation for a loan-affordability assistant.

    Invariance: changing the applicant's name or reordering the application fields leaves the verdict unchanged. Directional: raising income, all else equal, does not lower affordability. Equivalence: the same application in Arabic and English gives the same verdict.

    4. A name swap changes the model's output in 2 of 20 pairs. What can you say?

    Very little. The observed rate is 10%, but a 95% interval runs from roughly 3% to 30%. It could be a serious problem or a minor one. Run several hundred pairs before deciding.

    5. Model B scores 68% on a public set, model A 70%. 25% of the set leaked into B's training; B recalls leaked items at 95%. What is B's likely score on fresh questions?

    68 = 0.75·t + 0.25·95, so t = (68 − 23.75) ÷ 0.75 ≈ 59%. The apparent 2-point gap hides a gap of about 11 points on unseen questions if A is clean.

    6. Your team keeps adjusting prompts after reading the failures on the test set. What has gone wrong and what do you do?

    The test set has become a development set; its score is now optimistic. Split it: keep the failures as development material, and build or hold out a fresh locked set that nobody reads failures from until release.

    7. Name two properties you would test with property-based testing in a document-extraction pipeline.

    Examples: the output always conforms to the schema; every extracted amount appears verbatim in the source text; redaction is idempotent and removes all account numbers; extraction on a page rotated by 180° and then corrected gives the same fields.
