    AI Agents Doing Data Science

    Part 1

    What a data science agent is

    In one sentenceA data science agent is a language model in a loop: it writes code, runs it, reads the result and decides what to try next, then writes up what it found. Your job moves from doing the analysis to checking it.

    Running example: a product head asks an agent, "Why are premium card customers leaving?" Eight minutes later she has a tidy report. But the report is written after the work, and nothing forces it to match what the code did.

    Agents make every report look professionally typeset, but checking costs the same as before.

    Part 2

    How it differs from similar things

    • Human analyst. Makes the same mistakes, but you can ask what they tried. An agent does 200 attempts in seconds and the report never mentions the 199 that failed.
    • Text-to-SQL. Turns a plain-English question into one database query (SQL is the database language). One step, not a whole workflow.
    • Automated discovery. The same loop, but an automatic scorer replaces you. It proposes ideas, scores them and keeps the best.

    On benchmarks such as DSBench and DA-Code the best agents solve a meaningful share of well-posed tasks, but long, open-ended work still lags a competent human.

    Part 3

    How to audit one

    Treat the report as a list of claims, each needing a supporting line in the log. Work in this order.

    1. Follow the row counts. Check how many rows survive every filter and join.
    2. Match every number to a log line. A figure with no line behind it may be invented text.
    3. Check for leakage. No feature should be recorded after the outcome (for churn, a "closure code").
    4. Count what was tried. How many slices and models were tested before this one was picked?
    5. Question any "will" claim. "Calling customers will cut churn" needs an experiment behind it.
    6. Recompute the central number yourself, or with a second agent that has not seen the first one's story.

    Six ways agents go wrong

    FailureWhat it looks like
    Invented numbersA statistic with no matching output in the log
    Silent data handling"Handled missing values" while 31% of rows vanished
    LeakageA feature that only exists after the customer left
    Forking pathsBest of many slices reported, with the count unstated
    Causal overreachAn association read as an effect, with an AED figure attached
    Success by redefinitionThe test set quietly swapped, or a failing test commented out
    Part 4

    How to read an agent's report

    AUC 0.97 for predicting churn
    AUC is a score where 0.5 is guessing and 1.0 is perfect. A churn model at 0.75 is normal, so 0.97 usually means leakage. Look at the top features.
    "2% of rows dropped", log shows 48,310 rows then 33,330
    That is about 31% lost. If the missing rows relate to who leaves, the headline rate is probably biased.
    "Segment X is the key problem, p = 0.01", after 40 slices
    By luck alone, a p-value under 0.05 turns up in about 87% of such searches. Confirm on fresh data.
    A query that ran with no error
    That only means the SQL was valid. "Last month's spend" can mean booked or posted date, with or without reversals, and the model picks silently.

    The fix for text-to-SQL

    Small benchmarks such as Spider are nearly solved, but real warehouses are harder, which is why Spider 2.0 exists. A semantic layer is a company dictionary where "card spend" is defined once (tools such as dbt MetricFlow, Cube, LookML). The model then picks a metric, not from 400 tables.

    Why automated discovery needs a good scorer

    AlphaEvolve (Google DeepMind) has a model propose code changes, an automatic scorer rate each, and an evolutionary loop keep the best. Reported results include multiplying 4×4 complex matrices with 48 scalar multiplications. The AI Scientist (Sakana AI) automates idea, experiment and paper. These work where the score is cheap and trustworthy, such as runtime. Where it is a proxy, such as another model's review, the loop optimises the scorer, not the goal.

    Part 5

    Which to use, and is it ready?

    OptionPick it whenAvoid when
    Agent plus human auditExploring, drafting, standard modelsNobody will read the log
    Text-to-SQL on a semantic layerFrequent questions on governed metricsNovel questions with no defined metric
    Automated searchThe score is exact, cheap and hard to gameThe score is a proxy
    • Strong at: routine analysis at speed, first-draft exploration, and search with an exact scorer.
    • Weak at: unchecked output (right and wrong read the same), ambiguous business definitions (the guess is invisible), and causal questions (they cannot run the experiment).

    Production today: agent-plus-audit and text-to-SQL over governed metrics are usable now. Automated paper-writing is not; use it, if at all, as a source of ideas to test. Start narrow: have it print row counts after every step and list every test it ran. Score it on 50 real questions with known answers from your own database, and keep it read-only.

    Show the formulas

    Chance of at least one false "hit" = 1 − 0.95k, for k slices tested where nothing real exists. For k = 40 that is about 87%.

    Honest cut-off (Bonferroni) = 0.05 ÷ k. For 40 slices, a slice needs p below 0.00125.

    In banking, agents suit exploratory churn, spend and portfolio analysis, but model-validation and regulatory work still needs a named person who can defend each step.

    Part 6

    Common mistakes and quick check

    • Trusting the write-up instead of the log

      The report is generated text. Only the log shows what the code did.

    • Ignoring how many things were tried

      The best of 200 slices is nearly always "significant".

    • Treating "the query ran" as "the answer is right"

      Valid SQL can still answer a slightly different question than the one you asked.

    • Quoting benchmark scores as readiness

      A public benchmark score says little about your database. Test on your own questions.

    1. An agent tested 40 segments and reports the one with p = 0.01. Is it significant?

    No. After correcting for 40 tests the cut-off is 0.00125. Treat it as a hypothesis and confirm on fresh data.

    2. The log shows 48,310 rows before cleaning and 33,330 after. The report says 2% were dropped. Why does it matter?

    About 31% were lost. If missingness relates to churn, the analysis covers a biased subset.

    3. Why can a query that runs without error still be wrong?

    Running only means the SQL is valid. The question is vague, so the model may pick the wrong table, date, filter or currency treatment.

    4. A report says "calling at-risk customers will cut churn by 4 points". What do you ask first?

    What experiment supports the effect. Predicting who leaves says nothing about whether a call changes it, so without a trial the figure is only a scenario.
