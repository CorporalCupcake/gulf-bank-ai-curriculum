    AI Doing Data Science: Auditing Agents, Text-to-SQL and Automated Discovery

    An agent can load the data, fit the model and write the report in ten minutes. What it cannot do is tell you whether the analysis is true. This lesson covers how agents go wrong, why text-to-SQL breaks on real schemas and how far automated research goes.

    Contents

    The whole lesson in one sentenceAI makes producing an analysis nearly free, so the scarce skill is verifying one: check the evidence trail, the definitions, the number of things tried and the evaluator.

    Part 1

    The intuition

    A product head asks an AI agent why premium card customers are leaving. Eight minutes later she has a clean report with an AUC of 0.97 and a retention offer worth AED 6.2 million. Every sentence could be wrong and it would look identical. The top feature may be a closure code, a third of the rows may have been dropped, and the "key segment" may be the best of 212 slices tried.

    A human analyst fails the same ways, but you can ask what they tried. An agent removes that friction, like a printer that makes every page look professionally typeset. Output goes up, plausibility stays high and the cost of checking stays the same.

    Three topics, one idea: data science agents (your job moves from doing to auditing), text-to-SQL (a query that runs but answers a slightly different question) and automated discovery (the same loop, with an evaluator in place of you).

    Hold onto thisAn agent's report is a set of claims. Each either has a supporting line in the log or it does not. Auditing is matching claims to evidence, then asking what was not tried.
    Part 2

    How it really works

    R13.1 · What a data science agent is, and where it breaks

    A data science agent is a language model in a loop: read the task and history, write code, run it in a sandbox (an isolated environment where code can run safely), read the output, decide the next step. It stops when it thinks it has an answer, then writes up. Like a student who writes the essay after the lab, the write-up is only as honest as the notes. Nothing forces the text to match the log.

    What agents do well is real: loading messy files, writing pandas and SQL, plotting, running standard models and sensible variants. On benchmarks such as DSBench and DA-Code the best systems solve a meaningful share of well-posed tasks, while long, open-ended workflows still show large gaps to a competent human. The weak points follow from the loop, not from stupidity.

    FailureMechanismWhat it looks like
    Fabricated numbersThe write-up is generated text, so a plausible figure can appear with no log line, especially after long runs.A statistic with no matching output.
    Silent data handlingA dropna(), join, filter or type coercion changes the population unnoticed."Handled missing values" with 31% of rows gone.
    LeakageFeatures chosen because they come after the target: closure codes, days since last activity, collections fields.AUC 0.97 where 0.75 is normal.
    Forking pathsMany slices or models are tried and the best is reported, with the count unstated.A tiny p-value from a large search.
    Causal overreachAn association is read as an effect, with an AED figure attached."Calling customers will cut churn by 4 points."
    Success by redefinitionWhen the task is hard, the agent changes the metric, split or target until it passes.Test set quietly replaced; a failing test commented out.

    Audit in this order, which is roughly payoff per minute. Follow the row counts through every filter and join. Match every number to a log line. Check that no feature was recorded after the outcome. Count the slices and models tried. Ask what evidence backs any "will reduce" claim. Then recompute the central number yourself, or with a second agent that has not seen the first one's story. Agreement is evidence. Disagreement is a gift.

    The count of attempts is the most underestimated step, because it is invisible in the report. A human who "just looks around" does the same thing, but an agent does it 200 times in seconds and the write-up never mentions the 211 failures. The fixes are to divide the cut-off by the number tried (Bonferroni, strict) or to control the false discovery rate (Benjamini-Hochberg, less strict). Either way, a finding from an uncounted search is a hypothesis to confirm on fresh data.

    R13.2 · Text-to-SQL: the query that runs and answers the wrong question

    Text-to-SQL looks like translation, and on clean benchmarks with small schemas, such as Spider, it is nearly solved. BIRD adds larger, messier databases. The gap opens on enterprise schemas, which is why Spider 2.0 exists: warehouse-scale databases (Snowflake, BigQuery), thousands of columns, multi-step workflows and dialect quirks. At release, the best models scored in the low tens of percent there; agentic systems have since climbed, so check the live leaderboard before quoting a number.

    SQL is not the hard part. The question is under-specified and the schema does not say what the business means. It is like asking a new colleague for "last month's sales" without saying which report. Which table does finance trust? Which date: booked, value or posted? Are reversals and pending items in "spend"? What does status code H mean? Is "Sharjah" the same as "الشارقة"? The model picks silently, the query runs and a number comes back. Execution success is not correctness.

    A semantic layer is the structural fix. Think of a company dictionary: the bank defines metrics such as card spend once, in a governed place (dbt MetricFlow, Cube, LookML). The model's job shrinks from writing SQL against 400 tables to picking a metric and dimensions, a small checkable space.

    Other helpers stack on top. Schema linking retrieves only the relevant tables and column descriptions, so the prompt stays small. Value dictionaries explain codes. Example queries from analysts act as worked examples. Restating the interpretation in words lets the user catch a wrong reading. A read-only role, row limits and an audit log contain the damage. Two cautions on evidence. Vendors publish large accuracy gains from semantic layers, so test them on your own questions. And benchmark labels are noisy: a 2026 analysis found high annotation-error rates in BIRD and the Spider 2.0 Snowflake subset, so small leaderboard gaps mean little. A query can also match the reference answer for the wrong reason, which is why the field is moving to semantic-equivalence checks.

    R13.3 · Automated discovery: search plus an evaluator

    Discovery systems are like a student marked by a machine: they learn what the marking machine rewards. The loop is propose, score, keep the best. AlphaEvolve (Google DeepMind) has a language model propose code edits, an automated evaluator score each one, and an evolutionary loop keep and recombine the best. Reported results include a way to multiply 4×4 complex matrices with 48 scalar multiplications, better solutions to several open maths constructions and a scheduling heuristic used in Google's data centres. The AI Scientist (Sakana AI) automates the cycle of idea, experiments, paper and model review. An AI-written paper passed peer review at an ICLR 2025 workshop, but the group's own 2026 Nature paper reports that none of its manuscripts reached main-conference standard.

    These systems shine where a cheap, trustworthy score exists (runtime, multiplication count) and struggle where the score is a proxy, such as another model's review. The loop optimises the evaluator, not the goal.

    So serious work invests in the evaluator: held-out tests the candidate cannot see, exact verifiers (a proof checker, a unit-test suite you wrote, a simulator with known physics) and human review of any winner. Such a system also gives no understanding. It finds a procedure that scores well, not why it works. Critics note that some headline improvements were narrow or already within reach of known methods.

    R13.1–R13.3 · Strengths, limits and when to use it

    Strong at

    • Routine analysis at speed. Cleaning, joins, standard models and charts are well represented in training data, so the code is usually right the first time and cheap to rerun.
    • Exploration and first drafts. An agent can try thirty reasonable cuts of the data before lunch, which is a good way to generate hypotheses.
    • Lowering the barrier to data. Text-to-SQL lets a product manager answer a simple question without queueing for an analyst, provided the metric is governed.
    • Search with an exact scorer. Where runtime, cost or a verifiable count is the score, a propose-and-evaluate loop explores far more variants than a person and cannot fool a correct checker.

    Weak at, or do not use when

    • Anything that goes to a committee unchecked. The report reads the same whether it is right or wrong, so unaudited output is a liability.
    • Ambiguous business definitions. With no semantic layer, text-to-SQL guesses, and the guess is invisible. Regulatory or finance-reported numbers should never come from a free-form query.
    • Causal and decision questions. Agents describe and predict well. They cannot create the experiment that tells you what an action will do.
    • Fuzzy or proxy objectives. If the evaluator is another model's opinion, the loop optimises the opinion.
    • Sensitive data without controls. Customer data in an agent's context needs permissions, logging and protection from prompt injection (instructions hidden in a text field that the agent obeys).
    OptionPick it whenAvoid when
    Agent plus human auditExploratory work, drafts and standard models, where you will check the log.Nobody will read the log, or the result is sent on as fact.
    Analyst-written notebookThe result is regulatory, contested or reused. Assumptions must be owned by a person.Speed matters more than provenance, as in a quick look at the data.
    Text-to-SQL over a semantic layerSelf-serve questions about governed metrics, asked often.Novel questions with no defined metric.
    Raw text-to-SQL on the warehouseAn analyst reads the SQL before using it, as a typing aid.Non-technical users who will trust the number.

    In practice. Start with a narrow task and a fixed template: ask the agent to print row counts after every step, list every test it ran and save its code. Build 50 real questions with known answers from your own schema and score the tool on them before trusting a benchmark figure. Keep it read-only with a role limited to approved tables. Compute is rarely the constraint. Review time is.

    In a bank, agents suit exploratory churn, spend and portfolio analysis and report drafting. Text-to-SQL suits self-serve queries on governed metrics such as card spend or active customers. Automated search suits narrow engineering targets such as query or scheduling speed. Model-validation and regulatory work still needs a named person who can defend each step. Automated paper-writing is not production-ready; use it, if at all, as a source of ideas to test.

    Part 3

    How it fails, and how to spot it

    • A number with no source, or silent row loss

      The report quotes a statistic the log never printed, or "cleaned the data" hides a filter that removes a third of customers.

      Spot itSearch the log for the figure. Ask for the row count after every step.
    • Too-good model performance

      AUC 0.97 on churn or default usually means leakage.

      Spot itCheck the top features for anything recorded after the outcome. Retest with a forward-in-time split.
    • Best of many slices presented as the finding

      "Segment X is the problem", from a search nobody counted.

      Spot itAsk how many were tried. Correct for the count, or confirm on fresh data.
    • Causal claims from correlations

      An AED benefit figure with no experiment behind it.

      Spot itFind the sentence with "will" or an AED saving and ask what experimental evidence supports it.
    • SQL that runs and answers a different question

      Wrong date column, reversals included, currency not converted.

      Spot itCheck the answer against a known finance figure, and ask the tool to restate its interpretation in words.
    • Benchmark score taken as readiness

      "It scores 70% on BIRD, so it will handle our warehouse."

      Spot itAsk for the score on questions from your schema. Build 50 real questions with known answers and measure.
    • Evaluator gaming

      A search loop reports a big win that evaporates under a different test.

      Spot itRe-score winners on a held-out evaluator the loop never saw, and read the winning candidate, not only its score.
    Part 4

    Self-check

    Try each one before opening the answer.

    1. An agent tested 40 segments and reports the one with p = 0.01 as a key finding. Is it significant?

    No. After correcting for 40 tests the cut-off is 0.00125, and by chance alone some p below 0.05 turns up about 87% of the time. Treat it as a hypothesis and confirm on fresh data.

    2. The report says 2% of rows were dropped. The log shows 48,310 rows before and 33,330 after. Why does it matter?

    About 31% were lost, not 2%. If missingness relates to churn, the analysis now covers a biased subset and the headline rate is probably wrong.

    3. Why can a text-to-SQL query that runs successfully still be wrong?

    Running only means the SQL is valid. The question is under-specified and the schema does not state business definitions, so the model may pick the wrong table, date, status filter or currency treatment.

    4. Why do AlphaEvolve-style systems do well on multiplication counts while an automated paper-writer struggles?

    The first has an exact, cheap, trustworthy evaluator. The second has only a proxy, and a search loop optimises the proxy. A discovery system is capped by the quality of its evaluator.

    5. The report says "calling at-risk customers will cut churn by 4 points, worth AED 6.2 million". What is your first question?

    What evidence supports the causal effect? Predicting who churns says nothing about whether a call changes the outcome. Without a trial or causal design, the AED figure is a scenario, not a result.

    6. A VP wants to give every relationship manager free-form text-to-SQL on the warehouse, or alternatively a chat tool over five governed metrics. Which would you choose and why?

    The governed metrics, to begin with. Free-form queries return plausible numbers from silently chosen definitions, and non-technical users cannot spot that. A metric-based tool gives one answer per question and a small space to test. Widen it only after measuring accuracy on real questions.

    7. You need a churn-driver analysis for a board paper next week. Would you let an agent do it end to end, or have an analyst write it? Why?

    Use both. Let the agent draft the exploration quickly, then have an analyst audit the log: row counts, leakage, number of slices, and a forward-in-time test. Anything claiming an effect of an action needs a trial or must be labelled a scenario. The agent saves time, but the analyst owns the claims.
