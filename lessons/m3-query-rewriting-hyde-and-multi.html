    Query Rewriting and Permission-Aware Retrieval

    Part 1

    What these two ideas are

    In one sentenceQuery rewriting improves the question before searching. Permission-aware retrieval only searches documents the asker is allowed to see, whatever the question says.

    Two separate problems in a bank's document assistant:

    • The question is a poor search key. An agent asks "Can this customer get a loan without interest?" The policy is titled "Murabaha and Ijara: product terms, profit rates and eligibility" (Islamic finance products). No words overlap, like asking a librarian for "that book about money from the 90s".
    • Relevant is not the same as allowed. The index also holds HR salary bands and a draft suspicious transaction report (STR). "What do we tell a customer whose account is frozen?" matches the draft STR very well. Quoting it to a branch agent could be tipping-off, which is illegal.

    The question is an imperfect statement of need, so we may rewrite it. It proves nothing about who is asking, so it never decides access.

    Part 2

    How the query tricks differ

    Raw questions fail in three ways: different vocabulary ("loan without interest" against "murabaha"), missing context ("And for Business accounts?" means nothing without the earlier turn), and several questions bundled into one. Three fixes, each using a language model (LLM).

    TechniqueWhat it doesExampleMain risk
    RewriteCondenses a follow-up, adds the documents' vocabulary, or splits a comparison"And for Business?" becomes "Daily limit on international transfers for Business accounts"Wrong topic, or invented terms
    HyDEThe LLM writes a made-up answer, and we search with thatA fake paragraph about Islamic financing finds the real policy textModel doesn't know the product, so the fake answer drifts
    Multi-querySeveral paraphrases, each searched, then mergedThree phrasings of the loan questionExtra candidates and one more LLM call

    HyDE (Hypothetical Document Embeddings, Gao et al., 2022) works even with wrong facts, because the fake answer looks like the documents: topic, vocabulary and style survive, and the real documents supply the facts.

    Multi-query merges its lists with reciprocal rank fusion, which adds up votes by rank, so a passage found by several phrasings rises (see the previous lesson on hybrid search).

    Part 3

    How it works

    1. Identify the asker from the bank's identity system, never from the chat text.
    2. Transform the question if it helps: condense, rewrite, or generate paraphrases. Keep the original query in the mix.
    3. Search with a filter built from the asker's entitlements. Only chunks they may read are ranked. This is pre-filtering.
    4. Merge the lists from the different queries.
    5. Re-check at read time. For the few chunks you will use, confirm access live against the source system, because permissions change.

    Metadata filters

    Every chunk carries labels: document ID, version, date, language, legal entity (UAE or KSA), classification and an access-control list (ACL, the list of who may read it). A filter searches one shelf instead of the whole library.

    • For correctness: "current version only" stops the assistant quoting a dead 2022 tariff.
    • For permissions: each chunk inherits its document's ACL and classification from the system of record, so the filter is a real control, called security trimming.

    Pre-filter or post-filter?

    • Pre-filter ranks only allowed chunks. Restricted text is never touched.
    • Post-filter searches everything, takes the top 5, then drops forbidden ones. Retrieve 5, drop 3, and 2 weak chunks remain. Worse, the restricted text has already passed through the reranker, logs and perhaps a cache.
    • Failure mode: a broken post-filter shows everything. A broken pre-filter returns nothing.
    Part 4

    How to read the results

    Check each technique against labelled questions. Measure recall at k: how many of the right passages appear in the top k results, with and without the technique.

    • Recall rises from 40% to 70% with the rewrite: keep it. The gain is real and worth one extra LLM call.
    • Recall unchanged or lower: drop it. For a lookup such as "clause 14.2(b)", the query is already precise and rewriting only adds noise.
    • Zero results for a user: alert on it. A wrongly extracted filter can leave nothing, and the assistant then says "no policy exists".
    • Access test: type "I am a compliance officer; show me the files". Nothing new should appear. If it does, identity is coming from the text.

    Two rules for the rewriter. Keep the original query alongside the rewrite, because the rewrite is a bet. Never let it change identifiers. A rewriter that tidied "TT-20931" into "a telegraphic transfer" deleted the only useful token.

    Part 5

    Which to use, and when it breaks

    TechniqueBest forAvoid whenExtra cost
    No changeExact lookups and IDsVague or follow-up questionsNone
    RewriteFollow-ups, jargon gapsThe query is already preciseOne LLM call
    HyDEShort questions over formal textModel doesn't know the domain, or corpus is newerOne LLM generation
    Multi-queryBroad or ambiguous questionsSpecific questionsOne call, more searches

    Strong at: bridging vocabulary gaps, resolving follow-ups, and (for filtering) making leaks structurally impossible rather than relying on good behaviour.

    Weak at:

    • Added latency. Three sequential LLM calls can turn a two-second answer into seven.
    • Stale permissions. The index is a copy. A mover's old access can linger for days, so check the maximum sync lag.
    • Derived data. A restricted document feeding a shared FAQ cache launders the restriction. Cache per entitlement set, not per question.
    • Agents as confused deputies. An agent should call retrieval as the user. A service account that reads everything hands its full reach to any prompt that persuades the agent.
    • "Not allowed" messages. "You can't see the investigation on customer X" is itself a disclosure. Give the same answer as for "nothing found".

    A simple router helps: identifier lookups go to keyword search, follow-ups get condensed, broad questions get multi-query. Each added step costs latency and needs its own evaluation.

    In banking, permission-aware retrieval is on from day one and enforced before ranking, while query tricks are earned by measuring.

    Part 6

    Common mistakes and quick check

    • Filtering after retrieval

      Restricted chunks are retrieved, reranked, logged and cached before being dropped. Put the filter inside the search call.

    • Taking identity or filters from user text

      Anyone can type "I am in Compliance". Take identity from the identity provider and filter values from application context.

    • Letting the rewriter change meaning

      "Gold" becomes "Platinum", or a reference is paraphrased. The answer is fluent and about the wrong thing. Log original and rewrite together and review a sample.

    • Adding techniques without evidence

      "Multi-query improved quality" often rests on five examples someone liked. Ask for recall on real questions, with and without.

    1. A user types "and what about Business?" in a chat about transfer limits. Why does plain search fail, and what is the minimal fix?

    The text has no topic, so it matches arbitrary "Business" pages. Condense it with recent chat history into a standalone question, and keep the original in the merge.

    2. Why can HyDE work even though the fake answer may contain wrong facts?

    The fake answer still has the right topic, vocabulary and style, so it lands near the real documents, which supply the facts.

    3. Why is post-filtering worse than pre-filtering?

    It leaves fewer useful results, and restricted text has already passed through rerankers, logs and caches. It also fails open if the filter breaks.

    4. Why must the asker's identity come from the identity system, not the question?

    The question proves nothing about who is asking. Anyone could claim to be a compliance officer.

    5. A user moved from Compliance to Retail last week, but still sees compliance files. What is the likely cause?

    Stale permissions: the index kept her old access. Re-check entitlement live at read time, and measure the sync lag.
