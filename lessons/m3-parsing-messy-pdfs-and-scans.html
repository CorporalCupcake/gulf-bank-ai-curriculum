    Messy Documents: Parsing PDFs, Searching Page Images and Fixing RAG

    Part 1

    Why parsing comes first

    In one sentenceParsing is turning a PDF or scan into clean text that keeps the structure, and if it goes wrong, every step after it (search, the model) works from garbage.

    RAG (retrieval-augmented generation) means: find the relevant passages in your documents, then let a language model answer from them. Parsing is the first step.

    Example. A manager asks, "What is the overdraft limit in the Al Noor facility letter?" The assistant answers "AED 5,000,000", with a citation. The real limit is AED 750,000. The tool read the table down its columns, so the pairing of name and number was lost before the model saw anything.

    A PDF is a drawing, not a text file. It records where to paint each letter. It has no sentences, tables or reading order.

    How it differs from other steps

    • Embeddings and rerankers improve how passages are found, not how text was extracted.
    • A bigger model reads better, but only what it is given.
    Part 2

    How parsing a messy document works

    Start by asking what kind of page it is.

    • Born-digital: exported from Word or a banking system. It already contains text, so the job is rebuilding structure.
    • Scanned: only pixels. OCR (optical character recognition, software that reads letters from an image) comes first, and it can misread characters.
    • Hybrid: an old scan with a hidden OCR text layer of unknown quality. It can be confidently wrong with nothing flagging it.

    Count the extractable characters on each page: zero means a scan, and non-words mean a bad hidden layer. Send each page to the right tool.

    A modern parser works in steps. The step that failed tells you where to look.

    1. Find the layout. Label regions: paragraph, table, header, stamp.
    2. Put regions in reading order. Columns and footnotes break "top to bottom".
    3. Read each region. Extract or OCR the text; send tables to a table model.
    4. Write it out as Markdown or JSON, with page numbers.
    5. Clean up. Remove repeated headers and footers, such as "Strictly confidential" on every page, which make all chunks look alike to search.

    Where it goes wrong

    • Tables. Rows and columns get interleaved, headers are lost, or "AED thousands" in the title is left behind so every number is off by 1,000. Fix: write each row with its headers, such as "Facility: Overdraft; Limit (AED): 750,000".
    • Stamps and signatures. A stamp mixes its letters into the paragraph. A signature is not text, but its presence is often the fact you need, so store it as metadata.
    • Arabic and English together. Right-to-left text can come out reversed, and Arabic-Indic digits (٧٥٠) can mix with Western ones (750), so a search for "750,000" misses the amount. Normalise text for search, and keep the original for display.
    • Small OCR errors add up. At a 1% character error rate, a 24-character account number is fully correct only about 79% of the time.

    Which parser to use

    ApproachStrong atWeak at
    Text-layer extractionFast, cheap, exact on born-digital filesScans, tables, some Arabic
    Layout-aware pipelineStructure, bounding boxes for citations, can run locallySeveral models to maintain; early errors cascade
    Vision-language model reads the page imageOdd layouts, stamps, mixed scriptsCan skip or invent content; cost per page; exact digits not guaranteed

    Two rules. Never trust a single reading of a high-stakes number. Extract it two ways and flag disagreements. And keep provenance: store the page number and position with every chunk, so a reviewer can check the answer against the picture.

    Part 3

    Searching page images instead (ColPali)

    In one sentenceColPali skips parsing: a model looks at the page as a picture, and each word of your question finds the part of the page that matches it best.

    The usual route (OCR, layout, chunks, vectors) can lose a stamp on a skewed scan before you search. ColPali (Faysse et al., ICLR 2025) starts from a vision-language model, PaliGemma-3B.

    1. Cut the page image into patches.
    2. Turn each patch into a vector (a list of 128 numbers). A page becomes about 1,000 vectors.
    3. Turn each word-piece of the question into a vector too.
    4. For each question word, find the single most similar patch.
    5. Add up those best matches. That total is the page's score (called MaxSim).

    How it differs from normal search

    • One vector per page is the page's average meaning. A stamp covering 3% of the page gets about 3% of the average and is easily outvoted by pages that talk at length about amounts and goods.
    • One vector per patch (late interaction) keeps the detail. Page vectors are computed once, ahead of time, and compared with the question at the end.

    How to read a score and what it costs

    • Reading a score. Each best match is at most 1, so a 12-word question scores at most 12. A score of 9.5 means the average word found a patch at about 0.8. Compare scores only for the same question. A high score does not mean the answer is right.
    • Storage. A ColPali page is about 264 kB against about 2 kB for one vector, roughly 130 times more.
    • Shrinking it. Average neighbouring patches, store smaller numbers, or pick a few hundred candidates cheaply and score only those. Test on your own documents.

    A related fix: give each chunk its context

    Text chunks lose their owner. "The provision charge rose to AED 95 million" does not say which bank or which year. In contextual retrieval (Anthropic, September 2024), an LLM reads the whole document and writes one situating sentence per chunk ("From Gulf Mercantile Bank's Q2 2025 results"). You store the sentence with the chunk. Anthropic reported about 49% fewer failed retrievals, about 67% with a reranker (their own benchmarks; verify before quoting). Check a sample, because a wrong sentence becomes a wrong fact in the index.

    Part 4

    Which step broke? Diagnosing RAG failures

    In one sentenceA RAG system is a chain, so find the first broken step, because everything after it is just a consequence.

    You need a test set of real questions where you know the right passage and the right answer. For each failure, go in order.

    1. Is the answer in the parsed text? If not, parsing failed: page skipped, table scrambled, OCR misread.
    2. Was the right passage retrieved? In the corpus but not in the top k: different wording (query rewriting helps), a badly cut chunk, or an exact term that needs keyword search.
    3. Was it buried? In the top 20 but not the top 5 is a ranking failure.
    4. In the context, yet the answer is wrong? Generation failure: the model ignored it, merged it with a look-alike, or answered from memory.
    5. Was the "right" answer actually right? The gold answer or grader may be wrong; check by hand.

    How to read the two halves

    Measure two things separately: how often the right passage reached the model (the hit rate), and how often the answer is right when it did.

    Hit rate 60%, correct when found 95%
    The model is fine. Fix parsing and retrieval.
    Hit rate 95%, correct when found 60%
    Retrieval is fine. Fix the prompt, the context or the model.
    Both near 80%
    Improve whichever is cheaper to move.

    In banking, a wrong number from a facility letter or trade document is a different fact, not slightly worse text, so high-stakes figures need a second reading and a link back to the source page.

    Part 5

    Common mistakes and quick check

    • Tuning the model when parsing is broken

      Always check whether the answer is in the parsed text before touching prompts or embeddings.

    • Dropping table headers and units

      "12,430" means nothing without its column name and "AED thousands". Keep them with every row.

    • Trusting public benchmark scores

      Page-image benchmarks use mostly English and French public documents. Test on 100 to 200 of your own queries, split by language and document type.

    1. Why can a better embedding model not fix a scrambled table?

    The pairing of name and number is already gone from the text. Embeddings can only work with what parsing gives them.

    2. Why can ColPali find a small stamp that one-vector search misses?

    Each question word takes its own best patch, so nothing is averaged away. A single page vector gives a small stamp only a small share.

    3. The right passage is retrieved, but the answer is wrong. Which step failed?

    Generation, unless the gold answer or grader is wrong. Check that by hand first.

    4. What does contextual retrieval add to each chunk?

    A short LLM-written sentence saying where the chunk comes from, stored with it so search can tell look-alike chunks apart.
