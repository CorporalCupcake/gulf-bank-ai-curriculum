    Embeddings That Shrink, See and Compare: Matryoshka, Multi-Vector and What Contrastive Learning Really Learns

    How one embedding can be cut to any length and still work, why a page of a trade document needs a thousand vectors rather than one, and what the training objective behind all of it really rewards, including the shortcuts it takes when you let it.

    Contents

    The whole lesson in one sentenceAn embedding is a compressed answer to "what is this like?", and the three levers on it are how many numbers you keep (Matryoshka), how many vectors you keep per item (multi-vector and multimodal), and what the training task forced it to notice (contrastive learning, which only learns as much as the task makes necessary).

    Part 1

    The intuition

    An embedding turns a piece of text, an image or a page into a list of numbers, so that things which mean similar things sit close together. You have met this in dense retrieval: embed every chunk of every policy once, embed the question, return the nearest chunks. This lesson is about three things that go wrong or get expensive once you do that at bank scale, and what the research has done about them.

    Cost. A bank with 50 million chunks (policies, emails, call transcripts, product terms, in Arabic and English) at 1,024 numbers each, stored as 4-byte floats, holds about 205 GB of vectors that must sit in fast memory to search quickly. Most of that precision buys nothing. Matryoshka embeddings are trained so that the first 64 numbers are already a decent summary, the first 256 a better one, and all 1,024 the best. Like the Russian dolls, you can stop at whichever size you can afford.

    Resolution. One vector for a whole page is an average. A scanned letter of credit has a header, a stamp, a table of goods and a signature, and a question like "what is the amount and who stamped it?" is about two small corners. Multi-vector embeddings keep one vector per token or per image patch and compare the question to each piece. Multimodal ones put text and page images into the same space, so you can search a scan without first running OCR and hoping.

    What was actually learned. Almost all modern embeddings are trained contrastively: pull matching pairs together, push everything else apart. That objective is clever and cheap, but it only asks the model to tell the right match from the wrong ones in the batch. If a cheap cue does that job (the bank's letterhead, the language of the text, the length of the passage), the model may learn the cue and stop. Knowing what the objective rewards tells you when to trust an embedding and when to test it.

    Hold onto thisAn embedding is a design choice with three dials: length, number of vectors, and training task. Each dial trades accuracy against cost, and each has a way of looking fine on a demo and failing on your documents. The rest of this lesson turns each dial and shows what it does.
    Part 2

    How it really works

    R10.1 · Matryoshka training: nested prefixes

    Ordinary embedding training uses only the full vector in the loss. Nothing says which numbers matter, so information ends up smeared over all of them, and any prefix is an arbitrary slice that works poorly. Matryoshka Representation Learning (Kusupati et al., 2022) changes only the loss. Pick a set of nested sizes, say 64, 128, 256, 512, 1,024. Compute the same contrastive loss on each prefix and add them up:

    L=∑m∈Mcm·Lcontrastive(z1:m)

    z1:m is the first m numbers of the embedding, M the chosen sizes and cm a weight per size (often all 1). The network must make the 64-number prefix good on its own, so the coarse, high-value distinctions (topic, language, document type) get packed into the earliest numbers. The finer details fill in the later ones. Nothing about the architecture changes, and at full length the model gives up very little.

    Three practical details matter in a bank.

    • Re-normalise after cutting. A prefix of a unit-length vector is shorter than unit length. Divide by its norm before using cosine similarity or dot products, or scores from different lengths are not comparable.
    • It stacks with quantisation. Length and precision are independent savings. 1,024 floats to 256 8-bit integers is a 16-fold cut, and binary codes go further, usually followed by a re-check with higher precision (P3 covers the same idea for model weights).
    • Only models trained for it truncate gracefully. Check the model card. Several major embedding APIs and open models are now trained this way, but chopping a model that was not is exactly the red line in Simulation 1.

    Adaptive retrieval: a short pass, then a careful one

    Having nested sizes opens a cheap trick. Search the whole corpus with a short prefix (cheap per document), take a shortlist, then re-score only the shortlist with the full vector. Cost falls roughly in proportion to the shortlist-to-corpus ratio plus the cost of the short pass, while the final ranking comes from the full embedding. This is the same shape as retrieve-then-rerank, except the first stage and the second stage are the same model at two resolutions.

    The speed-up on offer in the Matryoshka paper was up to 14 times for large-scale retrieval on ImageNet, at similar accuracy; text results vary by model and corpus, so measure on your own documents. One more point on cost: shorter vectors also make the index structure cheaper (approximate-nearest-neighbour graphs are built from distance computations), as covered in the vector search lesson.

    R10.2 · Multimodal embeddings: text and pictures in one space

    A multimodal embedding maps different kinds of input into the same space, so that the text "customs declaration, 40 pallets of dates" lands near a scan of that declaration. CLIP (Radford et al., 2021) did this for photographs and captions: one encoder for images, one for text, trained contrastively on hundreds of millions of image-caption pairs. The matching pair is the positive; every other caption in the batch is a negative.

    Two consequences are worth knowing. First, the modalities do not truly overlap. Even after training, image vectors and text vectors tend to occupy different regions of the space, the "modality gap" (Liang et al., 2022). Within-modality search (text to text) and cross-modality search (text to image) can therefore have very different score ranges, which matters when you mix them in one ranked list and apply a single cut-off. Second, for documents the older route was OCR first, then text embedding. That throws away layout: a number in a table cell, a stamp, a handwritten margin note or a signature box carries meaning that flat text loses. Newer document models embed the page image itself, or the patches of it.

    Multi-vector retrieval: late interaction and MaxSim

    A single vector per document forces everything into one point, which is a weighted average of everything on the page. For a long or varied document, averaging washes out the specific thing a query is about. Late interaction, introduced by ColBERT (Khattab and Zaharia, 2020), keeps a vector per token. The query is also a set of token vectors. Relevance is computed after encoding, as follows: for each query token, find the best-matching document token, then add up those best scores.

    score(Q,D)=∑i∈Qmaxj∈Dqi·dj

    qi are the query token vectors and dj the document token (or image patch) vectors, each normalised. Each query word looks for its best partner anywhere in the document, and the scores are added. "Amount" can match one corner and "stamp" another, and neither is diluted by the rest of the page. This is called MaxSim.

    ColPali (Faysse et al., 2024) applied the same idea to page images: split each page into patches (about a thousand), embed each patch with a vision-language model, and match query tokens against patches. It needs no OCR, layout detection or chunking, and on a benchmark of visually rich documents it beat pipelines built on those steps. The price is storage and compute: about a thousand 128-number vectors per page.

    The cost of multi-vector is real, and the field's recent work is about reducing it. Storing 1,030 vectors of 128 numbers in 16-bit format is about 264 KB per page, against 4 KB for one 1,024-float vector, a 64-fold difference. Approaches include pruning patches, quantising them, using fewer, learned summary vectors, and (the link back to R10.1) nesting the multi-vector budget the way Matryoshka nests dimensions, so you can choose at query time how many vectors to use. The common production pattern is hybrid: a cheap single-vector (or keyword) pass to shortlist a few hundred pages, then MaxSim only on those.

    R10.3 · What contrastive training actually asks for

    Everything above is trained with some version of the InfoNCE loss, the objective from F5.7. For one anchor with its true partner (the positive) and the other items in the batch (negatives), the loss is the negative log of the probability the model puts on the correct partner:

    L=−logexp(sim(a,p+)/τ)∑jexp(sim(a,xj)/τ)

    The sum runs over the positive and all the negatives in the batch. τ is a temperature that sets how sharply the model must separate them. A model that cannot tell them apart over a batch of B items has loss ln B; a perfect one has loss near 0. The loss is a classification problem, "which of these B is mine?", and nothing else.

    Wang and Isola (2020) showed what the loss does in geometric terms: it pushes for two properties. Alignment: matched pairs end up close. Uniformity: all the embeddings spread over the sphere rather than clumping, so that different things stay distinguishable. Both are desirable, and both are measurable on your own embeddings.

    The catch is in the phrase "which of these B is mine?". The model only has to learn whatever distinguishes the positive from those particular negatives. Three consequences follow.

    • Shortcut features. If positives share an easy cue that negatives lack, the model can use the cue and ignore the meaning. In image work this is colour histograms; in text it can be language, document template, length, boilerplate or formatting. Chen et al. (2021) called the effect feature suppression: learning an easy feature can stop the model learning others.
    • The negatives define the lesson. If random negatives differ in template, the template is enough. If every negative in the batch shares the template and differs only in content, the model must learn content. That is why batch size, hard-negative mining and batches built from similar items matter so much, and why a false negative (a "negative" that is really a near-duplicate) actively teaches the wrong thing.
    • Dimensions can go unused. Without care, contrastive models can use only a low-dimensional subspace of the space they were given (dimensional collapse; Jing et al., 2022). This is part of why shortened Matryoshka embeddings can work at all, and a reason to check how many dimensions your embeddings actually use.

    The practical reading: a low training loss does not mean the model learned what you want. It means the model learned enough to win the game it was set. Whether the learned features are the ones your bank needs is an empirical question, answered with evaluation on your own queries and your own near-miss documents.

    Where it shows up at the bank:

    • Staff copilot over policies and procedures. Tens of millions of chunks, Arabic and English, strict latency. Shorter vectors and 8-bit storage cut memory many-fold; the evaluation question is whether Arabic queries lose more than English ones when truncated.
    • Trade finance and onboarding documents. Scans with stamps, tables and signatures. Page-image models can answer "find the invoices stamped by this customs office" where OCR text fails.
    • Complaints and call-centre triage. Clustering transcripts by embedding. If the model groups by dialect or channel rather than issue, that is the shortcut problem showing up as a business artefact.
    • Name and entity matching (sanctions, KYC). Embeddings for transliterated Arabic names are a candidate-generation tool only; they can place unrelated names close together. The match decision still needs exact and fuzzy rules.
    • Fraud and AML. Embedding accounts or merchants as vectors for similarity search and graph models. The training task decides what "similar" means.
    Part 4

    Where the field is now

    Matryoshka is now routine in embedding models. Multi-vector visual retrieval is moving from research to products, with the argument shifting from "does it work" to "can we afford it". The deepest open questions are about what contrastive features are, and how to evaluate them.

    Part 5

    How it fails, and how to spot it

    Each failure comes with the quickest check.

    • Truncating a model that was not trained for it

      The vendor documentation says nothing about shorter vectors, and someone chops to 256 to save money. Accuracy drops silently.

      Spot itCheck the model card for Matryoshka training. Always compare recall at each length on a labelled query set.
    • Forgetting to re-normalise

      Prefixes of normalised vectors have shrinking norms. Dot-product scores no longer compare across lengths or documents.

      Spot itPrint the norms of truncated vectors. They should all be 1.
    • Averaged accuracy hides a language gap

      The mean recall loss from truncation is 2 points, but Arabic queries lose 9 and English 1. Arabic morphology, dialects and transliteration are underrepresented in many training sets.

      Spot itReport every embedding evaluation split by language, script and document type.
    • Benchmark rank is not task fit

      The top model on a public leaderboard is chosen for the bank, then misses internal acronyms, product names and Arabic legal phrasing.

      Spot itBuild a small labelled set from real staff questions, including hard near-misses, before choosing.
    • Mixing modalities in one ranked list with one threshold

      Image-to-text and text-to-text scores sit on different scales because of the modality gap.

      Spot itPlot score histograms per modality pair. Calibrate or rank within modality first.
    • Multi-vector storage surprise

      The pilot ran on 5,000 pages. Production has 2 million, and the index is half a terabyte.

      Spot itMultiply vectors per page by dimensions by bytes by pages before the pilot, not after.
    • The embedding clusters by nuisance, not meaning

      Complaints cluster by channel, dialect or template. A topic map looks neat and is wrong.

      Spot itCheck cluster purity against a known label such as product or issue type, and check whether the clusters predict template or language better than meaning.
    • Near-duplicates treated as different

      Contrastive training with near-duplicate "negatives" (the same policy in two versions) teaches the model to separate what should be identical, or retrieval returns an old version with equal confidence.

      Spot itTest retrieval of superseded versus current documents; add version metadata filters.
    • Using an embedding as a decision

      A close vector to a sanctioned name is treated as a match, or a distant one as clearance.

      Spot itEmbeddings generate candidates. Decisions in regulated flows need rules, thresholds set on labelled data, and a human step.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “Our search index is mostly numbers that describe each document. Newer models let us keep only the most useful part of those numbers, so the index can be four to sixteen times smaller and faster, with a small, measured loss in accuracy. For scanned trade documents there's a heavier option that treats the page like a picture and looks at its parts separately; it finds things text extraction misses but costs much more storage. I'd test both on our own documents, in Arabic and English, before we commit.”
    To a technical interviewer or validator
    “I'd start with a Matryoshka-trained embedding and evaluate recall at several truncation lengths, with 8-bit or binary quantisation and a full-precision re-score on the shortlist, split by language. For visually rich documents I'd consider ColPali-style patch embeddings with MaxSim, behind a cheap single-vector first stage to control storage. For any embedding we train in-house, I'd test for shortcut features by checking whether template, language or length predict similarity beyond meaning, and I'd build negatives from same-template documents so the contrastive loss has to learn content.”
    “Can we just cut our existing embeddings to 256 dimensions?”

    Only if the model was trained for it. A Matryoshka-trained model packs the most useful information into the earliest numbers, so cutting costs little. An ordinary model spreads information everywhere and degrades faster. Either way I'd measure recall at each length on our own queries, split by language, and re-normalise after cutting.

    “Why not store a vector per word and be done with it?”

    Quality is good, but storage multiplies by the number of tokens or patches. A page-image model stores about a thousand vectors per page, roughly 64 times a single 1,024-float vector. The usual compromise is a cheap first pass to pick a few hundred candidates, then token-level matching on those only, and compressing or pruning the stored vectors.

    “Is a multimodal embedding better than OCR plus text embedding?”

    It depends on what carries the meaning. For pages where layout, stamps, tables or handwriting matter, page-image retrieval often finds what OCR text loses. For clean text documents, OCR plus a good text model is cheaper and easier to explain and audit. I'd run both on a labelled sample of our documents and compare recall and cost.

    “The model's training loss is tiny. Doesn't that mean it understands our documents?”

    No. It means it can pick the right partner from the batch, which can be done with shallow cues like template or language. What it learned depends on what the negatives looked like. Test on queries and near-miss documents from our own domain, and look at what is predicted by template and language.

    “Can we use embeddings to screen names against a sanctions list?”

    As one candidate generator among several, possibly helpful for cross-script and transliteration variants. Not as the decision. Embeddings can put unrelated names close together and similar ones apart. Sanctions decisions need exact and fuzzy matching, thresholds validated on labelled cases, and analyst review. I'd check what the regulator and the bank's own policy require, since I can't state that for you.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. A bank has 50 million chunks. Vectors are 1,024 numbers as 4-byte floats. What is the size, and what is it with 256 numbers as 8-bit integers?

    50,000,000 × 1,024 × 4 bytes = 204.8 GB. With 256 numbers at 1 byte: 50,000,000 × 256 = 12.8 GB. That is 16 times smaller (4 times from length, 4 times from precision), before any index overhead.

    2. Why does a Matryoshka-trained model survive truncation and an ordinary one not?

    Its loss is applied to every nested prefix, so the first numbers are forced to carry the coarse, most useful distinctions on their own. An ordinary model's loss sees only the full vector, so nothing places information early and any prefix is an arbitrary slice.

    3. A document page is split into 1,030 patches of 128 numbers each, stored in 16 bits. How much storage for 2 million pages, against one 1,024-float vector per page?

    Per page: 1,030 × 128 × 2 bytes = 263,680 bytes. For 2 million pages: about 527 GB. A single 1,024-float vector is 4,096 bytes, so 2 million pages need about 8.2 GB. The multi-vector index is 64 times larger.

    4. A query has 3 tokens. A document has 500 token vectors. What does MaxSim compute, and how many comparisons?

    For each of the 3 query tokens, the best dot product against the 500 document tokens; then the three best values are added. That is 3 × 500 = 1,500 dot products per document, against one for a single-vector comparison.

    5. A batch holds 256 documents, and a model can see only the template (16 equally likely). Roughly what loss can it reach, against ln 256?

    On average about 16 of the other 255 documents share the anchor's template (255 ÷ 16), so the model is choosing among about 17 equally good candidates. The loss is close to ln 17 ≈ 2.8, against a ceiling of ln 256 ≈ 5.5. The shortcut removes about half the loss. The remainder is the only pressure left to learn content. The exact value is slightly lower because the average of a logarithm sits below the logarithm of the average.

    6. How would you change batch construction to push a model to learn content rather than template?

    Build batches from documents that share the template and differ in content, or add hard negatives of the same template but different topic. Then template no longer separates positive from negatives. Also remove near-duplicate false negatives, which teach the model to separate things that should match.

    7. Name one reason image and text scores from the same model cannot be compared on one threshold.

    The modality gap: image and text embeddings occupy different regions of the shared space, so text-to-image similarities sit on a different scale from text-to-text ones. Rank within modality or calibrate each pair type.
