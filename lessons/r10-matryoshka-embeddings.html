    Matryoshka and Multi-Vector Embeddings

    Part 1

    What these embeddings are

    In one sentenceAn embedding is a list of numbers that stands for a piece of text so that similar texts get similar lists. Matryoshka embeddings can be cut short without breaking, and multi-vector embeddings use one list per word or patch instead of one per document.

    Search over embeddings embeds every document chunk once, embeds the question, and returns the chunks whose lists are closest. Two things then hurt at scale: size (50 million chunks at 1,024 numbers each is about 205 GB of fast memory) and lost detail (one list per page is an average, so a question about one stamp or amount gets diluted).

    Running example: a search over 50 million bank document chunks, such as policies, contracts and scanned forms.

    How they differ from ordinary embeddings

    • Ordinary embedding: information is smeared across all the numbers. Chop it short and the result is an arbitrary slice that works badly.
    • Matryoshka: trained so that coarse facts land first and fine detail later. Chopping costs little. Named after Russian nesting dolls.
    • Multi-vector: keeps one list per piece (word or image patch), so nothing is averaged away. It costs far more storage.
    Part 2

    How they work

    Matryoshka: train every prefix

    Matryoshka Representation Learning (Kusupati et al., 2022) changes only the training loss. The architecture is the same.

    1. Pick nested sizes, such as 64, 128, 256, 512 and 1,024.
    2. Score each prefix with the usual training loss, as if it were the whole embedding.
    3. Add the scores up and train on the total.

    The 64-number prefix must work alone, so it learns the broad facts first. Full-length quality drops very little.

    • Re-normalise after cutting. A prefix of a length-1 vector is shorter than 1, so divide by its length or scores from different sizes will not compare.
    • It stacks with compression. Storing each number as an 8-bit integer instead of a 32-bit float is 4 times smaller. Cutting 1,024 floats to 256 8-bit numbers is 16 times smaller.
    • Only trained models cut well. Check the model card. Chopping an ordinary model fails badly.

    A cheap trick: short pass, then careful pass

    Search everything with a short prefix, keep a shortlist, then re-score only the shortlist with the full vector. It is like skimming headlines, then reading a few articles. Keep the shortlist generous (tens to hundreds): a document that misses it cannot be rescued.

    Multi-vector: one list per piece

    ColBERT (Khattab and Zaharia, 2020) keeps a vector for every token. Each query token finds its best-matching document token, and those best scores are added. This is MaxSim. "Amount" matches one corner of the page and "stamp" another, neither diluted by the rest.

    Documents and queries are encoded separately, so document vectors can be precomputed. That makes it much faster than a cross-encoder, which reads query and document together, while keeping much of the precision.

    Pictures too. Multimodal models such as CLIP (Radford et al., 2021) put text and images in one space. ColPali (Faysse et al., 2024) applies MaxSim to page images, about a thousand patches per page, with no text extraction or chunking, and beat pipelines built on those steps on a benchmark of visually rich documents.

    How to read the trade-offs

    • Matryoshka at 256 vs 1,024: if search quality at 256 is close to quality at 1,024, the cut was almost free. A big gap means the model was not trained for it.
    • MaxSim score: high means the query is covered somewhere in the document, not that the document is mainly about it.
    • Storage: ColPali needs about 64 times the storage of one vector per page (roughly a thousand 128-number vectors).
    • Mixed text and images: text-to-text and text-to-image scores sit in different ranges (the "modality gap", Liang et al., 2022), so rank within each type rather than using one cut-off.

    Which to use

    OptionStorageDetail keptUse when
    Full single vector1xAverage of the pageSmall collections, simple questions
    Matryoshka, cut4x to 16x smallerCoarse, a little less fineMemory and speed matter
    Multi-vector (MaxSim)Far largerPer word or patchQuestions about specific details
    Keyword searchSmallExact words onlyExact codes and names; often combined with the above
    • Strong at: cutting memory and latency (Matryoshka), matching paraphrases such as "cancel my card" with "terminate a plastic" (all dense vectors), and detail-specific questions or scans (multi-vector).
    • Weak at: near-identical documents, such as forty versions of one loan template, which differ only in fine detail that cutting removes. Multi-vector storage is heavy.

    Usable today? Yes. Several embedding models advertise Matryoshka support, and multi-vector search is common as a second step: a cheap pass shortlists a few hundred pages, then MaxSim re-scores only those. Test on your own documents first, since the gains depend on them.

    In banking, cutting embeddings makes searching tens of millions of policy chunks affordable, and MaxSim helps find the one clause, amount or stamp inside long scanned trade documents.

    Part 4

    Common mistakes and quick check

    • Chopping a model that was not trained for it

      Ordinary embeddings fall apart when shortened. Pick a model whose card says it supports Matryoshka sizes.

    • Forgetting to re-normalise

      After cutting, divide by the new length, or scores from different sizes cannot be compared.

    • A tiny shortlist

      In short-then-full search, a document that misses the shortlist is lost for good. Keep it generous.

    • Ignoring multi-vector storage

      Per-piece vectors can cost around 64 times as much. Use them on a shortlist, not the whole collection.

    1. What does Matryoshka training change?

    Only the loss: it scores every nested prefix, so each short prefix works alone.

    2. Why does a normal embedding break when cut short?

    Its information is spread over all the numbers, so a prefix is an arbitrary slice.

    3. What is MaxSim?

    Each query token finds its best-matching document token, and those best scores are added to give the document score.

    4. Why not use multi-vector for everything?

    It stores many vectors per document, far more memory. Use it to re-score a shortlist.

    5. Going from 1,024 floats to 256 8-bit integers shrinks storage by how much?

    Sixteen times: 4 times from fewer numbers and 4 times from smaller numbers.
