    Embeddings That Shrink, See and Compare

    How one embedding can be cut short, why a page may need many vectors, and what contrastive training really rewards.

    Contents

    The whole lesson in one sentenceAn embedding has three dials: how many numbers you keep (Matryoshka), how many vectors per item (multi-vector) and what the training task forced it to notice (contrastive learning).

    Part 1

    The intuition

    An embedding turns text, an image or a page into numbers so that similar things sit close together. Dense retrieval embeds every chunk once, embeds the question, and returns the nearest chunks.

    Three things then matter at bank scale. Cost: 50 million chunks at 1,024 numbers is about 205 GB of fast memory, so you want embeddings you can cut to size. Resolution: one vector per page is an average, so a question about a stamp or an amount gets lost; you may need one vector per piece. What was learned: contrastive training is a multiple-choice exam, and a model can pass by spotting a cheap cue such as letterhead or length.

    Hold onto thisAn embedding has three dials: length, number of vectors, and training task. Each trades accuracy against cost, and each can look fine in a demo and fail on your documents.
    Part 2

    How it really works

    R10.1 · Matryoshka: nested prefixes

    Ordinary training puts only the full vector in the loss, so information smears across all the numbers and any prefix is an arbitrary slice, like cutting a photo file in half. Matryoshka Representation Learning (Kusupati et al., 2022) changes only the loss. You pick nested sizes (say 64, 128, 256, 512 and 1,024), compute the same contrastive loss on each prefix, and add the results, optionally with a weight per size. The architecture is unchanged and full-length quality drops very little.

    Because the 64-number prefix must work alone, coarse facts (topic, language, document type) land first and fine detail fills in later. Like Russian dolls, you stop at the size you can afford. Reading it in practice: if recall at 256 numbers is close to recall at 1,024, the cut was nearly free. A big gap means the model was not trained for it.

    The knobs are few. The list of nested sizes should be the sizes you might deploy; in-between sizes usually work but are not guaranteed, so test them. The weights decide how much the small prefixes are favoured over the full vector. What it costs is a model trained this way, which means picking one that advertises it. It assumes your documents differ mainly in coarse features that fit the early numbers. Near-identical documents (forty versions of one loan template) differ only in fine detail, and lose more on cutting.

    • Re-normalise after cutting. A prefix of a unit-length vector is shorter than 1. Divide by its norm, or scores from different lengths do not compare.
    • It stacks with quantisation (storing each number in fewer bits). 1,024 floats to 256 8-bit integers is 16 times smaller; binary goes further, usually with a higher-precision re-check (P3 covers the same idea for model weights).
    • Only models trained for it truncate well. Check the model card. Chopping any other model gives the red line in Simulation 1.

    Many models already use only a low-dimensional corner of their space (dimensional collapse; Jing et al., 2022). That is part of why truncation can work at all, and a reason to check how many dimensions yours really use.

    Adaptive retrieval: short pass, then careful pass

    Nested sizes allow a cheap trick, like skimming headlines before reading the articles. Search everything with a short prefix, take a shortlist, then re-score only the shortlist with the full vector. The cost is roughly the short pass plus (shortlist ÷ corpus) of the full pass, and the final ranking still comes from the full embedding. It is retrieve-then-rerank using one model at two resolutions.

    Two knobs matter: the first-pass length and the shortlist size. A document that misses the shortlist can never be rescued, so be generous (tens to hundreds, not five). The saving is large, but measure it on your own documents.

    R10.2 · Multimodal embeddings

    Text and page images share one space, so the words "customs declaration, 40 pallets of dates" land near a scan of that declaration and a query can find a scan without OCR (optical character recognition, turning pixels into text). CLIP (Radford et al., 2021) trained this on photos and captions: one image encoder, one text encoder, hundreds of millions of pairs. The matching caption is the positive; every other caption in the batch is a negative.

    • The modalities do not truly overlap. Image and text vectors sit in different regions, the "modality gap" (Liang et al., 2022). Text-to-text and text-to-image scores therefore have different ranges, so one cut-off on a mixed list is wrong. Rank within each type, or calibrate each pair type separately.
    • OCR-first throws away layout. A number in a table cell, a stamp or a signature box carries meaning that flat text loses. Newer document models embed the page image or its patches instead.

    Multi-vector retrieval: MaxSim

    One vector per page averages everything and washes out the detail a query asks about. Late interaction (ColBERT; Khattab and Zaharia, 2020) keeps a vector per token. Each query token finds its best-matching document token, and those best scores are added. This is MaxSim. It is like checking a shopping list against a shop: each item finds its own shelf, so "amount" matches one corner and "stamp" another, neither diluted by the rest of the page.

    "Late" means the query and document are encoded separately, so document vectors can be precomputed, and only the cheap matching happens at query time. That is why it is far faster than a cross-encoder (which reads query and document together) while keeping much of its precision. A high score means the query is covered somewhere in the document, not that the document is about it.

    ColPali (Faysse et al., 2024) applies this to page images: about a thousand patches per page, each embedded by a vision-language model, matched to query tokens. It needs no OCR, layout detection or chunking, and beat pipelines built on those steps on a benchmark of visually rich documents. The price is storage, around 64 times a single vector (roughly a thousand 128-number vectors per page). The usual production pattern is a cheap single-vector or keyword pass that shortlists a few hundred pages, then MaxSim on those only.

    R10.3 · What contrastive training asks for

    All of this is trained with some form of the InfoNCE loss (F5.7). It is a multiple-choice question: for one anchor, the true partner (positive) hides among the other batch items (negatives), and the loss punishes the model for giving the right one low probability. A model that cannot tell them apart across B items has loss ln B; a perfect one is near 0. The temperature sets how sharply the model must separate them.

    Wang and Isola (2020) gave it a geometric reading. Alignment: matched pairs end up close. Uniformity: embeddings spread over the sphere instead of clumping, so different things stay distinguishable. Both can be measured on your own embeddings.

    The catch is that the model learns only whatever separates the positive from those particular negatives.

    • Shortcut features. If positives share an easy cue that negatives lack (language, template, length, boilerplate), the model uses the cue and ignores meaning. Chen et al. (2021) called this feature suppression.
    • The negatives define the lesson. Random negatives allow shortcuts; same-template negatives force content. Larger batches and mined hard negatives (wrong items that look right) raise the difficulty. A false negative, such as a near-duplicate labelled as a negative, teaches the wrong thing.

    A low training loss does not mean the model learned what you want. It means the model won the game it was set. Check on your own queries and near-miss documents.

    Strengths, limits and when to use it

    Strong at:

    • Cutting memory and latency. Search cost and index size scale with vector length, and a Matryoshka model keeps the useful signal in the early numbers, so a 4x cut often costs little accuracy.
    • Paraphrase and cross-language matching. Dense vectors compare meaning, so "cancel my card" finds "terminate a plastic" where keyword search sees no shared word.
    • Detail-specific questions (multi-vector). Each query token matches its own part of a page, so a stamp, an amount or a clause is not averaged away.
    • No OCR for scans (multimodal and ColPali). The page image is embedded directly, so layout survives: table cells, stamps, signature boxes.
    • One model, two resolutions. A short prefix for the broad pass and the full vector for the careful one gives retrieve-then-rerank without a second model.

    Weak at, or don't use when:

    • Exact strings. Account numbers, IBANs, clause references and rare acronyms are poorly captured by dense vectors. Pair them with keyword search.
    • Truncating an ordinary model. Without Matryoshka training the prefix is a random slice, and accuracy collapses.
    • Small corpora. On a small corpus, full-length search is cheap and the engineering is not worth it.
    • Multi-vector at huge scale without a shortlist. Storage is tens of times larger and matching costs more per document.
    • Regulated decisions. Similarity is a ranking signal, not a verdict. Sanctions screening and credit decisions need rules, thresholds set on labelled data and a human step.

    Alternatives and how to choose:

    In practice: start with one Matryoshka-trained model at full length, build a labelled set of real staff questions, and measure recall at 256, 512 and full length. Pick the smallest length within about a point of full recall, store it in 8 bits, and add a full-vector re-score of the top 100 or so. Only reach for multi-vector when your labelled failures are detail or layout questions that a single vector cannot answer. Compute is modest: embedding is a one-off batch job, and the saving shows up at tens of millions of chunks, not thousands.

    In banking this shows up in policy and procedure assistants over millions of chunks, trade-finance and KYC document search over scans, and adverse-media screening, where embeddings propose candidates and rules and analysts decide.

    Part 3

    How it fails, and how to spot it

    • Truncating an untrained model

      Accuracy drops silently when you chop to save money.

      Spot itCheck the model card, and compare recall at each length on labelled queries.
    • Averages hide a language gap

      A 2-point mean loss may be 9 points for Arabic and 1 for English.

      Spot itReport every evaluation split by language, script and document type.
    • Benchmark rank is not task fit

      The leaderboard winner misses internal acronyms and Arabic legal phrasing.

      Spot itBuild a small labelled set from real staff questions, with near-misses.
    • Multi-vector storage surprise

      A 5,000-page pilot becomes a half-terabyte index at 2 million pages.

      Spot itMultiply vectors per page, dimensions, bytes and pages before the pilot.
    • One threshold across modalities

      Image-to-text and text-to-text scores sit on different scales, so a single cut-off passes the wrong items.

      Spot itPlot score histograms per modality pair and calibrate or rank within each.
    • Shortcut cues and false negatives

      A fine-tuned encoder separates documents by template, and old and new versions of one policy are pushed apart, so retrieval returns the wrong version with confidence.

      Spot itTest on same-template near-misses and on superseded versus current documents; add version filters.
    • Using an embedding as a decision

      A close vector to a sanctioned name is treated as a match, or a distant one as clearance.

      Spot itEmbeddings generate candidates; regulated decisions need rules and a human step.
    Part 4

    Self-check

    1. Why does a Matryoshka-trained model survive truncation and an ordinary one not?

    Its loss covers every prefix, so the first numbers must carry the coarse distinctions alone. An ordinary loss sees only the full vector, so any prefix is an arbitrary slice.

    2. Why must you re-normalise a truncated vector?

    A prefix of a unit-length vector is shorter than 1, so scores at different lengths are not comparable.

    3. When does MaxSim beat one averaged vector, and what does it cost?

    When the question asks about a few small parts of a long page, which the average dilutes. It costs many vectors per page, so far more storage.

    4. How would you push a model to learn content rather than template?

    Build batches from same-template documents or add same-template hard negatives, so template no longer separates positive from negatives. Remove near-duplicate false negatives.

    5. Why can image and text scores not share one threshold?

    The modality gap puts them on different scales. Rank within modality or calibrate each pair type.

    6. Your RAG index holds 50 million chunks from a 1,024-number model that was not Matryoshka-trained, and memory is tight. Which option would you choose and why?

    Do not truncate. Quantise to 8-bit (4x smaller) or binary with a full-precision re-score of the shortlist, which works on any model. Or move to a Matryoshka-trained model and re-embed once. Decide by measuring recall on a labelled set.

    7. Staff search scanned trade-finance PDFs with stamps and tables. Would you pick OCR plus a single vector, or ColPali-style multi-vector? Why?

    If questions are about stamps, table cells or layout, multi-vector page embeddings, because OCR flattens those and one vector averages them. Control storage by shortlisting with a cheap pass first. If questions are about plain prose, OCR plus a single vector is cheaper and good enough.
