    LLMOps: Prompt Versions, Traces and Evals in CI

    Part 1

    What LLMOps adds

    In one sentenceLLMOps is three habits for a language-model app: number every release (versions), record every request (traces), and test every change before it ships (evals in CI, meaning checks that run automatically on each change).

    Our running example is a card-fee assistant. It tells a customer the fee is waived after AED 20,000 of spend, but the policy says AED 30,000. The team now needs three answers.

    • What changed? Versioning. Every prompt release gets a number, like a flight number.
    • What happened on that call? Tracing. Each request leaves a record of its steps, like a parcel's tracking page.
    • How do we stop a repeat? Evals in CI. A fixed set of test questions runs on every change and blocks the release if quality drops.

    How it differs from ordinary software practice

    • Output is free text. A normal test asks "does it equal 42?". An LLM test asks "was this answer acceptable?", which is harder to score.
    • More than code changes behaviour. A new model version, a changed setting or a different search setting alters answers with no code change.
    • Scores are noisy. The same system scored twice on 100 questions gives slightly different results (see the standard error lesson).
    Part 2

    How it works

    Prompt versions

    A release is more than the prompt text. It bundles the template, the exact model version, sampling settings, tools, search settings and any required output format. Change one and behaviour changes, so they share one number. Two rules:

    • Versions are immutable. Version 7 is always the same. An edit makes version 8, so any old request can be replayed against exactly what it used.
    • Labels move. "production" and "candidate" are bookmarks that point at a version. Promotion moves the bookmark forward. Rollback moves it back, with no redeploy.

    Pin the model too. An alias such as "latest" can change under you, and a model change needs testing exactly like a prompt change.

    Traces

    A trace is the record of one request. It is made of spans, one per step, each with a start, a duration and notes such as model name, prompt version and token counts. Drawn as bars, it is called a waterfall.

    You add business context to each trace: language, prompt version and the IDs of retrieved documents. Never store raw customer identifiers. Then you can ask "show every Arabic answer that used policy document 118, 2022 version".

    Evals in CI

    An eval runs the app over a fixed set of cases and scores the outputs. In CI it runs whenever a prompt, model or setting changes, and fails the build if scores drop below a threshold. Cheap checks come first, expensive last.

    1. Check the rules. Is it valid JSON, free of card numbers, in the right language? Free, runs on every change.
    2. Check key facts. Does the answer contain "AED 30,000"? Cheap, but a correct paraphrase can fail.
    3. Ask a judge model. Another model grades helpfulness and accuracy. It costs tokens and has biases, so compare it against human labels.
    4. Ask humans. Experts grade a sample before major releases. Slow and costly.
    Part 3

    How to read it

    Reading a trace

    Read in order: the shape (which bar is longest), the model spans (token counts), the retrieval span (what came back), and only then the answer text. This tells you where the fault lies.

    • Right paragraph retrieved but ignored: a prompt or model problem.
    • Wrong paragraph retrieved: a search problem.
    • Right paragraph, old version: a data problem. In our example, retrieval returned the 2022 fee policy. Time and cost looked normal, so only a quality score would catch it.

    Reading an eval score

    87% vs a 90% baseline on 100 cases. Not clearly worse. Two identical systems often differ by about 6 points on 100 cases, so 3 points is noise.
    Overall up from 83% to 87%. Check the slices before promoting. A version can improve overall while Arabic questions get worse.
    Nine answers got worse, two got better on the same cases. Strong evidence of a regression, stronger than comparing two overlapping percentages.

    To cut noise, in order of value: use more cases, especially on costly topics such as fees. Compare baseline and candidate on the same cases and count the flips. Use zero tolerance for rules and safety, and a margin for quality, checked per slice (language, risk level).

    Part 4

    Which tool for which job

    PracticeAnswersStrong atWeak at
    VersioningWhat changed?Audit, replay, rollbackDoes not say if a version is good
    TracingWhat happened on this call?Cost, delay, root causeNeeds a quality score attached
    Evals in CIIs this change safe?Blocks regressions earlyNoisy on small test sets
    Ordinary logsDid something fail?Errors and crashesBlind to wrong but fluent answers

    Where to keep prompts: in git beside the code gives review and audit for free. A registry with sign-off suits teams where non-engineers edit prompts.

    Where test cases come from: production failures, policy documents, and hard Arabic and mixed-language questions. Keep a held-out set that nobody tunes against, or you measure memorisation.

    In banking, a prompt change alters customer-facing behaviour, so treat it like a policy change: reviewed, versioned, tested, and traceable to the exact release, with traces redacted and access controlled under CBUAE or SAMA rules.

    Part 5

    Common mistakes and quick check

    • Editing the prompt live, or versioning only the prompt

      A model alias or search setting changes while the prompt number stays put. Test: can you recover last month's exact prompt, model and settings from a trace?

    • Gating on a tiny test set

      Fifty easy English cases either pass everything or fail on noise, and people rerun until green. Ask for case counts per slice.

    • Tuning prompts on the test cases

      The score rises but live quality does not. Compare scores on a held-out set.

    • Trusting an overall average

      Overall can rise while Arabic or complaints fall. Demand a per-slice table beside every headline number.

    1. Why are versions immutable while labels such as "production" move?

    Immutability lets any old trace be replayed against exactly what ran. Movable labels make promotion and rollback a pointer change.

    2. Name three things besides prompt text that belong in a release.

    The pinned model version, sampling settings, tools, search settings and output format.

    3. A trace shows normal time and cost, yet the answer quotes an old fee. Where is the fault?

    In the data: retrieval returned an old document version. Only a quality score or a test case on that fee would flag it.

    4. What is the most reliable way to make an eval gate less noisy?

    More test cases, especially on costly topics. Four times the cases halves the noise.

    5. Why record the prompt version on every trace?

    To tie any complaint to the release that produced it, and to copy a failing trace into a permanent regression test.
