    Seeing and Gating an LLM System: Prompt Versions, Traces and Evals in CI

    Contents
    Part 1

    The intuition

    A card-fee assistant tells a customer the fee is waived after AED 20,000 of spend. The policy says AED 30,000. The team needs three answers.

    • What changed? Versioning: every prompt, model name and setting is a numbered, immutable release, like a flight number.
    • What happened on that call? Tracing: each request leaves a record of every step, like a parcel's tracking history.
    • How do we stop a repeat? Evals in CI: a test set runs on each change and blocks the release if quality drops.

    The twist: output is free text, so an LLM test asks "was this acceptable?" rather than "equals 42". And a score from 100 cases is itself a noisy estimate (Simulation 3).

    Hold onto thisIf you cannot name the exact prompt, model and settings that handled a request, you cannot debug, audit or roll it back.
    Part 2

    How it really works

    Tracing: a request as a tree of timed steps

    A trace is the record of one request, like a delivery tracking page. It is made of spans, one per step ("retrieve", "rerank", "call model"), each with a duration and attributes such as model name, prompt version and token counts. Spans nest into a tree, usually drawn as a waterfall of bars. The standard is OpenTelemetry.

    You add the business context: segment (never raw identifiers), language, prompt version, retrieved document IDs and versions. Then you can ask "show every Arabic answer that used policy document 118, 2022 version". Traces tell you what logs do not:

    • Where time and money went. Generation usually dominates both; retrieval often dominates variance.
    • Why the answer was wrong. Right paragraph retrieved but ignored: prompt or model problem. Wrong paragraph: search problem (M3). Right paragraph, stale version: data problem.
    • A path from complaint to fix. Copy the trace into a test case, fix, keep the case forever (M5).

    Two limits: keep all error and low-score traces plus a random sample, not everything. And prompts contain customer data, so decide what is redacted and who reads traces, with security and the regulator's rules (CBUAE or SAMA).

    Read a trace in order: the shape, the model spans (token counts), the retrieval span (what came back), and only then the text.

    Prompt versioning: immutable releases, movable labels

    A prompt release is more than the text: template, pinned model version, sampling settings, tools, retrieval settings (top-k, chunking) and any output schema. Change one and behaviour changes, so they share one number. Two rules:

    • Versions are immutable. Version 7 is always the same; an edit makes version 8. Old traces can be replayed against exactly what they used.
    • Labels are movable. "production" and "candidate" are pointers, like a bookmark. Promotion moves the pointer; rollback moves it back, with no redeploy.

    A bank will usually want prompts in git beside the code (review and audit for free), or a registry with sign-off, since a prompt change alters customer-facing behaviour. Pin the model too: an alias such as "latest" can move under you, and a model change needs re-evaluation exactly like a prompt change.

    Evals in CI: a test set as a release gate

    An eval runs the app over a fixed set of cases and scores the outputs. In CI it runs automatically whenever a prompt, model, retrieval setting or tool changes, and fails the build if scores drop below a threshold. Cheap checks first, expensive last:

    LayerWhat it checksBlind spot
    Deterministic checksValid JSON, required fields, no card number, language matches. Free, every commit.Not whether content is right.
    Golden answersKey facts present ("AED 30,000"). Free, fast.A correct paraphrase can fail.
    LLM-as-judgeAnother model grades helpfulness, faithfulness, tone. Costs tokens.Biases and drift; calibrate against human labels (M5).
    Human reviewExperts grade a sample before major releases. Slow, costly.Small samples, disagreement.

    Cases come from production failures, policy documents and hard Arabic and mixed-language variants. Keep a held-out set nobody tunes against, or you measure memorisation.

    The hard part is noise. Like polling: 100 people wobble, 400 steady. A score from 100 cases at 90% wobbles by about 3 points between reruns of an identical system, and two identical runs routinely differ by 6. A gate of "fail below baseline minus 3" on 100 cases wrongly blocks a good change about one time in eight and passes a real 5-point regression about a third of the time (F2.1).

    What to do about noise, in order of value:

    • More cases where it matters. Quadrupling the set halves the noise. Go bigger on costly topics (fees, eligibility, complaints).
    • Paired comparison. Run baseline and candidate on the same cases and count flips. Nine got worse and two better is far stronger evidence than two overlapping pass rates.
    • Hard rules versus soft scores. Zero tolerance for structure and safety; a margin for quality, checked per slice such as language and risk tier.
    Part 3

    How it fails, and how to spot it

    • Prompt edited live, or only the prompt versioned

      A "small tweak", or a model alias or top-k that changes while the prompt number stays put.

      Spot itTry to recover last month's exact prompt, model and retrieval settings from a trace.
    • Gate on a tiny or unrepresentative set

      Fifty easy English cases. The gate passes everything, or fails on noise and people rerun until green.

      Spot itAsk for case count per slice, and count failures that pass on rerun.
    • Overfitting to the eval

      Prompts tuned on the same cases until the score rises; live quality does not follow.

      Spot itCompare held-out and tuning-set scores.
    • Uncalibrated LLM judge

      It prefers long, polite answers and drifts when updated.

      Spot itMeasure judge-human agreement; pin the judge version.
    • Average hides a slice

      Overall rises while Arabic or complaints fall.

      Spot itDemand a per-slice table beside every headline number.
    • Green dashboards, bad answers, exposed data

      Latency is fine while answers are stale; customer data sits in traces with broad access.

      Spot itCheck quality scores are attached to traces; sample traces for IBAN or card patterns.
    Part 4

    Self-check

    1. Why are prompt versions immutable while labels such as "production" move?

    Immutability lets any old trace be replayed against exactly what ran. Movable labels make promotion and rollback a pointer change with no redeploy.

    2. Name four things besides prompt text that belong in a release.

    Pinned model version, sampling parameters, tool definitions, retrieval settings, output schema.

    3. A trace shows normal latency and cost, yet the answer quotes an old fee. Where is the fault?

    In the data: retrieval returned a stale document version, visible in the trace attributes. Only a quality score or a CI case on that fee would flag it.

    4. With 100 test cases, a candidate scores 87% against a 90% baseline. Is it worse?

    Not necessarily. Two identical systems routinely differ by about 6 points on 100 cases, so 3 points is noise. Add cases or compare on the same cases.

    5. What is the most reliable way to make a gate less noisy?

    More cases, especially on costly topics. Quadrupling the set roughly halves the noise.

    6. The overall score rose from 83% to 87%. What do you check before promoting?

    Per-slice scores, paired flips, hard-rule checks and a held-out set. Simulation 2's v4 is better overall but worse in Arabic.

    7. Why record the prompt version on every trace?

    To tie any complaint to the release that produced it and copy a failing trace into a regression test.
