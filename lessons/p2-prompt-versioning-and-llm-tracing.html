    Seeing and Gating an LLM System: Prompt Versions, Traces and Evals in CI

    A prompt is code that nobody can read the output of in advance. This lesson covers how to version it, how to see every step an LLM application took, and how to stop a bad change reaching customers by running tests automatically, including the arithmetic of how many test cases that takes.

    Contents

    The whole lesson in one sentenceTreat prompts, models and retrieval settings as versioned releases, record a trace of every step so a bad answer can be explained, and run a test set on every change as a statistical gate whose size you have chosen on purpose.

    Part 1

    The intuition

    Picture a card-fee assistant that tells a customer the annual fee is waived after AED 20,000 of spend. The policy says AED 30,000. Complaints arrive, and the team needs three answers.

    • What changed? A prompt tweak, a new chunk size, or a silent model update. Answered by versioning: every prompt, model name and setting is a numbered, immutable release (like a flight number, so you can say exactly which flight).
    • What happened on that call? Which text was retrieved and sent? Answered by tracing: each request leaves a record of every step, with inputs, outputs, timings and cost (like a parcel's tracking history).
    • How do we stop a repeat? Answered by evals in CI: a test set runs automatically on each change and blocks the release if quality drops (like a smoke test before a factory line ships).

    The twist: output is free text that varies run to run. A normal test says "equals 42". An LLM test asks "was this acceptable?", scored by rules, another model or a person. And a score from 100 cases is itself a noisy estimate (Simulation 3).

    Hold onto thisAn LLM app's behaviour is the product of a prompt, a model, retrieval settings, tools and data. If you cannot name the exact combination that handled a request, you cannot debug, audit or roll it back.
    Part 2

    How it really works

    Tracing: a request as a tree of timed steps

    A trace is the record of one request, like a delivery tracking page. It is made of spans, one per step ("retrieve", "rerank", "call model", "output check"). Each span has a start time, duration, parent and attributes: for a model call, the model name, prompt version, token counts and optionally the prompt and answer text. Spans nest into a tree, usually drawn as a waterfall of bars.

    This is distributed tracing from microservices, and the standard is the same: OpenTelemetry, with "GenAI semantic conventions" (agreed attribute names such as gen_ai.request.model) so tools can read each other's data. A minimal span:

    with tracer.start_as_current_span("generate_answer") as span:
    span.set_attribute("gen_ai.request.model", MODEL)
    span.set_attribute("app.prompt_name", "card-faq")
    span.set_attribute("app.prompt_version", 7)      # link trace to release
    reply = client.call(messages)
    span.set_attribute("gen_ai.usage.input_tokens", reply.usage.input)
    span.set_attribute("gen_ai.usage.output_tokens", reply.usage.output)

    SDKs auto-instrument most of this. You add the business context: segment (never raw identifiers), channel, language, prompt version, retrieved document IDs and versions. That lets you ask "show every Arabic answer that used policy document 118, 2022 version". Traces give you what logs do not:

    • Where time and money went. Generation usually dominates both; retrieval often dominates variance.
    • Why the answer was wrong. Right paragraph retrieved but ignored: prompt or model problem. Wrong paragraph: search problem (M3). Right paragraph, stale version: data problem.
    • A path from complaint to fix. Copy the trace into a test case, fix, keep the case forever (M5).

    Two limits. Sampling: storing every full prompt is expensive, so keep all error and low-score traces plus a random fraction of the rest. Privacy: prompts contain customer data, so decide what is redacted before storage, who reads traces, retention and location. Whether a managed tracing service is acceptable is a question for security and the regulator's data rules (CBUAE or SAMA).

    Read a trace in order: the shape (one long bar or many short?), the model spans (token counts), the retrieval span (what came back), and only then the text. Most incidents show before you read a word of the answer.

    Prompt versioning: immutable releases, movable labels

    A prompt release is more than the text: template, pinned model version, sampling settings, tool definitions, retrieval settings (top-k, chunking) and any output schema. Change one and behaviour changes, so they share one number. Two rules:

    • Versions are immutable. Version 7 is always the same bytes; an edit makes version 8. Old traces can be replayed against exactly what they used.
    • Labels are movable. "production", "staging" and "candidate" are pointers, like a bookmark. Promotion moves the pointer; rollback moves it back. The app asks for "card-faq at production", so rollback needs no redeploy.

    Where the text lives: git beside the code gives review, blame and CI for free. A registry editable by non-engineers gives fast iteration but needs its own approvals and audit trail. A bank will usually want git, or a registry with sign-off, since a prompt change alters customer-facing behaviour. Either way, the trace records which version answered.

    Pin the model too. An alias such as "latest" can move under you, and providers retire old versions. A model change forces re-evaluation exactly like a prompt change.

    Evals in CI: a test set as a release gate

    An eval runs the app over a fixed set of cases and scores the outputs. In CI it runs automatically whenever anything that can change behaviour changes (prompt, model, retrieval settings, tool, library), and fails the build if scores drop below a threshold. Promptfoo is built for this; Langfuse and MLflow store datasets and results. Cheap checks first, expensive last:

    LayerWhat it checksCost and speedBlind spot
    Deterministic checksValid JSON, schema, required fields, no card number, language matches, citation points to a retrieved document.Free, milliseconds. Every case, every commit.Not whether content is right.
    Golden answersKey facts present ("AED 30,000"), or exact match for classification and extraction.Free, fast.Brittle for free text; a correct paraphrase fails.
    LLM-as-judgeAnother model grades helpfulness, faithfulness, tone against a rubric.Costs tokens, minutes. Full set on pull requests.Biases and drift; calibrate against human labels (M5).
    Human reviewExperts grade a sample, settle disputes, refresh labels.Slow, costly. Before major releases.Small samples, annotator disagreement.
    Adversarial casesPrompt injection, data-reveal requests, off-policy advice.Moderate. On a schedule and before release.Only finds attacks someone thought of.

    A skeleton of the gate:

    results = run_suite("card-faq-cases.jsonl", prompt="card-faq@candidate")
assert results.schema_failures == 0                    # hard rules: zero tolerance
assert results.pass_rate("faithfulness") >= 0.88       # soft score vs a threshold
for sl in results.slices():                            # never only the average
    assert sl.pass_rate >= baseline[sl.name] - 0.05, sl.name

    Cases come from production failures, policy documents (each rule becomes questions), compliance and product staff, and hard variants in Arabic, mixed Arabic and English, typos and dialects. Keep a held-out set nobody tunes against, or you measure memorisation.

    The hard part is noise. Think of polling: ask 100 people and the result wobbles; ask 400 and it steadies. Each case is pass or fail, so the pass rate over n cases has a standard error

    SE≈p(1−p)n

    p is the true pass rate, n the number of cases. SE is the typical wobble in the measured score between reruns of an identical system. At p = 90% and n = 100 it is 3 points, so two identical runs routinely differ by 6. A gate of "fail below baseline minus 3" on 100 cases wrongly blocks a good change about one time in eight and passes a real 5-point regression about a third of the time (F2.1). Common misreading: a 3-point drop is not a regression; it is inside the noise. Model non-determinism and judge noise add more.

    What to do about noise, in order of value:

    • More cases where it matters. Noise falls with √n, so quadrupling the set halves it. Go bigger on costly topics (fees, eligibility, complaints).
    • Paired comparison. Run baseline and candidate on the same cases and count flips. 9 got worse and 2 better is far stronger evidence than two overlapping pass rates.
    • Hard rules versus soft scores. Zero tolerance for structure and safety; a margin with intervals for quality.
    • Repeat runs. Run each case a few times and average; keep temperature low, though identical output is never guaranteed.
    • Slices. Gate separately on language, product and risk tier (Simulation 2). Small slices need a wider margin or a human look.
    • Human override with a record. A named approver can ship a blocked release and write down why (the model-risk pattern, G3).
    Part 3

    How it fails, and how to spot it

    • Prompt edited live, no version

      A "small tweak" in production. Behaviour changes and nobody can say when.

      Spot itPick last month's trace and try to recover the exact prompt. If you cannot, versions are not immutable.
    • Only the prompt is versioned

      Model alias, top-k or chunk size changes while the prompt number stays put.

      Spot itCheck the release ID covers model version, parameters, tools and retrieval settings.
    • Gate on a tiny or unrepresentative set

      Fifty hand-picked, easy, English cases. The gate passes everything.

      Spot itAsk for case count per slice and the interval; compute the block-probability curve (Simulation 3).
    • Overfitting to the eval

      Prompts tuned on the same cases until the score rises; live quality does not follow.

      Spot itCompare scores on a held-out set with the tuning set.
    • Uncalibrated LLM judge

      It prefers long, polite answers or its own model family, and drifts when updated.

      Spot itMeasure judge-human agreement on a sample; pin the judge version.
    • Average hides a slice

      Overall rises while Arabic or complaints fall.

      Spot itDemand a per-slice table beside every headline number.
    • Traces full of customer data

      Names, account numbers and IDs in a third-party service with broad access.

      Spot itSample stored traces for IBAN or card patterns; check retention, access and hosting against policy.
    • Flaky gate gets ignored

      It fails on noise, people rerun until green, and a real regression is rerun away.

      Spot itCount failures that pass on rerun. A high rate means an under-sized set or wrong margin.
    • Healthy latency, bad quality

      Dashboards green while answers are stale or wrong.

      Spot itAsk whether quality scores are attached to traces (Simulation 1, stale index).
    Part 4

    Self-check

    1. Why are prompt versions immutable while labels such as "production" move?

    Immutability lets any old trace be replayed against exactly what ran (debugging, audit). Movable labels make promotion and rollback a pointer change with no redeploy.

    2. Name four things besides prompt text that belong in a release.

    Model name and pinned version, sampling parameters, tool definitions, retrieval settings (top-k, chunking), output schema. Possibly the document index version.

    3. A trace shows normal latency and cost, yet the answer quotes an old fee. Where is the fault and how would you have caught it?

    In the data: retrieval returned a stale document version, visible in the trace attributes. A faithfulness score on the trace, or a CI case on that fee, would have flagged it. Latency and cost cannot.

    4. 100 cases, baseline 90%. What is the standard error of the candidate's measured pass rate if it is truly 90%?

    √(0.9 × 0.1 ÷ 100) = 0.03, so 3 points. A 95% interval is about ±6, so a 3-point gap between runs is noise.

    5. How many more cases to halve the noise?

    SE falls with √n, so four times as many: 100 becomes 400, SE goes from 3 to 1.5 points.

    6. The overall score rose from 83% to 87%. What do you check before promoting?

    Per-slice scores with sizes and intervals, the paired flips, hard-rule checks, and a held-out set. Simulation 2's v4 is better overall but worse in Arabic.

    7. Why record the prompt version on every trace?

    To tie any complaint to the release that produced it, compare monitoring scores by version, and copy a failing trace into a regression test with the right context.
