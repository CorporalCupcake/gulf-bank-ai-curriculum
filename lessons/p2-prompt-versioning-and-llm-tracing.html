    Seeing and Gating an LLM System: Prompt Versions, Traces and Evals in CI

    A prompt is code that nobody can read the output of in advance. This lesson covers how to version it, how to see every step an LLM application took, and how to stop a bad change reaching customers by running tests automatically, including the arithmetic of how many test cases that takes.

    Contents

    The whole lesson in one sentenceTreat prompts, models and retrieval settings as versioned releases, record a trace of every step so a bad answer can be explained, and run a test set on every change as a statistical gate whose size you have chosen on purpose.

    Part 1

    The intuition

    A bank's customer-service assistant answers questions about card fees from policy documents. On Tuesday a customer is told that the annual fee is waived after AED 20,000 of spend. The policy says AED 30,000. Complaints arrive. The team asks three questions at once.

    • What changed? Someone tweaked the system prompt last week, someone else changed the chunk size, and the provider quietly updated the model. Which one?
    • What happened on that call? What was retrieved? Which prompt text was sent? Did the model see the right paragraph and ignore it, or never see it?
    • How do we stop it happening again? Without a human re-reading a hundred answers after every edit.

    Each question has an ordinary software answer, with one twist. Versioning answers the first: every prompt, model name and setting is a numbered, immutable release. Tracing answers the second: every request leaves a record of each step, with inputs, outputs, timings and cost. Evals in CI answers the third: a test set runs automatically on each change and blocks the release if quality drops.

    The twist is that the output is free text and varies from run to run. A normal unit test says "equals 42". An LLM test says "was this answer acceptable", scored by rules, by another model, or by a person, and a score from 100 cases is itself a noisy estimate. The third simulation shows how noisy.

    Hold onto thisAn LLM application has no single function to read. Its behaviour is the product of a prompt, a model, retrieval settings, tools and data. If you cannot name the exact combination that handled a request, you cannot debug it, audit it or roll it back.
    Part 2

    How it really works

    Tracing: a request as a tree of timed steps

    A trace is the record of one request. It is made of spans: one per step, such as "retrieve", "rerank", "call model", "run output check". Each span has a start time, a duration, a parent span, and attributes: for a model call, the model name, prompt version, input and output token counts, and (if you choose to keep them) the prompt and completion text. Spans nest, so the picture is a tree, usually drawn as a waterfall of bars on a time axis.

    This is the same idea as distributed tracing for microservices, and the standard is the same: OpenTelemetry. It has a set of "GenAI semantic conventions", agreed attribute names such as gen_ai.request.model and gen_ai.usage.input_tokens, so different tools can read each other's data. A minimal hand-written span looks like this:

    with tracer.start_as_current_span("generate_answer") as span:
    span.set_attribute("gen_ai.request.model", MODEL)
    span.set_attribute("app.prompt_name", "card-faq")
    span.set_attribute("app.prompt_version", 7)      # link trace to release
    reply = client.call(messages)
    span.set_attribute("gen_ai.usage.input_tokens", reply.usage.input)
    span.set_attribute("gen_ai.usage.output_tokens", reply.usage.output)

    In practice the SDKs and platforms auto-instrument most of this. What you must add yourself is the business context: customer segment (never raw identifiers), channel, language, prompt version, retrieved document IDs and their versions. That is what lets you ask "show me every answer in Arabic that used policy document 118 version 2022".

    Three things traces give you that logs do not:

    • Where the time and money went. The generation span usually dominates both. Retrieval often dominates variance.
    • Why the answer was wrong. Right paragraph retrieved but ignored is a prompt or model problem. Wrong paragraph retrieved is a search problem (M3). Right paragraph, stale version is a data problem.
    • A path from complaint to fix. Pull the trace, copy it into a test case, fix, and keep the case forever (M5, "building test sets from real failures").

    Two practical limits. Sampling: storing every full prompt and answer at volume is expensive, so teams keep all error and low-score traces and a random fraction of the rest. Privacy: prompts contain customer data. Decide what is redacted before it is stored, who can read traces, how long they are kept and where they live. Whether a managed tracing service is acceptable for a bank's data is a question for security and the regulator's data rules (CBUAE or SAMA), not something to settle in a notebook.

    A good habit when reading a trace: first the shape (one long bar, or many short ones?), then the model spans (token counts), then the retrieval span (what came back), and only then the text. Most incidents are visible before you read a word of the answer.

    Prompt versioning: immutable releases, movable labels

    The thing you version is bigger than the prompt text. A prompt release is the template, the model name and pinned model version, the sampling settings (temperature and so on), the tool definitions, the retrieval settings (top-k, chunking) and, for structured output, the schema. Change any one and behaviour changes, so they travel together under one number.

    The working pattern, used by prompt registries and by MLflow's and Langfuse's prompt features alike, has two parts:

    • Versions are immutable. Version 7 is always the same bytes. An edit creates version 8. Nothing is overwritten, so an old trace can always be replayed against the exact prompt it used.
    • Labels or aliases are movable. "production", "staging" and "candidate" are pointers to a version. Promotion is moving a pointer; rollback is moving it back. Application code asks for "card-faq at production" and never hard-codes a number, so a rollback needs no redeploy.

    Where should the text live? Two honest options. In git beside the code you get review, blame, branches and CI for free, and prompt changes go through the same change control as everything else. In a registry that non-engineers can edit you get fast iteration and a product owner who can tune wording, but you need your own approvals and audit trail. Many banks will want the git route, or a registry whose promotions require sign-off, because a prompt change is a change to customer-facing behaviour. Either way, the trace must record which version answered.

    Pin the model too. A provider's alias such as "latest" can move under you. Use a dated or versioned identifier where one exists, and expect that providers retire old versions on a schedule: a model change forces a re-evaluation exactly like a prompt change.

    Evals in CI: a test set as a release gate

    An eval runs the application, or a part of it, over a fixed set of cases and scores the outputs. In CI means it runs automatically whenever something that can change behaviour changes: a prompt, a model name, retrieval settings, a tool, a library. The pipeline compares scores with a threshold and fails the build if they drop. Tools such as Promptfoo are built for this, and platforms such as Langfuse and MLflow store the datasets and results; the mechanics are the same whichever you pick.

    Cheap checks first, expensive ones last:

    LayerWhat it checksCost and speedBlind spot

    Golden answersKey facts present ("AED 30,000"), or exact match for classification and extraction.Free. Fast.Brittle for free text. A correct paraphrase fails.

    A skeleton of the gate, in the style of any test runner:

    results = run_suite("card-faq-cases.jsonl", prompt="card-faq@candidate")
assert results.schema_failures == 0                    # hard rules: zero tolerance
assert results.pass_rate("faithfulness") >= 0.88       # soft score vs a threshold
for sl in results.slices():                            # never only the average
    assert sl.pass_rate >= baseline[sl.name] - 0.05, sl.name

    Where do the cases come from? From production traces, especially the failures; from policy documents (turn each rule into questions); from compliance and product staff who know the awkward ones; and from deliberately hard variants in Arabic, mixed Arabic and English, typos and unusual dialects. Keep a held-out set that nobody tunes prompts against, or you are measuring memorisation of the test.

    The hard part is the statistics. Each case is a pass or fail, so the pass rate over n cases has a standard error

    SE≈p(1−p)n

    p is the true pass rate and n the number of cases. At p = 90% and n = 100 the standard error is 3 points, so two runs of an identical system routinely differ by 6. This is the interval logic of F2.1. It means that a gate "fail if the score drops below baseline minus 3 points" on 100 cases will wrongly block a perfectly good change about one time in eight, and wave through a change that is really 5 points worse about a third of the time. Model non-determinism and judge noise add to this on top.

    What to do about the noise, in order of value:

    • More cases where it matters. The curve steepens with √n, so quadrupling the set halves the noise. Go bigger on the cases that are expensive when wrong (fees, eligibility, complaints).
    • Paired comparison. Run baseline and candidate on the same cases and look at the cases that flipped. If 9 got worse and 2 got better, that is far stronger evidence than two overlapping pass rates. A paired test uses the flips only.
    • Hard rules versus soft scores. Zero tolerance for structural and safety checks; a margin with intervals for quality scores.
    • Repeat runs. For stochastic systems, run each case a few times and average; set temperature low, though even then providers do not guarantee identical output.
    • Slices. Gate separately on language, product and risk tier, as in Simulation 2. Small slices need a wider margin, or a human look rather than an automatic block.
    • A human override with a record. A blocked release can be shipped by a named approver who writes down why. That is the normal model-risk pattern (G3), applied to prompts.

    How it connects

    This lesson is the operating layer for everything built in the M tracks. It is MLOps, adapted to systems whose logic lives in text.

    Retrieval settings are part of the release. A trace shows what the retriever returned, so search failures are separated from generation failures.

    Simulation 3 is a confidence-interval problem. The testing mindset (F10) supplies the discipline of regression tests.

    Versions, traces and gate results are the audit trail that independent validation will ask to see.

    Where it shows up at the bank:

    • Customer-service assistant. Answers on fees and products must match current policy. Version the prompt and the document index together; gate on faithfulness to sources, with Arabic and English slices.
    • Complaints and KYC document summarisation. Traces let a reviewer see which passage a summary came from. Hard rules catch missing mandatory fields.
    • Internal copilots for analysts and compliance. Trace retention and redaction are the main design question, because prompts may contain customer data.
    • Agentic workflows (payments queries, case triage). Traces are the record of what the system did and why; they are what an investigator or auditor reads after an incident.
    • Vendor-hosted models. When the provider changes the model, your gate is the only early warning. Ask what notice the contract gives (G3, vendor risk).
    Part 4

    Where the field is now

    The practice has converged quickly: versioned prompts with labels, OpenTelemetry-style traces, and eval suites run in pull requests. What is unsettled is the standardisation of the data, how to evaluate long-running agents, and how far to trust automated judges.

    Part 5

    How it fails, and how to spot it

    Each comes with the quickest check.

    • Prompt edited live in a console, no version

      A "small wording tweak" in production. Behaviour changes and nobody can say when.

      Spot itPick a trace from last month and ask if you can recover the exact prompt used. If not, versions are not immutable.
    • Only the prompt is versioned

      The model alias, top-k or chunk size changes and the prompt number stays the same.

      Spot itCheck what a release identifier covers. It should include model version, parameters, tools and retrieval settings.
    • Gate on a tiny or unrepresentative set

      Fifty hand-picked cases, all English, all easy. The gate passes everything.

      Spot itAsk for the case count per slice and the interval on the score. Compute the block-probability curve as in Simulation 3.
    • Overfitting to the eval

      Prompts tuned until the score rises; the same cases used every time. Live quality does not follow.

      Spot itKeep a held-out set that no one tunes against, and compare scores on it with the tuning set.
    • Uncalibrated LLM judge

      The judge prefers long, polite answers, or its own model family. It drifts when the judge model is updated.

      Spot itMeasure agreement between judge and human labels on a sample, and pin the judge version.
    • Average hides a slice

      Overall score rises while Arabic or complaints fall.

      Spot itDemand a per-slice table beside every headline number.
    • Traces full of customer data

      Raw prompts with names, account numbers and IDs stored in a third-party service with broad access.

      Spot itSample stored traces and search for IBAN or card patterns. Check retention, access and hosting location against policy.
    • Flaky tests teach people to ignore the gate

      The gate fails on noise, people rerun until green, and a real regression gets rerun away.

      Spot itCount how often failures pass on rerun. A high rate means the gate is under-sized or the margin is wrong.
    • Quality problems with healthy latency

      All dashboards green while answers are stale or wrong.

      Spot itAsk whether quality scores are attached to traces. Latency and cost alone cannot show it (Simulation 1, stale index).
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “Every answer our assistant gives will be traceable to an exact version of the instructions, the model and the documents it used, and every change is tested automatically before customers see it. If something goes wrong, we can show what happened on that call and roll back in minutes. The tests cannot be perfect, so for high-risk topics like fees and eligibility we use a larger test set and a human sign-off.”
    To a technical interviewer or validator
    “A release pins prompt, model version, sampling parameters, tools and retrieval settings under an immutable version, with production as a movable alias. Each request is traced with that version and retrieved document IDs, with redaction before storage. CI runs deterministic checks on every change and judge-scored suites on pull requests, gated per slice. I size the set from the binomial noise: at 100 cases a 3-point margin blocks good changes about one time in eight, so I go to several hundred cases on high-risk slices and use paired comparisons.”
    “Why not just test the prompt by trying it a few times?”

    Because behaviour varies between runs and between inputs, and a few good answers say little. A fixed test set run on every change gives a number you can compare over time. Ten hand-tried examples have a margin of error of roughly ±20 points on a pass rate.

    “The gate failed but the change looks fine. Can we override?”

    Yes, with a record. First check whether it is noise: rerun, and look at the paired flips. If the drop is within the interval and the slices are stable, a named approver can release it with the reason logged. If one safety or hard-rule check failed, no override without a fix.

    “Is it safe to send our prompts to a hosted tracing tool?”

    Not by default. Prompts contain customer data, so I'd check redaction before storage, where the data is hosted, retention, access, and what our data-protection and regulator rules require. A self-hosted option or tracing inside our own cloud is often the safer starting point. I would not assume a specific legal answer; that is for security and compliance to sign off.

    “The provider updated the model. Do we need to re-test?”

    Yes. A model change is a release. Pin a version where the provider allows it, run the full suite on the new one before switching, and watch the slices. A silent alias change is the reason to pin and to keep production traces scored.

    “Can an LLM judge replace human reviewers in CI?”

    For routine gating, if it has been calibrated: it agrees with human labels at an acceptable rate on a sample, its version is pinned, and humans still review a sample regularly and all the blocked or borderline cases. It is not a replacement for human sign-off on high-risk behaviour.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. Why are prompt versions immutable while labels such as "production" move?

    Immutability means any old trace can be replayed against exactly what ran, which is what debugging and audit need. Movable labels make promotion and rollback a pointer change with no redeploy, because the app asks for "production" rather than a number.

    2. Name four things besides prompt text that belong in a release.

    Model name and pinned version, sampling parameters, tool definitions, retrieval settings (top-k, chunking), and the output schema. Possibly the document index version too.

    3. A trace shows normal latency and cost, yet the answer quotes an old fee. Where is the fault likely to be and how would you have caught it?

    In the data: retrieval returned a stale document version. The trace attributes (document IDs and versions) show it. A quality or faithfulness score attached to the trace, or a CI case on that fee, would have flagged it. Latency and cost cannot.

    4. Your suite has 100 cases and baseline 90%. Roughly what is the standard error of the candidate's measured pass rate if it is truly 90%?

    √(0.9 × 0.1 ÷ 100) = 0.03, so 3 points. A 95% interval is about ±6. A difference of 3 points between two runs is well within noise.

    5. You want to halve the noise in the pass rate. How many more cases?

    The standard error falls with √n, so four times as many: 100 becomes 400, and the SE goes from 3 to 1.5 points.

    6. The overall score rose from 83% to 87%. What do you check before promoting?

    The per-slice scores (language, product, risk tier) with their sample sizes and intervals; the paired flips (what got worse); hard-rule checks; and a held-out set not used for tuning. Simulation 2's v4 is the example: better overall, worse in Arabic.

    7. Why record the prompt version on every trace?

    So any complaint can be tied to the exact release that produced it, so scores in monitoring can be compared by version, and so a failing trace can be copied into a regression test with the right context.
