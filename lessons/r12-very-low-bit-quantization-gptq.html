    Making Big Models Fit: Low-Bit Quantization, Attention and KV-Cache Tricks, Pruning and Distillation

    How a 70-billion-parameter model shrinks from 140 GB to about 36 GB, why long context is a memory problem, and how small models inherit a big model's skill.

    Contents

    The whole lesson in one sentenceServing a model is mostly a memory problem (weights plus a KV cache that grows with context), so efficiency means storing less: fewer bits, smarter caches, fewer weights, or a small model trained to imitate a big one.

    Part 1

    The intuition

    A 70-billion-parameter model stored as 16-bit numbers takes about 140 GB, and one data-centre GPU has 80 GB. A Gulf bank that keeps data in-country must run it on its own servers, so memory decides the bill. The KV cache, the model's working memory of the text so far (M1.5), adds more.

    A GPU calculates faster than it fetches, so fewer bytes per token means more answers per dirham. Four levers: quantization (fewer bits per weight), attention and cache tricks (move and store less), pruning (delete weights) and distillation (train a small model on a big one's outputs).

    Hold onto thisAsk of any efficiency claim: which memory does it shrink, what quality does it risk, and measured on which tasks? "No loss" usually means on an average benchmark, not your Arabic contract clauses.
    Part 2

    How it really works

    Very low-bit quantization: GPTQ, AWQ and FP4

    Think of measuring heights with a ruler marked every 10 cm: you store the nearest mark plus the ruler's spacing. Quantization stores a small integer per weight and a shared scale. Two choices matter. Group size is how many weights share a scale: smaller is more accurate and costs a little more storage (a 16-bit scale per 128 weights adds 0.125 bits each; per 32 adds 0.5). So "4-bit" really means about 4.1 to 4.5 bits stored. Outliers are a few huge weights that stretch the scale, so everyone else rounds to zero. Simulation 1 shows it.

    Plain rounding ("round-to-nearest") treats each weight alone. It works at 8 bits and often at 4 for big models, then degrades fast. Smarter methods ask which errors the model feels least.

    • GPTQ quantizes a layer one column at a time. After rounding each column, it nudges the not-yet-rounded weights to cancel the damage, guided by second-order information (how sharply the layer's output reacts to each weight, measured on a few hundred calibration texts). It quantizes a 175B model in GPU-hours, with no retraining.
    • AWQ finds the roughly 1% of channels that matter most by looking at the activations (the values flowing through), not the weights. It scales those channels up before rounding, so they get more of the grid. It needs less calibration data than GPTQ and tends to be less sensitive to which texts you choose.
    • Outlier handling. LLM.int8() keeps the outlier dimensions in 16-bit. SmoothQuant moves difficulty from activations into weights so both fit in 8 bits. QLoRA's NF4 spaces 16 levels to suit bell-shaped weights, so you can fine-tune on one GPU.
    • Below 4 bits, methods such as QuIP# and AQLM store groups of weights as an index into a learned codebook, reaching usable quality near 2 bits for the largest models. Small models suffer more, because they have less redundancy to spare. BitNet b1.58 trains ternary weights (-1, 0, +1) from scratch, which is a different job from compressing a finished model.

    FP4 is a 4-bit floating-point grid with 16 values bunched near zero and sparse far out, which suits bell-shaped weights. Each small block shares a scale: MXFP4 uses 32 values per block and a power-of-two scale, NVFP4 uses 16 values and a finer 8-bit scale, usually reported as more accurate. Recent GPUs multiply FP4 natively, so you save arithmetic time as well as memory. Integer weight-only schemes unpack to 16-bit before multiplying, so they save memory and bandwidth only.

    That split matters. Weight-only schemes (W4A16) suit single-user chat, where each token is limited by reading weights. Weight-and-activation schemes (W8A8, W4A4) also speed up arithmetic for big batches and long prompts, but activations have worse outliers, so they are harder to squeeze.

    FlashAttention and KV-cache compression

    Naive attention writes an N × N table of scores out to the GPU's slow memory and back. FlashAttention gives exactly the same result without storing the table, working in small tiles in fast on-chip memory. It is exact, so there is no quality trade. The trick is an "online softmax": it keeps a running maximum and total as each tile arrives, so the normalisation finishes without ever seeing the whole row. The arithmetic is unchanged; the saving is traffic to slow memory, which is why it is faster too.

    The KV cache is separate: it grows with layers, KV heads, bytes per number and tokens. For a 70B-class model with 8 KV heads it is about 43 GB at 131,072 tokens, for one user. FlashAttention does not shrink it. Each factor is a lever.

    • Fewer KV heads. Multi-query attention shares one key-value head across all query heads. Grouped-query attention is the middle ground and is in almost every current open model. DeepSeek's MLA caches a compressed latent instead. All are chosen at pre-training; you cannot bolt them on later.
    • Fewer bytes. Quantize the cache to 8 or 4 bits. KIVI quantizes keys per channel and values per token, because keys have channel-wise outliers.
    • Fewer tokens. Evict rarely-attended tokens (H2O), or keep a few "attention sink" tokens plus a recent window (StreamingLLM). Lossy: it can drop page 90.
    • Less waste. PagedAttention (vLLM) stores the cache in small pages, removing fragmentation and letting requests share a long system prompt. No quality cost.

    Pruning and distillation for on-premises models

    Pruning sets weights to zero and skips them. Unstructured pruning zeroes scattered weights: it saves storage, but ordinary GPUs cannot skip them, so no speed-up. Structured pruning removes whole rows, heads or layers: real speed, but it hurts more. NVIDIA's 2:4 pattern sits between: two of every four weights are zero, and recent GPUs exploit it. Structured pruning usually needs retraining to recover.

    Which weights go? Magnitude pruning drops the smallest. SparseGPT applies GPTQ-style compensation to prune in one shot. Wanda scores weight times typical input size: a small weight on a busy channel is not small in effect. Simulation 3 tests it.

    Distillation trains a small student to copy a big teacher. A hard label says "genuine". The teacher's full output says "genuine 89%, card fraud 5%, account takeover 4%, mule 0.5%", which shows how cases resemble each other. A temperature flattens the output so the small numbers show. The student's loss is usually a mix: match the true label, and match the teacher's softened distribution.

    For language models there are two forms. Logit distillation matches the teacher's token probabilities and needs its internals. Sequence-level distillation trains on text the teacher wrote, which works through an API and is how the distilled DeepSeek-R1 models inherit step-by-step reasoning. The two combine: prune a large model, then distil to recover quality, which needs far fewer training tokens than training from scratch.

    At the bank, a large model can label thousands of complaints or letters of credit once, offline. A small student then runs cheaply on a CPU, inside your perimeter. Check the teacher's labels on a human-reviewed sample first: the student inherits every mistake and cannot beat the teacher.

    Strengths, limits and when to use it

    Strong at

    • Fitting on hardware you own. 4-bit weights take a 70B model from 140 GB to about 36 GB with no retraining, only a calibration pass, so it fits one 80 GB card.
    • Faster generation. One user's decoding is limited by reading weights from memory. Halve the bytes and speed nearly doubles.
    • More users per GPU. Grouped heads, a smaller cache and paging shrink the per-user cache, which is what caps concurrency on long documents.
    • Free wins. FlashAttention and PagedAttention are exact. There is no quality to lose, so switch them on first.
    • Cheap specialists. Distillation turns a big model's labels into a small student that runs in milliseconds on a CPU inside your perimeter.

    Weak at, or don't use when

    • Hidden tail damage. Rounding errors concentrate in rare cases: long numbers, negations, Arabic, long reasoning chains. An average benchmark will not show them.
    • Very low bits on small models. Below about 4 bits, models under roughly 10B parameters degrade sharply because they have little redundancy.
    • Busy, batched serving. With many requests per batch, arithmetic matters as much as memory, so weight-only quantization helps less.
    • Unstructured pruning on ordinary GPUs. Scattered zeros save storage, not time.
    • Open-ended tasks for a distilled student. It copies the teacher's mistakes and cannot beat it. Check that the teacher's licence also allows training on its outputs.
    • Regulated models. Each compressed version is a different model and needs its own validation evidence.

    In practice. Start with the exact tricks: FlashAttention and a paged serving engine such as vLLM. Then try an 8-bit model, then a published 4-bit AWQ or GPTQ checkpoint. Compare each with full precision on 200 of your own examples, split by language and length. The knobs that matter are bits, group size (128 is a common default, 32 for harder cases), calibration text (a few hundred of your own Arabic and English samples) and cache precision. Quantizing a 70B model takes GPU-hours on one card. Distillation needs thousands to tens of thousands of teacher-labelled examples, produced once.

    In banking this shows up in on-premises assistants and Arabic document extraction under data-residency rules, and in complaint triage handled by a distilled small classifier. Fraud and credit scorecards are small tabular models, so none of this applies to them.

    Part 3

    How it fails, and how to spot it

    Compression failures are quiet: the model still answers fluently.

    • "No loss" measured on the wrong thing

      The vendor averages English multiple-choice tasks; yours is Arabic contract extraction.

      Spot itAsk what was measured and in which languages. Test on 200 of your own documents.
    • Averages hiding the tails

      Mean accuracy drops 0.5 points, but long numbers, negations and low-resource languages lose far more.

      Spot itBreak results down by language, length and document type. Diff the answers, not only the scores.
    • Calibration set unlike your data

      GPTQ and AWQ tune on a few hundred texts. If those are English web pages, Arabic financial text may round badly.

      Spot itAsk what calibration data was used.
    • Long context and reasoning degrading silently

      A compressed cache looks fine on short prompts and loses the clause on page 70.

      Spot itPlant a known fact deep in a long document and test it.
    • Memory saved, speed not gained

      Pruned weights the hardware cannot skip, or 4-bit weights unpacked in a slow kernel.

      Spot itMeasure tokens per second and cost per request on target hardware, not file size.
    • Distilling a teacher's mistakes

      The student copies every teacher error confidently and cannot beat its labels.

      Spot itHave humans label a sample independently and compare student, teacher and humans.
    • Forgetting the validated model changed

      Model risk signed off the 16-bit model; operations deploys a 4-bit one.

      Spot itCheck the deployed version against the validation report.
    Part 4

    Self-check

    Try each before opening the answer.

    1. Why does one huge outlier hurt a 4-bit group so much?

    It sets the scale, so the grid becomes coarse and most ordinary weights round to zero or one step.

    2. Why is generation speed limited by memory rather than arithmetic?

    Each token needs all the weights read from memory, with little arithmetic per byte. Halving the bytes nearly doubles the speed.

    3. What does FlashAttention change, and what does it not change?

    It avoids storing the N × N table, so traffic falls. The output is identical and the KV cache is no smaller.

    4. A vendor says their 2-bit model "matches the original". What do you check?

    Model size, which benchmarks and languages, long-context results, and speed on your hardware. Then test 200 of your own examples.

    5. Why does a temperature-softened teacher teach more than the correct label?

    A hard label says nothing about how wrong the wrong answers are. The softened output shows which classes look alike. Too high a temperature flattens it into noise.

    6. You need Arabic complaint triage, thousands a day, on CPU servers. Do you quantize a 70B model or distil? Why?

    Distil. The task is narrow and high-volume, so a small student trained on the big model's labels is far cheaper than serving even a 4-bit 70B. Check the labels on a human-reviewed sample first. Quantize only if the task needs the big model's broad knowledge at run time.

    7. Your GPUs are ordinary data-centre cards and memory is the problem. Would you prune or quantize? Why?

    Quantize. Weight-only 4-bit cuts memory and bandwidth with no retraining. Unstructured pruning would save storage but not time on these cards, and structured pruning hurts quality and needs retraining. Test the result on your own documents either way.
