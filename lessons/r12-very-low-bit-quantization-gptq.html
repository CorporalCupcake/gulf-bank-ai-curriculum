    Making Big Models Fit: Low-Bit Quantization, Attention and KV-Cache Tricks, Pruning and Distillation

    How a 70-billion-parameter model gets squeezed from 140 GB to about 36 GB, why long context was a memory problem before it was a model problem, and how small models inherit most of a big model's skill. All of it is what makes on-premises AI at a bank affordable.

    Contents

    The whole lesson in one sentenceServing a language model is mostly a memory problem (weights, plus a KV cache that grows with every token of context), so efficiency means storing or moving less: fewer bits per number, smarter attention and cache layouts, fewer weights, or a small model trained to imitate a big one. Each trades a little quality for a lot of hardware; the skill is knowing where the loss hides.

    Part 1

    The intuition

    A 70-billion-parameter model stored as 16-bit numbers takes 70 billion × 2 bytes = 140 GB. One data-centre GPU has 80 GB. A Gulf bank that cannot send data abroad must run this on its own servers, so it needs two or three cards before the first question. It is like a removals van that is too small: you either pack tighter or hire more vans.

    Two more bills follow. The KV cache is the model's working memory of everything read so far (M1.5), and for a long document it can exceed the weights. Naive attention also writes a table of (context length)², which is 17 billion entries per head at 128,000 tokens.

    None of this is about intelligence. It is about moving numbers. A GPU does arithmetic far faster than it fetches from memory, so generation speed is set by bytes read per token. Fewer bytes means more answers per second per dirham.

    Four levers:

    • Quantization: keep every weight, store it in 4 bits not 16. Like rounding prices to the nearest dirham, done so the errors land where they hurt least.
    • Attention kernels and cache layouts: same attention, never write the giant table (FlashAttention); store fewer or smaller keys and values.
    • Pruning: delete the least useful weights.
    • Distillation: train a small model on a big model's outputs.

    Quantization comes first because it needs no retraining and is a one-line option in serving tools.

    Hold onto thisAsk of any efficiency claim: which memory does it shrink (weights, KV cache, activations), what quality does it risk, and on which tasks was that measured? "4-bit with no loss" usually means no loss on an average benchmark, not on your Arabic contract clauses.
    Part 2

    How it really works

    Very low-bit quantization: round-to-nearest, GPTQ, AWQ and FP4

    Think of measuring heights with a ruler marked only every 10 cm: you store the nearest mark, plus the ruler's spacing. Quantization stores a small integer q and a shared scale s:

    w^=s·q,s=max|w|2b−1−1

    With b bits there are 2b levels; the integer q runs from −(2b−1−1) to +(2b−1−1). The scale s is set so the largest weight in the group just fits. Everything else is rounded to the nearest multiple of s. At 4 bits the integer is between −7 and 7: fifteen usable values for each weight in the group.

    Two choices matter before any clever algorithm.

    • Group size: how many weights share a scale. One scale per matrix is cheap but coarse. One per 128 or 32 weights costs an extra 16-bit number per group (about 0.125 or 0.5 bits per weight) and is much more accurate.
    • Outliers: a few weights, and especially a few activation channels, are many times larger than the rest. One outlier stretches the scale, like one giant in a class forcing the ruler to be marked in metres, so everyone else rounds to zero or one mark. Simulation 1 shows it.

    Plain round-to-nearest (RTN) rounds each weight alone. It works at 8 bits and often at 4, then degrades fast. Newer methods ask: given that I must round, which errors does the model feel least?

    • GPTQ (Frantar et al., 2022) quantizes a layer one column at a time and, after each, adjusts the not-yet-rounded weights to compensate, using second-order information (the Hessian of output error, from a few hundred calibration examples). Like a baker who rounded one ingredient up and trims the next to keep the cake right. It took 175B-parameter models to 3–4 bits in GPU-hours.
    • AWQ (Lin et al., 2023) notes that about 1% of weight channels matter far more, and you find them from the activations flowing through, not the weights. It scales those channels up before rounding (and the activation down) so they get more of the grid. No retraining, no mixed precision.
    • Outlier relatives. LLM.int8() keeps outlier dimensions in 16-bit. SmoothQuant shifts difficulty from activations to weights so both fit 8-bit. QLoRA's NF4 spaces its 16 levels to suit bell-shaped weights, for fine-tuning on one GPU.
    • Below 4 bits. QuIP#, AQLM and codebook methods store groups of weights as an index into a learned table, reaching usable quality near 2 bits for the largest models. Small models suffer more, with less redundancy to spare. BitNet b1.58 trains ternary weights (−1, 0, +1) from scratch, which is different from compressing a finished model.

    FP4: a floating-point grid with block scales

    FP4 (E2M1: one sign, two exponent, one mantissa bit) has 16 values bunched near zero and sparse far out: 0, 0.5, 1, 1.5, 2, 3, 4, 6 and negatives. Like a ruler with fine marks near zero and coarse ones far away, it suits bell-shaped weights. Range is limited, so each block shares a scale. MXFP4 (open standard) uses 32 values per block and a power-of-two scale. NVIDIA's NVFP4 uses blocks of 16, a finer 8-bit floating-point scale and a per-tensor scale, which is why it is usually reported as more accurate. Recent GPUs multiply FP4 natively, so you save arithmetic time as well as memory; integer weight-only schemes dequantize to 16-bit first and do not.

    Weight-only (W4A16) saves memory and bandwidth, which is what single-user chat needs. Weight-and-activation (W4A4, W8A8) also speeds arithmetic for big batches and long prompts, but activations have worse outliers and are harder to squeeze.

    FlashAttention and KV-cache compression

    Attention (F5.3) scores every token against every earlier one: an N × N table. Written naively it goes out to the GPU's slow main memory (HBM) and back. The arithmetic is cheap; the traffic is the cost. It is like carrying every page of a report to a distant filing room instead of working at your desk.

    FlashAttention (Dao et al., 2022) computes exactly the same result without storing the table. It processes tiles small enough for the chip's fast on-chip memory (SRAM), keeping a running maximum and sum so the softmax finishes incrementally ("online softmax"). Score memory drops from N² to nothing extra, and time falls because fewer bytes cross the slow bus. Versions 2 and 3 improve tiling and add 8-bit support on Hopper GPUs. It is exact, with no quality trade, so it spread everywhere.

    The KV cache holds, per layer and per earlier token, one key and one value vector per KV head:

    KV bytes=2×layers×kvHeads×headDim×bytes×tokens

    The 2 is for keys and values. For a 70B-class model with 80 layers, head dimension 128 and 16-bit storage: if every one of 64 query heads had its own key and value (multi-head attention), that is 2 × 80 × 64 × 128 × 2 bytes = 2.6 MB per token. With grouped-query attention sharing 8 KV heads, it is 327,680 bytes per token, 42.9 GB at 131,072 tokens, for one user.

    Each term is a lever:

    • Fewer KV heads. Multi-query attention shares one KV head across all queries; grouped-query attention (GQA) is the middle ground and is in almost all current open models. DeepSeek's MLA caches a compressed latent instead. Chosen at pre-training; you cannot bolt it on later without retraining.
    • Fewer bytes. Quantize the cache to 8 or 4 bits (KIVI quantizes keys per channel and values per token, since keys have channel-wise outliers). Engines offer 8-bit and FP4 options.
    • Fewer tokens. Evict rarely-attended tokens (H2O), keep a few "attention sink" tokens plus a recent window (StreamingLLM), or use sliding-window layers. Lossy: it can drop the detail from page 90.
    • Less waste. PagedAttention (vLLM) stores the cache in small pages, removing fragmentation and letting requests share a common prefix such as a long system prompt.

    Pruning and distillation for on-premises models

    Pruning sets some weights to zero and skips them, like cutting the least-read chapters from a manual. Whether it speeds things up depends on the kind.

    • Unstructured: zeroes individual weights anywhere. Accuracy survives high sparsity, but ordinary GPUs cannot skip scattered zeros, so you save storage, not time.
    • Structured: removes whole rows, heads or layers, so matrices shrink and every GPU benefits. It hurts more per parameter and usually needs retraining. NVIDIA's 2:4 sparsity sits between: two of every four weights are zero, and recent GPUs exploit the pattern.

    Which weights go? Magnitude pruning drops the smallest. SparseGPT (2023) applies GPTQ-style compensation to prune in one shot. Wanda (2023) scores |weight| × typical input size, the AWQ insight again: a small weight on a busy channel is not small in effect. Simulation 3 tests it.

    Distillation trains a fresh, smaller student to copy a bigger teacher (Hinton, Vinyals and Dean, 2015). A hard label says "genuine". The teacher's full output says "genuine 89%, card fraud 5%, account takeover 4%, mule 0.5%", so this case looks more like card fraud than a mule. A teacher marking a pupil's essay with comments teaches more than a bare grade. Hinton called it dark knowledge. A temperature T flattens the distribution so the small numbers show:

    pi=exp(zi/T)∑jexp(zj/T)

    z are the teacher's raw scores (logits). At T = 1 this is the ordinary softmax; higher T spreads probability onto the runner-up classes. The student's loss is usually a mix: cross-entropy against the true label plus a divergence from the teacher's softened distribution (F6.1 covers both).

    For language models there are two forms. Logit distillation matches the teacher's token probabilities and needs its internals. Sequence-level distillation trains on text the teacher wrote, which works through an API and is how distilled DeepSeek-R1 models inherit step-by-step reasoning. Prune a large model, then distil to recover quality is the most efficient route so far: NVIDIA's Minitron used a small fraction of the training tokens that training from scratch needs.

    At the bank, the same idea works for narrow tasks (classify a complaint in Arabic or English; extract fields from a letter of credit). A large model labels thousands of examples once, offline. A small student, even a classic classifier, trains on those labels and runs in milliseconds on a CPU at a fraction of the cost, inside your perimeter. Check the teacher's labels on a human-reviewed sample first: the student inherits every teacher mistake and cannot exceed it.

    Part 3

    How it fails, and how to spot it

    Compression failures are quiet: the model still answers fluently.

    • "No loss" measured on the wrong benchmark

      The vendor averages English multiple-choice tasks; yours is Arabic contract extraction.

      Spot itAsk what was measured and in which languages. Compare full-precision and compressed models on 200 of your own documents.
    • Averages hiding the tails

      Mean accuracy drops 0.5 points, but rare hard cases (long numbers, negations, tables, low-resource language) lose far more.

      Spot itBreak results down by language, length and document type. Diff the answers, not only the scores.
    • Calibration set unlike your data

      GPTQ and AWQ tune on a few hundred texts. If those are English web pages, Arabic and numeric financial text may round badly.

      Spot itAsk what calibration data was used. Re-quantize with your own text if you can.
    • Long-context recall silently degrading

      A quantized or evicted cache looks fine on short prompts and loses the clause on page 70.

      Spot itPlant a known fact at several depths in a long document ("needle" test) at the context length you will use.
    • Reasoning models degrading more than chat models

      Long chains of thought compound small errors. A model fine for summaries can fail multi-step calculations at 4 bits.

      Spot itTest the exact multi-step tasks, at the chain-of-thought length you will allow.
    • Memory saved, speed not gained

      Pruned weights the hardware cannot skip, or W4 weights dequantized in a slow kernel.

      Spot itMeasure tokens per second and cost per request on target hardware, not file size.
    • Forgetting the validated model changed

      Model risk signed off the 16-bit model; operations deploys a 4-bit one.

      Spot itCheck the model hash or version in the deployment record against the validation report. A compressed model needs its own evidence.
    • Distilling a teacher's mistakes and bias

      The student copies every teacher error confidently and cannot beat its labels.

      Spot itHave humans label a sample independently, and compare student, teacher and humans.
    • Comparing different true bit-widths

      "4-bit" with group size 32 and outlier storage is nearer 4.6 bits than 4.0.

      Spot itAsk for effective bits per weight and file size in GB.
    Part 4

    Self-check

    Try each before opening the answer. The numeric ones need only Part 2's formulas.

    1. A 70B-parameter model is stored at 4 bits with one 16-bit scale per 128 weights. How many GB, and how does that compare with 16-bit?

    Bits per weight = 4 + 16/128 = 4.125. Memory = 70 × 10⁹ × 4.125 ÷ 8 ≈ 36.1 GB, against 140 GB: about 3.9 times smaller, not exactly 4.

    2. Why does one huge outlier hurt a 4-bit group so much?

    The scale is set by the largest value fitting −7 to +7. If the outlier is 10 times a typical weight, one grid step is about 1.4 times a typical weight, so nearly every ordinary weight rounds to 0 or ±1 step. Smaller groups, or keeping the outlier in 16-bit, restore a fine grid.

    3. A model has 32 layers, 8 KV heads, head dimension 128. What is the KV cache for one user at 32,768 tokens in 16-bit?

    2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes per token. × 32,768 tokens ≈ 4.29 × 10⁹ bytes, about 4.3 GB. At 4-bit, about a quarter, ignoring scales.

    4. Why is generation speed limited by memory rather than arithmetic?

    Each token needs all the weights (and cache) read from memory, with little arithmetic per byte. The chip multiplies faster than it fetches, so time per token is roughly bytes read ÷ bandwidth. Halving bytes nearly doubles speed. With many users batched, arithmetic per byte rises and compute matters more.

    5. What does FlashAttention change, and what does it not change?

    It changes where the work happens: tiles in on-chip memory with an online softmax, so the N × N table is never stored and traffic falls. It does not change the output (it is exact) and does not shrink the KV cache.

    6. A vendor says their 2-bit model "matches the original". List three things you would check.

    Model size and task (large models tolerate low bits better); which benchmarks and languages, including long-context and multi-step tasks; and effective bits per weight, calibration data and speed on your hardware. Then run 200 of your own examples against the full-precision model.

    7. Why does distilling from a temperature-softened teacher teach more than training on the correct label?

    A hard label says nothing about how wrong the wrong answers are. The softened output shows which classes the teacher sees as close (card fraud, account takeover) and which far (money mule). That similarity structure is extra supervision per example. Too high a temperature flattens it into noise.

    8. Why is 2:4 sparsity often more useful in practice than 50% unstructured pruning, though it prunes the same fraction?

    The fixed pattern is something hardware can skip efficiently, giving real speed; scattered zeros save storage but a normal GPU still multiplies by them. The price is somewhat larger accuracy loss, as the black dot in Simulation 3 shows.
