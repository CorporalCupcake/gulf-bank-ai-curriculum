    Making Big Models Fit: Low-Bit Quantization, Attention and KV-Cache Tricks, Pruning and Distillation

    How a 70-billion-parameter model gets squeezed from 140 GB to about 36 GB, why long context was a memory problem before it was a model problem, and how small models inherit most of a big model's skill. All of it is what makes on-premises AI at a bank affordable.

    Contents

    The whole lesson in one sentenceServing a language model is mostly a memory problem (weights, plus a KV cache that grows with every token of context), so the efficiency toolkit is four ways of storing less or moving less: fewer bits per number, smarter attention kernels and cache layouts, fewer weights, and a smaller model trained to imitate a bigger one. Each trades a little quality for a lot of hardware, and the art is knowing where the quality loss hides.

    Part 1

    The intuition

    A Gulf bank wants an internal assistant that reads credit memos and trade documents. Data may not leave the country, so the model must run on the bank's own servers. The best open-weight model for the job has 70 billion parameters. Stored as 16-bit numbers, that is 70 billion × 2 bytes = 140 GB. A single high-end data-centre GPU has 80 GB. The model does not fit on one card, and before it answers a single question you are already renting two or three.

    Now the surprise. Fix the weights, and a second memory bill appears: the KV cache, the model's working memory of everything it has read so far (M1.5 explains it). For a long document it can be bigger than the weights. And a third cost hides in the arithmetic: the naive way to compute attention writes out a table of size (context length)², which at 128,000 tokens is 17 billion entries for every attention head.

    None of this is about making the model smarter. It is about fitting and moving numbers. A modern GPU can do arithmetic far faster than it can fetch numbers from its memory, so for chat-style generation the speed limit is how many bytes you must read per token. Fewer bytes means more answers per second, per rupee, per dirham.

    Four levers follow from that:

    • Quantization: keep every weight but store it with 4 bits instead of 16. It is rounding, done cleverly, so the rounding errors land where they hurt least.
    • Better attention kernels and cache layouts: compute exactly the same attention but never write the giant table (FlashAttention), and store keys and values in fewer, smaller pieces (grouped heads, quantized or evicted cache).
    • Pruning: delete the weights that matter least.
    • Distillation: train a small model on the outputs of a big one, so it learns the big model's judgements and not only the training labels.

    Quantization is the one you will meet first and most, because it needs no retraining and is a one-line option in serving tools. Start with the first simulation: round a set of weights to a few bits, and watch what breaks.

    Hold onto thisAsk of any efficiency claim: which memory does it shrink (weights, KV cache, or activations), what quality does it risk, and on which tasks was that measured? "4-bit with no loss" usually means no loss on a benchmark average, not on your Arabic contract clauses.
    Part 2

    How it really works

    Very low-bit quantization: round-to-nearest, GPTQ, AWQ and FP4

    A weight is stored as a 16-bit floating-point number. Quantization stores a small integer q plus a shared scale s, and recovers an approximation at run time:

    w^=s·q,s=max|w|2b−1−1

    With b bits there are 2b levels; the integer q runs from −(2b−1−1) to +(2b−1−1). The scale s is set so the largest weight in the group just fits. Everything else is rounded to the nearest multiple of s. At 4 bits the integer is between −7 and 7: fifteen usable values for each weight in the group.

    Two design choices matter before any clever algorithm. The first is the group size: how many weights share one scale. One scale for the whole matrix is cheapest but fragile; one scale per 128 or 32 weights costs an extra 16-bit number per group (about 0.125 or 0.5 extra bits per weight) and is much more accurate. The second is the outlier problem. Large language models contain a few weights, and especially a few activation channels, that are many times larger than the rest. One outlier in a group stretches the scale, and every ordinary weight in that group collapses onto zero or one level. The next simulation shows it.

    Plain round-to-nearest (RTN) handles each weight independently, and it works acceptably at 8 bits and often at 4. Below that it degrades fast, so the research since 2022 asks: given that I must round, which rounding errors does the model feel least?

    • GPTQ (Frantar et al., 2022) quantizes one layer at a time. It rounds weights one column at a time and, after each, adjusts the not-yet-rounded weights to compensate for the error just introduced, using second-order information (the Hessian of the layer's output error, estimated from a few hundred calibration examples). The intuition: if rounding one weight pushes the output up, nudge its neighbours down. It brought 175-billion-parameter models to 3–4 bits in a few GPU-hours with small quality loss.
    • AWQ (Lin et al., 2023, activation-aware weight quantization) observes that about 1% of weight channels matter far more than the rest, and that you find them by looking at the activations that flow through them, not at the weights themselves. Instead of storing those channels in higher precision (awkward for hardware), it multiplies them by a factor before rounding and divides the activation by the same factor, so the important channels get more of the integer grid. No retraining, no mixed precision.
    • Outlier-handling relatives. LLM.int8() (Dettmers et al., 2022) keeps outlier feature dimensions in 16-bit. SmoothQuant moves difficulty from activations into weights so both can be 8-bit. QLoRA's NF4 format spaces its 16 levels to match a bell-shaped weight distribution, and is used to fine-tune big models on a single GPU.
    • Below 4 bits. Methods such as QuIP#, AQLM and vector or codebook quantization store small groups of weights as an index into a learned table, and reach usable quality near 2 bits per weight for the largest models. Smaller models suffer more, because they have less redundancy to spare. BitNet b1.58 goes further and trains a model with ternary weights (−1, 0, +1) from the start, which is a different thing from compressing a finished model.

    FP4: a floating-point grid with block scales

    The methods above use evenly spaced integers. The newest hardware formats instead use tiny floating-point numbers. FP4 (called E2M1: one sign bit, two exponent bits, one mantissa bit) has only 16 values, bunched near zero and sparse further out: 0, 0.5, 1, 1.5, 2, 3, 4, 6 and their negatives. That shape suits bell-shaped weights. The catch is range, so every block of values shares a scale. Two formats are in use: MXFP4, the open microscaling standard, with 32 values per block and a power-of-two scale; and NVIDIA's NVFP4, with blocks of 16 and a finer 8-bit floating-point scale plus a per-tensor scale. Smaller blocks and a finer scale lower the error, which is why NVFP4 is usually reported as more accurate. The point of hardware formats is speed: recent GPUs multiply FP4 numbers natively, so you save arithmetic time as well as memory, which integer weight-only schemes (dequantize, then compute in 16-bit) do not.

    One distinction to hold: weight-only quantization (W4A16: 4-bit weights, 16-bit activations) saves memory and bandwidth, which is what matters for single-user chat. Weight-and-activation (W4A4, W8A8) also speeds the arithmetic, which matters for large batches and long prompts, but activations have worse outliers and are much harder to squeeze.

    FlashAttention and KV-cache compression

    Attention (F5.3) scores every token against every earlier token: an N × N table, softmaxed row by row, then used to mix value vectors. Written naively, the table goes to the GPU's main memory (HBM) and is read back. It is not the arithmetic that is slow, it is the traffic: the table is huge and HBM is slow relative to the chip's compute.

    FlashAttention (Dao et al., 2022) computes exactly the same result without ever materialising the table. It cuts the queries, keys and values into tiles small enough to sit in the chip's fast on-chip memory (SRAM), processes one tile of scores at a time, and keeps a running maximum and running sum so that the softmax can be finished incrementally ("online softmax"). Memory for the scores falls from N² to nothing extra, and the time falls because far fewer bytes cross the slow bus. Later versions (FlashAttention-2 and -3) rework the tiling and use newer hardware features, including 8-bit support on Hopper-generation GPUs. It is an exact method: no approximation, no quality trade. That is why it spread everywhere, and why a 128,000-token window stopped being a memory crisis for the scores.

    The second cost is the KV cache. During generation the model keeps, for every layer and every earlier token, one key vector and one value vector per KV head. Its size is:

    KV bytes=2×layers×kvHeads×headDim×bytes×tokens

    The 2 is for keys and values. For a 70B-class model with 80 layers, head dimension 128 and 16-bit storage: if every one of 64 query heads had its own key and value (multi-head attention), that is 2 × 80 × 64 × 128 × 2 bytes = 2.6 MB per token. With grouped-query attention sharing 8 KV heads, it is 327,680 bytes per token, 42.9 GB at 131,072 tokens, for one user.

    Every term in the formula is a lever:

    • Fewer KV heads. Multi-query attention (Shazeer, 2019) shares one KV head across all queries; grouped-query attention (Ainslie et al., 2023) is the middle ground. Almost all current open models use GQA. DeepSeek's multi-head latent attention (MLA) goes further, caching a compressed latent vector from which keys and values are rebuilt. This is decided at pre-training time. You cannot bolt it on later without some retraining.
    • Fewer bytes. Quantize the cache to 8 or 4 bits (for example KIVI, which quantizes keys per channel and values per token because keys have channel-wise outliers). Serving engines now offer 8-bit and FP4 cache options.
    • Fewer tokens. Evict tokens the model rarely attends to (H2O), keep the first few "attention sink" tokens plus a recent window (StreamingLLM), or use sliding-window layers that only look back a fixed distance. This is lossy and can fail on exactly the detail you needed from page 90.
    • Less waste. PagedAttention (the vLLM engine, Kwon et al., 2023) stores the cache in small pages instead of one large block per request, which removes most fragmentation and allows requests to share the cache for a common prefix, such as a long system prompt.

    Pruning and distillation for on-premises models

    Quantization keeps every weight and stores each one coarsely. Pruning instead sets some weights to zero and skips them. There are two kinds, and the difference decides whether you get a speed-up.

    • Unstructured pruning zeroes individual weights anywhere. Accuracy survives remarkably high sparsity, but ordinary GPUs cannot skip scattered zeros, so you save storage and not much time.
    • Structured pruning removes whole rows, attention heads, or layers, so the matrices simply become smaller and every GPU benefits. It hurts quality more per parameter removed, and usually needs some retraining to recover. NVIDIA's 2:4 sparsity sits between: in every group of four weights, two must be zero, and recent GPUs have hardware that exploits the pattern.

    Which weights to remove? Plain magnitude pruning drops the smallest. SparseGPT (Frantar and Alistarh, 2023) applies GPTQ-style second-order compensation to prune large models in one shot. Wanda (Sun et al., 2023) scores each weight by |weight| × the typical size of the input it multiplies, the same insight as AWQ: a small weight attached to a large, busy activation channel is not small in effect. Simulation 3 tests it.

    Pruning and quantization both end in a model that is a little off. Distillation asks for something different: train a fresh, smaller student to copy a bigger teacher. The trick (Hinton, Vinyals and Dean, 2015) is what the student copies. A normal label says "this transaction is genuine". The teacher's full output says "genuine 89%, card fraud 5%, account takeover 4%, mule 0.5%". That tells the student that this case resembles card fraud more than it resembles a mule, information no one-hot label contains. Hinton called it dark knowledge. A temperature T in the softmax flattens the teacher's distribution so those small numbers become visible:

    pi=exp(zi/T)∑jexp(zj/T)

    z are the teacher's raw scores (logits). At T = 1 this is the ordinary softmax; higher T spreads probability onto the runner-up classes. The student's loss is usually a mix: cross-entropy against the true label plus a divergence from the teacher's softened distribution (F6.1 covers both).

    For language models, distillation has several forms. Logit distillation matches the teacher's token probabilities, which needs the teacher's internals. Sequence-level distillation simply trains the student on text the teacher wrote, which works through an API and is how many "reasoning" students inherit step-by-step behaviour (the distilled DeepSeek-R1 models are an example). Combining the two crafts, prune a large model and then distil to recover quality, is the most efficient route found so far: NVIDIA's Minitron work compressed models to a fraction of the size while using a small fraction of the training tokens that training from scratch would need. The same pattern sits behind the small variants in several model families.

    For the bank, distillation has a second use. A specific task (classify a complaint in Arabic, English or both; extract fields from a letter of credit) can be done by a large model once, offline, on thousands of examples. A small student, even a classic classifier, is then trained on those outputs and runs in milliseconds on a CPU. You get the large model's judgement at a thousandth of the serving cost, inside your own perimeter. The rules still apply: check the teacher's labels on a human-reviewed sample first, because the student inherits every teacher mistake and cannot exceed it.

    Where it shows up at the bank:

    • On-premises copilots for credit memos, policies and trade documents under data-residency rules. The first question from infrastructure is always how many GPUs, and the answer comes straight from Simulation 2.
    • Document-heavy workflows (trade finance, KYC files) that need long context. Cache size, not model size, is often what limits how many analysts can use the system at once.
    • High-volume classification such as complaints, transaction narratives, sanctions-screening triage. Distil to a small model for cost and latency, keep the large model for the hard cases and for auditing.
    • Edge and branch use, such as voice or on-device assistants, where a 1–4 billion parameter model at 4 bits is the only practical option.
    • Model risk management. A quantized model is a different model from the one that was validated. It needs its own test on the bank's own data, in both Arabic and English.
    Part 4

    Where the field is now

    The basics are settled: 8-bit is routine, 4-bit weights are the default for self-hosting, and FlashAttention-style kernels and grouped-query attention are standard. The live questions are how low precision can go for reasoning models, whether the KV cache can be shrunk without losing long-range recall, and how far hardware formats such as FP4 should be used during training as well as serving.

    Part 5

    How it fails, and how to spot it

    Compression failures are quiet: the model still answers fluently. Each one comes with the quickest check.

    • "No loss" measured on the wrong benchmark

      The vendor shows an average over English multiple-choice tasks. Your task is Arabic contract extraction or long-document question answering.

      Spot itAsk what was measured and in which languages. Run the full-precision and compressed models on 200 of your own documents and compare.
    • Averages hiding the tails

      Mean accuracy drops by 0.5 points, but rare, hard cases (long numbers, negations, low-resource language, tables) lose far more.

      Spot itBreak results down by slice: language, length, document type. Diff the answers, not only the scores.
    • Calibration set that does not look like your data

      GPTQ and AWQ tune themselves on a few hundred example texts. If those are English web pages, Arabic and numeric-heavy financial text may be rounded badly.

      Spot itAsk what calibration data was used. Re-quantize with samples of your own text if you can.
    • Long-context recall silently degrading

      A quantized or evicted cache looks fine on short prompts and loses the clause on page 70.

      Spot itPlant a known fact at several depths in a long document ("needle" test) and check recall at each depth, at the context length you will actually use.
    • Reasoning models degrading more than chat models

      Long chains of thought compound small errors. A model that is fine for summaries can fail multi-step calculations after 4-bit compression.

      Spot itTest the exact multi-step tasks, with the chain-of-thought length you plan to allow, not a short-answer proxy.
    • Memory saved, speed not gained

      Pruned weights that the hardware cannot skip, or W4 weights dequantized on the fly in a slow kernel.

      Spot itMeasure tokens per second and cost per request on the target hardware. Do not infer speed from the file size.
    • Forgetting the validated model changed

      Model risk signed off the 16-bit model; operations deploys a 4-bit version.

      Spot itCheck the model hash or version in the deployment record against the validation report. A compressed model needs its own evidence.
    • Distilling a teacher's mistakes and bias

      The student copies every teacher error with high confidence, and cannot be better than its labels.

      Spot itHave humans label a sample independently of the teacher, and compare student, teacher and humans.
    • Comparing quantization levels at different true bit-widths

      "4-bit" with group size 32 and extra outlier storage is closer to 4.6 bits than to 4.0.

      Spot itAsk for effective bits per weight, and the file size in GB.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “A model of this size normally needs about 140 GB of memory. Storing each number in 4 bits instead of 16 brings it to roughly 36 GB, which fits on one GPU. That cuts our hardware bill by two thirds or more. The price is a small quality loss that we measure on our own Arabic and English documents before anything goes live. Long documents have a separate memory cost, and I'll give you that figure by use case.”
    To a technical interviewer or validator
    “I'd start from an AWQ or GPTQ 4-bit checkpoint with group size 128, calibrated on our own text, and compare it to the 16-bit model on a task suite that includes long-context recall at depth, Arabic, and the multi-step cases, reported by slice with intervals. I'd size the KV cache per user explicitly, since it often dominates at long context, and consider 8-bit cache before 4-bit. Distillation to a smaller student is the option for high-volume narrow tasks, with human-checked labels.”
    “Why does a 4-bit model not lose 75% of its quality?”

    Because the information is in the pattern across billions of weights, not in the precision of any one. Rounding adds small, mostly independent noise that averages out, and good methods (GPTQ, AWQ) steer the noise away from the weights that matter. Outliers are the exception, which is why the careful methods exist. Quality does fall, more at 3 bits and sharply at 2.

    “What is FlashAttention? Does it make the model worse?”

    No. It computes exactly the same attention result, but in tiles that stay in fast on-chip memory, so the huge intermediate table is never stored. It is a faster way to do the same sum, not an approximation.

    “We have 80 GB cards. Can we serve a 70B model with 100 users reading 100-page files?”

    Not on one card. At 4-bit weights, about 36 GB remain for about 36 GB of cache; at 128k tokens each user's cache is 43 GB at 16-bit, 11 GB at 4-bit. We would need several cards, a smaller model, cache quantization or sharing, or to retrieve passages (RAG) instead of loading whole files. I'd size it from the real document lengths and peak concurrency.

    “Pruning or quantization: which should we use?”

    Quantization first. It is mature, needs no retraining, and tools support it. Pruning only pays off if the hardware can exploit the sparsity (structured or 2:4), and it usually needs retraining or distillation to recover quality. For most banks, the practical pruning is picking a smaller model someone else has already pruned and distilled.

    “Can we just train a small model on the big model's answers?”

    Yes, and for narrow tasks it often works well. Check the licence of the teacher (some forbid using outputs to train other models), validate the teacher's labels on a human sample, and remember that the student inherits the teacher's mistakes. Keep a monitored sample of the student's decisions going to the larger model for drift detection.

    Part 7

    Self-check

    Try each one before opening the answer. The numeric ones need only the formulas in Part 2.

    1. A 70B-parameter model is stored at 4 bits with one 16-bit scale per 128 weights. How many GB, and how does that compare with 16-bit?

    Bits per weight = 4 + 16/128 = 4.125. Memory = 70 × 10⁹ × 4.125 ÷ 8 ≈ 36.1 GB, against 140 GB at 16-bit: about 3.9 times smaller, not exactly 4.

    2. Why does one huge outlier hurt a 4-bit group so much?

    The scale is set by the largest value so it just fits in the integer range −7 to +7. If the outlier is 10 times a typical weight, one step of the grid is about 1.4 times a typical weight, and nearly every ordinary weight rounds to 0 or ±1 step. Smaller groups, or keeping the outlier in 16-bit, restore a fine grid for the rest.

    3. A model has 32 layers, 8 KV heads, head dimension 128. What is the KV cache for one user at 32,768 tokens in 16-bit?

    2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes per token. × 32,768 tokens = 4.29 × 10⁹ bytes, about 4.3 GB. At 4-bit it is about a quarter of that, ignoring scales.

    4. Why is generation speed limited by memory rather than arithmetic?

    To produce each token for one user the GPU must read all the weights (and the cache) from memory, but it does only a small amount of arithmetic per byte read. The chip can multiply much faster than it can fetch, so time per token is roughly bytes read ÷ memory bandwidth. Halving the bytes nearly doubles speed. With many users batched together the arithmetic per byte rises and compute matters more.

    5. What does FlashAttention change, and what does it not change?

    It changes where the work happens: tiled computation in on-chip memory with an online softmax, so the N × N table is never stored and memory traffic falls. It does not change the output (it is exact), and it does not shrink the KV cache. Cache size is a separate problem.

    6. A vendor says their 2-bit model "matches the original". List three things you would check.

    The model size and task (large models tolerate low bits better than small ones); which benchmarks and languages, and whether long-context and multi-step tasks were included; and the effective bits per weight, calibration data and speed on your hardware. Then run it on 200 of your own examples against the full-precision model.

    7. Why does distilling from a temperature-softened teacher teach more than training on the correct label?

    A hard label has no information about how wrong the wrong answers are. The softened distribution says which classes the teacher considers close (card fraud and account takeover) and which far (money mule). That similarity structure is extra supervision on every example, so the student learns from fewer examples. Too high a temperature flattens it into noise.

    8. Why is 2:4 sparsity often more useful in practice than 50% unstructured pruning, even though it prunes the same fraction?

    The fixed pattern (two zeros in every four) is something the hardware can skip efficiently, so it gives real speed. Scattered zeros save storage but a normal GPU still multiplies by them. The price is a somewhat larger accuracy loss than free-form pruning at the same sparsity, as the black dot in Simulation 3 shows.
