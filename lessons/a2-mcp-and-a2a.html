    MCP, A2A and Computer-Use Agents

    Part 1

    What these three things are

    In one sentenceMCP is a standard plug that lets an AI agent use tools and data, A2A is a standard way for one agent to hand work to another, and a computer-use agent operates a screen like a person when there is no plug at all.

    A language model only writes text. To be useful at a bank it must read balances, search transactions and open cases, and each of those lives in a different system. These three ideas are the three ways it can reach them.

    How they differ

    • MCP (Model Context Protocol) points down: an agent reaching a tool or a data source. Think of a USB-C port: wrap each system once, and any agent can plug in.
    • A2A (Agent2Agent) points sideways: one agent delegating to a peer, perhaps built by another team. It covers finding who can do what, handing over a task, following progress and getting a result, without sharing code or memory.
    • Computer use points at a screen: the agent takes a screenshot, asks a model what to click or type, does one action, and repeats. It works almost anywhere, which is both the appeal and the danger.
    • Plain API calls and RPA scripts are the older routes. An API call is fixed code. RPA (robotic process automation) replays clicks at fixed screen positions, so it breaks when a screen changes.

    The saving from MCP is simple counting. Six agent applications reaching twelve systems by hand need 6 × 12 = 72 custom connectors. With a shared protocol each side speaks it once, so you need 6 + 12 = 18.

    Part 2

    How it works

    1. Connect. The agent app (the host) opens one MCP client connection to each MCP server.
    2. List. The server describes its tools in words, such as search_transactions: "search a customer's card transactions by date". It can also offer resources (documents attached as context) and prompts (templates a user picks).
    3. Decide. The model reads those descriptions and chooses a tool and its inputs. This is a guess made from text.
    4. Call. The client sends the call. The server checks who is asking and whether they may see that customer.
    5. Return. The result goes back into the model's context as text.

    A2A works differently. The other agent is treated as an outside contractor you cannot see inside. It publishes an Agent Card (a business card listing its skills and how to log in). You send it a task that has a state (working, waiting for input, done, failed) and can run for days. It returns an artifact, the finished deliverable. Inside one team, a function call or queue is simpler.

    Part 3

    How to judge what is safe

    Rule of thumbProtocols solve plumbing: find, call, report. They do not decide whether a call should be allowed. Every tool is a button the model can press, steered by text someone wrote.

    For each tool ask: if the model were fooled, what is the worst it could do?

    • Read before write. get_balance is far safer than transfer_funds. Start with read-only tools.
    • Act as the user. A shared service account lets a tricked model reach everything that account can (a "confused deputy": a trusted program misled into using its power for someone else). Pass the signed-in user's identity instead.
    • Limits in code, not the prompt. "Never transfer over AED 5,000" in a prompt is a request. A cap in server code is a rule.
    • Human approval for money and record changes, showing the real parameters.
    • Log every call so an investigator can rebuild what happened.

    Reading a computer-use agent's reliability

    Small errors compound. If each step works with probability p, a task of n steps works with probability p multiplied by itself n times. At 95% per step, 15 steps finish correctly only about 46% of the time. At 97% per step, 20 steps give about 54%; at 90% per step they give about 12%.

    • Check after every step that the screen changed as expected. A retry costs seconds; a silent wrong click that posts a payment costs far more.
    • Detection matters more than retries. Retries only happen when the agent notices a failure.
    • Treat everything on screen as input. A page can say "ignore your instructions", and that works through pixels too.
    • Run it in a recorded sandbox, not in an employee's logged-in session. Test Arabic and mixed Arabic-English screens, a known weak spot.
    Part 4

    Which route to use

    RouteUse it whenWeak at
    Plain API callThe task is fixed and an API existsEach integration must be written
    MCP serverAn agent chooses among tools; several apps share systemsTool descriptions are an attack surface
    A2AAnother team or vendor owns the capabilityHard to test; trust must be built
    RPA scriptA stable, rules-based screen workflowBreaks when screens change
    Computer useNo API and low volumeSlow, probabilistic, injectable

    Work down the table and stop at the first row that fits. Computer use answers "we cannot get an integration this year"; it is not the architecture to aim for.

    Show the formula

    P(task correct) = pn, where p is the chance one step works and n is the number of steps. Each step multiplies in another chance of failure, so long chains lose reliability fast. Shorter workflows and per-step checks beat a slightly better model.

    In banking, the question is rarely "can the agent reach it?" but "whose identity does the core system see, and what is the worst a fooled model can do with it?"

    Part 5

    Common mistakes and quick check

    • One shared service account behind every tool

      Any user, or any injected instruction, gets that account's full reach. Ask whose identity the downstream system sees.

    • Limits written only in the prompt

      A persuasive input can override them. Test the limit with a direct call that bypasses the model.

    • Trusting tool descriptions and remote agents

      A third-party description can hide instructions, or change after approval. A peer agent's output is untrusted input: validate it, never obey it. Pin versions and alert on changes.

    • Long screen workflows with no step checks

      Fifteen steps at 95% finish correctly under half the time, and the failures look like successes.

    1. Eight agent applications must reach ten systems. How many connectors without a standard, and with one?

    80 without (8 × 10), 18 with (8 + 10). The standard does not remove the work of building and securing one good wrapper per system.

    2. What is the difference between MCP and A2A?

    MCP connects an agent to tools and data. A2A connects an agent to another agent, treated as an opaque peer.

    3. Why is "never exceed AED 5,000" in a system prompt not a control?

    The model can be persuaded to ignore it. A cap in server code applies whatever the model says.

    4. A screen agent succeeds 97% per step over 20 steps with no checks. What is the success rate?

    About 54%. At 90% per step it falls to about 12%.

    5. With no failure detection, do retries help?

    No. Retries only fire when the agent notices a failure, so detection is what makes them useful.
