    Code That Can Change, and Code That Can Scale: Design Judgement and Performance Intuition

    How to tell, without writing it yourself, whether AI-written code will be easy to change in six months, and why one approach finishes in a second while another runs past the end of the batch window.

    Contents

    The whole lesson in one sentenceGood code gives each decision one home behind a small, stable boundary, so a change costs one edit rather than seven; fast code does work in proportion to the data, not its square or the number of round trips; and you judge both by asking where a change would land and by measuring first.

    Part 1

    The intuition

    A data scientist asks an AI assistant for a script that emails the fraud team every card transaction scored above 10%. It works in twenty minutes: 400 lines, one file, the path typed on line 12, the 10% repeated on lines 87, 203 and 340, one long function doing everything.

    Three months later a column is renamed, risk wants 8%, and volume grows tenfold, so the six-minute run takes nine hours and misses its window. Each change is easy in principle. In this file each is a scavenger hunt, and a missed spot ships a quiet inconsistency.

    Two judgements you can make by reading, without typing the code:

    • Design (F10.5): where would a change land? Think of a kitchen where every ingredient has one labelled shelf. A module is a shelf: one home for one decision (data shape, threshold, model, output). An interface is the small, stable door other code uses to reach it. Configuration holds decisions you can change without editing code.
    • Performance (F10.6): how does the work grow? Think of a teacher marking papers: checking each paper once is fine; comparing every paper against every other is not. At 10,000 rows the two look the same. At 10 million, one finishes before your coffee and the other next week.

    AI assistants optimise for "works now" in the context they were shown, so they are strong at code that runs and weak, by default, at both judgements.

    Hold onto thisAsk two questions. If this one fact changed, how many places would I edit? If the data were 100 times bigger, what would grow faster than the data? You can answer both from the outline of the code.
    Part 2

    How it really works

    Modules, cohesion and coupling: the cost of a change

    A module is a unit of code (file, package, class) that owns one job and hides how it does it. Parnas (1972) said to split a system by the decisions likely to change, not by the order of steps, and let each module hide one. Two properties tell you if the split is good:

    • Cohesion: things inside a module belong together. A features.py that also sends emails is a junk drawer.
    • Coupling: how much one module must know about another. If report code reaches into the model's internal coefficients, a change in one forces a change in the other.

    You want high cohesion and low coupling, for an economic reason: the cost of a change is roughly the number of places edited plus the behaviours re-tested because those edits might have broken them. A well-built house has one fuse box; a badly built one has wires through every wall. Pick a change below and compare two designs of a seven-step pipeline.

    In the tangled design a fact (column name, threshold, currency) is known in many places. In the modular design each fact is known once: column names by the loader, currency by a money step, threshold by the config. This is one source of truth (the DRY principle, "don't repeat yourself"), and the most useful thing to check in AI-written code.

    Don't overdo it. A 60-line script that runs once doesn't need five modules. Match effort to how long the code lives and how many people touch it: a notebook exploration can be messy; a nightly scoring job maintained for two years by someone who hasn't met you needs structure.

    Interfaces: the narrow door between pieces

    An interface is what a module promises and nothing else, like a vending machine: coins in, snack out, no view of the mechanism. Here: "give me a table with these columns and I return one probability per row." A logistic regression or a gradient-boosted ensemble can sit behind it and the caller never knows.

    In Python this is usually a function signature with type hints, or a small class with an agreed method. Test: can I replace this piece with a fake in a test? If scoring takes a table and returns probabilities, a test passes three rows and a fake model. If scoring opens a database and a file path inside itself, testing needs the whole world (F10.3 and F10.4).

    from typing import Protocol
import pandas as pd

class Scorer(Protocol):
    def predict_proba(self, features: pd.DataFrame) -> pd.Series:
        """One probability in [0, 1] per row, same index as the input."""

def alert_ids(scorer: Scorer, features: pd.DataFrame, threshold: float) -> list[str]:
    p = scorer.predict_proba(features)
    return list(features.index[p > threshold])

    Here alert_ids knows nothing about how scoring works, so swapping the model leaves it untouched. When reading an AI-written version, look for:

    • Small surface. A few clearly named inputs, one clear output. Eight parameters, or a whole DataFrame of which twelve columns are quietly used, is a wide hidden interface.
    • Pure where possible. A pure function computes a result from its inputs only, so it is easy to test. One that also writes a file, reads the clock and updates a global is not. Separate "decide" (pure) from "do" (touch the world): compute alerts in one place, send them in another.
    • Data contracts. The agreed shape between steps: columns, types, units (AED or fils? UTC or Gulf time?). Check it once at the boundary and fail loudly. This is the code-level cousin of F3.1 and F3.4.
    • No reaching around. Step 5 must not read a variable step 2 left lying around. Hidden global state is the usual cause of "works on my machine, different numbers on yours".
    • Notebook versus package. A notebook runs cells in whatever order you clicked. Great for exploring, poor for production. Maturity is when the logic that matters lives in importable, testable functions in a file.

    Configuration: facts that change without a code change

    Some values change for business reasons, not logic reasons: threshold, lookback window, input table, model version, currency list. Like a thermostat dial, they should be turned without opening the boiler. Put them in configuration, read once at start, not as literals in the code. Twelve-Factor test: could you publish the code today without leaking anything, and move it to a new environment by changing only config?

    EnvironmentWhich database or bucket, dev versus productionEnvironment variables or per-environment config.
    SecretsPasswords, API keys, tokensA secrets manager. Never in code or the repository, even a private one.

    The left column has three visible problems: a path that exists on one laptop, a password in the file, and a threshold written twice. Assistants produce this shape because the prompt's example had a path and a number and they copied the pattern. Hard-coded secrets are the worst: they get committed, copied and indexed. Treat any password-shaped string in a diff as a stop sign.

    Config also serves the auditor. With a versioned threshold, "what was live on 3 March?" is answered by version history; with a literal on line 340 it is archaeology (G3, P1 lineage). Reproducibility needs the same: fixed seeds, pinned library versions, config saved with each run's output.

    Each place is consistent with its own number. The failure is between them, and it is silent: nothing crashes, dashboards just disagree. That is why one source of truth is not tidiness: it removes an error class that testing each piece will not find.

    A reading checklist for AI-written code

    You will be handed pull requests and notebooks an assistant produced. Skip line-by-line reading and run this five-minute pass first:

    1. Outline. Do function and file names tell the story? One 300-line main is a flag.
    2. Search for literals. Every number, path, URL, column name, secret. Which appear more than once?
    3. Duplicates. Near-identical blocks (training and scoring versions of "clean the data") drift apart. GitClear's analyses report more copy-pasted and less refactored code as AI assistants spread (vendor, correlational).
    4. Where is the world touched? Reads, writes, network, clock, randomness: at the edges, or buried in calculations?
    5. Boundaries. Is there a check for expected columns and types, with a clear error?
    6. Loops over rows. A for over a DataFrame, or a database call in a loop, is a performance flag.
    7. Tests. At least one for the logic that matters, runnable without the production database?
    8. Surprising dependencies. A library added for something five lines would do? Each one must be patched and, in a bank, approved.

    Then tell the assistant in design terms: "pull the threshold, path and currency list into a config object", "split scoring from alerting", "add a schema check at the top of load". It follows structural instructions well and rarely volunteers them.

    Performance intuition: how the work grows

    Performance is about how work grows with data, not clever tricks. Call the row count n.

    • Linear, about n. Touch each row once. 10x data, 10x time. Fine.
    • Quadratic, about n2. For each row, look at every other row. 10x data, 100x time. Like a party where everyone must shake hands with everyone: 10 guests is 45 handshakes, 1,000 guests is about 500,000.
    • n log n. Sorting. Nearly linear in practice.
    • Constant per lookup. A hash table (Python set or dict, a database index) finds an item as fast in a million entries as in a thousand, like a dictionary's alphabetical index versus reading every page.

    The classic banking trap is matching two lists: for each transaction, is the counterparty on the watchlist? Naive code scans the whole list per transaction. Fast code puts the list in a set once and looks each name up. Same answer, different universe of time. (Fuzzy matching for real sanctions screening uses blocking or indexing for the same reason; see B2.)

    The second trap is round trips. Every database or API call has a fixed wait, often a millisecond or more, however little data comes back. One call per transaction pays it a million times. This is the "N+1 query" pattern (one query for the list, then n more to enrich each item), and the most common serious fault in AI-written data code, because "for each row, fetch the customer" is how a person describes the task.

    The shape matters: two bars grow in step with the data; one grows with the data times something else. Doubling n in the nested loop quadruples the time if the watchlist grows too, and doubles it if the list is fixed. Either way the product bites.

    What is slow in data code, and the usual cures

    Four patterns cause most of the pain in Python data work.

    1. Row-by-row loops on tables. iterrows() and apply(..., axis=1) run Python once per row. Whole-column operations run compiled code over all rows at once: vectorisation (F11). Think of stamping one page at a time versus pressing a whole stack. Gains of 10 to 1,000x are normal.
    # Slow: Python runs once per row
flags = []
for _, row in df.iterrows():
    flags.append(row.amount_aed > 50_000 and row.channel == "online")
df["flag"] = flags
# Fast: one operation over whole columns
df["flag"] = (df["amount_aed"] > 50_000) & (df["channel"] == "online")
    1. Lists searched inside loops. if name in watchlist on a list scans it each time. Use watch = set(watchlist) once. For tables, a join does the same in optimised code.
    2. A query per row. Replace "for each transaction, fetch the customer" with one join in the warehouse or one batched query (F3.3). Move the work to the data and let the database use its indexes.
    3. Too much data moved or held. Reading a 20 GB CSV when you need three columns and one month. Use Parquet (columnar: reads only requested columns, compresses, keeps types), filter and select early, and avoid accidental copies from chained pandas operations. When data no longer fits in memory, everything slows or crashes.

    Two more levers. Parallelism: split independent work across cores (each customer's features separately). In standard CPython the global interpreter lock (GIL) stops threads running Python in parallel, so CPU-heavy work uses processes or compiled libraries. A free-threaded build became officially supported (not default) in Python 3.14, but many libraries need special builds. Hardware: GPUs help large matrix work, not a row loop waiting on database calls. If the bottleneck is waiting, a faster chip does nothing.

    The same thinking applies to models. A card-authorisation service must answer in tens of milliseconds, so latency constrains the model and a smaller or distilled one may win (P3); a batch propensity job has hours (P2). Throughput is rows per hour (a batch problem); latency is time for one answer (a real-time problem). They are optimised differently.

    Measure first: profiling and the cost of cleverness

    Knuth's "premature optimisation is the root of all evil" has a more useful full form: about 3% of a program is where the time goes, so optimise only after finding it. Intuition about which part is slow is often wrong, even for experts, like guessing which room is wasting heating without a meter. Method: measure, find the hot spot, fix it, measure again.

    • Time the job and each stage. Often one stage is 90% of the run.
    • A profiler (built-in cProfile) lists where time went by function. Asking the assistant to run it and show the top ten lines is a good use of an agent.
    • Check memory too: peak memory decides whether the job runs at all.
    • Test at realistic size. 1,000 rows won't reveal a quadratic or a network wait. Time at 10,000 and 100,000: if 10x data takes 100x time, it is quadratic.

    Weigh the cost of speed. A 30-line vectorised expression can be harder to read than a 6-line loop, and a custom cache can serve stale data. Optimise where it is slow and matters: a nightly job taking 12 minutes in a 6-hour window is fast enough. Spend the effort on correctness and clarity.

    Part 3

    How it fails, and how to spot it

    These appear in AI-written code and in human code written in a hurry.

    • The magic number in many places

      A threshold or date range typed in several spots. One is updated; the rest silently disagree.

      Spot itSearch the repository for the number. More than one hit needs a name and one home.
    • Secrets and personal paths in code

      Passwords, API keys, C:/Users/ali/... in a committed file.

      Spot itScan the diff for password-, key- or token-shaped strings and absolute paths. Treat a committed secret as leaked and rotate it.
    • The 400-line function

      Loading, cleaning, modelling and reporting in one block; nothing testable or reusable alone.

      Spot itCheck function lengths in the outline. Could any piece be tested with three rows of fake data?
    • Copy-pasted variants

      Training and live scoring each have a slightly different "clean the data". They drift, causing training-serving skew.

      Spot itLook for near-identical blocks. Ask for one shared function.
    • Hidden state and notebook order

      Results depend on which cells ran, in what order, or on a global changed elsewhere.

      Spot itRestart the kernel and run all top to bottom. If numbers change or it errors, it isn't reproducible.
    • Silent shape changes at boundaries

      A column is renamed upstream or amounts switch from AED to fils, and the code runs on wrong numbers.

      Spot itIs there a check at each boundary (columns, types, ranges, row counts) that fails loudly?
    • A loop over rows, or a query per row

      Fine at 10,000 rows, a missed deadline at 10 million.

      Spot itSearch for iterrows, apply(..., axis=1) and any database or API call inside a for. Time it at 10x size.
    • Quadratic lookups in innocent code

      if x in some_list inside a loop; nested loops over two tables.

      Spot itIs the searched thing a list? Does time grow about 4x when data doubles?
    • Optimising before measuring

      A clever rewrite of something that isn't the bottleneck, now harder to read.

      Spot itAsk for the profile and before-and-after timings on realistic data.
    • A faster version that gives different answers

      A vectorised or parallel rewrite changes handling of missing values, ties, ordering or rounding.

      Spot itRun old and new on the same sample and compare outputs exactly (or within a stated tolerance).
    • Over-engineering

      Abstract classes, plug-ins and five layers for a run-once script.

      Spot itAsk who will extend this and how often. "No one, rarely" means simpler is better.
    Part 4

    Self-check

    Answer before opening. The numeric ones use only figures from Part 2.

    1. A threshold of 0.10 appears in four files. Risk lowers it to 0.08 and the developer edits three. What goes wrong, and what is the design fix?

    The fourth keeps behaving at 10%. Nothing crashes, but parts disagree (live service at 8%, report or capacity plan at 10%). Fix: one named value in a versioned config read by all four.

    2. A scoring step reads a file path and a database password from inside its own function. Name two problems beyond security.

    It can't be tested without the real file and database, since inputs aren't arguments. And it can't move between environments (dev, production, the Saudi entity) without editing code. Fix: pass in data and a config object; keep secrets in a vault.

    3. Match 2 million transactions against 100,000 watchlist names with a nested loop at about 50 nanoseconds per comparison. How long does it take, and how long with a set?

    Nested: 2,000,000 x 100,000 = 2x1011 comparisons x 50 ns = 10,000 seconds, about 2.8 hours. Set: about 2.1 million operations at roughly 150 ns, around 0.3 seconds. About 30,000 times faster, same answer.

    4. A job takes 10 minutes on 100,000 rows and 40 minutes on 200,000. What does that suggest, and what at 1 million?

    Doubling the data quadrupled the time: quadratic. At 10x the rows expect about 100x the time: roughly 1,000 minutes, or 17 hours. Look for nested loops or lists searched in loops.

    5. Enriching 3 million transactions needs one customer lookup each, 1 millisecond per query. How long as a loop, and what is the alternative?

    3,000,000 x 1 ms = 3,000 seconds, 50 minutes, almost all waiting. One join (or a few batched queries) does it in seconds to a couple of minutes. Round trips cost the same however small the answer.

    6. An assistant replaces an iterrows loop with a vectorised expression and the job drops from 40 minutes to 30 seconds. What do you check before merging?

    That outputs are identical (or within a stated tolerance) on a real sample, including missing values, ties, empty groups and rounding. A big speed-up is when a subtle change is easiest to miss.

    7. When is it right not to refactor an AI-written script into modules?

    When it is short, run once or by one person, and feeds no decision, regulator or team. Effort should follow how long the code lives and how many depend on it. Once it is a scheduled job, structure it.

    8. Why is "profile first" better advice than "rewrite the slow-looking part"?

    Intuition about where time goes is often wrong, and a small part of the code usually accounts for most of it. Optimising a non-bottleneck adds complexity and no speed. A profile on realistic data picks the target and gives a baseline to prove the gain.
