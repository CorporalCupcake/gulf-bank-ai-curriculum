    Code That Can Change, and Code That Can Scale: Design Judgement and Performance Intuition

    How to tell whether AI-written code will be easy to change in six months, and why one approach finishes in a second while another misses the batch window.

    Contents

    The whole lesson in one sentenceGood code gives each decision one home behind a small, stable boundary; fast code does work in proportion to the data; and you judge both by asking where a change would land and by measuring first.

    Part 1

    The intuition

    An AI assistant writes a 400-line script in twenty minutes, with the 10% alert threshold typed on lines 87, 203 and 340. Three months later risk wants 8% and volume grows tenfold. Changing the threshold is a scavenger hunt, and the run takes nine hours.

    Two judgements you can make by reading. Design: where would a change land? Think of a kitchen with one labelled shelf per ingredient. Performance: how does the work grow? Marking papers once each is fine; comparing every paper with every other is not. Assistants optimise for "works now", so they are weak at both.

    Hold onto thisAsk two questions. If this one fact changed, how many places would I edit? If the data were 100 times bigger, what would grow faster than the data?
    Part 2

    How it really works

    Modules, cohesion and coupling

    A module owns one job and hides how it does it. Good ones have high cohesion (things inside belong together) and low coupling (little needs knowing about the neighbours). The cost of a change is the number of places you edit and re-test. Compare two designs below.

    In the tangled design a fact is known in many places. In the modular design each fact is known once: one source of truth. It is the most useful thing to check in AI-written code. A 60-line one-off script doesn't need five modules.

    Interfaces: the narrow door between pieces

    An interface is what a module promises and nothing else, like a vending machine: coins in, snack out. "Give me a table with these columns and I return one probability per row" lets a logistic regression or a boosted ensemble sit behind it. The test: can you replace the piece with a fake in a test? If scoring opens a database inside itself, testing needs the whole world.

    Look for a small surface (a few named inputs, not a DataFrame with twelve quietly used columns) and agreed columns, types and units (AED or fils?) checked once at the boundary.

    Configuration: facts that change without a code change

    Values that change for business reasons, such as threshold, lookback window and input table, belong in configuration, read once at start. Business parameters go in a versioned config file, environment choices in environment variables, and secrets in a secrets manager, never in code.

    Treat any password-shaped string or personal file path in a diff as a stop sign. Versioned config also answers the auditor's "what was live on 3 March?" (G3, P1).

    Each place is consistent with its own number. The failure is between them, and it is silent.

    A reading checklist for AI-written code

    Run a five-minute pass instead of reading line by line. Check the outline (one 300-line main is a flag). Search for literals that appear more than once. See whether files, network and clock are touched at the edges or buried in calculations. Look for loops over rows. Ask whether there is a test that runs without production. Then ask in design terms: "pull the threshold into a config object".

    Performance intuition: how the work grows

    Performance is about how work grows with data. Linear: touch each row once, so 10x data is 10x time. Quadratic: compare every row with every other, so 10x data is 100x time, like a party where everyone shakes hands with everyone. A hash table (a Python set or a database index) finds an item as fast in a million entries as in a thousand.

    The banking trap is matching two lists, such as transactions against a watchlist: scanning the list per transaction is quadratic, a set is not (B2). The second trap is round trips: every database call has a fixed wait, so one call per transaction pays it millions of times (the "N+1 query" pattern).

    One bar grows with the data times something else. That product is what bites.

    What is slow in data code, and the usual cures

    Row-by-row loops (iterrows(), apply(..., axis=1)) run Python once per row; whole-column vectorised operations run compiled code over all rows at once, often 10 to 1,000x faster (F11). Searches inside loops and queries per row are fixed with a set or one join in the warehouse (F3.3).

    Measure first: profiling and the cost of cleverness

    Intuition about which part is slow is often wrong. Measure, find the hot spot, fix it, measure again, and test at realistic size: 1,000 rows won't reveal a quadratic. A nightly job taking 12 minutes in a 6-hour window is fast enough, so spend the effort on clarity.

    Part 3

    How it fails, and how to spot it

    • The magic number in many places

      One copy is updated; the rest silently disagree.

      Spot itSearch for the number. More than one hit needs one home.
    • Secrets and personal paths in code

      Passwords or C:/Users/ali/... in a committed file.

      Spot itScan the diff. Treat a committed secret as leaked.
    • The 400-line function and copy-pasted variants

      Training and live scoring each get a slightly different "clean the data", and drift apart.

      Spot itCould any piece be tested with three rows of fake data?
    • Loops over rows and queries per row

      Fine at 10,000 rows, a missed deadline at 10 million.

      Spot itSearch for iterrows and database calls inside a for. Time it at 10x size.
    • Optimising before measuring, or changing the answer

      A faster version may handle missing values or ties differently.

      Spot itAsk for the profile, and compare old and new outputs on the same sample.
    Part 4

    Self-check

    1. A threshold appears in four files and the developer edits three. What goes wrong?

    The fourth keeps behaving at the old value and nothing crashes. Fix: one named value in a versioned config.

    2. Why is a set so much faster than a nested loop for watchlist matching?

    The loop compares every pair; the set does one quick lookup per transaction. The answer is the same.

    3. A job takes 10 minutes on 100,000 rows and 40 on 200,000. What does that suggest?

    Quadratic growth. Look for nested loops or lists searched inside loops.

    4. Why is one customer query per transaction slow even though each query is tiny?

    Each pays a fixed wait however small the answer. One join or batched queries avoids it.

    5. Why is "profile first" better advice than "rewrite the slow-looking part"?

    Intuition about where time goes is often wrong. A profile on realistic data picks the target and gives a baseline.
