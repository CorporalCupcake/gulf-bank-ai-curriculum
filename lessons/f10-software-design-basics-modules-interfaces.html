    Code That Can Change, and Code That Can Scale: Design Judgement and Performance Intuition

    How to tell, without writing it yourself, whether AI-written code will be easy to change in six months, and why one approach finishes in a second while another runs past the end of the batch window.

    Contents

    The whole lesson in one sentenceGood code puts each decision in one place behind a small, stable boundary, so a change costs one edit rather than seven; fast code does work in proportion to the data rather than to the data squared or to the number of round trips; and you judge both by asking where a change would land and by measuring before you believe anything.

    Part 1

    The intuition

    A data scientist asks an AI assistant for a script that scores yesterday's card transactions and emails the fraud team the ones above a 10% probability. Twenty minutes later it works. It is 400 lines in one file. The file path is typed into line 12. The 10% appears on lines 87, 203 and 340. Column names are spelt out wherever they are used. The model is loaded, scored, explained and reported in one long function.

    Three months later three things happen. The data team renames a column. Risk wants the threshold at 8%. The volume grows tenfold and the nightly run, which took six minutes, now takes nine hours and misses its window. None of these changes is hard in principle. In this file each one is a scavenger hunt, and each hunt risks missing a spot and shipping a quiet inconsistency.

    This lesson is about two judgements you can make by reading, without being the one who types the code.

    • Design (F10.5). Where would a change land? Code is a set of decisions: how the data looks, what the threshold is, which model scores, where the output goes. Good design gives each decision one home. A module is a home. An interface is the small, stable door through which other code talks to it. Configuration is the set of decisions that should be changeable without editing code at all.
    • Performance (F10.6). How does the work grow? Some code does a fixed amount of work per row. Some does work per row per other row, or waits on a network call for every row. At 10,000 rows you can't tell them apart. At 10 million, one finishes before your coffee and the other finishes next week.

    They connect. Code that is well organised is also easier to speed up, because the slow part lives in one place and can be replaced without disturbing the rest. And AI assistants are strong at producing code that runs and weak, by default, at the judgements above, because they are optimising for "works now" in the context they were shown.

    Hold onto thisWhen you read any code, ask two questions. If this one fact changed, how many places would I have to edit? And if the data were a hundred times bigger, what would grow faster than the data? You can answer both from the outline of the code, long before you understand every line.
    Part 2

    How it really works

    Modules, cohesion and coupling: the cost of a change

    A module is a unit of code (a file, a package, a class) that owns one job and hides how it does it. Parnas's 1972 paper made the idea precise: split a system not by the order of steps but by the decisions likely to change, and let each module hide one of them. Two properties tell you whether the split is any good.

    • Cohesion: things inside a module belong together. A module called features.py that also sends emails has low cohesion.
    • Coupling: how much one module has to know about another. If the report code reaches into the model's internal coefficients, or the cleaning code knows the exact names of the columns the alert code will later want, they are tightly coupled. A change in one forces a change in the other.

    You want high cohesion and low coupling. The reason is economic, not aesthetic. The cost of a change is roughly the number of places that must be edited, plus the number of behaviours that must be re-tested because those edits might have broken them. The simulation uses a toy scoring pipeline with seven steps. Choose a change and compare two designs.

    Notice the pattern. In the tangled design, a fact (a column name, a threshold, a currency) is known in many places. In the modular design, each fact is known in exactly one: the column names by the loading step, the currency by a money-handling step, the threshold by the config. This is often called one source of truth, or the DRY principle ("don't repeat yourself"), and it is the single most useful thing to check in AI-written code.

    One honest caution: you can overdo it. A 60-line script that runs once does not need five modules. Design effort should track how long the code will live and how many people will touch it. A throwaway exploration in a notebook can be messy. A scoring job that will run nightly for two years, feed a regulator's questions and be maintained by someone who has not met you needs structure. The skill is calibrating.

    Interfaces: the narrow door between pieces

    An interface is what a module promises to the outside, and nothing else: "give me a table with these columns, and I return one probability per row." Everything behind the promise can change. The value of an interface is that the caller doesn't need to know whether a logistic regression or a gradient-boosted ensemble sits behind it.

    In Python an interface is usually just a function signature with type hints, or a small class with an agreed method. A useful test: can I replace this piece with a fake one in a test? If scoring is a function that takes a table and returns probabilities, a test can pass a three-row table and a fake model. If scoring reaches out to a database and a file path inside itself, testing means standing up the whole world (F10.3 and F10.4 build on this).

    from typing import Protocol
import pandas as pd

class Scorer(Protocol):
    def predict_proba(self, features: pd.DataFrame) -> pd.Series:
        """One probability in [0, 1] per row, same index as the input."""

def alert_ids(scorer: Scorer, features: pd.DataFrame, threshold: float) -> list[str]:
    p = scorer.predict_proba(features)
    return list(features.index[p > threshold])

    Here alert_ids knows nothing about how scoring works. Swap the model and it is untouched. What to look for when reading an AI-written version:

    • Small surface. Functions take a few clearly named inputs and return one clear thing. Functions with eight parameters, or that take a whole DataFrame and quietly use twelve of its columns, have a wide, hidden interface.
    • Pure where possible. A function that computes a result from its inputs (a pure function) is easy to test and reason about. A function that also writes a file, reads the clock and updates a global is not. Good design separates "decide" (pure) from "do" (touch the world): compute the alerts in one place, send them in another.
    • Data contracts. The table passed between steps has an agreed shape: column names, types, units (AED or fils? UTC or Gulf time?). Checking that shape once at the boundary, and failing loudly, prevents the silent kind of bug where the code runs on the wrong thing. This is the code-level cousin of the point-in-time discipline in F3.1 and the training-serving consistency in F3.4.
    • No reaching around. Step 5 should not read a variable that step 2 happened to leave lying around. Hidden global state is the commonest source of "it works on my machine and gives different numbers on yours".
    • Notebook versus package. A notebook runs cells in whatever order you clicked; state lives invisibly between them. It is excellent for exploring and poor as a production job. A sign of maturity is when the logic that matters has moved from cells into functions in a file that can be imported, tested and run top to bottom.

    Configuration: facts that change without a code change

    Some values change for business reasons, not because the logic changed: the alert threshold, the lookback window, the file or table to read, the model version, the currency list. These belong in configuration, a file or a settings object read once at the start, rather than as literals scattered through the code. The Twelve-Factor App guideline puts the test crisply: could you publish the code today without leaking anything, and could you move it to a new environment by changing only the config?

    Three kinds of value, three different homes:

    KindExamplesWhere it lives
    Business parametersAlert threshold, lookback days, cost per review (AED 40)A versioned config file, reviewed like code, with a note on who owns each value.
    EnvironmentWhich database, which bucket, dev versus productionEnvironment variables or a per-environment config.
    SecretsPasswords, API keys, tokensA secrets manager. Never in code or in the repository, even in a private one.

    The left column has three problems you can see at a glance: a path that only exists on one laptop, a password in the file, and a threshold written twice. AI assistants produce this shape routinely, because the example in the prompt had a path and a number, and the model copied the pattern. Hard-coded secrets are the most serious of the three: they get committed, copied and indexed. Treat any password-shaped string in a diff as a stop sign.

    Configuration also helps the validator and the auditor. If the threshold is a named, versioned value, the question "what threshold was live on 3 March?" has an answer in the version history. If it is a literal on line 340, the answer is an archaeology project (see G3 and P1 lineage). Reproducibility needs the same: fixed random seeds, pinned library versions, and the config saved with each run's output.

    The simulation shows what happens when a value is not in one place.

    None of the four places is wrong on its own terms. Each is consistent with the number it holds. The failure is between them, and it is silent: nothing crashes, the dashboards simply disagree. This is why "one source of truth" is not tidiness. It removes a class of error that testing individual pieces will not find.

    A reading checklist for AI-written code

    You will often be handed a pull request or a notebook that an assistant produced. You do not need to follow every line. Run this pass first; it takes five minutes and catches most structural problems.

    1. Outline. List the function and file names. Do they tell the story of the task? One function called main or run_pipeline with 300 lines is a flag.
    2. Search for literals. Find every number, path, URL, column name and secret. Which appear more than once?
    3. Duplicates. Does the same block appear with small differences (the training version and the scoring version of "clean the data")? Duplicated logic drifts apart. GitClear's analyses of hundreds of millions of changed lines report more copy-pasted code and less refactoring as AI assistants spread (Part 4), which matches this experience.
    4. Where is the world touched? Reads, writes, network, clock, randomness. Are they at the edges, or buried deep in calculations?
    5. Boundaries. Is there a check that the input has the expected columns and types, with a clear error if not?
    6. Loops over rows. Any for over a DataFrame or a database call inside a loop is a performance flag (next section).
    7. Tests. Is there at least one test for the logic that matters, and could it run without the production database?
    8. Surprising dependencies. Did the assistant add a library for something five lines would do? Every dependency is something to patch and, in a bank, to approve.

    You can then ask the assistant to fix what you found. Name the problem in design terms: "pull the threshold, path and currency list into a config object", "split scoring from alerting so alerting takes probabilities as input", "add a schema check at the top of load". Assistants follow structural instructions well. They rarely volunteer them.

    Performance intuition: how the work grows

    Performance is not about clever tricks. It is about how the amount of work grows with the amount of data. Call the number of rows n.

    • Linear, about n. Touch each row once. Ten times the data, ten times the time. Fine.
    • Quadratic, about n2. For each row, look at every other row (or every item in a long list). Ten times the data, a hundred times the time. This is the one that surprises people.
    • n log n. Sorting. Nearly linear in practice.
    • Constant per lookup. A hash table (a Python set or dict, a database index) finds an item in about the same time whether it holds a thousand entries or a million.

    The standard quadratic trap in banking is matching two lists: for each of today's transactions, check whether the counterparty is on the sanctions or watchlist. The naive code scans the whole watchlist for each transaction. The fast code puts the watchlist in a set once and looks each name up. Same answer. A different universe of time. (Fuzzy matching, which sanctions screening really needs, is harder and uses blocking or indexing for the same reason; see B2.)

    The second trap is not about computation at all: round trips. Every call to a database, an API or another service has a fixed waiting cost, often a millisecond or more, that has nothing to do with how much data comes back. A loop that makes one call per transaction pays that wait a million times. This is the "N+1 query" pattern: one query to get the list, then n more to enrich each item. It is the most common serious performance fault in AI-written data code, because writing "for each row, fetch the customer" is how a person describes the task.

    OperationRough timeWhat it means
    One arithmetic step in compiled code (NumPy, Polars)about a nanosecondA billion simple operations a second per core.
    One step in a pure-Python looptens to hundreds of nanosecondsPython is often 10–100 times slower per element than compiled code.
    Read from memoryabout 100 nanosecondsData that fits in memory is cheap to revisit.
    Read from a local SSDabout 100 microseconds1,000 times slower than memory.
    Network round trip inside one data centreabout 0.5–1 millisecondAnother 10 times slower; a loop of a million calls is a quarter of an hour.
    Round trip between regions or to an external APItens to hundreds of millisecondsNever in a per-row loop.

    These are orders of magnitude, not guarantees; real values depend on hardware and load. Their use is for building a feel. If a design moves from the top of the table to the bottom once per row, expect trouble.

Doubling n in the nested loop quadruples the time if the watchlist grows with it, and doubles it if the list stays fixed. Either way it is the product that bites.

    What is slow in data code, and the usual cures

    In Python data work, four patterns account for most of the pain.

    1. Row-by-row loops on tables. for _, row in df.iterrows() and df.apply(lambda r: ..., axis=1) run Python code once per row, with heavy per-row overhead. Whole-column operations run in compiled code over all rows at once. This is vectorisation, built properly in F11. Gains of 10 to 1,000 times are normal.
    # Slow: Python runs once per row
flags = []
for _, row in df.iterrows():
    flags.append(row.amount_aed > 50_000 and row.channel == "online")
df["flag"] = flags

# Fast: one operation over whole columns
df["flag"] = (df["amount_aed"] > 50_000) & (df["channel"] == "online")
    1. Lists searched inside loops. if name in watchlist where watchlist is a list scans it every time. Make it a set once: watch = set(watchlist). For tables, a join (merge) does the same thing with the work done in optimised code.
    2. A query per row. Replace "for each transaction, fetch the customer" with one join in the warehouse, or one batched query for all needed keys (see F3.3). Move the work to where the data is, and let the database use its indexes.
    3. Too much data moved or held. Reading a 20 GB CSV into memory when you need three columns and one month. Use a columnar format such as Parquet (reads only the columns requested, compresses well, keeps types), filter early, and select columns early. Memory pressure is also a speed problem: when data no longer fits, everything slows or crashes. Watch for accidental copies, such as chained pandas operations that each build a new table.

    Beyond those, there are two more levers worth knowing exist. Parallelism: split independent work across cores or machines (each customer's features can be computed separately). In standard CPython the global interpreter lock (GIL) stops threads from running Python code in parallel, which is why CPU-heavy Python is usually parallelised with processes or pushed into compiled libraries; Part 4 covers what is changing. Hardware: GPUs help for large matrix work (training, embeddings) and are no use for a row loop making database calls. If the bottleneck is waiting, a faster chip does nothing.

    Last, a point about models rather than data code. The same thinking applies to inference. A scoring service for card authorisation must answer in tens of milliseconds, so latency, not accuracy alone, constrains the model: a smaller or distilled model may be the right answer (P3), and a batch propensity job has hours to spare (P2). Know whether you are bound by throughput (rows per hour, a batch problem) or latency (time for one answer, a real-time problem). They are optimised differently.

    Measure first: profiling and the cost of cleverness

    Donald Knuth's remark is usually quoted as "premature optimisation is the root of all evil". The fuller sentence is more useful: in programs, a small part of the code (he says about 3%) is where the time goes, and you should optimise only after you have found it. Intuition about which part is slow is regularly wrong, including among experienced engineers, so the method is: measure, find the hot spot, fix that, measure again.

    • Time the whole job and its stages first. A simple timer around each stage often shows one stage is 90% of the run.
    • A profiler (Python's built-in cProfile, or a sampling profiler) lists where the time actually went, by function. Ask the assistant to run it and show you the top ten lines; this is a good use of an agent.
    • Check memory as well as time. Peak memory decides whether the job runs at all.
    • Test on realistic size. A profile on 1,000 rows will not show a quadratic or a network wait. Time at 10,000 and 100,000 and look at the trend: if ten times the data takes a hundred times as long, you have found a quadratic.

    And weigh the cost of speed. A 30-line vectorised expression can be harder to read than a 6-line loop, and a custom cache can serve stale data. Make code fast where it is slow and where it matters: a job that runs once a night in 12 minutes, inside a 6-hour window, is fast enough. Spend the effort on correctness and clarity instead.

    Where it shows up at the bank:

    • Nightly scoring jobs (fraud, collections, propensity). A batch window sets a hard time budget; thresholds and paths belong in config; the job must be rerunnable after a failure without double-sending alerts (a property called idempotence: running it twice has the same effect as once).
    • Sanctions and name screening. Quadratic matching on large customer and list files is the textbook performance failure. Blocking and indexing are the cure.
    • Feature pipelines for credit models. Per-customer features over years of transactions: row loops versus grouped, vectorised aggregation can be the difference between minutes and a weekend.
    • Regulatory and model-risk reporting. A number reproduced from config and a pinned environment can be defended; one produced from a notebook someone re-ran with their cell order can't. CBUAE and SAMA expectations on model governance are developing; check the current text with your bank's model-risk team rather than relying on a summary.
    • Multi-entity groups. A UAE bank with a Saudi subsidiary changes data sources, currency and rules. Whether that is an edit to a config file or a rewrite is decided on day one by the design.

    Where the field is now

    The principles are old and stable: Parnas wrote his in 1972. What moves is the tooling and the evidence about what AI assistance does to code quality. Three recent threads matter.

    Research checked on 6 November 2026. Several sources below are secondary commentary or vendor analyses; where figures disagreed between sources, I say so.

    1. 1972
      Decompose by decisions that may change

      Parnas argued that modules should hide design decisions likely to change, rather than follow the flowchart of processing steps. Still the best one-sentence definition of good modularity.

      Parnas, Communications of the ACM, 1972
    2. 2015
      Hidden technical debt in machine learning

      Researchers at Google described how ML systems accumulate costs ordinary code does not: entangled features where changing one input shifts everything, undeclared consumers of a model's output, glue code around libraries, and configuration debt. A small amount of model code sits inside a large amount of surrounding plumbing.

      Sculley et al., NeurIPS, 2015
    3. 2025
      Python's free-threaded build becomes officially supported

      Python 3.14 (October 2025) made the build without the global interpreter lock an officially supported option under PEP 779, though not the default: the standard interpreter still has the lock. Reported single-thread overhead has fallen to roughly 5–10% in some third-party measurements; the official how-to gives smaller figures on some platforms. Multi-threaded CPU-bound code can scale across cores, but many C-extension libraries need versions built for it, so check your dependencies before relying on it.

      PEP 779; Python 3.14 release documentation; third-party benchmarks vary
    4. 2025
      AI as an amplifier of the team you already have

      The 2025 DORA report, drawing on nearly 5,000 technology professionals, found AI adoption near 90% and associated with higher delivery throughput, but also with lower delivery stability. Its reading is that AI magnifies existing strengths and weaknesses; the capabilities it highlights include small, frequent commits and robust rollback. About 30% of respondents reported little or no trust in AI-generated code. Different summaries give slightly different adoption figures.

      DORA, State of AI-assisted Software Development, 2025

      Faster dataframe tooling is mainstream

    Part 5

    How it fails, and how to spot it

    These show up in AI-written code and in human code written in a hurry. Each comes with the quickest check.

    • The magic number in many places

      A threshold, rate or date range typed in several spots. One is updated; the others silently disagree.

      Spot itSearch the repository for the number. More than one hit means it needs a name and one home.
    • Secrets and personal paths in code

      Passwords, API keys, C:/Users/ali/... in a file that will be committed.

      Spot itScan the diff for anything password-, key- or token-shaped and any absolute path. Treat a committed secret as leaked and rotate it.
    • The 400-line function

      Loading, cleaning, modelling and reporting in one block, so nothing can be tested or reused separately.

      Spot itLook at function lengths in the outline. Ask whether any piece could be tested with three rows of fake data.
    • Copy-pasted variants

      Training and live scoring each have their own slightly different "clean the data". They drift and produce training-serving skew.

      Spot itLook for two blocks of near-identical code. Ask for one shared function used by both.
    • Hidden state and notebook order

      Results depend on which cells were run, in which order, or on a global variable changed elsewhere.

      Spot itRestart the kernel and run all cells top to bottom. If numbers change or it errors, the notebook is not reproducible.
    • Silent shape changes at boundaries

      A column is renamed upstream or an amount switches from AED to fils, and the code runs without complaint on the wrong numbers.

      Spot itIs there a schema or sanity check at each boundary (columns, types, ranges, row counts) that fails loudly?
    • A loop over rows, or a query per row

      Fine at 10,000 rows, a missed deadline at 10 million.

      Spot itSearch for iterrows, apply(..., axis=1), and any database or API call inside a for. Time it at 10 times the size.
    • Quadratic lookups hidden in innocent code

      if x in some_list inside a loop; nested loops over two tables.

      Spot itIs the thing searched a list? Does time grow about four times when the data doubles?
    • Optimising before measuring

      An assistant or colleague rewrites something clever that is not the bottleneck and is now harder to read.

      Spot itAsk for the profile that shows where the time went and the before-and-after timing on realistic data.
    • A faster version that gives different answers

      A vectorised or parallel rewrite changes handling of missing values, ties, ordering or rounding.

      Spot itRun old and new on the same sample and compare outputs exactly (or within a stated tolerance) before accepting the speed-up.
    • Over-engineering

      Abstract classes, plug-in systems and five layers for a script that runs once.

      Spot itAsk who will extend this and how often. If the answer is "no one, rarely", simpler is better.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “AI tools now produce working code in minutes, but working isn't the same as maintainable. What I check is whether a business change, like moving the alert threshold or adding the Saudi entity, is a one-line edit or a hunt through the code, and whether the nightly job will still finish in its window when volume grows ten times. Those two checks cost us an hour of review and save weeks later, and they are what keep an audit question answerable.”
    To an engineer or interviewer
    “I review structure before logic: where each decision lives, whether config and secrets are out of the code, whether steps have narrow typed interfaces and can be tested with fake inputs, and whether state is explicit. For performance I look at how work scales: row loops, lists searched in loops, queries per row. Then I profile on realistic sizes before changing anything, and I compare outputs of old and new versions, because a faster answer that differs isn't a speed-up.”
    “The assistant wrote this in one file and it works. Why do you want it split up?”

    Because the cost shows up on the second change, not the first. I'd ask how many places we'd edit to change the threshold, add a data source or swap the model. If the answer is "several", we pay that every time. For a one-off analysis I wouldn't bother; for a job that runs nightly for years I would, and I'd have the assistant do the refactor against tests that pin the current outputs.

    “What is the difference between a module and an interface?”

    A module is a piece of code that owns one job. The interface is the part of it other code is allowed to depend on: the function names, inputs and outputs it promises. Everything else is private and free to change. Good design keeps interfaces small so that most changes stay inside one module.

    “Why not just hard-code the threshold? It's quicker.”

    It is quicker once. Then it appears in the scoring code, the report and the monitoring job, and when risk changes it someone updates two of three and the dashboards disagree. A named, versioned config value is also what lets us answer "what was live on a given date?" for an auditor or validator.

    “The job takes nine hours now. Should we buy bigger machines?”

    First find out what it is waiting on. If most of the time is a loop making a query per row, or a nested lookup, bigger hardware won't help much, and a join or a set lookup may cut it to minutes. I'd profile on a realistic sample, fix the hot spot, and only then consider scaling out, because hardware multiplies the cost of an inefficient design.

    “Is Python too slow for this? Should we rewrite in something else?”

    Rarely. Python is slow per element, but the heavy work in data jobs runs in compiled libraries such as NumPy, pandas, Polars and the database. Problems are usually row-by-row Python loops or network round trips, not the language. Rewrite only after profiling shows a hot spot that vectorisation or the right data structure can't fix.

    “Can we trust AI to optimise the code too?”

    It's useful for proposing candidates and running the profiler. It is poor at knowing what must not change. So I'd require a profile before, a timing after on realistic data, and an exact comparison of outputs between versions. The assistant proposes; the tests and a reviewer decide.

    Part 7

    Self-check

    Try each one before opening the answer. The numeric ones use only the figures in Part 2.

    1. A threshold of 0.10 appears in four files. Risk lowers it to 0.08 and the developer edits three. What goes wrong, and what is the design fix?

    The fourth place keeps behaving at 10%. Nothing crashes; two parts of the system now disagree (for example the live service alerts at 8% while the report or the capacity plan assumes 10%). The fix is one named value in a versioned config, read by all four, so there is a single source of truth.

    2. A scoring step reads a file path and a database password from inside its own function. Name two problems this causes beyond security.

    It can't be tested without the real file and database, since the inputs are not arguments. And it can't move between environments (development, production, the Saudi entity) without editing code. The password in code is also a security incident waiting to happen. The fix: pass in data and a config object; keep secrets in a vault.

    3. Match 2 million transactions against 100,000 watchlist names with a nested loop at about 50 nanoseconds per comparison. Roughly how long does it take, and how long with a set?

    Nested: 2,000,000 × 100,000 = 2×1011 comparisons × 50 ns = 10,000 seconds, about 2.8 hours. With a set: about 2.1 million operations at roughly 150 ns is around 0.3 seconds. A gap of about 30,000 times, from the same answer.

    4. A job takes 10 minutes on 100,000 rows and 40 minutes on 200,000. What does that suggest, and what would you expect at 1 million?

    Doubling the data quadrupled the time: quadratic growth. At 10 times the rows, expect about 100 times the time: roughly 1,000 minutes, or 17 hours. Look for nested loops or lists searched inside loops.

    5. Enriching 3 million transactions needs one customer lookup each, 1 millisecond per query. How long as a loop, and what is the alternative?

    3,000,000 × 1 ms = 3,000 seconds, 50 minutes, almost entirely waiting. A single join (or a few batched queries) lets the database do the whole thing in seconds to a couple of minutes. Round trips cost the same however small the answer.

    6. An assistant replaces an iterrows loop with a vectorised expression and the job drops from 40 minutes to 30 seconds. What do you check before merging?

    That the outputs are identical (or equal within a stated tolerance) on a real sample, including edge cases: missing values, ties, empty groups, rounding. A big speed-up is exactly when a subtle behaviour change is easy to miss.

    7. When is it right not to refactor an AI-written script into modules?

    When it is short, run once or by one person, and will not feed a decision, a regulator or another team. A throwaway exploration can be messy. The effort should follow how long the code will live and how many people will depend on it. The moment it becomes a scheduled job, structure it.

    8. Why is "profile first" better advice than "rewrite the slow-looking part"?

    Intuition about where the time goes is often wrong, and a small part of the code usually accounts for most of it. Optimising something that is not the bottleneck adds complexity and no speed. A profile on realistic data tells you which part to fix and gives a baseline to prove the improvement.
