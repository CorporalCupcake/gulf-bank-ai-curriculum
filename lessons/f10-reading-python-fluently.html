    Reading Python Fluently, and Catching Analyses That Are Hollow

    How to review code you did not write, in the order that finds the expensive bugs first, and how to tell when an analysis is fabricated, leaky or simply does not say what its author claims.

    Contents

    The whole lesson in one sentenceMost of your job will be judging code and results that an AI or a colleague produced, so read for shape, grain and split (how many rows, one row per what, fitted on what) before you read for syntax, and distrust any number that is too good, too clean or not backed by the printed output.

    Part 1

    The intuition

    You will read far more code than you write: colleagues' notebooks, inherited scripts, and above all code an assistant produced in seconds. Writing was once the bottleneck. Now checking is.

    A crash is cheap: you see it and fix it. Code that runs cleanly and prints a plausible number is expensive. A model with AUC 0.97 and a join that quietly duplicated 8% of transactions both look like success. Think of a smoke alarm that never sounds: silence tells you nothing.

    So fluent reading means knowing where the quiet failures live and going straight there. Five or six places matter: where data comes in, where tables are joined, where the train/test split happens, what is fitted on what, how the target is built, and what is reported.

    The second half applies the same skill to results. An analysis is hollow when the data was random, the printed number does not match the sentence beside it, or the metric was computed on rows the model had already seen. Often nobody is lying: a tired analyst, or an assistant told to "make the results look good", takes the easy path.

    Hold onto thisRead for the few lines that can silently change the answer: joins, splits, fits, the target and the reported metric. The rest is plumbing. If you distrust a line, ask for the row count or printed output that settles it.
    Part 2

    How it really works

    F10.1 · Reading Python fluently

    A reading order that finds bugs early

    Read like a building inspector, not like a novel: check the load-bearing parts first.

    1. Outputs and inputs. Read the last ten lines and the function signatures. What is reported or saved? If you cannot say it in one sentence, the rest is guesswork.
    2. The grain. After each load or join, one row is what: a transaction, a customer, a customer-month? Rates, counts and splits all depend on it. What should the row count be, and where is it printed?
    3. The target. Where is is_fraud or default_90d built, from which columns, as of which date? A feature known only after the outcome (a chargeback amount, a "closed" status) is leakage (F3.1).
    4. The split, then every fit. Find the split. Then find every fit, fit_transform, scaler, imputer, encoder, feature selector and resampler. Each must come after the split and see only training rows, ideally inside a pipeline.
    5. The metric. Which array goes in: predictions or probabilities, test or training rows, resampled or real prevalence?
    6. The plumbing (plots, logging, helpers): skim.

    Reading the idioms

    Most data Python is a small vocabulary used repeatedly. Know these and scripts shrink.

    # Boolean mask: keep rows where both conditions hold. & and | need brackets.
big = df[(df.amount > 5000) & (df.channel == "online")]

# Named aggregation: one row per customer, three summary columns.
per_cust = (df.groupby("customer_id")
              .agg(n=("txn_id", "count"),
                   total=("amount", "sum"),
                   last=("ts", "max")))

# transform keeps the original rows: each row gets its group's value.
df["amount_vs_cust_mean"] = df.amount / df.groupby("customer_id").amount.transform("mean")

# List comprehension with a condition; the dict maps code to label.
flags = [c for c in df.columns if c.startswith("flag_")]
labels = {1: "fraud", 0: "ok"}

    The classic confusion: agg shrinks to one row per group, transform keeps every row, and apply can do either. Always ask "how many rows come out?".

    The traps that run silently

    None of these raises an error.

    TrapWhat it looks likeWhat actually happensThe check

    The join is the costliest at a bank: customer, account and device tables are rarely one row per key (old versions, joint accounts, re-issued cards). It is like a guest list with some names written twice: everyone is counted, some twice.

    Two habits catch this class of error. Assert shapes: after a join, assert len(df) == len(tx). Reconcile to something known: AED total against the finance ledger, count against the source system. A tie-out beats any amount of reading.

    Assistant-written code is fluent, confident and over-complete: extra helpers, unused arguments, comments describing intent rather than what the line does. When comment and code disagree, the code wins. Ask for the smallest version that works, and read that.

    F10.2 · Spotting hollow or fabricated analyses

    A hollow analysis has a conclusion that the computation does not support. Three flavours, each with tells.

    1. Metrics on the wrong split

    It is like marking an exam after the student has seen the answer sheet. Take 200 customers, 3,000 candidate features and a target of pure noise. Pick the 20 features most correlated with the target, then cross-validate on those 20. Accuracy comes out well above chance, because selection already saw the labels of the rows you then "tested" on. This is the textbook "wrong way to cross-validate" (Hastie, Tibshirani and Friedman, section 7.10.2; Ambroise and McLachlan, 2002).

    Any step that touches labels does the same: target encoding, imputation by class, SMOTE (F3.5), threshold tuning, early stopping on the test set. So does tuning on the test set: try twenty settings, report the best test score, and the test set has become a training set (see cross-validation and temporal splits, hyperparameter tuning). A 2023 survey found leakage in hundreds of ML-based science papers across many fields (Kapoor and Narayanan, 2023), so this is not a beginner's problem.

    2. Random or synthetic data passed off as real

    The data may be generated by np.random for a demo, or an AI-written notebook may fill a missing file with simulated numbers and carry on. Real bank data has texture that generators lack.

    PropertyReal banking dataGenerator output
    Amount shapeRight-skewed with a long tail; median far below meanFlat (uniform) or symmetric bell (normal), median near mean
    Round numbersSpikes at AED 100, 200, 500, 1,000Almost none
    Missing valuesPatterned: whole columns missing for a channel or a productNone, or scattered uniformly at random
    RelationshipsMessy but present: income and limit, tenure and balanceFeatures independent; correlation matrix near the identity
    IDs and timestampsGaps, duplicates, clusters at business hours and month-endConsecutive IDs, evenly spread times
    The signalModest AUC (0.7 to 0.9) that took work to reachEither 0.50, or a planted rule recovered at 0.99

    You rarely need a test. Plot the column and look.

    3. Text that contradicts the output

    The prose says one thing, the output another. It happens when an assistant writes the narrative without looking at the numbers, or a notebook is edited and not re-run. Match each sentence to the output line it relies on.

    The write-up saysThe output showsThe problem
    "Recall improved to 86%"recall: 0.79 in the cell aboveNarrative from an earlier run or invented. Re-run and compare.
    "The model generalises well (AUC 0.91 on held-out data)"The cell computes AUC on X_trainWrong split. The number is a training score.
    "Significant difference (p < 0.05)"Twelve segments tested, one p-value of 0.04 reportedMultiple comparisons (F2.4); the other eleven are missing.
    "Fraud fell 20% after the new rule"A before and after table with no control groupCausation claimed from a trend (F2.6, F9.3).
    "Trained on 3 years of data"df.shape shows dates from the last 5 monthsThe filter or file was not what the text describes.
    "Top features: tenure, salary"Importance plot headed by account_status_codeThe narrative describes a plausible story; the plot shows a likely leak.

    The general test: could I regenerate every number in the text from the code and data, today? If a clean run with a fixed seed does not give the same figures, the analysis is not finished. Add three cheap checks to any result you rely on:

    • A trivial baseline (predict the average, or yesterday's value): does the model clear it?
    • A shuffled-label run: permute the target and re-run the whole pipeline. Still scoring well means something leaks.
    • A look at the five worst errors, by eye.
    Part 3

    How it fails, and how to spot it

    These are failures of the reviewer, each with its quickest check.

    • Trusting code because it ran

      Most bugs here raise no error.

      Spot itAsk what output would differ if the code were wrong. If nothing, add a check that would.
    • Reviewing plumbing, not pivots

      Comments on naming and plot colours while the split sits above the scaler.

      Spot itBefore any style comment, say where the split, target and metric are.
    • Metrics too good for the problem

      AUC 0.99 on fraud, 95% accuracy on credit default.

      Spot itTreat it as a bug report. Check top features for post-outcome columns and run the shuffled-label test.
    • Row counts never printed

      The notebook shows head() but never shape. Fan-out and silent filters hide here.

      Spot itAsk: rows in, rows in the final table, what was dropped and why?
    • Narrative written first

      The text numbers match no cell.

      Spot itRestart kernel, run all, diff numbers against the text.
    • Results that cannot be re-run

      Hard-coded local paths, no seed, a cell using a deleted variable.

      Spot itRun it from a clean checkout. Two seeded runs must agree.
    • Synthetic stand-ins left in

      The real file was missing, so placeholder data was generated and reported as findings.

      Spot itSearch for np.random, faker, make_classification, sample(, "dummy", "mock". Plot amounts and look for a round-number spike.
    • Selection from many tries

      Twenty models or segments tried; only the best reported.

      Spot itAsk how many variants were tried and where the test set was first used.
    • Over-trusting a second assistant

      "Another AI said the code is correct."

      Spot itReviewers miss quiet bugs too. Demand line numbers and evidence (shapes, outputs), not a verdict.
    Part 4

    Self-check

    Answer before opening.

    1. A merge of 500,000 transactions with a customer table returns 541,000 rows. What happened, and which two things would you add to the code?

    Some customers appear twice in the customer table, so their transactions were duplicated (fan-out). Add validate="m:1" so pandas raises, and assert row count after equals before. Reconcile the AED total to the source.

    2. What is wrong with df[df.risk == "high"]["flag"] = 1, and what do you write instead?

    Chained assignment: the first indexing returns a temporary copy, so df may not change (in pandas 3, never). Write df.loc[df.risk == "high", "flag"] = 1.

    3. A script scales the features, selects the 30 best by correlation with the label, then runs 5-fold cross-validation. The labels are pure noise. Is the CV accuracy at chance?

    No, above chance, more so with more candidate features. Selection saw every label, including held-out ones. Put scaling and selection in a pipeline, refitted within each training fold.

    4. roc_auc_score(y_test, model.predict(X_test)) prints 0.71 for a model whose probabilities would score about 0.90. Why?

    predict returns hard 0/1 labels; AUC needs scores that rank rows. Use predict_proba(X_test)[:, 1].

    5. You are handed amounts that are evenly spread from AED 1 to 1,000 with no repeated values, and 100% complete. What do you suspect?

    A random-number generator. Real amounts are right-skewed, spike at round values and repeat (subscriptions), and are rarely 100% complete. Ask for source and lineage.

    6. A notebook says "AUC on the held-out set: 0.93" but the cell computes roc_auc_score(y_train, p_train). What do you do?

    Unsupported: it is a training score. Re-run on held-out rows, ideally forward in time, and correct the text from the output.

    7. Name three cheap checks you can add to any result you rely on.

    A trivial baseline (mean, last value); a shuffled-label run, which should score at chance; the five worst errors. Also row-count assertions after joins and a clean run-all.
