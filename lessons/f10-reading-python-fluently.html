    Reading Python Fluently, and Catching Analyses That Are Hollow

    How to review code you did not write, in the order that finds the expensive bugs first, and how to tell when an analysis is fabricated, leaky or simply does not say what its author claims.

    Contents

    The whole lesson in one sentenceMost of your job will be judging code and results that an AI or a colleague produced, so read for shape, grain and split (how many rows, one row per what, fitted on what) before you read for syntax, and distrust any number that is too good, too clean or not backed by the printed output.

    Part 1

    The intuition

    In your first month you will write some code. You will read far more: notebooks from colleagues, scripts from the previous team, and above all code produced by Claude or another assistant in seconds. Writing code was once the bottleneck. Now checking it is.

    Here is the uncomfortable part. Code that is wrong in a loud way, with a crash or a stack trace, is cheap. Code that runs cleanly and produces a plausible number is expensive. A model with AUC 0.97 and a join that quietly duplicated 8% of transactions both look like success. Nothing in the output says otherwise.

    So fluent reading is not about knowing every pandas method. It is about knowing where the quiet failures live and going straight to those lines. A good reviewer spends most attention on five or six places: where the data comes in, where tables are joined, where the train and test split happens, what gets fitted on what, how the target is built, and what is finally reported.

    The second half of the lesson is the same skill pointed at results rather than code. Some analyses are hollow: the data was random, the number printed does not match the sentence beside it, or the metric was computed on rows the model had already seen. Often nobody is lying. A tired analyst, or an assistant asked to "make the results look good", takes the path of least resistance. Your job is to notice.

    Hold onto thisReading is a search for the few lines that can silently change the answer: joins, splits, fits, the target and the reported metric. Everything else is plumbing. When you do not trust a line, do not argue about it. Ask for the row count or the printed output that would settle it.
    Part 2

    How it really works

    F10.1 · Reading Python fluently

    A reading order that finds bugs early

    Do not read top to bottom like a story. Read in this order, and stop to ask each question.

    1. Outputs and inputs. Read the last ten lines and the function signatures first. What is being reported or saved? What goes in? If you cannot say in one sentence what the script produces, the rest is guesswork.
    2. The grain. After each load or join, what is one row: a transaction, a customer, a customer-month? Everything downstream (rates, counts, splits) depends on the answer. Ask what the row count should be, and where it is printed.
    3. The target. Where is is_fraud or default_90d built, from which columns, as of which date? A feature derived after the outcome (a chargeback amount, a "closed" status) is leakage (F3.1).
    4. The split, then every fit. Find the line that splits. Then find every fit, fit_transform, scaler, imputer, encoder, feature selection and resampler. Each must come after the split and touch only training rows. Better, they live inside a pipeline.
    5. The metric. Which array goes into it? Predictions or probabilities, test rows or training rows, resampled or real prevalence?
    6. Only then the plumbing: plots, logging, helper functions. Skim these.

    Reading the idioms

    Most Python in data work is a small vocabulary used repeatedly. Once you read these without effort, scripts get short.

    # Boolean mask: keep rows where both conditions hold. & and | need brackets.
big = df[(df.amount > 5000) & (df.channel == "online")]

# Named aggregation: one row per customer, three summary columns.
per_cust = (df.groupby("customer_id")
              .agg(n=("txn_id", "count"),
                   total=("amount", "sum"),
                   last=("ts", "max")))

# transform keeps the original rows: each row gets its group's value.
df["amount_vs_cust_mean"] = df.amount / df.groupby("customer_id").amount.transform("mean")

# List comprehension with a condition; the dict maps code to label.
flags = [c for c in df.columns if c.startswith("flag_")]
labels = {1: "fraud", 0: "ok"}

    The distinction that trips people most: agg shrinks the table to one row per group, transform keeps every row, and apply can do either depending on what the function returns. When reviewing, always ask "how many rows come out?".

    The most damaging of these in banking is the join. Customer, account and device tables are rarely clean one-per-key, because of historical versions, joint accounts and re-issued cards. The next simulation shows how little it takes.

    Two habits make this class of error nearly impossible to miss. First, assert shapes: after a join, assert len(df) == len(tx). Second, reconcile to something known: total AED against the finance ledger, transaction count against the source system. A reconciliation that ties out is worth more than any amount of reading.

    One more reading skill, specific to code written by an assistant: it tends to be fluent, confident and over-complete. Expect extra helper functions, unused arguments and comments that describe the intent rather than what the line does. When the comment and the code disagree, the code wins. Ask for the smallest version that does the job, and read that.

    F10.2 · Spotting hollow or fabricated analyses

    A hollow analysis is one whose conclusion is not supported by what was actually computed. It comes in three flavours, and each has its own tells.

    1. Metrics on the wrong split

    The cleanest example is leakage through feature selection. Suppose you have 200 customers and 3,000 candidate features, and the target is pure noise. Pick the 20 features most correlated with the target, then cross-validate a model on those 20. The estimated accuracy will be well above chance. The selection step already looked at the labels of the rows you then "tested" on. This is the textbook "wrong way to cross-validate" (Hastie, Tibshirani and Friedman, section 7.10.2; Ambroise and McLachlan, 2002).

    The same logic covers any step that touches labels: target encoding, imputation by class, SMOTE (see F3.5), threshold tuning, and early stopping on the test set. A related slip is tuning on the test set: try twenty settings, report the best test score, and the test set has become a training set (see cross-validation and temporal splits and hyperparameter tuning). A large 2023 survey of machine-learning-based science found leakage reported in hundreds of papers across many fields (Kapoor and Narayanan, 2023), so this is not a beginner's problem.

    2. Random or synthetic data passed off as real

    Sometimes the data itself is not what it claims to be: generated by np.random to make a demo, or an AI-written notebook that fills in a missing file with simulated numbers and carries on. Real bank data has texture that random generators lack.

    PropertyReal banking dataGenerator output
    Amount shapeRight-skewed with a long tail; median far below meanFlat (uniform) or symmetric bell (normal), median near mean
    Round numbersSpikes at AED 100, 200, 500, 1,000Almost none
    Missing valuesPatterned: whole columns missing for a channel or a productNone, or scattered uniformly at random
    RelationshipsMessy but present: income and limit, tenure and balanceFeatures independent; correlation matrix near the identity
    IDs and timestampsGaps, duplicates, clusters at business hours and month-endConsecutive IDs, evenly spread times
    The signalModest AUC (0.7 to 0.9) that took work to reachEither 0.50, or a planted rule recovered at 0.99

    3. Text that contradicts the output

    The third kind needs no data forensics. The prose says one thing and the printed result says another. This happens when an assistant writes the narrative before, or without, looking at the numbers, or when a notebook is edited and not re-run. Compare each sentence of the write-up with the line of output it relies on.

    The write-up saysThe output showsThe problem
    "Recall improved to 86%"recall: 0.79 in the cell aboveNarrative from an earlier run or invented. Re-run and compare.
    "The model generalises well (AUC 0.91 on held-out data)"The cell computes AUC on X_trainWrong split. The number is a training score.
    "Significant difference (p < 0.05)"Twelve segments tested, one p-value of 0.04 reportedMultiple comparisons (F2.4); the other eleven are missing.
    "Fraud fell 20% after the new rule"A before and after table with no control groupCausation claimed from a trend (F2.6, F9.3).
    "Trained on 3 years of data"df.shape shows dates from the last 5 monthsThe filter or file was not what the text describes.
    "Top features: tenure, salary"Importance plot headed by account_status_codeThe narrative describes a plausible story; the plot shows a likely leak.

    The general test is simple: could I regenerate every number in the text from the code and data, today? If the analysis cannot be re-run from a clean start with a fixed random seed and give the same figures, it is not finished, whatever the prose says. Add three cheap checks to any result you are going to rely on. A trivial baseline (predict the average, or yesterday's value) to see if the model clears it. A shuffled-label run: permute the target and re-run the whole pipeline. If it still scores well, something is leaking. And a look at the five worst errors, by eye.

    How it connects

    Reading code and auditing results are the working form of almost everything else in the curriculum.

    Every wrong-split bug here is leakage by another route. That lesson tells you what to look for in the target and features; this one tells you where in the code.

    Row-count assertions, reconciliation to the ledger and shuffled-label runs become automatic tests rather than things you remember.

    F10.4 · Software design basicsCode that can be reviewed

    Small functions with clear inputs and outputs are far easier to read, and to check, than a 600-line notebook.

    F11 · Python hands-onThe mechanics under the idioms

    Broadcasting, vectorisation and index behaviour explain several of the traps above.

    R13 · Auditing data scienceThe research frontier of this skill

    Where this lesson stops: systematic methods for auditing analyses, including AI-generated ones.

    F7 · MetricsWhich number belongs in the report

    Knowing what each metric measures lets you spot a mismatch between the claim and the number.

    Where it shows up at the bank:

    • Model validation. The validation team (G3) reproduces your results independently. Code that is readable and re-runnable is the difference between a two-day review and a two-week one.
    • Inherited notebooks. The previous owner of a churn or collections model leaves a notebook with hard-coded paths and silent filters. Reading it fluently is how you find out what it really does.
    • AI-assisted work. Whether your own Claude Code session or a vendor's output, the same review order applies. Regulators and internal audit will ask who checked it, and "the assistant wrote it" is not an answer.
    • Vendor and consultant claims. A proof of concept reporting 98% detection on a dataset nobody can inspect is the standard case for Part 5.
    Part 4

    Where the field is now

    Two things changed the picture in the past two years. Assistants now write much of the analysis code, so review is the main human job. And the tools themselves are tightening, which removes some old traps.

    Checked 6 November 2026 with a few light searches. Items below are ones I could confirm; others are marked.

    1. 2002
      Selection bias in cross-validation, named and measured

      Ambroise and McLachlan showed on gene-expression data that selecting features on all samples before cross-validation produces optimistic error estimates, even on data with no signal. The textbook treatment is in Hastie, Tibshirani and Friedman.

      Ambroise & McLachlan, PNAS, 2002
    2. 2023
      Leakage as a reproducibility crisis

      Kapoor and Narayanan surveyed papers in machine-learning-based science and catalogued leakage affecting results in many fields; they proposed a taxonomy and model-info sheets for reporting. From memory, the count was in the hundreds of papers across about seventeen fields. Check the paper for the exact figures.

      Kapoor & Narayanan, Patterns, 2023
    3. 2025
      Runtime logic bugs in data science code are poorly caught by LLMs

      DSDBench builds benchmarks of data science code with bugs that run without error, including multiple bugs per script, and finds that language models handle this kind of error tracing poorly.

      DSDBench, EMNLP 2025
    4. 2026
      Pandas 3.0: copy-on-write becomes the only mode

      The pandas team announced that copy-on-write is now the default and only behaviour in pandas 3.0, with a new string dtype. Chained assignment no longer works, so the old "sometimes it modifies, sometimes it doesn't" confusion goes away, at the cost of breaking old code.

      pandas 3.0 release post, 2026
    5. 2026
      Long-horizon data analysis by agents fails by cascade

      LongDS-Bench, a preprint on long multi-turn analysis tasks, attributes most agent failures to errors that cascade and to losing track of state across steps, not to isolated coding mistakes. That matches the review advice here: an early silent error contaminates everything after it. Preprint; I read only its summary.

      arXiv 2605.30434, 2026 (preprint)

    Part 5

    How it fails, and how to spot it

    These are failures of the reviewer, not only of the code. Each comes with the quickest check.

    • Trusting code because it ran

      No error is taken as evidence of correctness. Most of the bugs in this lesson produce none.

      Spot itAsk what output would look different if the code were wrong. If nothing would, add a check that would.
    • Reviewing the plumbing, not the pivots

      Comments on naming and plot colours while the split sits above the scaler.

      Spot itBefore any style comment, say aloud where the split, the target and the metric are.
    • Metrics too good for the problem

      AUC 0.99 on fraud, 95% accuracy on credit default, near-perfect forecasts of customer behaviour.

      Spot itTreat an unusually high score as a bug report until shown otherwise. Look at the top feature importances for post-outcome columns, and run the shuffled-label test.
    • Row counts never printed

      The notebook shows head() but never shape. Fan-out and silent filters live here.

      Spot itAsk: how many rows did you start with, and how many are in the final modelling table? What was dropped, and why?
    • The narrative written first

      The summary predates the final run; the numbers in the text match no cell.

      Spot itRe-run top to bottom (restart kernel, run all) and diff the numbers against the text.
    • Results that cannot be re-run

      Hard-coded local paths, no random seed, a cell that depends on a deleted variable.

      Spot itAsk a colleague to run it from a clean checkout. Two runs with a fixed seed must agree.
    • Synthetic stand-ins left in

      The real file was missing, so the code generated placeholder data and carried on, and the results were reported as findings.

      Spot itSearch for np.random, faker, make_classification, sample( and "dummy" or "mock" in the loading code. Plot the amounts and check for a round-number spike.
    • Selection from many tries

      Twenty models, features or segments tried; the best is reported with no mention of the rest.

      Spot itAsk how many variants were tried, and where the final test set was first used.
    • Over-trusting a second assistant

      "I asked another AI and it said the code is correct."

      Spot itReviewer assistants miss quiet logic bugs too. Make it point to line numbers and the evidence (printed shapes, outputs), not give a verdict.
    Part 6

    What to say in the room

    To a manager when handed a notebook · 30 seconds
    “Before I trust the numbers I'd like to check four things: how many rows go in and come out of each step, where the train and test split is relative to every fit, how the fraud flag is defined and when, and whether the headline figure reproduces from a clean run. I'll also reconcile the totals to the ledger. That's half a day, and it saves us presenting something we have to retract.”
    To a technical interviewer or validator
    “I read for grain, split and target first. I check joins for fan-out with row-count assertions or a many-to-one validation, make sure scalers, selectors and encoders are fitted inside the training fold, check metrics are computed on probabilities from held-out rows at the real prevalence, and run a shuffled-label control. For AI-written code I ask for the smallest version that does the job and I verify the outputs, not the explanation.”
    “The model gets AUC 0.98. Can we take it to the steering committee?”

    Not yet. In fraud and credit that figure is more often a leak than a triumph. I'd check which features drive it, whether any are only known after the outcome, whether the split was by time, and run it with shuffled labels. If it survives, great; we then report it with an interval and the precision at the alert volume we can handle.

    “Claude wrote this and it passes the tests. Why review it?”

    Tests only check what someone thought to test. The bugs that matter here, a duplicated join or a scaler fitted on the full data, give correct-looking output and pass most unit tests. A human has to own the question of whether the code does what the business meant. The assistant speeds up writing; it doesn't take the accountability.

    “How would you tell if a vendor's demo data is made up?”

    Ask for the data dictionary and a column profile, then look at the shapes. Real amounts are skewed with round-number spikes and patterned gaps. Fabricated ones are flat or bell-shaped, features are uncorrelated, IDs are consecutive. And I'd ask them to run the model on a sample we choose, which settles it quickly.

    “The report says recall is 86% but the notebook prints 79%. Which is right?”

    Neither until we know why they differ. Possibly the text came from an earlier run, the cell was edited and not re-run, or a different split was used. I'd restart the kernel, run all, and then correct the text from the output. Then I'd ask whether anyone relied on the 86%.

    “Do we really need all these checks on a quick exploratory analysis?”

    The depth should match the stakes. For exploration, row counts and a glance at distributions are minutes. The full set (clean re-run, reconciliation, shuffled-label control) is for anything that drives a decision, goes to the committee or enters a model inventory. The cost of the checks is small compared with the cost of retracting a number.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. A merge of 500,000 transactions with a customer table returns 541,000 rows. What happened, and which two things would you add to the code?

    Some customers appear more than once in the customer table, so their transactions were duplicated (fan-out). Add validate="m:1" to the merge so pandas raises, and an assertion that the row count after equals the row count before. Also reconcile the AED total to the source.

    2. What is wrong with df[df.risk == "high"]["flag"] = 1, and what do you write instead?

    Chained assignment: the first indexing returns a temporary object, so the assignment may not reach df. In pandas 3 it never does. Write df.loc[df.risk == "high", "flag"] = 1.

    3. A script scales the features, selects the 30 best by correlation with the label, then runs 5-fold cross-validation. The labels are pure noise. Is the CV accuracy at chance?

    No, it will be above chance, more so the more candidate features there were. Selection looked at all labels, including those later held out. Put scaling and selection inside the pipeline so they are refitted within each training fold.

    4. roc_auc_score(y_test, model.predict(X_test)) prints 0.71 for a model whose probabilities would score about 0.90. Why?

    predict returns hard 0 or 1 labels, which have only one threshold. AUC needs scores that rank rows. Use predict_proba(X_test)[:, 1].

    5. You are handed amounts that are evenly spread from AED 1 to 1,000 with no repeated values, and 100% complete. What do you suspect?

    A random-number generator, not card data. Real amounts are right-skewed with a long tail, show spikes at round values, and often repeat for subscriptions. Completeness at 100% is also unusual. Ask for the source and lineage.

    6. A notebook says "AUC on the held-out set: 0.93" but the cell computes roc_auc_score(y_train, p_train). What do you do?

    Treat the claim as unsupported. The number is a training score. Re-run on the held-out rows, preferably forward in time, and correct the text from the output.

    7. Name three cheap checks you can add to any result you rely on.

    A trivial baseline (mean, last value) to beat; a shuffled-label run of the whole pipeline, which should score at chance; and reading the five worst errors. Add row-count assertions after each join and a clean restart-and-run-all.
