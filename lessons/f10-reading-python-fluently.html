    Reading, Testing and Structuring Code

    Part 1

    Why code needs checking

    In one sentenceCode that runs without an error can still give the wrong number, so you need three habits: read the risky lines, test what could break, and keep each fact in one place.

    You will read far more code than you write, much of it written by an AI assistant. A crash is cheap, because you see it at once. Code that runs cleanly and prints a believable number is the expensive kind.

    Throughout this lesson we use one example: a script that reports average monthly spend per customer from a table of card transactions and a table of customers.

    Part 2

    Reading code

    In one sentenceReading code means checking the few load-bearing lines first, not following every line in order.

    Think of a building inspector: they check the foundations and beams, not the paint. In data code, the load-bearing parts are joins, the train/test split, and the metric.

    What to check, in order

    1. The grain. After each load or join, what is one row? Customer, account or transaction? Is the row count printed anywhere?
    2. The target. Where is the thing you predict built, and as of which date? A feature only known after the outcome is leakage.
    3. The split, then every fit. Scalers, imputers and feature selectors must be fitted on training rows only.
    4. The metric. Is it scored on test rows, using probabilities rather than hard 0/1 labels?

    This is the most common quiet failure. Joint accounts and re-issued cards mean customer tables are rarely one row per customer. Two habits catch it:

    • Assert shapes. After the join, check len(df) == len(transactions), or ask pandas to enforce it with validate="m:1".
    • Reconcile to something known. Compare your total with the finance ledger.

    Reading AI-written code

    • Comment versus code. When they disagree, the code is what ran.
    • Ask for evidence. If you distrust a line, ask for the printed row count or output that settles it.
    Part 3

    Testing

    In one sentenceA test feeds the code a known input and checks the output against an answer that came from outside the code.

    A green tick means "nothing I thought to check has broken", not "this works". Take a function that sorts loans into overdue buckets. A loan exactly 30 days overdue can land in the wrong bucket even when the tests pass and coverage reads 100%, because coverage only says which lines ran, not whether the answers were right.

    What a good test checks

    • Boundaries. Values like 0, 29 and 30, an empty table, missing values. Bugs live at the edges.
    • An outside answer. Use a policy example or a ledger figure. A test that reuses the formula it tests can never fail.

    The question to ask of every test

    Ask: what bug would make this test fail? If you cannot name one, the test proves little. A passing test also does not prove the requirement was right, or that the data looks like production.

    Part 4

    Structuring code

    In one sentenceGood structure means each fact lives in one place and each piece does one job, so a change touches as little code as possible.

    In our example, an alert threshold of 10% is typed on lines 87, 203 and 340. When risk wants 8%, you must find all three. Miss one and the numbers disagree, with no error.

    • One source of truth. Values that change for business reasons (threshold, date window, input table) go in one config file, read once.
    • One job per piece. A piece (module) should hide how it works and expose a narrow door, its interface: "give me a table with these columns, I return one probability per row". Then you can swap the model without touching the rest.
    • Edges do the touching. Reading files, databases and the clock happens at the edges, so the middle can be tested without production.

    Do not over-engineer: a 60-line one-off script does not need five modules.

    Part 5

    Which habit, and when

    HabitCatchesWeak at
    ReadingJoins, leakage, wrong metricLong code; you will miss things
    TestingEdge cases, later breakageWrong requirements; weak tests
    ReconcilingTotals that drift from a known figureErrors that cancel out
    StructuringInconsistent copies of one factDoes nothing for a wrong formula

    In banking, an auditor can ask you to rebuild any reported number, so every figure needs its code version, data snapshot, library versions, seeds and settings recorded.

    Part 6

    Common mistakes and quick check

    • Trusting clean output

      No error and a plausible number is not evidence. Print a row count or reconcile to a known total.

    • Believing coverage

      100% coverage means every line ran, not that any answer was checked.

    • Copying the code's output into the test

      If the expected value comes from running the function, the test enshrines any bug.

    • Fitting before splitting

      Scaling or selecting features on all rows lets test data leak into training and inflates the score.

    1. Three transactions join to a customer table and four rows come out. What is the likely cause?

    A customer appears twice in the lookup table, so its transactions are duplicated. Use validate="m:1" or assert the row count.

    2. Why might a loan exactly 30 days overdue be misclassified despite 100% coverage?

    Coverage only shows the lines ran. Nobody tested the boundary at 30.

    3. What question tells you whether a test is any good?

    What bug would make it fail? If none, it proves little.

    4. Risk lowers the threshold from 10% to 8%. How do you make that a one-line change?

    Store it once in a config file and have every step read it from there.
