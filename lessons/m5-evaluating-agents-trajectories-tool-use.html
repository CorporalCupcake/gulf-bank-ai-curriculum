    Judging the Path, Then Watching the Live System: Evaluating Agents and Online Feedback

    An agent can reach the right answer by an unsafe route, or announce an action it never took. This lesson covers how to grade trajectories and tool calls, why one success is not reliability, and what to measure once real customers and staff are using the thing.

    Contents

    The whole lesson in one sentenceAn agent is a process, so grade the process (which tools, in what order, with what side effects) as well as the outcome, measure how often it succeeds every time rather than once, and then treat live traffic as the final and most biased test: sparse thumbs, delayed outcomes, and changes that need weeks of data to detect.

    Part 1

    The intuition

    A customer messages the bank's assistant: "There is an AED 2,400 payment on my card I did not make." A good human agent does five things in order. Verify who is asking. Find the transaction. Block the card. Open a dispute. Tell the customer what happens next.

    Now picture an AI agent that writes a lovely final message: "Your card is blocked and a dispute is open." A text grader gives it full marks. But suppose it never called the dispute tool. Or it skipped identity verification. Or it also issued a refund nobody approved. The words at the end were fine. The work was wrong.

    That is the core difficulty. A chat answer can be judged on its text (M5.1, M5.2). An agent acts: it calls tools, changes records, spends money, sends messages. The thing to grade is the whole trajectory and the state of the world afterwards, not just the last paragraph.

    Two further facts make agent evaluation different again.

    • One success proves little. The same agent given the same task twice can succeed once and fail once. A bank needs "works every time", and that number falls fast as you ask for more repeats and more steps.
    • The test set is never the customer. Once the agent is live, the interesting evidence is what real people do: whether they escalate to a human, rephrase, abandon, or press thumbs-down. That evidence is plentiful but biased, and it arrives with delay. Online evaluation is a discipline of reading it honestly.
    Hold onto thisFor every agent, write down three things before building any metric. What must be true of the world at the end (the outcome)? What must never happen on the way (the constraints)? How many times in a row must it work (the reliability bar)? Offline tests check those three. Online evaluation checks whether the tests were measuring the right things.
    Part 2

    How it really works

    Grading the trajectory, not only the answer

    A trajectory is the full record of a run: the messages, each reasoning step if logged, each tool call with its arguments, each tool result, and the final reply. If you cannot log it, you cannot evaluate it (see tracing). Everything below works on that log.

    There are two families of grader, and good evaluations use both.

    GradeQuestion it answersHowWeakness
    Outcome (state-based)Is the world in the right state at the end?Compare the final database or ticket state to a target. Code, not opinion.Blind to unsafe routes and to side effects you did not think to check.
    Process (trajectory-based)Did it get there acceptably?Rules on the call log: required steps, forbidden tools, order, step budget. Optionally an LLM judge reads the whole trace.Rigid rules punish harmless alternative routes. Judges inherit all the judge problems of M5.2.
    Response (text)Did it say the right thing, safely, in the right language?Rubric plus judge or human review.Says nothing about whether the claims in the text are true of the system.

    The most useful single idea comes from the τ-bench benchmark (Yao et al., 2024): grade by comparing the final state of the environment to the state a correct run would leave, rather than reading what the agent said. That catches an agent that claims success without acting. Then layer rules on top for the things state cannot show: the order of checks, the sensitive data in the reply, the tools it must not touch.

    Process grading has a trap. If you require an exact sequence, you punish valid variation. An agent that blocks the card before opening the dispute is fine. So write rules as constraints ("verification must precede any write", "no refund tool without approval") not as a script. Check what must hold, and leave the rest free.

    The simulation lets you do this by hand. Eight runs of the same task all end with a friendly message. Turn graders on and off and see which bad runs each one lets through.

    Note run G, which blocks the card before opening the dispute. A rigid "exact sequence" grader would fail it. That is a false rejection, and too many of them train the team to ignore the evaluation. The aim is a set of rules that fail the dangerous runs and nothing else.

    A small version in code makes the idea concrete. The grader reads a list of tool calls and returns reasons, not just a score.

    def grade(run, final_db):
    calls = [c.name for c in run.tool_calls]
    reasons = []
    if final_db["card_status"] != "blocked":      reasons.append("card not blocked")
    if final_db["dispute_txn"] != "TX-88213":     reasons.append("wrong or missing dispute")
    if "refund_customer" in calls:                reasons.append("forbidden tool")
    writes = [i for i, n in enumerate(calls) if n in WRITE_TOOLS]
    if writes and "verify_identity" not in calls[:writes[0]]:
                                                  reasons.append("write before verification")
    if PAN_REGEX.search(run.final_reply):         reasons.append("card number in reply")
    return {"pass": not reasons, "reasons": reasons, "steps": len(calls)}

    Returning the reasons matters. A bare pass rate tells you the agent is at 71%. A list of reasons tells you 40% of failures are "write before verification", which is a fix you can make.

    Tool use: right tool, right arguments, right moment

    Most agent failures are tool-use failures, and they are more specific than "it got it wrong". Break them apart.

    CheckWhat goes wrongHow to test
    SelectionCalls the wrong tool, or no tool when one is needed (answers from memory instead of looking up the balance).Compare tool names called against an expected set for each test task.
    ArgumentsRight tool, wrong inputs: the AED 240 transaction instead of the AED 2,400 one, a wrong IBAN, a date in the wrong format.Validate against a schema, then against the state the arguments should point to. Schema-valid is not the same as correct.
    Sequence and dependenciesWrites before reading, or acts before approval.Constraint rules on call order.
    Honest reportingSays "done" when the call failed or never happened. Treats an error result as success.Compare each claim in the reply with the log and final state.
    RecoveryOn a timeout or error, retries blindly, loops, or invents a result.Inject faults: make a tool return an error and check what the agent does next.
    RestraintCalls tools it did not need, or tools with side effects it was never asked to use.Allow-lists per task, and a check that the final state differs from the target only where intended.

    Public tool-use benchmarks, such as the Berkeley Function-Calling Leaderboard, test the first two rows well: given a request and a set of function definitions, does the model emit the right call with valid arguments? They are good for choosing a base model. They say little about your bank's tools, data and policies, which is why the bank needs its own task set built from real cases (M5.3 and A4.1 cover how to build and size one).

    The test environment matters as much as the grader. To grade state you need tools that run against a sandbox copy of the systems, reset between runs, with seeded customers and transactions. Building that sandbox is real engineering effort, and it is usually the thing that separates a serious agent evaluation from a demo. It also lets you simulate the user, a second model playing the customer, which is the approach of simulation testing in A4.

    Task success, and why "it worked once" is not a number

    Define task success from the outcome and the constraints: the end state is right and no rule was broken. That gives a pass or fail per run. Now two effects bite.

    Steps compound. If each step succeeds with probability s and a task needs n steps in a row, then (treating steps as independent, which is generous) the task succeeds with probability

    ptask=sn

    At 99% per step and 10 steps: 0.9910 = 90.4%. At 95% per step and 10 steps: 59.9%. At 98% per step and 20 steps: 66.8%. A model that is "98% accurate" at each move is a coin-flip-and-a-bit on a 20-step job. Real steps are not independent (a bad early step often spoils later ones), so treat this as the optimistic shape, not a forecast.

    Repeats compound too. Run the same task k times. Two different questions are worth asking. pass@k: did at least one of the k runs succeed? That is 1 − (1 − p)k, and it climbs towards 100%: useful if a human or a checker picks the good attempt. pass^k (read "pass hat k"): did all k runs succeed? That is pk, and it falls. τ-bench introduced pass^k precisely because a customer-facing agent has to work every time, not on the best of eight tries. In the original paper a strong model's retail pass^1 of about 61% dropped to under 25% at pass^8.

    Four consequences for how you report.

    • Report the success rate with its interval and the number of tasks and repeats. "78% on 60 tasks" is ±10 points or so, the same positives-are-the-sample-size logic as imbalanced data and F2.1. Comparing two agent versions on 60 tasks usually cannot separate them.
    • Separate "succeeded" from "succeeded safely". A run that reaches the goal by breaking a rule is a failure with a good-looking outcome. Report both counts.
    • Split failures by cause. Wrong tool, wrong argument, policy breach, gave up too early, looped, misreported. The mix tells you whether to fix tools, prompts, or the model.
    • Include cost and time. Steps, tokens, wall-clock seconds and AED per task are part of "success". An agent that solves the task in 40 calls is not the same product as one that takes 6. Cost data can be read straight from the trace.

    For long jobs, such as multi-hour investigations, success is often partial. Then grade checkpoints (each sub-goal reached) and the point at which the run went wrong, a theme taken up in long-running agents. On the research side, METR measures how long a task, in human-expert time, an agent can complete at a given success rate (R7), which is the same reliability question stretched over duration.

    Online evaluation: what happens once people use it

    Offline evaluation tells you the agent can do the job on a fixed set of tasks. It cannot tell you what customers will actually ask, in Arabic dialects and mixed Arabic-English, at the end of Ramadan when volumes spike, with typos and half-formed questions. Online evaluation is everything you measure on live traffic. It has four layers, from cheapest to most conclusive.

    LayerWhat you doWhat it gives youCatch
    1. Shadow modeThe agent runs on live requests but its output is not used. Humans do the work as before. Compare.Realistic inputs with zero customer risk. Agreement with the human decision.The human decision is itself an imperfect label. No effect on the user can be measured.
    2. Passive monitoringLog every run. Track rates: tool errors, escalations, retries, refusal, latency, cost, guardrail triggers.Early warning and drift (F7.7).Tells you something changed, not whether it is good.
    3. Sampled reviewPull a random slice of live runs (plus all flagged ones) for human or judge grading against the same rubric as offline.An unbiased quality estimate on real traffic, and fresh failures for the test set.Costs reviewer time. Needs a random sample, not only the flagged cases.
    4. Controlled experimentRandomly route customers to old or new version (A/B test) or ramp a share of traffic.The only clean causal answer to "is the new version better for customers and the bank?"Needs enough traffic and time (Simulation 4). Needs guardrails in case it is worse.

    For a regulated bank, the ramp matters. Typical practice is shadow mode first, then a small share of low-risk requests with human approval on actions, then wider release with automatic rollback if guardrail metrics breach thresholds. Which actions may ever run without a person approving them is a risk decision (M4.5), and a model-risk question for the validators (G3).

    Choose the live metrics in two groups. Outcome metrics are what the bank actually wants: resolved without a human, disputes filed correctly, handling time, repeat contact within seven days, complaints. Guardrail metrics are what must not get worse: policy violations, escalations that came too late, privacy incidents, cost per conversation. A change that lifts resolution by two points and doubles complaints is not a win, so look at both together.

    User feedback: plentiful, biased and easy to misread

    Explicit feedback means thumbs up or down, star ratings, a "was this helpful?" prompt. Implicit feedback means behaviour: the customer rephrases the question, asks for a human, abandons the chat, copies the answer, or calls the contact centre an hour later about the same issue. Staff copilots add a further signal: did the employee accept, edit or discard the draft?

    Both are useful and both mislead in predictable ways.

    • Non-response bias. Only a small fraction of people press a button, and unhappy people press it much more often than content ones. Thumbs-up share is not satisfaction. Simulation 3 shows how far apart they can sit.
    • Wrong proxy. A customer who gets a confident wrong answer may thank it and leave. One who gets a correct, unwelcome "no, we cannot reverse that" may press thumbs-down. Feedback measures how people felt, which correlates with correctness without being it. Studies of real chat logs find that user feedback is informative about the user's state but noisy as a training signal (see Part 4).
    • Selection and context. Feedback arrives from the people who stayed in the conversation. Those who gave up earlier are missing, which is the selection problem of F2.6.
    • Gaming and drift. If you optimise directly for thumbs-up, you can get agreeable, flattering answers (see the sycophancy lesson, R4). Staff feedback can also be coerced or bypassed when the button is an extra click.
    • Delay. The real outcome of an advice or dispute conversation may be known only weeks later: did the chargeback succeed, did the customer come back? This is the label-delay problem of B1, and recent weeks look better or worse than they are.

    What to do about it.

    • Use feedback to find failures, not to measure rate. Every thumbs-down with a free-text comment is a candidate test case. Read them weekly.
    • Measure rate from a random sample you review yourself. A few hundred randomly chosen conversations, graded against a rubric, give an unbiased number with an interval.
    • Prefer behavioural outcomes that map to value. Repeat contact within seven days is harder to game than a rating.
    • Calibrate the cheap signal against the careful one. If a judge or a proxy metric is going to be used for monitoring, check periodically that it still agrees with human review, using the agreement methods of M5.3 and M5.4.
    • Close the loop. Promote every confirmed live failure into the offline test set, with a note on why. Over time the offline set starts to look like real life.

    Is the new version better? Detecting a change in a live metric

    You have a new prompt or model and a live metric: say the share of conversations escalated to a human, currently 18%. You route half of customers to the new version. How long until you can tell whether it moved? The standard two-proportion sample size (F2.7, and R8 on A/B testing) gives, per arm, about

    n≈2(zα/2+zβ)2p¯(1−p¯)d2

    d is the smallest change you care about (in proportion terms), p̄ the average rate across arms, and the z values set the false-alarm rate (1.96 for 5%) and the power (0.84 for 80%), so (1.96 + 0.84)² ≈ 7.85. Halving d quadruples n. If one customer has many conversations, they are not independent, so multiply by a design effect above 1.

    Three cautions on live experiments. Peeking: checking daily and stopping when it looks good inflates false wins; use a fixed plan or a sequential method. Novelty and weekday effects: a new assistant gets curiosity traffic in week one, and demand differs between weekdays and around salary dates and holidays, so run full weeks. Non-random routing: if routing depends on customer type or channel, you are comparing different populations; randomise by customer, not by request. When traffic is thin, use many cheap proxy metrics for quick filtering, and reserve the slow experiment for decisions that matter.

    Where it shows up at the bank:

    • Customer service assistants. Verification before account actions, correct dispute and card-block calls, right language and tone, handoff to a human with a good summary. Live metrics: containment, repeat contact, complaints.
    • Staff copilots. Draft acceptance and edit rate, time saved, and sampled review of drafts for policy and factual errors (B7).
    • Fraud and AML investigation agents. Gather evidence from several systems and draft a case note. Grade tool use against what a senior investigator would query, and the final note against a rubric. A wrong action is expensive, so approvals gate every write.
    • KYC and document agents. Extract, cross-check, flag. State-based grading works well: compare the structured output to a verified record.
    • Arabic and English. Run the same tasks in both, and in dialect, and report results per language. An average over languages hides the weak one.
    Part 4

    Where the field is now

    The direction of travel is clear: from judging single answers to judging environments, from one run to repeated runs, from benchmark scores to logs and live signals. The open arguments are how far automated judges of whole trajectories can be trusted, how much benchmark numbers depend on the test harness, and how to evaluate long, open-ended work.

    Research checked on 6 November 2026 with a small number of searches. Items from earlier years are from my own knowledge of the literature; items marked as preprints I could only partly verify.

    1. 2023
      Benchmarks for agents act in environments

      AgentBench tested models as agents across several interactive environments. SWE-bench graded software agents by whether the repository's tests passed after the change, an early example of outcome-by-execution. GAIA posed real-world assistant questions needing tools.

      Liu et al., arXiv 2308.03688; Jimenez et al., ICLR 2024; Mialon et al., arXiv 2311.12983
    2. 2024
      τ-bench: state comparison and pass^k

      Simulated customers talk to an agent bound by written policy and tools (retail, airline). Success means the final database state matches the target. The pass^k metric exposed how much reliability drops over repeated trials.

      Yao et al., arXiv 2406.12045
    3. 2024
      Judging agents with agents

      Agent-as-a-Judge proposed using an agentic system, with tools, to grade another agent's intermediate work, rather than a single prompt reading a transcript. Promising, but it brings the judge-bias problems with it.

      Zhuge et al., arXiv 2410.10934
    4. 2024
      Function-calling leaderboards

      The Berkeley Function-Calling Leaderboard scores tool selection and argument correctness, with multi-turn and multi-step categories added over time. Use for model selection, not as proof of fitness for your own tools.

      Berkeley Function-Calling Leaderboard, gorilla.cs.berkeley.edu
    5. 2025
      Dual-control and task-length measures

      τ²-bench added a telecom domain where the user also acts on their own device, so the agent must guide rather than only act. METR proposed measuring the length of task, in human time, that models complete at a given success rate.

      Barres et al., arXiv 2506.07982; Kwa et al., METR, arXiv 2503.14499
    6. 2026
      Read the logs, and mind the harness

      A 2026 preprint argues that log analysis is necessary for credible agent evaluation: on a τ-bench split it found several ways the harness under-elicits what the agent can do, and tested whether agents resist persuasion into breaking policy. Another study reports that implementation details of the official τ-bench harness (how earlier reasoning is retained) shift scores by a few points, so scores from different harnesses are not directly comparable. A third preprint on agent reliability appeared in the same period; I saw only its title and abstract.

      arXiv 2605.08545 (preprint); arXiv 2602.16666 (preprint, not read in full)
    7. 2026
      Banking-specific agent tests, reported

      Practitioner write-ups describe τ-bench successors with banking and voice domains. I found these only in vendor and blog sources, not in a peer-reviewed paper, so treat the details as unverified until you read the benchmark's own documentation.

      Vendor and blog posts found by search; verify before citing
    8. 2025
      Live user feedback is informative, noisy as a training signal

      An analysis of real human-LLM dialogues found that follow-up messages carry signals of user satisfaction and dissatisfaction, but that using them naively as learning feedback is noisy, with mixed gains depending on the type of question. Practitioner guides recommend treating feedback as sparse and promoting confirmed production failures into offline test suites.

      arXiv 2507.23158; Langfuse, "LLM Evaluation: Methods and Best Practices", Nov 2025

    Part 5

    How it fails, and how to spot it

    These show up in vendor demos, internal pilots and AI-written evaluation plans. Each comes with the quickest check.

    • Grading only the final message

      The agent says the dispute is open. Nobody checked the system of record.

      Spot itAsk what the grader compares the reply to. If the answer is not a database state or tool log, claims are untested.
    • One run per task

      "92% success" from a single attempt on each test case. Re-running gives 85%, then 90%.

      Spot itAsk how many repeats, and whether the number is pass@1, pass@k or pass^k. Ask for the spread across repeats.
    • Rigid scripts as the process grade

      The agent is marked wrong for doing steps in a harmless alternative order, so the team loosens everything.

      Spot itCheck whether rules are constraints ("verify before write") or an exact required sequence. Review a sample of failures for false rejections.
    • Side effects nobody checks

      The target state is right, but the agent also sent a message, issued a credit, or changed a second record.

      Spot itDiff the full final state against the expected state, not only the fields you hoped it would change.
    • A sandbox that is too clean

      Test tools never time out, return tidy data and never conflict. Live systems do all three.

      Spot itAsk which faults were injected: errors, slow responses, empty results, contradictory records.
    • A small task set quoted as a precise number

      "We improved from 74% to 79%" on 50 tasks.

      Spot itAsk for the task count and an interval. At 50 tasks the interval is about ±12 points; the difference is invisible.
    • Thumbs-up as satisfaction

      A dashboard shows 40% positive feedback and nobody asks who presses the button.

      Spot itAsk for the share of conversations that give any feedback, and for a random-sample review next to it.
    • Optimising the proxy

      The team tunes the agent to raise containment (no human needed) and complaints rise because customers cannot reach a person.

      Spot itCheck that each outcome metric has a guardrail partner: containment with complaints and repeat contact.
    • A test run that is too short or peeked at

      "It looked better after three days, so we shipped it."

      Spot itAsk for the pre-set duration, the sample size calculation and whether the run covered whole weeks.
    • Judge or benchmark drift unnoticed

      The judge model is updated, or the harness changed, and trend lines move for no real reason.

      Spot itPin versions of judge, harness and prompts. Re-score a frozen reference set after every change.
    Part 6

    What to say in the room

    To an executive · 30 seconds
    “It is not enough that the assistant sounds right. We test whether it did the right thing in a copy of our systems: the card actually blocked, the dispute actually filed, nothing else touched. We run each test several times, because what matters is working every time, not once. After launch we release in stages, watch complaints and repeat contacts next to the savings, and read a random sample of real conversations each week. Customer ratings alone would mislead us, because unhappy people rate far more often.”
    To a technical interviewer or validator
    “I'd grade final state against a target in a sandbox, with constraint rules over the trace: verification before writes, an allow-list of tools, no sensitive data in replies. Each task repeats k times and I report pass^k with an interval and a failure taxonomy. Online: shadow mode, a staged ramp with guardrail metrics and automatic rollback, random sampled review against the offline rubric, and live failures promoted into the test set. Feedback is used to find failures, not to estimate rate, because of non-response bias.”
    “The agent scored 90% in the pilot. Can we go live?”

    Not on that number alone. I'd ask 90% of what: tasks, runs, or steps; how many tasks (an interval on 60 tasks is about ±8 points); whether each was repeated; and what the failing 10% looked like. If those failures are dangerous, say wrong actions on accounts, then 90% is not close. If they are polite refusals that route to a human, it may be fine. I'd want a staged release with approvals on write actions.

    “Why not just use an LLM to judge the conversations?”

    For text quality it is a useful, cheap first pass. For actions it is the wrong tool where we have ground truth: the database state and the tool log are exact, and a judge can be fooled by a confident message. I'd use code for state and rules, a judge for tone and completeness of explanation, and humans on a random sample to check the judge keeps agreeing with them.

    “Customer satisfaction scores on the bot are only 40% positive. Is it failing?”

    Maybe, but that figure is the share of people who chose to respond. Unhappy customers respond several times more often. If satisfied users respond at 2% and unhappy ones at 8%, a true 70% satisfaction shows as about 37% positive. I'd read a random sample of conversations to estimate the real rate, and use the thumbs-down comments to find what to fix.

    “How long should we run the A/B test on the new version?”

    Set the smallest change we care about and compute it up front. Detecting a 2-point change in an 18% escalation rate needs about 6,000 conversations per arm, more if customers repeat. Round to whole weeks so weekday patterns balance, and don't stop early because it looks good. If traffic is too thin, accept a larger minimum effect or use a staged ramp with guardrail limits.

    “The bot says it opened a dispute. How do we know it did?”

    We don't from the reply. We check the tool log for the call and its result, then the case system for the record with the right transaction. That check is automated in testing and sampled in production. Every claim of action in a reply should be verifiable against a log entry, and a mismatch is a high-severity defect.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. An agent succeeds at each of 8 steps with probability 96%. What is the chance it completes the task, and the chance it does so on all of 3 repeats?

    0.968 ≈ 72.1% for one run. For all three: 0.7213 ≈ 37.5%. At least once in three: 1 − (0.279)3 ≈ 97.8%. The gap between 37.5% and 97.8% is the gap between pass^k and pass@k.

    2. Why can a text-only grader give full marks to an agent that did the wrong thing?

    Because the reply can claim an action that never happened, or describe an action on the wrong record, in perfectly good prose. The grader sees language, not the system. State comparison and trace rules check the world.

    3. Name two reasons to write process rules as constraints rather than a fixed sequence.

    Valid agents vary the order of harmless steps, so a script rejects good runs and teaches people to ignore the grader. Constraints also express what actually matters (verify before write, never touch the refund tool) and stay valid when you add a tool or change a prompt.

    4. You test two agent versions on 80 tasks and get 70% and 76%. Can you say version B is better?

    Almost certainly not. The standard error on each is about √(0.73 × 0.27 ÷ 80) ≈ 5 points, so a difference of 6 is well inside the noise, even allowing that the same tasks are used for both. Add tasks, repeat runs, and compare per task with a paired method or bootstrap.

    5. Satisfied users give feedback 1.5% of the time and unhappy ones 6%. True satisfaction is 80%. What thumbs-up share will you see?

    Per 1,000 conversations: 800 × 0.015 = 12 positive; 200 × 0.06 = 12 negative. The dashboard shows 50% positive, against a true 80%. The bias is a property of who responds, not of the agent.

    6. What is the difference between an outcome metric and a guardrail metric online? Give a pair for a dispute assistant.

    Outcome metrics are what you are trying to improve; guardrails are what must not get worse. For a dispute assistant: share of disputes filed correctly without staff rework (outcome), paired with complaints, policy breaches and repeat contact within seven days (guardrails).

    7. Escalation rate is 18%. You want to detect a change of 2 points with 80% power at 5% significance. Roughly how many conversations per arm?

    p̄ = 0.19, so p̄(1 − p̄) = 0.1539. n ≈ 2 × 7.85 × 0.1539 ÷ 0.02² ≈ 6,040 per arm, before any design effect for repeat customers.

    8. Why should live failures be promoted into the offline test set?

    Because the offline set is written by people who cannot predict every way customers phrase things. Each confirmed live failure is a real case the agent got wrong, so adding it prevents regressions and slowly makes the test set resemble real traffic.
