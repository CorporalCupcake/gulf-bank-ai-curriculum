    Judging the Path, Then Watching the Live System: Evaluating Agents and Online Feedback

    An agent can reach the right answer by an unsafe route, or announce an action it never took. This lesson covers how to grade trajectories and tool calls, why one success is not reliability, and what to measure once real customers and staff are using the thing.

    Contents

    The whole lesson in one sentenceAn agent is a process, so grade the process (which tools, in what order, with what side effects) as well as the outcome, measure how often it succeeds every time rather than once, and then treat live traffic as the final and most biased test: sparse thumbs, delayed outcomes, and changes that need weeks of data to detect.

    Part 1

    The intuition

    A customer writes: "There is an AED 2,400 payment on my card I did not make." A good human agent verifies identity, finds the transaction, blocks the card, opens a dispute, then tells the customer what happens next.

    An AI agent might end with: "Your card is blocked and a dispute is open." A text grader gives full marks. But perhaps it never called the dispute tool, skipped verification, or issued a refund nobody approved. Like a builder who sends a tidy invoice for work never done, the words were fine and the work was wrong.

    A chat answer is judged on its text (M5.1, M5.2). An agent acts: it calls tools, changes records, sends messages. Grade the whole trajectory and the state of the world afterwards. Two more differences:

    • One success proves little. The same agent on the same task can pass once and fail once. A bank needs "works every time", and that number falls fast with more repeats and more steps.
    • The test set is not the customer. Live evidence (escalations, rephrasing, abandonment, thumbs-down) is plentiful but biased and delayed. Online evaluation is reading it honestly.
    Hold onto thisBefore building any metric, write down three things. What must be true of the world at the end (outcome)? What must never happen on the way (constraints)? How many times in a row must it work (reliability bar)? Offline tests check these. Online evaluation checks the tests measured the right things.
    Part 2

    How it really works

    Grading the trajectory, not only the answer

    A trajectory is the full log of a run: messages, tool calls with arguments, tool results, final reply. No log, no evaluation (tracing). Three kinds of grade, best used together:

    GradeQuestion it answersHowWeakness
    Outcome (state-based)Is the world in the right state at the end?Compare final database or ticket state to a target. Code, not opinion.Blind to unsafe routes and unchecked side effects.
    Process (trajectory-based)Did it get there acceptably?Rules on the call log: required steps, forbidden tools, order, step budget. Optionally an LLM judge reads the trace.Rigid rules punish harmless alternatives. Judges carry the problems of M5.2.
    Response (text)Did it say the right thing, safely, in the right language?Rubric plus judge or human.Silent on whether the claims are true of the system.

    Grade the final state of the environment against what a correct run would leave, as in τ-bench (Yao et al., 2024), rather than reading what the agent said. It is like checking the bank's ledger instead of the receipt the clerk handed over. It catches an agent that claims success without acting. Then add rules for what state cannot show: order of checks, sensitive data in the reply, forbidden tools.

    Write those rules as constraints ("verification must precede any write", "no refund tool without approval"), not as a script. Blocking the card before opening the dispute is fine. Check what must hold and leave the rest free.

    In the simulation, eight runs of one task all end with a friendly message. Toggle graders to see which bad runs each lets through.

    Run G blocks the card before opening the dispute. A rigid "exact sequence" grader fails it. That false rejection, repeated, trains the team to ignore the evaluation. Aim for rules that fail dangerous runs and nothing else.

    A small grader reads the tool calls and returns reasons, not just a score.

    def grade(run, final_db):
    calls = [c.name for c in run.tool_calls]
    reasons = []
    if final_db["card_status"] != "blocked":      reasons.append("card not blocked")
    if final_db["dispute_txn"] != "TX-88213":     reasons.append("wrong or missing dispute")
    if "refund_customer" in calls:                reasons.append("forbidden tool")
    writes = [i for i, n in enumerate(calls) if n in WRITE_TOOLS]
    if writes and "verify_identity" not in calls[:writes[0]]:
                                                  reasons.append("write before verification")
    if PAN_REGEX.search(run.final_reply):         reasons.append("card number in reply")
    return {"pass": not reasons, "reasons": reasons, "steps": len(calls)}

    Returning the reasons matters. A bare "71% pass" says little; "40% of failures are write before verification" is a fix you can make.

    Tool use: right tool, right arguments, right moment

    Most agent failures are tool-use failures. Think of a new hire: wrong form, wrong customer number, wrong order, claiming a task done that they never finished. Test each separately.

    CheckWhat goes wrongHow to test
    SelectionWrong tool, or none when needed (answers from memory instead of looking up the balance).Compare tools called with the expected set per task.
    ArgumentsRight tool, wrong inputs: the AED 240 transaction instead of AED 2,400, a wrong IBAN, a bad date format.Validate against a schema, then against the state the arguments should point to. Schema-valid is not correct.
    SequenceWrites before reading, or acts before approval.Constraint rules on call order.
    Honest reportingSays "done" when the call failed or never happened.Compare each claim in the reply with the log and final state.
    RecoveryOn a timeout, retries blindly, loops, or invents a result.Inject faults: make a tool error and watch what happens next.
    RestraintCalls tools it did not need, or with unrequested side effects.Per-task allow-lists, and a check that final state differs from target only where intended.

    Public benchmarks such as the Berkeley Function-Calling Leaderboard test selection and arguments well. They help choose a base model but say little about your bank's tools and policies, so build your own task set from real cases (M5.3, A4.1).

    You also need a sandbox copy of the systems, reset between runs, with seeded customers and transactions. That is real engineering effort and what separates a serious evaluation from a demo. It also lets a second model play the customer (A4 simulation testing).

    Task success, and why "it worked once" is not a number

    Task success means the end state is right and no rule was broken: pass or fail per run. Two effects then bite.

    Steps compound. Like a relay team where one dropped baton loses the race: if each step succeeds with probability s and the task needs n steps in a row, the task succeeds with probability

    ptask=sn

    99% per step over 10 steps gives 90.4%; 95% gives 59.9%; 98% over 20 steps gives 66.8%. A "98% accurate" model is little better than a coin flip on a 20-step job. Each extra step costs a bit more than the last looks. Real steps are correlated (an early slip spoils later ones), so read this as the optimistic shape.

    Repeats compound too. Run the same task k times. pass@k asks whether at least one run succeeded: 1 − (1 − p)k. It climbs towards 100%, like taking the best of eight tries. Useful only if a checker picks the good attempt. pass^k asks whether all k succeeded: pk. It falls, and it is what a customer-facing agent needs, since customers get whichever attempt they get. In τ-bench a strong model's retail pass^1 of about 61% fell below 25% at pass^8. A pass^8 of 25% means the agent handles the same request correctly eight times running only one time in four.

    How to report:

    • Give the success rate with an interval, task count and repeats. "78% on 60 tasks" is about ±10 points (imbalanced data, F2.1). Two versions on 60 tasks usually cannot be separated.
    • Separate "succeeded" from "succeeded safely". Reaching the goal by breaking a rule is a failure. Report both counts.
    • Split failures by cause: wrong tool, wrong argument, policy breach, gave up, looped, misreported. The mix says whether to fix tools, prompts or model.
    • Include cost and time: steps, tokens, seconds and AED per task. 40 calls is not the same product as 6. Read them from the trace.

    For long jobs, success is partial: grade checkpoints and where the run went wrong (long-running agents). METR measures how long a task, in human-expert time, an agent completes at a given success rate (R7), which is reliability stretched over duration.

    Online evaluation: what happens once people use it

    Offline tests are a driving test on a closed course; online evaluation is the road. It covers what customers really ask, in Arabic dialects, mixed Arabic-English, typos, and end-of-Ramadan volume spikes. Four layers, cheapest to most conclusive:

    LayerWhat you doWhat it gives youCatch
    1. Shadow modeAgent runs on live requests, output unused. Humans work as before. Compare.Realistic inputs, zero customer risk, agreement with humans.The human decision is itself an imperfect label. No user effect measured.
    2. Passive monitoringLog every run. Track tool errors, escalations, retries, refusals, latency, cost, guardrail triggers.Early warning and drift (F7.7).Says something changed, not whether it is good.
    3. Sampled reviewGrade a random slice of live runs (plus all flagged) with the offline rubric.Unbiased quality estimate on real traffic, and fresh test cases.Costs reviewer time. Needs a random sample, not only flagged cases.
    4. Controlled experimentRandomly route customers to old or new version (A/B test), or ramp traffic.The only clean causal answer to "is the new version better?"Needs traffic, time (Simulation 4) and guardrails in case it is worse.

    At a bank, ramp in stages: shadow mode, then a small share of low-risk requests with human approval on actions, then wider release with automatic rollback if guardrails breach. Which actions may ever run unapproved is a risk decision (M4.5, G3).

    Track two groups of live metrics. Outcome metrics are what the bank wants: resolved without a human, disputes filed correctly, handling time, repeat contact within seven days. Guardrail metrics must not get worse: policy violations, late escalations, privacy incidents, cost per conversation, complaints. Resolution up two points with complaints doubled is not a win. Read both together.

    User feedback: plentiful, biased and easy to misread

    Feedback is like restaurant reviews: the delighted and the furious write them, the content majority stay silent. Explicit feedback is thumbs, stars, "was this helpful?". Implicit feedback is behaviour: rephrasing, asking for a human, abandoning, calling the contact centre an hour later. For staff copilots, the signal is whether the employee accepted, edited or discarded the draft. Both mislead in predictable ways.

    • Non-response bias. Few people press a button, and unhappy people press it far more often. Thumbs-up share is not satisfaction. Simulation 3 shows the gap.
    • Wrong proxy. A confident wrong answer may earn thanks; a correct "no, we cannot reverse that" may earn a thumbs-down. Feedback measures how people felt, which correlates with correctness without being it.
    • Selection. Only people who stayed in the conversation give feedback; those who gave up are missing (F2.6).
    • Gaming. Optimising for thumbs-up breeds agreeable, flattering answers (R4). Staff feedback is skipped when it costs an extra click.
    • Delay. Whether a chargeback succeeded or the customer returned may be known only weeks later, so recent weeks look better or worse than they are (B1).

    What to do about it:

    • Use feedback to find failures, not to measure rate. Every thumbs-down with a comment is a candidate test case. Read them weekly.
    • Measure rate from a random sample you review yourself. A few hundred random conversations graded against a rubric give an unbiased number with an interval.
    • Prefer behavioural outcomes. Repeat contact within seven days is harder to game than a rating.
    • Calibrate the cheap signal against the careful one. Check periodically that any judge or proxy still agrees with human review (M5.3 and M5.4).
    • Close the loop. Promote each confirmed live failure into the offline test set.

    Is the new version better? Detecting a change in a live metric

    Telling a 1-point change from noise is like hearing a whisper in a busy room: you need many samples. Say escalation to a human is 18% and you split customers half and half. The standard two-proportion sample size (F2.7, R8) gives, per arm, about

    n≈2(zα/2+zβ)2p¯(1−p¯)d2

    d is the smallest change worth detecting (as a proportion), p̄ the average rate across arms, and the z values set false alarms (1.96 for 5%) and power (0.84 for 80%), so (1.96 + 0.84)² ≈ 7.85. Halving d quadruples n. Repeat customers are not independent, so multiply by a design effect above 1.

    • Peeking. Checking daily and stopping when it looks good inflates false wins, like re-rolling a die until you get a six. Fix a plan up front, or use a sequential method.
    • Novelty and weekday effects. A new assistant draws curiosity traffic in week one, and demand shifts around salary dates and holidays. Run whole weeks.
    • Non-random routing. Routing by customer type or channel compares different populations. Randomise by customer, not request.

    When traffic is thin, use cheap proxy metrics for quick filtering and keep the slow experiment for decisions that matter.

    Part 3

    How it fails, and how to spot it

    • Grading only the final message

      The agent says the dispute is open. Nobody checked the system of record.

      Spot itAsk what the grader compares the reply to. If it is not a database state or tool log, claims are untested.
    • One run per task

      "92% success" from one attempt per case. Re-running gives 85%, then 90%.

      Spot itAsk how many repeats, whether it is pass@1, pass@k or pass^k, and the spread across repeats.
    • Rigid scripts as the process grade

      The agent is marked wrong for a harmless alternative order, so the team loosens everything.

      Spot itCheck whether rules are constraints ("verify before write") or an exact sequence. Review failures for false rejections.
    • Side effects nobody checks

      The target state is right, but the agent also sent a message, issued a credit, or changed a second record.

      Spot itDiff the full final state against the expected state, not only the fields you hoped would change.
    • A sandbox that is too clean

      Test tools never time out, return tidy data and never conflict. Live systems do all three.

      Spot itAsk which faults were injected: errors, slow responses, empty results, contradictory records.
    • A small task set quoted as a precise number

      "We improved from 74% to 79%" on 50 tasks.

      Spot itAsk for task count and an interval. At 50 tasks it is about ±12 points; the difference is invisible.
    • Thumbs-up as satisfaction

      A dashboard shows 40% positive and nobody asks who presses the button.

      Spot itAsk what share of conversations give any feedback, and for a random-sample review beside it.
    • Optimising the proxy

      The team raises containment (no human needed) and complaints rise because customers cannot reach a person.

      Spot itCheck each outcome metric has a guardrail partner: containment with complaints and repeat contact.
    • A test run that is too short or peeked at

      "It looked better after three days, so we shipped it."

      Spot itAsk for the pre-set duration, the sample-size calculation and whether it covered whole weeks.
    • Judge or benchmark drift unnoticed

      The judge model or harness changed and trend lines move for no real reason.

      Spot itPin versions of judge, harness and prompts. Re-score a frozen reference set after every change.
    Part 4

    Self-check

    1. An agent succeeds at each of 8 steps with probability 96%. What is the chance it completes the task, and the chance it does so on all of 3 repeats?

    0.968 ≈ 72.1% for one run. All three: 0.7213 ≈ 37.5%. At least once in three: 1 − 0.2793 ≈ 97.8%. That gap is pass^k versus pass@k.

    2. Why can a text-only grader give full marks to an agent that did the wrong thing?

    The reply can claim an action that never happened, or describe one on the wrong record, in perfect prose. The grader sees language, not the system. State comparison and trace rules check the world.

    3. Name two reasons to write process rules as constraints rather than a fixed sequence.

    Valid agents reorder harmless steps, so a script rejects good runs and teaches people to ignore the grader. Constraints also state what matters (verify before write, never touch the refund tool) and survive new tools or prompt changes.

    4. You test two agent versions on 80 tasks and get 70% and 76%. Can you say version B is better?

    Almost certainly not. Each standard error is about √(0.73 × 0.27 ÷ 80) ≈ 5 points, so a 6-point gap is inside the noise. Add tasks, repeat runs, and compare per task with a paired method or bootstrap.

    5. Satisfied users give feedback 1.5% of the time and unhappy ones 6%. True satisfaction is 80%. What thumbs-up share will you see?

    Per 1,000 conversations: 800 × 0.015 = 12 positive; 200 × 0.06 = 12 negative. The dashboard shows 50%, against a true 80%. The bias comes from who responds, not from the agent.

    6. What is the difference between an outcome metric and a guardrail metric online? Give a pair for a dispute assistant.

    Outcome metrics are what you want to improve; guardrails must not get worse. Pair: disputes filed correctly without staff rework (outcome) with complaints, policy breaches and repeat contact within seven days (guardrails).

    7. Escalation rate is 18%. You want to detect a change of 2 points with 80% power at 5% significance. Roughly how many conversations per arm?

    p̄ = 0.19, so p̄(1 − p̄) = 0.1539. n ≈ 2 × 7.85 × 0.1539 ÷ 0.02² ≈ 6,040 per arm, before any design effect for repeat customers.

    8. Why should live failures be promoted into the offline test set?

    The offline set is written by people who cannot predict how customers phrase things. Each confirmed live failure is a real miss; adding it prevents regressions and makes the test set resemble real traffic.
