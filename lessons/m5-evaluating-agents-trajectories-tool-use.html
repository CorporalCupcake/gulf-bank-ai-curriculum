    Judging the Path, Then Watching the Live System: Evaluating Agents and Online Feedback

    An agent can reach the right answer by an unsafe route, or announce an action it never took. This lesson covers how to grade trajectories and tool calls, why one success is not reliability, and what to measure once real customers and staff are using the thing.

    Contents

    The whole lesson in one sentenceAn agent is a process, so grade the process (which tools, in what order, with what side effects) as well as the outcome, measure how often it succeeds every time rather than once, and then treat live traffic as the final and most biased test: sparse thumbs, delayed outcomes, and changes that need weeks of data to detect.

    Part 1

    The intuition

    A customer writes: "There is an AED 2,400 payment on my card I did not make." A good human agent verifies identity, finds the transaction, blocks the card, opens a dispute, then explains what happens next.

    An AI agent might end with: "Your card is blocked and a dispute is open." A text grader gives full marks. But perhaps it never called the dispute tool, skipped verification, or issued a refund nobody approved. Like a builder who sends a tidy invoice for work never done, the words were fine and the work was wrong.

    So an agent that acts needs grading on its whole trajectory and the state of the world afterwards. Two more differences:

    • One success proves little. The same agent can pass a task once and fail it the next time. A bank needs "works every time".
    • The test set is not the customer. Live evidence (escalations, rephrasing, thumbs-down) is plentiful but biased and delayed.
    Hold onto thisBefore building any metric, write down three things. What must be true of the world at the end? What must never happen on the way? How many times in a row must it work?
    Part 2

    How it really works

    Grading the trajectory, not only the answer

    A trajectory is the full log of a run: messages, tool calls with arguments, tool results, final reply. No log, no evaluation (tracing). Three kinds of grade, best used together:

    GradeQuestion it answersWeakness
    Outcome (state-based)Is the world in the right state at the end? Compare final database or ticket state to a target.Blind to unsafe routes.
    Process (trajectory-based)Did it get there acceptably? Rules on the call log: required steps, forbidden tools, step budget.Rigid rules punish harmless alternatives.
    Response (text)Did it say the right thing, safely, in the right language?Silent on whether the claims are true.

    Grade the final state against what a correct run would leave, as in τ-bench (Yao et al., 2024). It is like checking the bank's ledger instead of the receipt the clerk handed over. Then add rules for what state cannot show, written as constraints ("verification must precede any write", "no refund tool without approval"), not as a script. Blocking the card before opening the dispute is fine.

    In the simulation, eight runs of one task all end with a friendly message. Toggle graders to see which bad runs each lets through.

    Run G blocks the card before opening the dispute. A rigid "exact sequence" grader fails it, and that false rejection, repeated, trains the team to ignore the evaluation. Aim for rules that fail dangerous runs and nothing else. Also return the reasons: "40% of failures are write before verification" is a fix you can make, where "71% pass" is not.

    Tool use: right tool, right arguments, right moment

    Most agent failures are tool-use failures. Think of a new hire: wrong form, wrong customer number, claiming a task done that they never finished. Test each separately.

    CheckWhat goes wrongHow to test
    SelectionWrong tool, or none when needed.Compare tools called with the expected set.
    ArgumentsRight tool, wrong inputs: the AED 240 transaction instead of AED 2,400.Check against the state the arguments should point to. Schema-valid is not correct.
    Honest reportingSays "done" when the call failed or never happened.Compare each claim in the reply with the log and final state.
    RecoveryOn a timeout, retries blindly, loops, or invents a result.Inject faults: make a tool error and watch what happens.

    Public benchmarks such as the Berkeley Function-Calling Leaderboard help choose a base model but say little about your bank's tools and policies, so build your own task set from real cases (M5.3, A4.1). You also need a sandbox copy of the systems, reset between runs, with seeded customers. That is real engineering effort and separates a serious evaluation from a demo (A4 simulation testing).

    Task success, and why "it worked once" is not a number

    Task success means the end state is right and no rule was broken. Two effects then bite.

    Steps compound. Like a relay team where one dropped baton loses the race, every step must work. At 99% per step a 10-step task works about 90% of the time; at 95% per step, only about 60%. A "98% accurate" model is little better than a coin flip on a 20-step job.

    Repeats compound too. pass@k asks whether at least one of k runs succeeded. It climbs towards 100%, like taking the best of eight tries, and is useful only if a checker picks the good attempt. pass^k asks whether all k succeeded. It falls, and it is what a customer-facing agent needs, since customers get whichever attempt they get. In τ-bench a strong model's retail pass^1 of about 61% fell below 25% at pass^8.

    How to report:

    • Give the success rate with an interval, task count and repeats. "78% on 60 tasks" is about ±10 points (F2.1). Two versions on 60 tasks usually cannot be separated.
    • Separate "succeeded" from "succeeded safely". Reaching the goal by breaking a rule is a failure.
    • Split failures by cause (wrong tool, wrong argument, policy breach, looped, misreported) and include cost and time per task. The mix says whether to fix tools, prompts or model.

    Online evaluation: what happens once people use it

    Offline tests are a driving test on a closed course; online evaluation is the road, with real Arabic dialects, mixed Arabic-English, typos and end-of-Ramadan spikes. Four layers, cheapest to most conclusive:

    LayerWhat you doCatch
    1. Shadow modeAgent runs on live requests, output unused. Compare with humans.Realistic inputs, zero customer risk; the human decision is itself an imperfect label.
    2. Passive monitoringTrack tool errors, escalations, retries, latency, cost (F7.7).Says something changed, not whether it is good.
    3. Sampled reviewGrade a random slice of live runs with the offline rubric.Unbiased quality estimate; costs reviewer time.
    4. Controlled experimentRandomly route customers to old or new version (A/B test).The only clean answer to "is the new version better?", but needs traffic and time.

    At a bank, ramp in stages: shadow mode, then a small share of low-risk requests with human approval on actions, then wider release with automatic rollback if guardrails breach (M4.5).

    Track two groups of live metrics. Outcome metrics are what the bank wants: resolved without a human, disputes filed correctly, repeat contact within seven days. Guardrail metrics must not get worse: policy violations, privacy incidents, complaints. Resolution up two points with complaints doubled is not a win.

    User feedback: plentiful, biased and easy to misread

    Feedback is like restaurant reviews: the delighted and the furious write them, the content majority stay silent. Explicit feedback is thumbs and stars. Implicit feedback is behaviour: rephrasing, asking for a human, abandoning. Both mislead in predictable ways.

    • Non-response bias. Few people press a button, and unhappy people press it far more often. Thumbs-up share is not satisfaction.
    • Wrong proxy. A confident wrong answer may earn thanks; a correct "no, we cannot reverse that" may earn a thumbs-down. Optimising for thumbs breeds flattery (R4).
    • Delay and selection. Whether a chargeback succeeded may be known only weeks later, and people who gave up leave no feedback (B1).

    What to do about it:

    • Use feedback to find failures, not to measure rate. Every thumbs-down with a comment is a candidate test case.
    • Measure rate from a random sample you review yourself. A few hundred graded conversations give an unbiased number.
    • Close the loop. Promote each confirmed live failure into the offline test set, and prefer behavioural outcomes such as repeat contact, which are harder to game than a rating.

    Is the new version better? Detecting a change in a live metric

    Telling a 1-point change from noise is like hearing a whisper in a busy room: you need many samples. Halving the change you want to detect quadruples the conversations needed, and repeat customers (who are not independent) push it higher still. If escalation to a human is 18% and you want to see a 2-point change, expect thousands of conversations per arm (R8).

    • Peeking. Checking daily and stopping when it looks good inflates false wins, like re-rolling a die until you get a six. Fix a plan up front.
    • Novelty and weekday effects. A new assistant draws curiosity traffic in week one, and demand shifts around salary dates. Run whole weeks.
    • Non-random routing. Routing by customer type compares different populations. Randomise by customer, not request.
    Part 3

    How it fails, and how to spot it

    • Grading only the final message

      The agent says the dispute is open. Nobody checked the system of record.

      Spot itAsk what the grader compares the reply to. If it is not a database state or tool log, claims are untested.
    • One run per task

      "92% success" from one attempt per case. Re-running gives 85%, then 90%.

      Spot itAsk how many repeats, whether it is pass@1, pass@k or pass^k, and the spread across repeats.
    • Rigid scripts as the process grade

      The agent is marked wrong for a harmless alternative order, so the team loosens everything.

      Spot itCheck whether rules are constraints ("verify before write") or an exact sequence. Review failures for false rejections.
    • A sandbox that is too clean

      Test tools never time out, return tidy data and never conflict. Live systems do all three.

      Spot itAsk which faults were injected: errors, slow responses, empty results, contradictory records.
    • Thumbs-up as satisfaction

      A dashboard shows 40% positive and nobody asks who presses the button.

      Spot itAsk what share of conversations give any feedback, and for a random-sample review beside it.
    • Optimising the proxy

      The team raises containment (no human needed) and complaints rise because customers cannot reach a person.

      Spot itCheck each outcome metric has a guardrail partner: containment with complaints and repeat contact.
    Part 4

    Self-check

    1. An agent is 96% reliable at each step of an 8-step task. Why is "it works 96% of the time" the wrong summary, and what happens over 3 repeats?

    Steps compound, so the whole task works only about 72% of the time. Needing all three repeats to succeed drops it to roughly 37%, while "at least once in three" climbs to about 98%. That gap is pass^k versus pass@k.

    2. Why can a text-only grader give full marks to an agent that did the wrong thing?

    The reply can claim an action that never happened, or describe one on the wrong record, in perfect prose. The grader sees language, not the system. State comparison and trace rules check the world.

    3. Name two reasons to write process rules as constraints rather than a fixed sequence.

    Valid agents reorder harmless steps, so a script rejects good runs and teaches people to ignore the grader. Constraints also state what matters (verify before write, never touch the refund tool) and survive new tools or prompt changes.

    4. You test two agent versions on 80 tasks and get 70% and 76%. Can you say version B is better?

    Almost certainly not. On 80 tasks each score is uncertain by around five points either way, so a 6-point gap is inside the noise. Add tasks, repeat runs, and compare per task.

    5. Satisfied users rarely press feedback buttons; unhappy ones press four times as often. True satisfaction is 80%. Will the dashboard show about 80%?

    No. Unhappy users are a minority but respond far more, so they are over-represented and the dashboard reads much lower (here about 50%). The bias comes from who responds, not from the agent.

    6. What is the difference between an outcome metric and a guardrail metric online? Give a pair for a dispute assistant.

    Outcome metrics are what you want to improve; guardrails must not get worse. Pair: disputes filed correctly without staff rework (outcome) with complaints, policy breaches and repeat contact within seven days (guardrails).

    7. Why does detecting a 1-point change in escalation rate take so much longer than a 2-point change, and why not just stop when it looks better?

    Halving the change you want to see needs about four times the conversations, because small effects hide in noise. Stopping early when it looks good inflates false wins. Fix the duration up front and run whole weeks.

    8. Why should live failures be promoted into the offline test set?

    The offline set is written by people who cannot predict how customers phrase things. Each confirmed live failure is a real miss; adding it prevents regressions and makes the test set resemble real traffic.
