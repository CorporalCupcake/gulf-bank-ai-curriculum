    The Agent Loop and the Tools It Holds

    What actually makes an agent different from a chatbot, how the reason-act-observe loop runs and where it breaks, and why the design of the tools it can call, far more than the prompt, decides whether it is safe to put near a bank's systems.

    Contents

    The whole lesson in one sentenceAn agent is a language model called in a loop: each turn it may ask a program to run a tool and sees the result before deciding what next. It handles open-ended tasks, but costs you compounding error and a growing context, and its safety comes from the tools you hand it (narrow, well described, permission-checked in code) more than from the prompt.

    Part 1

    The intuition

    A customer messages the bank's app: "My AED 1,850 payment at an electronics shop was declined. Why?"

    A chatbot sees only that sentence. It lists usual causes and guesses, like a call-centre agent with no screen.

    An agent is the same model plus one ability: "before I answer, run this lookup". A program outside the model runs it and returns the result. The agent checks the card, finds the declined attempt, reads the rule that held it, then answers: "Your payment was held for an extra check; the SMS code wasn't completed." Like the same call-centre agent, now with the screen.

    There is no separate "agent brain": just a model, a list of tools, and ordinary code that keeps calling the model until it stops asking for tools.

    • Feedback from the world is the difference. If you already know which facts are needed, pasting them into a chatbot works just as well; the agent earns its place when you cannot know in advance.
    • The model never runs anything. It emits a structured request. Your code decides whether to run it, with whose permissions. All the safety you can build lives in that gap.
    • Each step is a bet. More steps means more chances to err, more tokens and more powers to misuse. Use as few as the task allows.
    Hold onto thisAsk two questions of any agent. What may the loop do on its own, and what stops it? What are all its tools, and what is the worst each can do if misused?
    Part 2

    How it really works

    The agent loop: reason, act, observe

    Under the frameworks, the loop is about fifteen lines:

    messages = [system_prompt, user_request]          # the whole "memory" is this list
for step in range(MAX_STEPS):
    reply = model(messages, tools=TOOL_DEFS)      # one model call
    messages.append(reply)
    if reply.wants_tools:                         # structured tool requests
        for call in reply.tool_calls:
            result = run_tool(call, user_permissions)   # YOUR code, YOUR checks
            messages.append(tool_result(call.id, result))
    else:
        return reply.text                         # model chose to answer: done
raise Stopped("step budget exhausted")            # the loop must always end

    The three beats are reason (work out what is still needed), act (request a tool) and observe (the result is appended). Three things to expect in production.

    • State is just the message list. The model is stateless, like a colleague who rereads the whole case file before every reply. Total tokens grow faster than step count, and long tool outputs cause both cost and confusion.
    • The model decides when to stop, by answering instead of requesting a tool. Nothing guarantees it will, so the harness enforces a step cap, a cost ceiling, a timeout and repeated-call detection. Hitting a limit should hand off to a human, not fail silently.
    • Errors are observations. A failed tool returns its error text and the model adapts. Recovery depends on how useful that message is.

    Workflow versus agent. In a workflow your code fixes the sequence and calls the model at set points, like a recipe. In an agent the model chooses the sequence, like a cook improvising. Use the simplest thing that works: a bank's best early systems are often workflows with one small agentic step, since a fixed path can be tested and audited.

    Why long loops fail: error compounds

    Like a chain of ten links each 95% strong: the chain is weaker than any link. Ten steps at 95% each gives only about a 60% chance that every step is right; twenty steps gives about 36%. Per-step reliability that sounds excellent is poor over a long task. Real errors are messier, since an early wrong observation poisons later steps, but the lesson holds.

    Two levers. Make each step more reliable (better tools, prompts, model). And put checks in the loop: validate arguments, check output against a rule, compare to a second source, retry on failure. A check turns a silent wrong answer into a retry or a safe stop, like a smoke alarm.

    Do not ask only "how smart is the model?" Ask how many steps, how likely each is to fail, which failures a check could catch, and what happens on the paths it misses. "Wrong and nobody noticed" is the column a bank cares about.

    Designing tools an agent can use safely

    A tool is a function plus a description. The model never sees your code, only a name, a description and an argument schema. So the description is the interface: write it like documentation for a new colleague.

    // Broad: one sharp tool that can do anything
{ "name": "run_sql",
  "description": "Run a SQL query on the bank database.",
  "input_schema": { "query": "string" } }

// Narrow: one tool, one job, bounded, says when NOT to use it
{ "name": "list_recent_declines",
  "description": "Return the signed-in customer's declined card payments from the
     last 30 days, newest first, max 10. Each item has time, amount_aed, merchant,
     and reason_code. Use this to explain why a payment failed. Do NOT use it for
     settled payments; use list_transactions for those.",
  "input_schema": { "card_id": "string, from get_cards", "limit": "integer 1-10" } }

    The second is easier to choose and harder to misuse, and its worst case is small and known. Like handing a contractor one labelled key, not the master key.

    • Narrow beats general. One tool, one business action. A wrong query from run_sql has no ceiling on what it reads.
    • Permissions live in the tool, not the prompt. "Only look at the signed-in customer" in a prompt is a request; a tool that takes identity from the session and ignores any id the model supplies is a guarantee. Run tools with the end user's entitlements, never a broad service account. A prompt can be argued with, including by a malicious document (indirect prompt injection); code cannot.
    • Rank writes by reversibility. Reads can be liberal. Blocking a card is reversible; sending money or messaging a customer is not. Irreversible tools get hard limits, idempotency keys (a retry cannot pay twice) and human approval (M4.5).
    • Return small results and teaching errors. 40,000 tokens of raw JSON buries the answer, and "Error 400" is useless. "amount_aed must be 1 to 5,000; you sent 50,000" lets the model recover. Treat its arguments as untrusted input and validate them in code.
    • Log every call: who, tool, arguments, result. That is how you debug, evaluate (M5.5) and show an auditor (P2.5).

    Blast radius is how to judge a tool set: if the model were wrong or hijacked for the whole step budget, what is the most it could do? 1 record and AED 200 is a very different system from 2,000,000 records. Simulation 3 does the sum.

    Controls are layers: scoped tools bound the damage, limits bound it again, approval catches some of the rest, monitoring catches leaks. Keep approval for the few irreversible actions and show reviewers the consequence in plain words.

    Part 3

    How it fails, and how to spot it

    • An agent where a workflow would do

      A fixed three-step process wrapped in an open-ended loop adds cost and unpredictability for nothing.

      Spot itIs the sequence the same for 90% of requests? If yes, make it code, with a model call where language is needed.
    • No stop condition

      The model repeats the same failed call or wanders, burning tokens until a timeout.

      Spot itLook for hard limits on steps, tokens and time, repeated-call detection, and a defined hand-off to a human.
    • Error compounding hidden by demos

      Five clean demo runs, then a poor first month, because each step is 95% reliable and the task has 15 steps.

      Spot itAsk for success over many runs of the same tasks, not one run, and failure counts per tool.
    • Confident answers from an empty or failed tool result

      The lookup returns nothing or errors, and the model fills the gap with plausible text. Wrong tool choices and invented arguments (a made-up customer id) are the same family.

      Spot itTest with tools that return empty, error and time out. The answer should say it could not find the data, and arguments should come from earlier results or the user, never from nowhere.
    • Permissions in the prompt, or a broad service account

      "Never reveal other customers' data" in the prompt, while the tool accepts any customer id or runs with the bank's integration credentials.

      Spot itCall the tool directly with another customer's id, and test with a low-privilege user. If it answers, the control is only text.
    • Irreversible tools without limits, and gates nobody reads

      Send-money or close-account tools callable directly, or approvals that reviewers click through at 400 a day.

      Spot itList every write tool with its limits, idempotency and approval rule; a blank cell is a finding. Measure rejection rate and time per approval: near zero means the gate is not a control.
    Part 4

    Self-check

    Try each one before opening the answer.

    1. In one sentence, what is an agent, and who actually runs the tool?

    A language model called repeatedly in a loop, where it may request tools and sees their results before choosing its next step. The harness (ordinary code) runs the tool; the model only emits a request.

    2. Each step is 98% reliable, and the task has 25 steps. Is the whole task about 98% reliable, and what does that tell you about long tasks?

    No, it is far lower, roughly 60%, because small per-step failures multiply. Reliability that sounds excellent per step is poor over a long task, so shorten the task or add checks.

    3. Why does adding a check that catches most wrong steps help so much, even though it is not perfect?

    It turns a silent wrong answer into a retry or a safe stop. Only the errors the check misses stay silent, so "wrong and nobody noticed" drops sharply. A check that catches nothing makes retries useless.

    4. Why does the total tokens processed by a ten-step agent grow faster than ten times a one-step call?

    Each step re-sends the whole transcript so far, including all earlier tool results. Contexts keep growing, so total cost climbs faster than the step count, especially if results are large.

    5. A system prompt says "only access the signed-in customer's data", but the tool takes a customer_id argument. What is wrong and what is the fix?

    The restriction is only text, and the model (or an injected instruction) can pass any id. Take the identity from the authenticated session inside the tool and ignore any id the model supplies.

    6. Rewrite the tool description "get data: gets data for a customer" into something a model can use well.

    Name it for the job, e.g. get_card_status. Say what it returns, what input it needs and where that comes from, when to use it (explaining a decline), and when not to (transaction history).

    7. In Simulation 3, which control most reduces the "AED that could leave" figure and which the "records readable" figure?

    AED: dropping or capping the transfer tool, then the approval gate. Records: replacing run_sql with scoped read tools. Different risks need different controls; approval gates do nothing for read exposure.

    8. When should you build a workflow instead of an agent?

    When the steps are the same for nearly every request, or errors are costly and testability matters. Use the model where you need language understanding and keep the control flow in code.
