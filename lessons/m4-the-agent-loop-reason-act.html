    The Agent Loop and Tools

    Part 1

    What an agent is

    In one sentenceAn agent is a language model that can ask for tools to be run, with ordinary code that keeps calling the model until it gives a final answer.

    Running example: a customer messages the bank's app, "My AED 1,850 payment at an electronics shop was declined. Why?"

    • A chatbot sees only that sentence. It lists the usual causes and guesses, like a call-centre agent with no screen.
    • An agent can say "look up this customer's declined payments", get the result, read the rule that held the payment, then answer: "It was held for an extra check; the SMS code was not completed." Same person, now with a screen.

    There is no special "agent brain". It is a model, a list of tools, and a loop.

    How it differs from similar things

    • Chatbot: one reply from what it already knows. No feedback from the world.
    • Workflow: your code fixes the sequence (look up, then summarise) and calls the model at set points. Like a recipe.
    • Agent: the model chooses the sequence. Like a cook improvising. Use the simplest option that works: a fixed workflow with one small agentic step is easier to test and audit.
    Part 2

    How the loop works

    1. Start a message list: the instructions, the tool descriptions and the customer's question.
    2. Call the model with that list.
    3. If it asks for a tool, your code checks the request and runs it with the customer's own permissions.
    4. Add the result to the list and go back to step 2.
    5. If the model answers instead, return the answer. Stop at a step limit either way.

    The three beats are reason (what is still missing?), act (request a tool) and observe (read the result). Three facts follow.

    • The message list is the only memory. The model re-reads all of it every call, so long tool outputs raise cost and cause confusion.
    • The model decides when to stop, and nothing guarantees it will. Your code sets a step cap, a cost ceiling and a timeout. Hitting one should hand over to a human.
    • Errors are just results. A failed tool returns its error text and the model can adapt, if the message is useful.

    Why long loops fail

    Think of a chain of links. If each step is right 95% of the time, ten steps give about a 60% chance that all are right, and twenty give about 36%. Per-step quality that sounds excellent is poor over a long task.

    The fix is to make each step better and to add checks: validate arguments, compare against a rule or a second source, retry on failure. A check turns a silent wrong answer into a retry or a safe stop.

    Part 3

    Tools, and how to judge them

    A tool is a function plus a description. The model never sees your code, only a name, a description and the arguments it takes. So the description is the interface: write it like notes for a new colleague.

    Broad toolNarrow tool
    Examplerun_sql: run any query on the bank databaselist_recent_declines: this customer's declined payments, last 30 days, max 10
    Worst case if misusedReads any tableReads ten of one customer's own records
    Easy for the model to choose?NoYes, and the description says when not to use it

    Rules for safe tools

    • One tool, one job. Narrow tools have a small, known worst case.
    • Permissions live in the tool, not the prompt. A tool that takes the customer's identity from the session and ignores any id the model supplies is a guarantee. "Only look at this customer" in a prompt is a request, and a malicious document can argue against it.
    • Rank by reversibility. Reading is low risk. Blocking a card can be undone. Sending money cannot, so give it hard limits and human approval.
    • Return small results and helpful errors. "amount_aed must be 1 to 5,000; you sent 50,000" lets the model recover. "Error 400" does not.
    • Log every call: who, which tool, arguments, result. This is how you debug and how you answer an auditor.

    How to judge a tool set: blast radius

    Ask: if the model were wrong or hijacked for the whole step budget, what is the most it could do? One record and AED 200 is a very different system from two million records and an uncapped transfer.

    Ask two questions of any agent. What may the loop do on its own, and what stops it? What are all its tools, and what is the worst each can do?

    Part 4

    Which to use

    OptionChoose it whenMain risk
    Chatbot with pasted factsYou already know which facts are neededNone new
    Fixed workflowThe steps are known in advanceRigid on odd cases
    AgentYou cannot know in advance which lookups are neededErrors compound, cost grows, powers get misused
    • Agents are strong at open-ended tasks where each step depends on the last result.
    • Agents are weak at long tasks, predictable cost, and anything irreversible without checks.

    In banking, the best early systems are often workflows with one small agentic step, because a fixed path can be tested and audited. Read-only tools come first; money-moving tools come last, behind approval.

    Part 5

    Common mistakes and quick check

    • No step cap

      A loop that can run forever will, sooner or later. Always cap steps, cost and time, and hand off to a human.

    • One powerful general tool

      A tool like run_sql has no ceiling on what a wrong request can read.

    • Enforcing rules in the prompt

      Prompts can be argued with. Put limits and permissions in code.

    • Judging only by model quality

      Also count steps, per-step failure rate, and what happens on the failures no check catches.

    1. Who actually runs a tool: the model or your code?

    Your code. The model only writes a structured request.

    2. What is the agent's memory?

    The message list, which the model re-reads on every call.

    3. Ten steps, each 95% reliable. Roughly how often is every step right?

    About 60%.

    4. Which is riskier: block_card or send_payment?

    send_payment, because it cannot be undone. It needs limits and human approval.

    5. Why is a narrow tool safer than a broad one?

    Its worst case is small and known, and the model finds it easier to pick correctly.
