    Prompting and Context Engineering

    Part 1

    What prompting and context engineering are

    In one sentenceA language model only sees the text you send it on each call, so prompting is writing that text well, and context engineering is deciding what goes into it and what stays out.

    Think of a capable analyst who arrives every morning with no memory of your company. Whatever is on their desk is all they know, and they fill any gap with a plausible guess. The desk is the context window: the model's limited working space, measured in tokens (small chunks of text, roughly three-quarters of a word each).

    Our running example is an assistant that reads customer emails and sorts them into a category with an urgency level.

    How it differs from other ways of adapting a model

    • Prompting changes only the text you send. It is cheap, instant and reversible.
    • Retrieval (RAG) is one way to fill the desk: it searches your documents and pastes the relevant ones in. Context engineering decides how much of that to use.
    • Fine-tuning changes the model itself. Prompting never touches the model.

    The next lesson compares these three. This one is about getting the most from the first.

    Part 2

    How to write a good prompt

    A prompt is one long run of text. The model predicts what comes next. The chat labels (system, user) are just markers it was trained to treat differently: the system message is the standing brief, and the user message is the request.

    1. Role and goal. "You sort customer emails into a category and an urgency level."
    2. Reference material. Policy text or documents, each labelled with its source so the model can tell data from instructions.
    3. Examples. Two to five finished cases, including one tricky one. Five "approve" examples will tilt the answer towards approve, so vary them.
    4. The request. Put the new email last, close to where the model starts writing.
    5. Output format. Say exactly what shape the answer must take, and what to do when information is missing ("answer UNKNOWN, do not guess").

    How to think about instructions

    • They are nudges, not rules. The model follows "never reveal an account number" most of the time, and "most" is the problem. A rule that must always hold belongs in code.
    • The model cannot ask what you meant. Spell out what a good answer looks like.
    • It is stateless. "Memory" means you resend earlier text, and you pay for it again on every call.
    • Reasoning steps help on hard cases. Asking it to think first costs more tokens. The written reasoning is not a reliable account of why it answered, so it is not an audit trail.
    • Position matters. Models use the start and end of a long prompt better than the middle. Put standing rules first and the question last.
    Part 3

    Context engineering: managing the desk

    Real systems make many calls, and the desk changes at each one. A bigger window did not remove the need to manage it: everything on the desk costs money and time, and models attend less reliably to a crowded one. Treat context as a budget, not a bin.

    1. Select. Bring in only what this step needs. If the right clause is not on the desk, no wording will conjure it.
    2. Compress. Summarise old turns and trim tool results. A 400-line transaction dump becomes the 10 relevant rows.
    3. Isolate. Give sub-tasks their own small calls and pass back only the conclusions.
    4. Persist. Write facts needed later to a store and reload them on demand.

    The aim is the smallest set of useful tokens that makes a good answer likely. Add context only when it raises your evaluation score.

    How to read the cost

    • Tokens times calls. A 10,000-token prefix sent 50,000 times a day is 500 million tokens a day. Cutting it to 4,000 removes most of that bill.
    • Stable text first. Providers can cache a repeated prefix and charge less for it. Changing early text breaks the cache for everything after it.
    • Check before trimming. Confirm on a set of labelled examples that accuracy holds with the slimmer context.
    Part 4

    Getting back something a system can use

    "This looks like a fairly urgent card complaint, I'd say..." cannot be routed. A JSON object (a structured record of named fields) can. There are three levels of reliability:

    • Ask nicely ("reply in JSON"). Sometimes fails with a stray sentence or a missing field. Prototype only.
    • JSON mode. The syntax is valid, but the fields may not be yours.
    • Schema-constrained output. You supply a schema (a description of the allowed fields and values) and the decoder blocks any token that would break it. It is like a form that will not let you type letters into a number box.

    Design tips: use fixed choices (enums) instead of free text, add an "other" option so the model is not forced to invent, and keep the schema small. Put a short evidence quote before the decision field, since fields are written in order.

    The limit: constrained output guarantees the form, not the truth. A perfectly filled form can still carry the wrong answer. Errors also compound: if each field is right 97% of the time, a record with 12 fields is fully right only about 69% of the time.

    Tool calling: the model asks, your code acts

    A model cannot look up a balance or block a card. It can write a structured request, and your code decides whether to run it.

    • The description is part of the prompt. "Gets data" is useless. "Returns the status of one card for the signed-in customer; does not return transactions" works.
    • Separate reads from writes. Blocking a card or moving money needs confirmation, and the permission check lives in your code using the real user's identity, not what the model says.
    • MCP (Model Context Protocol) lets one tool server serve many applications.
    Part 5

    Which tool for which job

    TechniqueUse it forGuaranteesWeak at
    Clear prompt with examplesBehaviour, tone, formatNothing; it is a nudgeHard rules
    Context selectionGiving the right factsOnly what you retrieveFacts you never fetched
    Schema-constrained outputFeeding other systemsThe form of the answerWhether the values are true
    Checks in codeRules that must always holdThe rule, every timeJudgement and wording

    Prompting is strong at:

    • Speed. You can test a change in minutes.
    • Flexibility. One model handles many tasks by changing the text.

    It is weak at:

    • Guarantees. The model usually obeys, until it does not.
    • Large or private knowledge. The desk is small, and everything on it is paid for on every call.

    In banking, a rule such as "no card is blocked without customer confirmation" lives in the code that runs the tool, and the prompt only repeats it.

    Part 6

    Common mistakes and quick check

    • Tuning the prompt on three examples

      It works on the demo, then a long email or an Arabic dialect breaks it. Score it on a labelled set of real cases.

    • Stuffing the window

      "The window is 200,000 tokens, so put everything in" buries the key clause. Try only the top few passages.

    • Treating a valid schema as a correct answer

      The JSON parses and one field is wrong. Measure accuracy per field and per record against human labels.

    • Keeping hard rules only in the prompt

      For every rule that must hold, find the code that enforces it.

    1. Why does a model with no memory still seem to remember a chat?

    Your app resends the earlier turns with every call. You pay for them each time unless the provider caches the shared prefix.

    2. You extract 12 fields per record and each is right 97% of the time. How often is a whole record right?

    About 69%, because errors compound. Report accuracy per record as well as per field, and send doubtful records to a person.

    3. Constrained output is on and parse errors drop to zero. Is the system reliable?

    No. Only the form is guaranteed. Wrong values remain, and being well formed they are harder to notice.

    4. Answers got worse after you added 15 policy documents to every call. Why might that be?

    The relevant clause is diluted among distractors or sits in the weak middle of the prompt. Try fewer, better-ranked passages with the question at the end.

    5. A tool description says only "Gets customer info". What goes wrong?

    The model cannot tell when to call it or what it returns. State what it returns, what it does not, and the argument formats.
