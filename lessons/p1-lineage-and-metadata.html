    Lineage, Columnar Formats and Spark: Knowing Where Data Came From and Moving It Fast

    How a number is traced back to its source for an auditor, why Parquet and DuckDB scan billions of rows in seconds by reading less, and what changes when the data no longer fits on one machine: partitions, shuffles and lazy plans.

    Contents

    The whole lesson in one sentenceLineage is a recorded map of how every number was made, answering "where did this come from" and "what breaks if this changes"; columnar files are fast because the engine skips almost everything it does not need; Spark is for when one machine truly is not enough, at the price of a shuffle that a single hot key can wreck.

    Part 1

    The intuition

    The auditor. An examiner points at AED 1.84 billion to one corporate group in a large-exposures return: "Show me where that came from." If the answer is "a query someone wrote two years ago, in a notebook since deleted", the problem is bigger than the number. Lineage is the recorded chain from source system to final figure, like the receipts behind an expense claim. Metadata, data about data, makes the chain readable: owner, column meanings, last refresh, how it was built.

    The slow query. An analyst filters 50 million card transactions to one day and averages two columns. On CSV the engine reads every byte, around 16 GB. On columnar Parquet it reads two columns and skips 49 of 50 row blocks using stored minimum and maximum values: perhaps 15 MB. Same answer, a thousand times less work, like using a book's index instead of reading every page. It is layout, not magic.

    The big job. The nightly feature build joins two billion transactions to customers and will not fit on one machine. Spark splits the data into partitions across many machines. A join or group-by needs rows with the same key together, forcing a shuffle: every machine sends pieces to every other, like postal sorters passing bundles until each town's mail is in one bin. Shuffles are where the time goes and where things break.

    That graph walk is all lineage is as a tool: a directed graph of "produced from" edges, searched upstream for an audit and downstream for impact. The hard part is keeping the graph complete and current without hand maintenance. The Excel override above is the classic failure: the number came from somewhere the catalogue never saw.

    Columnar storage and Spark both avoid work: columnar formats avoid reading bytes, Spark avoids waiting by splitting the job. Try the smaller tool first.

    Hold onto thisEvery published number needs three answers: where did it come from, what happens if its inputs change, and can we recompute it. Lineage covers the first two; reproducible pipelines the third. Speed (Parquet, Spark) matters only after these.
    Part 2

    How it really works

    Lineage and metadata (P1.5)

    Metadata comes in four useful kinds.

    KindExamplesWho needs it
    TechnicalSchema, column types, file format, partition layout, row counts, table versionEngineers; query engines
    Business"Exposure" means drawn plus undrawn, in AED, at month end; glossary terms; data owner and stewardAnalysts, risk, auditors
    OperationalLast successful run, duration, rows in and out, failed checks, freshnessOn-call engineers; monitoring
    GovernanceSensitivity class (PII), retention period, access policy, approved usesCompliance, privacy, security

    Lineage comes at three grains, and the grain decides which questions you can answer.

    • Table-level: gold.exposure_aed was built from clean.transactions and clean.customers. Cheap, and enough for most impact analysis.
    • Column-level: exposure_aed comes from amount × fx_rate, with fx_rate from the raw FX feed. An auditor asking about one figure needs this, and so does a privacy officer asking "which downstream columns contain a national ID". Harder, because it means parsing every expression.
    • Run-level: this exact run, at 02:14 on 3 March, read these table versions with this code commit. This makes a number reproducible, not just explainable.

    Capture methods, weakest to strongest:

    1. By hand. A diagram or spreadsheet. Right on day one, wrong within weeks. A starting point, never evidence.
    2. Parsed from code. A tool reads SQL or dbt models and infers the graph from FROM and JOIN. Gives column-level lineage for SQL; misses logic in Python or UI tools.
    3. Emitted at runtime. The scheduler or engine reports "job X read A and B and wrote C" as it runs. OpenLineage is the open standard, with integrations for Airflow, Spark and dbt; Marquez and DataHub can store the events. It captures what actually ran, including Python.

    Even runtime capture has holes: a hand-run notebook, an Excel file, a CSV emailed to treasury, a manual adjustment. Make these rare, register them as owned sources, and flag any dataset whose lineage ends at "unknown".

    Why a bank cares. The Basel Committee's BCBS 239 principles on risk data aggregation ask large banks for accurate, complete, timely data with clear ownership and a documented, reconstructable path from source to report. The text speaks of data "taxonomies and architecture", not lineage tools, so a catalogue is a means, not a requirement. Which local rules (CBUAE, SAMA) bind your institution is a question for compliance and model risk; check before asserting it.

    Lineage for models. A prediction is auditable only if you can name the model version, training dataset version, feature definitions and code commit. A model is just another node in the graph, and a key one for validators (G3.2). P2.1 builds the full lifecycle on this.

    Contracts and checks are the other half of metadata. A data contract states what a producer promises (schema, freshness, null rates). A failed check is operational metadata that should stop downstream jobs. Lineage tells you who is affected when a contract breaks.

    Columnar formats and query engines (P1.6)

    A table is a grid, but a file is a line, so you must choose how to flatten it. Think of a spreadsheet saved either row by row or column by column.

    • Row layout (CSV, a database page): all fields of row 1, then row 2. Ideal for "fetch customer 4021" or "insert one payment". This is how transactional databases work.
    • Column layout (Parquet, ORC, Arrow in memory): all values of column 1, then column 2. Ideal for "average amount for last Tuesday", which touches 2 of 40 columns. Analytics wants a few columns across many rows.

    Parquet is a hybrid. A file is cut into row groups (often about a million rows or 128 MB; a writer setting). Within each, each column is a contiguous column chunk, split into pages. A footer lists every chunk's location and statistics, including minimum and maximum. Four tricks follow.

    1. Projection pushdown. Read only the columns named. 4 of 40 columns is a 10x cut at once.
    2. Predicate pushdown (zone maps). For WHERE txn_date = '2026-03-03', a row group whose min and max for txn_date span 1–2 March cannot contain it and is skipped unread, like skipping a shelf labelled A–C when you want a surname starting with M. It only pays when similar values sit together, so sorting or clustering by the filter column is the biggest tuning step.
    3. Compression that works because values are alike. A column holds one type with few distinct values (currency, channel, branch). Dictionary encoding swaps "AED" for a small integer; run-length encoding turns "AED, AED, AED..." into "AED × 40,000"; delta encoding stores sorted timestamps as small differences. zstd or Snappy squeezes further. 3x to 10x against CSV is typical, depending on the data.
    4. Vectorised execution. Engines like DuckDB process batches of a couple of thousand values, not one row at a time, so the CPU runs tight loops with good cache use and SIMD. This (from MonetDB/X100) is why a laptop scans hundreds of millions of rows a second.

    Where the engines fit. Parquet is only storage; a query engine reads it. DuckDB runs inside your Python process, reads Parquet, CSV, JSON and in-memory pandas or Arrow tables directly, and runs SQL with the vectorised tricks above. On a laptop or 32-core server it handles tens to hundreds of GB. Polars is the DataFrame-style equivalent. Spark, Trino and cloud warehouses spread the same ideas over many machines. Arrow is the in-memory columnar format that lets these tools exchange data without converting it.

    import duckdb

# Reads only 3 columns, and skips row groups whose txn_date range excludes the day
duckdb.sql("""
    SELECT channel, count(*) AS n, avg(amount_aed) AS avg_aed
    FROM 'txns/*.parquet'
    WHERE txn_date = DATE '2026-03-03'
    GROUP BY channel
""").df()

# What would it do? Look for the pushed-down filter and projected columns in the plan
duckdb.sql("EXPLAIN SELECT channel FROM 'txns/*.parquet' WHERE txn_date = DATE '2026-03-03'")

    Row layout still wins sometimes. Fetching one account 10,000 times a second, or inserting and updating single rows, is transactional work: a row store with an index wins (the offline versus online split of P1.4). Parquet files are also immutable. Delta Lake and Apache Iceberg add a transaction log on top for updates, deletes, time travel and schema evolution: the lakehouse idea of P1.1 to P1.3.

    Habits:

    • Write Parquet, not CSV, for anything analytic.
    • Aim for files of 100 MB to 1 GB; thousands of tiny files are slow, since each costs a metadata fetch.
    • Partition directories by a low-cardinality column you filter on, usually date; sort within files by the next most common filter.
    • Never partition by customer ID: millions of directories.

    Spark and distributed processing, in brief (P1.7)

    Architecture. A driver plans the job. Executors, processes on many machines, do the work. Data lives as partitions (chunks of rows); each is processed by one task on one core. With 64 cores and 200 partitions, tasks run in waves of 64.

    Lazy evaluation. Like writing a shopping list before going to the shop, transformations (filter, select, join, groupBy) only add steps to a plan. An action (count, show, collect, a write) runs it. The Catalyst optimiser then sees the whole plan, pushes filters and column choices down to the Parquet scan, reorders joins and fuses steps. The cost: an error in line 3 may surface at line 40, and a reused DataFrame is recomputed each time unless cached.

    from pyspark.sql import functions as F

txn  = spark.read.parquet("s3://bank-lake/clean/transactions")      # nothing read yet
cust = spark.read.parquet("s3://bank-lake/clean/customers")

feat = (txn.filter(F.col("txn_date") >= "2026-01-01")             # transformation
           .join(cust, "customer_id")                                 # wide: shuffle
           .groupBy("customer_id")                                    # wide: shuffle
           .agg(F.sum("amount_aed").alias("spend_ytd")))

feat.write.mode("overwrite").parquet("s3://bank-lake/gold/feat")      # action: runs it all
feat.explain()   # prints the physical plan: look for Exchange (= shuffle)

    Narrow and wide. A narrow transformation (filter, select, map) works on each partition alone: cheap, no network. A wide one (join, groupBy, distinct, sort) needs all rows with the same key in one place. Spark hashes the key and sends each row to the partition that owns it, across the network, often via disk. That is the shuffle, shown as Exchange in a plan; a job is cut into stages at each one. Rule: count your shuffles and shrink the data before them.

    Three things that go wrong.

    • Skew. A key held by many rows lands in one partition, so one task works while the other cores idle, like one till with a queue while the rest stand empty. Banking examples: a null or "UNKNOWN" merchant ID, a default branch code, a corporate payroll account. A stage lasts as long as its slowest task.
    • Too few or too many partitions. Too few leaves cores idle and tasks too big for memory; too many lets scheduling overhead dominate. Start at two to four partitions per core, each roughly 100 to 200 MB.
    • Pulling data to the driver. collect() or toPandas() on a big result crashes the one machine never meant to hold it.

    Standard remedies.

    • Broadcast join: send a small table to every executor so the big one is never shuffled (a 50 MB branch lookup against a billion transactions).
    • Adaptive query execution (default in recent Spark): re-plans at run time, merging small partitions, switching to a broadcast join when a side is small, and splitting skewed join partitions.
    • Salting: add a random suffix to a hot key so its rows spread out, at the cost of a second aggregation to combine them.

    Spark is not the default. Its overhead (JVM, scheduler, shuffle) is large, like hiring a removals lorry to carry one box. Below roughly 100 to 500 GB of Parquet, DuckDB or Polars on one big machine is often faster, cheaper and easier to debug. Spark earns its place at genuine terabytes, when a join needs many machines' memory, or when your platform (Databricks, Hadoop-style, Spark on Kubernetes) already runs on it. Test first: run the single-machine tool on a sample and extrapolate.

    Part 3

    How it fails, and how to spot it

    • Lineage that ends at a person

      The trail stops at "the treasury spreadsheet". The catalogue looks complete; the audit answer is not.

      Spot itWalk each key figure back to a system of record. Any dataset with no upstream, or a human-edited file in the middle, is a gap to register and own.
    • Lineage as a one-off diagram

      A map drawn before an audit; a year on, half the jobs have changed.

      Spot itAsk when it was last generated and from what. If the answer is a person, it is stale. Look for a "last captured" timestamp per edge.
    • Table-level lineage used to answer column-level questions

      "Which reports contain national ID?" answered with "every report downstream of the customer table". Overstates, or misses derived columns.

      Spot itAsk the grain, and whether it follows expressions such as hashing and concatenation.
    • A definition that exists only in a dashboard

      Two reports show different "active customers" because each defines it in its own query.

      Spot itAsk where the metric is defined. There should be one governed definition, referenced by both.
    • CSV, or many tiny Parquet files, in a big analytic pipeline

      Slow scans, big storage bills, jobs spending their time opening files.

      Spot itCount files and average size. Thousands of files under 10 MB, or any CSV above a few GB, need compaction or conversion.
    • Filters that cannot be pushed down

      A filter wrapped in a function (WHERE substr(txn_ts, 1, 10) = ...) or applied after a join defeats zone maps and partitions, so everything is read.

      Spot itRun EXPLAIN. The scan should show the filter and projected columns, and read a small share of the table.
    • Partitioning on a high-cardinality column

      Partitioning by customer ID or by minute produces millions of small directories and files.

      Spot itHundreds to a few thousand partitions is reasonable; millions is a bug.
    • Skewed keys that make a stage hang at 99%

      199 of 200 tasks finish quickly; one runs for an hour, usually on null, "UNKNOWN" or a default code.

      Spot itIn the Spark UI, compare task durations in the slow stage. One far above the median is skew. Count rows per join key to find it.
    • Using a cluster where one machine would do

      A 40 GB table on a 20-node cluster that takes longer to start than DuckDB takes to finish.

      Spot itCompare data size with one machine's memory; time a single-node run on a sample first.
    • Surprise from lazy evaluation

      Code "runs" instantly and fails later, or a DataFrame is recomputed five times, or a random sample differs between actions.

      Spot itCheck the physical plan and job count in the UI. Repeated identical scans mean a missing cache.
    Part 4

    Self-check

    1. What is the difference between audit lineage and impact analysis, and what graph operation is each?

    Audit asks "what does this figure depend on": search upstream from the figure. Impact asks "what is affected if this changes": search downstream from the source. Same graph, opposite directions.

    2. Why is table-level lineage not enough for a privacy question such as "where does national ID flow"?

    A table may have 80 columns and only one holds the ID. Table-level lineage flags every downstream table. Column-level lineage follows that column and its derivatives, so you can say which reports truly contain it.

    3. A table has 40 columns of 8 bytes and 50 million rows. A query touches 4 columns and one day of 30 (clustered by date). Roughly what does it read in a row store versus Parquet at 30% compression?

    Raw size is 50M × 40 × 8 = 16 GB, which a row store reads in full. Parquet reads 4 columns: 4 × 0.4 GB = 1.6 GB raw, × 0.3 = 0.48 GB. Zone maps keep roughly 1/30 of the row groups (the next whole group, so 2 of 50 here): 0.48 × 2/50 ≈ 19 MB. About 800 times less.

    4. Why does clustering by date matter for zone maps?

    A block is skipped only if its min/max range excludes the filter value. With dates mixed throughout, every block spans the whole range and none is skipped. Sorted by date, each block covers a narrow range and most are skipped.

    5. Name a transformation that causes a shuffle and one that does not. Why the difference?

    filter and select work on each partition independently, so no shuffle. groupBy and a join on a non-broadcast table need all rows with the same key in the same partition, so rows must be sent across the network to the partition that owns their key hash.

    6. In Spark you write ten lines of transformations and nothing happens. Why, and what is the benefit?

    Transformations are lazy: they add steps to a plan, and only an action runs it. The optimiser sees the whole plan, so it can push filters and columns down to the scan, choose join strategies and fuse narrow steps. The cost: errors appear late and reused results are recomputed unless cached.

    7. With 200 million rows, 64 cores and 20% of rows on one key, why does raising shuffle partitions from 200 to 2,000 barely help?

    Every hot-key row goes to one partition however many exist: 40 million rows, versus about 0.8 million in each other partition at 200. The stage lasts as long as that task. Salt the key, broadcast the smaller side or let adaptive execution split it.

    8. When is DuckDB the better choice than Spark?

    When the working data, after column selection and filters, fits on one machine (often hundreds of GB). It starts instantly, needs no cluster and is easy to debug. Spark wins when data or memory exceed one node, or the platform is already built on it.
