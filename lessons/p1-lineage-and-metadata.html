    Lineage, File Formats and Spark

    Part 1

    What these three things are

    In one sentenceLineage is the recorded trail from a source system to a final number, Parquet is a file format that stores data column by column so queries read less, and Spark is a tool that splits a big job across many machines.

    Picture a bank with one running example: a regulator's large-exposures return, built from card and loan transactions plus an exchange-rate feed. An examiner points at AED 1.84 billion owed by one corporate group and asks, "Show me where that came from."

    Three different problems follow from that single question. Can we prove where the number came from (lineage)? Can we compute it quickly (file format)? Can we compute it at all when the data is huge (Spark)?

    Part 2

    How they differ from things you know

    • Lineage vs a data dictionary. A dictionary says what a column means. Lineage says where it came from and what it feeds. Both are metadata, meaning data about data.
    • Parquet vs CSV. CSV stores one row after another, like a spreadsheet saved line by line. Parquet stores one column after another, so a query touching 2 of 40 columns reads only those 2.
    • Spark vs pandas. Pandas works on one machine and needs the data to fit in memory. Spark spreads the same sort of work (filter, join, group) over many machines.
    • Parquet vs a database. Parquet is only a file. A query engine (DuckDB, Spark, a cloud warehouse) reads it and runs the SQL.
    Part 3

    How each one works

    Lineage and metadata

    1. Record each step. Every job notes which datasets it read and which it wrote. The scheduler can emit this automatically; OpenLineage is the open standard.
    2. Join the records into a graph. Datasets are nodes and "was built from" links are arrows.
    3. Walk the graph. Walk backwards for an audit ("where did this come from?") and forwards for impact ("what breaks if the FX feed is wrong?").

    Lineage comes at three levels of detail. Table-level says table A was built from tables B and C. Column-level says exposure_aed is amount × fx_rate. Run-level says this exact run used these data versions and this code commit, which makes the number reproducible, not just explainable.

    Columnar files (Parquet)

    1. Store by column. All amounts together, all dates together.
    2. Cut into row groups. Each block of rows records the minimum and maximum of every column.
    3. Skip what you can. For "one day only", a block whose dates span other days is never read. This is called predicate pushdown. Reading only the named columns is projection pushdown.
    4. Squeeze. Similar values sit together, so files are typically 3x to 10x smaller than CSV.

    The example: averaging two columns for one day over 50 million card transactions. On CSV the engine reads around 16 GB. On sorted Parquet it reads perhaps 15 MB. Same answer, a thousand times less work.

    Spark

    1. Plan. A driver program builds the plan. Steps like filter and join are lazy: they only add to the plan until an action such as a write or a count runs it.
    2. Split. The data is cut into partitions. Each partition is handled by one task on one core of an executor (a worker machine).
    3. Shuffle when needed. A join needs rows with the same key on the same machine, so every machine sends pieces to every other. Shuffles are where jobs get slow and break.
    Part 4

    How to read it

    • Lineage question. Can I name every source behind this figure, and the code version? If any step is "someone's spreadsheet", the answer is no.
    • A query that reads 16 GB for 15 MB of answer is a format problem: check columns, sorting and file size before buying more machines.
    • A Spark job where one task runs far longer than the rest usually means one key holds far more rows than the others (skew).
    • Thousands of tiny files are slow. Aim for files of roughly 100 MB to 1 GB.

    The classic lineage failure is a missing arrow. If a manager's Excel override changes the figure but nobody registered it, the graph looks complete and is wrong.

    Part 5

    Which to use

    NeedUseWhy
    Prove a figure's originLineage at column and run levelAnswers audit questions and reproduces the number
    Analytics on big tablesParquet, not CSVReads only needed columns and blocks
    Fetch or update single rowsA database with an indexParquet files cannot be edited in place
    Data fits on one machine (up to hundreds of GB)DuckDB or PolarsSimple, fast, no cluster
    Billions of rows, joins that do not fitSparkSpreads work over many machines

    Strong at: Parquet and Spark make large analytics fast and cheap; lineage makes numbers defensible.

    Weak at: lineage is only as good as its coverage, Parquet is poor for row updates (table formats such as Delta Lake and Iceberg add a transaction log), and Spark is overkill for small data.

    In banking, the Basel Committee's BCBS 239 principles ask large banks for accurate, complete data with clear ownership and a reconstructable path from source to report; which local rules bind you is a question for compliance and model risk.

    Part 6

    Common mistakes and quick check

    • Lineage drawn by hand

      A diagram goes stale within weeks. Capture lineage from the jobs themselves.

    • Partitioning by customer ID

      It makes millions of tiny folders. Partition by a low-variety column you filter on, usually date.

    • SELECT * on a wide table

      It throws away the column advantage of Parquet. Name the columns you need.

    • Using Spark for small data

      The cluster set-up costs more than the work. Try DuckDB first.

    1. What is lineage in one line?

    The recorded chain from source systems to a final figure.

    2. Why is Parquet faster than CSV for averaging two columns?

    It stores columns separately, so only those two are read, and blocks outside the filter are skipped.

    3. Why does sorting by date help a one-day query?

    Each block then covers a narrow date range, so most blocks can be skipped unread.

    4. What is a shuffle and why does it matter?

    Machines exchanging data so rows with the same key meet. It is the slowest and most failure-prone part of a Spark job.

    5. Column-level or run-level lineage: which makes a number reproducible?

    Run-level, because it records the exact data versions and code commit used.
