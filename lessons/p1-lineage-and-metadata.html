    Lineage, Columnar Formats and Spark: Knowing Where Data Came From and Moving It Fast

    How a number is traced back to its source for an auditor, why Parquet and DuckDB scan billions of rows in seconds by reading less, and what changes when the data no longer fits on one machine: partitions, shuffles and lazy plans.

    Contents

    The whole lesson in one sentenceLineage is a recorded map of how every number was made, so you can answer "where did this come from" and "what breaks if this changes"; columnar files are fast because they let an engine skip almost everything it does not need; and Spark is what you reach for only when one machine truly is not enough, at the price of a shuffle that moves data across the network and can be wrecked by a single hot key.

    Part 1

    The intuition

    Three situations, one theme: the data is big and tangled, and you need to deal with it without reading or trusting more than necessary.

    The auditor. A regulator's examiner points at a line in a large-exposures return: AED 1.84 billion to one corporate group. "Show me where that came from." If the answer is "a query someone wrote two years ago, run by a notebook that has since been deleted", you have a problem larger than the number. Lineage is the recorded chain from source system to final figure. Metadata, data about data, is what lets that chain be read: who owns each table, what each column means, when it last refreshed, how it was built.

    The slow query. A risk analyst filters 50 million card transactions to one day and averages two columns. On a CSV file this reads every byte of every column, around 16 GB. On a columnar Parquet file the engine reads two columns, skips 49 of 50 blocks of rows using stored minimum and maximum values, and touches perhaps 15 MB. Same answer, a thousand times less work. That is not magic, it is layout.

    The big job. The nightly feature build joins two billion transactions to customers. It will not fit in one machine's memory, or finish in the night on one machine's cores. Spark splits the data into partitions spread over many machines. Anything that needs rows with the same key together, a join or a group-by, forces a shuffle: every machine sends pieces of its data to every other. Shuffles are where the time goes, and where things go wrong.

    That graph walk is the whole of lineage as a tool: a directed graph of "produced from" edges, searched upstream for an audit and downstream for impact analysis. The hard part is never the search. It is keeping the graph complete and current without asking busy people to maintain it by hand. The Excel override in the picture is the classic failure: the number came from somewhere the catalogue never saw.

    Columnar storage and Spark are different tools for the same underlying concern, which is cost. Both are about avoiding work. Columnar formats avoid reading bytes. Spark avoids waiting by splitting the job. And both are why you should usually try the smaller tool first.

    Hold onto thisEvery number a bank publishes needs an answer to three questions: where did it come from, what happens if its inputs change, and can we recompute it. Lineage answers the first two, reproducible pipelines answer the third. Speed topics (Parquet, Spark) only matter once those are in place.
    Part 2

    How it really works

    Lineage and metadata (P1.5)

    Metadata comes in four useful kinds.

    KindExamplesWho needs it
    TechnicalSchema, column types, file format, partition layout, row counts, table versionEngineers; query engines
    Business"Exposure" means drawn plus undrawn, in AED, at month end; glossary terms; data owner and stewardAnalysts, risk, auditors
    OperationalLast successful run, duration, rows in and out, failed checks, freshnessOn-call engineers; monitoring
    GovernanceSensitivity class (PII), retention period, access policy, approved usesCompliance, privacy, security

    Lineage comes at several grains, and the grain decides what questions you can answer.

    • Table-level: gold.exposure_aed was built from clean.transactions and clean.customers. Cheap, and enough for most impact analysis.
    • Column-level: the column exposure_aed comes from amount × fx_rate, with fx_rate from the raw FX feed. This is what an auditor asking about one figure and a privacy officer asking "which downstream columns contain a national ID" both need. Harder to capture, because it means parsing every expression.
    • Run-level (operational): this exact run, at 02:14 on 3 March, read these specific table versions with this code commit. This is what makes a number reproducible, not just explainable.

    How lineage is captured, from weakest to strongest:

    1. Documented by hand. A diagram or spreadsheet. It starts out right and drifts wrong within weeks. Fine as a starting point, never as evidence.
    2. Parsed from code. A tool reads SQL (or dbt models) and infers the graph from FROM and JOIN clauses. Gets column-level lineage for SQL, misses logic hidden in Python or in a UI tool.
    3. Emitted at runtime. The scheduler or engine reports "job X read datasets A and B and wrote C" as it runs. OpenLineage is an open standard for these events, with integrations for Airflow, Spark and dbt; catalogues such as Marquez and DataHub can store them, and some commercial platforms ship their own lineage. This captures what actually ran, including Python.

    Even runtime capture has holes: a hand-run notebook, an Excel file, a CSV emailed to treasury, a manual adjustment keyed into a report tool. The honest design admits this. Make those hand-offs rare, register them as explicit sources with an owner, and flag any dataset whose lineage ends at "unknown".

    Why a bank cares beyond tidiness. The Basel Committee's BCBS 239 principles on risk data aggregation and reporting, which large banks are expected to follow, ask for accurate, complete, timely data with clear ownership and a documented, reconstructable path from source to report. The text speaks of data "taxonomies and architecture", not of lineage tools, so a catalogue is a means rather than a requirement. Which local rules (CBUAE, SAMA) bind your institution, and how strictly, is a question for your compliance and model-risk teams; do not assert it in a meeting without checking.

    Lineage for models. A prediction is only auditable if you can name the model version, the training dataset version, the feature definitions and the code commit behind it. That extends the same graph one step: dataset versions in, model out, predictions out. P2.1 builds the full lifecycle on this; this lesson only needs the idea that a model is another node in the graph, and a particularly important one for validators (G3.2).

    A last practical point: data contracts and quality checks are the other half of metadata. A contract states what a producer promises (schema, freshness, null rates). A failed check is operational metadata that should stop downstream jobs. Lineage tells you who is affected when a contract breaks.

    Columnar formats and query engines (P1.6)

    A table is a grid. You must lay it out in a one-dimensional file, and there are two natural ways.

    • Row layout (CSV, a database page): all fields of row 1, then all of row 2, and so on. Perfect for "fetch customer 4021" or "insert one payment", since one row is stored together. This is how transactional databases work.
    • Column layout (Parquet, ORC, Arrow in memory): all values of column 1, then all of column 2. Perfect for "average of amount for last Tuesday", which touches 2 of 40 columns. Analytics wants a few columns across many rows.

    Parquet actually uses a hybrid, and the detail is what makes it fast. A file is cut into row groups (often around a million rows, or 128 MB or so; the exact size is a writer setting). Inside each row group each column is stored as a contiguous column chunk, split into pages. A footer at the end lists, for every column chunk, its location and statistics, including the minimum and maximum value. Four tricks follow.

    1. Projection pushdown. Read only the columns the query names. Reading 4 of 40 columns is a 10x cut before anything else.
    2. Predicate pushdown / zone maps. For WHERE txn_date = '2026-03-03', check each row group's min and max for txn_date. A group whose range is 1–2 March cannot contain it and is skipped without being read. This only pays when similar values sit together, which is why sorting or clustering the data by the filter column is the single biggest tuning step.
    3. Compression that works because values are alike. A column holds one type, often with few distinct values (currency, channel, branch). Dictionary encoding replaces "AED" with a small integer; run-length encoding turns "AED, AED, AED, ..." into "AED × 40,000"; delta encoding stores sorted timestamps as small differences. A general compressor such as zstd or Snappy then squeezes further. Ratios of 3x to 10x against CSV are typical, and they depend heavily on the data.
    4. Vectorised execution. Engines like DuckDB process values in batches of a couple of thousand rather than one row at a time, so the CPU runs tight loops over arrays, uses its cache well and can apply SIMD instructions. This is the idea from MonetDB/X100 and is why a laptop can scan hundreds of millions of rows a second.

    Where the engines fit. The file format is only the storage. A query engine reads it. DuckDB runs inside your Python process or notebook, reads Parquet (and CSV, JSON, and data in memory such as a pandas or Arrow table) directly, and executes SQL with the vectorised tricks above. It is single-machine, and on a modern laptop or a 32-core server it handles tens or hundreds of gigabytes comfortably. Polars is a similar single-machine option from the DataFrame side. Spark, Trino and cloud warehouses spread the same ideas over many machines. Arrow is the in-memory columnar format that lets these tools hand data to one another without converting it.

    import duckdb

# Reads only 3 columns, and skips row groups whose txn_date range excludes the day
duckdb.sql("""
    SELECT channel, count(*) AS n, avg(amount_aed) AS avg_aed
    FROM 'txns/*.parquet'
    WHERE txn_date = DATE '2026-03-03'
    GROUP BY channel
""").df()

# What would it do? Look for the pushed-down filter and projected columns in the plan
duckdb.sql("EXPLAIN SELECT channel FROM 'txns/*.parquet' WHERE txn_date = DATE '2026-03-03'")

    Row layout is still right sometimes. Fetching one account's record 10,000 times a second (an online service), or inserting and updating individual rows, is a transactional workload; a row store with an index wins. This is the offline versus online split of P1.4. Also, Parquet files are immutable: you do not edit a row in place. Table formats such as Delta Lake and Apache Iceberg add a transaction log on top of Parquet to give updates, deletes, time travel and schema evolution, which is the lakehouse idea of P1.1 to P1.3.

    Practical habits: write Parquet, not CSV, for anything analytic; aim for files of roughly 100 MB to 1 GB (thousands of tiny files are slow, since each costs a metadata fetch); partition directories by a low-cardinality column you filter on, usually date; sort within files by the next most common filter; and never partition by customer ID, which creates millions of directories.

    Spark and distributed processing, in brief (P1.7)

    The architecture. A driver program plans the job. A cluster of executors, processes on many machines, do the work. Data lives as partitions, chunks of rows, and each partition is processed by one task on one core. If you have 64 cores and 200 partitions, tasks run in waves of 64.

    Lazy evaluation. In Spark, transformations such as filter, select, join and groupBy do nothing when called. They add a step to a logical plan. Only an action (count, show, collect, a write) makes Spark run it. This lets the Catalyst optimiser see the whole plan, push filters and column selection down to the Parquet scan, reorder joins and fuse steps together, exactly the tricks above. It also means an error in line 3 may surface at line 40, and that a DataFrame you keep reusing is recomputed each time unless you cache it.

    from pyspark.sql import functions as F

txn  = spark.read.parquet("s3://bank-lake/clean/transactions")      # nothing read yet
cust = spark.read.parquet("s3://bank-lake/clean/customers")

feat = (txn.filter(F.col("txn_date") >= "2026-01-01")             # transformation
           .join(cust, "customer_id")                                 # wide: shuffle
           .groupBy("customer_id")                                    # wide: shuffle
           .agg(F.sum("amount_aed").alias("spend_ytd")))

feat.write.mode("overwrite").parquet("s3://bank-lake/gold/feat")      # action: runs it all
feat.explain()   # prints the physical plan: look for Exchange (= shuffle)

    Narrow and wide. A narrow transformation (filter, select, map) works on each partition on its own, so it is cheap and stays on one machine. A wide one (join, groupBy, distinct, sort) needs all rows with the same key in the same place. Spark hashes the key, sends each row to the partition that owns that hash, across the network, and often writes intermediate data to disk first. That is the shuffle, shown as Exchange in a plan. A job is cut into stages at each shuffle. The performance rule is short: count your shuffles and shrink the data before them.

    Three things that go wrong in practice.

    • Skew. A key shared by a large fraction of rows lands entirely in one partition, so one task does most of the work while the other cores idle. In banking: a null or "UNKNOWN" merchant ID, a default branch code, a corporate payroll account. The stage lasts as long as its slowest task.
    • Too few or too many partitions. Too few leaves cores idle and tasks too large for memory. Too many means each task does little and scheduling overhead dominates. A common starting point is two to four partitions per core, with partitions of roughly 100 to 200 MB.
    • Pulling data to the driver. collect() or toPandas() on a big result crashes the one machine that was never meant to hold it.

    The standard remedies. A broadcast join sends a small table to every executor so the big one is never shuffled (a 50 MB branch lookup joined to a billion transactions). Adaptive query execution (on by default in recent Spark) re-plans at run time: it merges small shuffle partitions, switches to a broadcast join when a side turns out small, and splits skewed partitions in joins. Salting adds a random suffix to a hot key so its rows spread over many partitions, at the price of a second aggregation step to combine them.

    Spark is not the default. Spark's overhead, from the JVM, the scheduler and the shuffle, is large. If your data is below roughly 100 to 500 GB in Parquet, DuckDB or Polars on one big machine is often faster, cheaper and much simpler to debug. Spark earns its place when data is genuinely terabytes, when you need many machines' memory for a join, or when your platform (Databricks, a Hadoop-style estate, Spark on Kubernetes) already runs everything on it. The test is simple: try the single-machine tool on a sample and extrapolate before building a cluster job.

    How it connects

    This lesson is the plumbing under most of the rest of the curriculum. Here is where it surfaces.

    P1.1 – P1.3 · Warehouses, lakes, lakehousesWhere the Parquet files live

    Delta and Iceberg are a transaction log over Parquet. Their snapshots are also what make run-level lineage ("this table version") possible.

    P1.4 · Feature storesOffline scans, online lookups

    The offline store is columnar and scanned; the online store is row-oriented and looked up. The same feature definition must feed both, and lineage proves it did.

    P2 · Model lifecycleA model is a node in the graph

    Registering a model with its dataset version, code commit and feature definitions extends lineage to predictions.

    P2 · Prompt versioning and tracingLineage for LLM systems

    For a retrieval system, lineage means which documents, which index version and which prompt produced an answer.

    F3.1 · Leakage and point in timeTime travel makes it possible

    Rebuilding a training set "as of" a date needs versioned tables and a record of when each value arrived. Lineage and snapshots are the infrastructure for that.

    F3.3 · SQL thinkingThe same SQL, three engines

    The SQL you write runs on DuckDB, Spark or a warehouse; the optimiser decides what to read. Joins are where the shuffle comes from.

    G3 · Model risk and validationWhat a validator asks for

    Independent validators need to reproduce the development data. See also ongoing monitoring, which relies on operational metadata such as freshness and volumes.

    F7 · Drift monitoringWhere did the shift come from?

    When a feature drifts, downstream lineage tells you which models are affected; upstream lineage tells you which source changed.

    G2 · PrivacyFind every copy of the national ID

    Column-level lineage with sensitivity tags is how you answer "where does this personal data flow" and honour deletion or minimisation duties.

    P4 · Cloud and on-premisesWhere the cluster runs

    Data residency rules may keep the lake and the Spark cluster in-country. See also cloud building blocks.

    Where it shows up at the bank:

    • Regulatory returns and risk reports. Large exposures, liquidity ratios, IFRS 9 provisions (B4.2). Every figure needs a traceable path, and every change to a source needs an impact check.
    • Fraud and AML feature pipelines. Billions of rows, nightly batches, and a hard need to rebuild last quarter's features exactly. Columnar formats, partition pruning and Spark carry the volume; lineage carries the proof. See delayed labels for why history must be reproducible.
    • Customer 360 and marketing. Joins across core banking, cards, digital channels and CRM, where a skewed key (a default branch, a null customer ID) quietly makes jobs hours slower.
    • Data scientists' own work. Most analysis on a few hundred million rows is DuckDB on Parquet in a notebook, not a cluster.

    Part 5

    How it fails, and how to spot it

    Each one has a quick check.

    • Lineage that ends at a person

      The trail reaches "the treasury spreadsheet" or a file emailed monthly. The catalogue looks complete and the audit answer is incomplete.

      Spot itFor any key regulatory figure, walk the trail to a system of record. Any dataset with no recorded upstream, or a human-edited file in the middle, is a gap to register and own.
    • Lineage as a one-off diagram

      A project produced a beautiful map before an audit. A year on, half the jobs have changed.

      Spot itAsk when the lineage was last generated and from what. If the answer is a person, it is stale. Look for a "last captured" timestamp per edge.
    • Table-level lineage used to answer column-level questions

      "Which reports contain customer national ID?" answered by "every report downstream of the customer table". Overstates, or misses derived columns.

      Spot itAsk at what grain the lineage is captured, and whether it follows expressions such as hashing, joins and concatenation.
    • A definition that exists only in a dashboard

      Two reports show different "active customers" because each defines it in its own query.

      Spot itAsk where the metric is defined. There should be one governed definition, referenced by both.
    • CSV, or many tiny Parquet files, in a big analytic pipeline

      Slow scans, large storage bills, jobs that spend most of their time opening files.

      Spot itCount files and average size in the table directory. Thousands of files under 10 MB, or any CSV above a few GB, need compaction or conversion.
    • Filters that cannot be pushed down

      A filter wrapped in a function (WHERE substr(txn_ts, 1, 10) = ...) or applied after a join, so zone maps and partitions are ignored and everything is read.

      Spot itRun EXPLAIN. The scan node should show the filter and the projected columns, and the bytes read should be a small share of the table.
    • Partitioning on a high-cardinality column

      Partitioning by customer ID or by minute produces millions of small directories and files.

      Spot itLook at partition counts. Hundreds to a few thousand is reasonable; millions is a bug.
    • Skewed keys that make a stage hang at 99%

      199 of 200 tasks finish quickly; one runs for an hour, usually on null, "UNKNOWN" or a default code.

      Spot itIn the Spark UI, compare task durations and input sizes in the slow stage. One task far above the median is skew. Count rows per join key to find the culprit.
    • Using a cluster where one machine would do

      A 40 GB table processed on a 20-node Spark cluster that takes longer to start than DuckDB takes to finish.

      Spot itCompare data size with one machine's memory and disk; time a single-node run on a sample before sizing a cluster.
    • Surprise from lazy evaluation

      Code "runs" instantly and fails later, or a DataFrame recomputed five times because nobody cached it, or a random sample that differs between actions.

      Spot itLook at the physical plan and the count of jobs in the UI. Repeated identical scans mean a missing cache or a persisted intermediate.
    Part 6

    What to say in the room

    To an executive or auditor · 30 seconds
    “For every figure we report, we can show the chain from the source system through each transformation to the final number, and we can list every report that depends on a given source if it changes. We capture that automatically from the jobs that run, not from a diagram someone drew. Where a figure still passes through a manual step, such as a spreadsheet adjustment, we have registered it as an owned source and are working to remove it.”
    To a data-platform engineer or architect
    “I'd keep analytic data as Parquet in an open table format, partitioned by date and sorted on our main filter column so zone maps do the work, with files around a few hundred megabytes. Lineage is emitted at run time, ideally with OpenLineage from the orchestrator and Spark, and enriched with column-level parsing of SQL. For jobs under a few hundred gigabytes I'd try DuckDB first. Where we need Spark, I'd count the shuffles, broadcast the small side of joins, leave adaptive execution on, and watch for key skew.”
    “Why do we need a data catalogue? We have documentation.”

    Documentation is written once and drifts. A catalogue that captures lineage and operational metadata from the jobs themselves stays current, and answers two questions documents can't: what does this number depend on, and what is affected if this source changes. That is what audits and incident response need.

    “Why is Parquet so much faster than CSV?”

    Three reasons. It stores columns together, so a query reads only the columns it names. It stores min and max per block, so a filter can skip whole blocks. And similar values compress very well. CSV has none of these: every query parses every byte. The trade-off is that Parquet files are not edited in place, so updates need a table format on top.

    “Should we move this to Spark?”

    Only if it needs it. I'd check the size of the data after filtering and selecting columns; if it fits comfortably on one machine, DuckDB or Polars is faster to build and cheaper to run. Spark is justified by terabytes, by a join that needs more memory than one node has, or by an existing platform. I'd test on a sample before committing.

    “The Spark job has been at 99% for an hour.”

    Most likely one partition is far bigger than the rest, usually skew on a key such as null or a default code. I'd open the stage's task list to compare durations, count rows per key, then broadcast the small side of the join, enable adaptive skew handling, or salt the hot key. Adding machines won't help; the one slow task is the bottleneck.

    “Do regulators require lineage tooling?”

    I would not claim they do. BCBS 239 sets outcomes: accurate, complete, timely risk data with documented sources and ownership. Lineage tooling is a common way to evidence that. What our local regulator expects in detail is a question for compliance, and I'd confirm it before making any statement.

    Part 7

    Self-check

    Try each one before opening the answer.

    1. What is the difference between audit lineage and impact analysis, and what graph operation is each?

    Audit asks "what does this figure depend on": search upstream (ancestors) from the figure. Impact analysis asks "what is affected if this changes": search downstream (descendants) from the source. Same graph, opposite directions.

    2. Why is table-level lineage not enough for a privacy question such as "where does national ID flow"?

    A table may contain 80 columns and only one holds the ID. Table-level lineage marks every downstream table as touched. Column-level lineage follows the specific column (and anything derived from it) so you can say which reports truly contain it.

    3. A table has 40 columns of 8 bytes and 50 million rows. A query touches 4 columns and one day of 30 (clustered by date). Roughly what does it read in a row store versus Parquet at 30% compression?

    Raw size is 50M × 40 × 8 = 16 GB, which a row store reads in full. Parquet reads 4 columns: 4 × 0.4 GB = 1.6 GB raw, × 0.3 = 0.48 GB. Zone maps keep roughly 1/30 of the row groups (the next whole group, so 2 of 50 here): 0.48 × 2/50 ≈ 19 MB. About 800 times less.

    4. Why does clustering by date matter for zone maps?

    Min/max statistics only exclude a block if the block's range excludes the filter value. If dates are mixed throughout the file, every block spans the whole range, so none can be skipped. If rows are sorted by date, each block covers a narrow range and most are skipped.

    5. Name a transformation that causes a shuffle and one that does not. Why the difference?

    filter and select work on each partition independently, so no shuffle. groupBy and a join on a non-broadcast table need all rows with the same key in the same partition, so rows must be sent across the network to the partition that owns their key hash.

    6. In Spark you write ten lines of transformations and nothing happens. Why, and what is the benefit?

    Transformations are lazy: they add steps to a plan. Only an action triggers execution. The benefit is that the optimiser sees the whole plan, so it can push filters and column choices down to the file scan, choose join strategies and fuse narrow steps. The cost is that errors appear late and reused results are recomputed unless cached.

    7. With 200 million rows, 64 cores and 20% of rows on one key, why does raising shuffle partitions from 200 to 2,000 barely help?

    All rows with the hot key go to the same partition however many partitions exist: that is 40 million rows, versus about 0.8 million in each of the others at 200 partitions. The stage lasts as long as that task. Fix the skew by salting the key, broadcasting the smaller side or letting adaptive execution split the partition.

    8. When is DuckDB the better choice than Spark?

    When the working data (after column selection and filters) fits on one machine, up to hundreds of gigabytes in many cases. It starts instantly, needs no cluster, and is easy to debug. Spark's advantage appears when data or memory needs exceed one node, or when the surrounding platform is already built on it.
