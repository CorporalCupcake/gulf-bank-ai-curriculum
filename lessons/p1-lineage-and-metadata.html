    Lineage, Columnar Formats and Spark: Knowing Where Data Came From and Moving It Fast

    How a number is traced back to its source for an auditor, why Parquet and DuckDB scan billions of rows in seconds by reading less, and what changes when the data no longer fits on one machine: partitions, shuffles and lazy plans.

    Contents

    The whole lesson in one sentenceLineage is a recorded map of how every number was made, answering "where did this come from" and "what breaks if this changes"; columnar files are fast because the engine skips almost everything it does not need; Spark is for when one machine truly is not enough, at the price of a shuffle that a single hot key can wreck.

    Part 1

    The intuition

    The auditor. An examiner points at AED 1.84 billion to one corporate group in a large-exposures return: "Show me where that came from." If the answer is "a query someone wrote two years ago, in a notebook since deleted", the problem is bigger than the number. Lineage is the recorded chain from source system to final figure, like the receipts behind an expense claim. Metadata, data about data, makes the chain readable.

    The slow query. An analyst filters 50 million card transactions to one day and averages two columns. On CSV the engine reads around 16 GB. On columnar Parquet it reads two columns and skips 49 of 50 row blocks: perhaps 15 MB. Same answer, a thousand times less work, like using a book's index instead of reading every page.

    The big job. A nightly feature build joins two billion transactions to customers and will not fit on one machine. Spark splits the data into partitions across many machines. A join needs rows with the same key together, forcing a shuffle: every machine sends pieces to every other, like postal sorters passing bundles until each town's mail is in one bin. Shuffles are where the time goes and where things break.

    That graph walk is all lineage is as a tool: a graph of "produced from" edges, searched upstream for an audit and downstream for impact. The hard part is keeping it complete and current. The Excel override above is the classic failure: the number came from somewhere the catalogue never saw.

    Hold onto thisEvery published number needs three answers: where did it come from, what happens if its inputs change, and can we recompute it. Speed (Parquet, Spark) matters only after these.
    Part 2

    How it really works

    Lineage and metadata (P1.5)

    Metadata comes in four useful kinds: technical (schema, types, row counts), business (what "exposure" means, who owns it), operational (last run, failed checks, freshness) and governance (sensitivity class, retention, approved uses).

    Lineage comes at three grains, and the grain decides which questions you can answer.

    • Table-level: gold.exposure_aed was built from clean.transactions and clean.customers. Cheap, and enough for most impact analysis.
    • Column-level: exposure_aed comes from amount × fx_rate. Auditors asking about one figure need this, and so does a privacy officer asking "which downstream columns contain a national ID".
    • Run-level: this exact run read these table versions with this code commit. This makes a number reproducible, not just explainable.

    Capture methods, weakest to strongest: by hand (a diagram; wrong within weeks), parsed from code (a tool reads SQL or dbt models; misses Python and UI tools) and emitted at runtime (the scheduler reports "job X read A and B and wrote C"; OpenLineage is the open standard). Even runtime capture misses a hand-run notebook, an Excel file or a CSV emailed to treasury. Register these as owned sources and flag any dataset whose lineage ends at "unknown".

    Why a bank cares. The Basel Committee's BCBS 239 principles ask large banks for accurate, complete data with clear ownership and a reconstructable path from source to report. Which local rules (CBUAE, SAMA) bind your institution is a question for compliance and model risk.

    Lineage for models. A prediction is auditable only if you can name the model version, training data version, feature definitions and code commit. A model is just another node in the graph, and a key one for validators (G3.2).

    Contracts and checks. A data contract states what a producer promises (schema, freshness, null rates). A failed check should stop downstream jobs, and lineage tells you who is affected.

    Columnar formats and query engines (P1.6)

    A table is a grid, but a file is a line, so you must choose how to flatten it. Think of a spreadsheet saved row by row or column by column.

    • Row layout (CSV, a database page): all fields of row 1, then row 2. Ideal for "fetch customer 4021".
    • Column layout (Parquet, ORC): all values of column 1, then column 2. Ideal for "average amount for last Tuesday", which touches 2 of 40 columns.

    Parquet cuts a file into row groups, and a footer records each column chunk's minimum and maximum. Three tricks follow.

    1. Projection pushdown. Read only the columns named. 4 of 40 columns is a 10x cut at once.
    2. Predicate pushdown (zone maps). For WHERE txn_date = '2026-03-03', a row group whose min and max span 1–2 March cannot contain it and is skipped unread, like skipping a shelf labelled A–C when you want a surname starting with M. It only pays when similar values sit together, so sorting by the filter column is the biggest tuning step.
    3. Compression that works because values are alike. A column holds one type with few distinct values (currency, channel), so it squeezes well: 3x to 10x against CSV is typical.

    Engines such as DuckDB also process values in batches rather than row by row, which is why a laptop scans hundreds of millions of rows a second.

    Where the engines fit. Parquet is only storage; a query engine reads it. DuckDB runs inside your Python process and reads Parquet, CSV and pandas tables directly with SQL. On a laptop or server it handles tens to hundreds of GB. Polars is the DataFrame-style equivalent. Spark, Trino and cloud warehouses spread the same ideas over many machines.

    import duckdb

# Reads only 3 columns, and skips row groups whose txn_date range excludes the day
duckdb.sql("""
    SELECT channel, count(*) AS n, avg(amount_aed) AS avg_aed
    FROM 'txns/*.parquet'
    WHERE txn_date = DATE '2026-03-03'
    GROUP BY channel
""").df()

# What would it do? Look for the pushed-down filter and projected columns in the plan
duckdb.sql("EXPLAIN SELECT channel FROM 'txns/*.parquet' WHERE txn_date = DATE '2026-03-03'")

    Row layout still wins sometimes. Fetching one account 10,000 times a second, or updating single rows, is transactional work, where a row store with an index wins (P1.4). Parquet files are immutable; Delta Lake and Iceberg add a transaction log for updates and time travel (P1.1 to P1.3).

    Habits: write Parquet, not CSV, for analytics; aim for files of 100 MB to 1 GB, since thousands of tiny files are slow; partition by a low-cardinality column you filter on, usually date, and never by customer ID.

    Spark and distributed processing, in brief (P1.7)

    How it works. A driver plans the job; executors on many machines do the work. Data lives as partitions (chunks of rows), each handled by one task on one core.

    Lazy evaluation. Like writing a shopping list before going to the shop, transformations (filter, join, groupBy) only add steps to a plan. An action (count, a write) runs it. The optimiser sees the whole plan and pushes filters and column choices down to the Parquet scan. The cost: an error in line 3 may surface at line 40, and a reused DataFrame is recomputed unless cached.

    from pyspark.sql import functions as F

txn  = spark.read.parquet("s3://bank-lake/clean/transactions")      # nothing read yet
cust = spark.read.parquet("s3://bank-lake/clean/customers")

feat = (txn.filter(F.col("txn_date") >= "2026-01-01")             # transformation
           .join(cust, "customer_id")                                 # wide: shuffle
           .groupBy("customer_id")                                    # wide: shuffle
           .agg(F.sum("amount_aed").alias("spend_ytd")))

feat.write.mode("overwrite").parquet("s3://bank-lake/gold/feat")      # action: runs it all
feat.explain()   # prints the physical plan: look for Exchange (= shuffle)

    Narrow and wide. A narrow step (filter, select) works on each partition alone: cheap. A wide one (join, groupBy, sort) needs all rows with the same key in one place, so rows travel across the network. That is the shuffle, shown as Exchange in a plan. Rule: count your shuffles and shrink the data before them.

    What goes wrong, and the fixes.

    • Skew. A common key (null, "UNKNOWN", a default branch code) lands in one partition, so one task works while the other cores idle, like one till with a queue while the rest stand empty. Fixes: salting (a random suffix spreads the hot key, at the cost of a second aggregation) or adaptive query execution (default in recent Spark), which splits skewed partitions at run time.
    • Too few or too many partitions. Too few leaves cores idle; too many lets scheduling overhead dominate. Aim for a few partitions per core.
    • Pulling data to the driver. collect() or toPandas() on a big result crashes the one machine never meant to hold it. Use a broadcast join (send a small table to every executor) to avoid shuffling the big one.

    Spark is not the default. Its overhead is large, like hiring a removals lorry to carry one box. Below roughly 100 to 500 GB of Parquet, DuckDB or Polars on one big machine is often faster, cheaper and easier to debug. Spark earns its place at genuine terabytes, when a join needs many machines' memory, or when your platform already runs on it. Test a single-machine tool on a sample first.

    Part 3

    How it fails, and how to spot it

    • Lineage that ends at a person

      The trail stops at "the treasury spreadsheet". The catalogue looks complete; the audit answer is not.

      Spot itWalk each key figure back to a system of record. A dataset with no upstream, or a human-edited file in the middle, is a gap to register and own.
    • Lineage as a one-off diagram

      A map drawn before an audit; a year on, half the jobs have changed.

      Spot itAsk when it was last generated and from what. If the answer is a person, it is stale.
    • Table-level lineage used for column-level questions

      "Which reports contain national ID?" answered with "every report downstream of the customer table". That overstates, or misses derived columns.

      Spot itAsk the grain, and whether it follows expressions such as hashing and concatenation.
    • Slow scans from the wrong files

      CSV, thousands of tiny Parquet files, or a filter wrapped in a function (WHERE substr(txn_ts, 1, 10) = ...) means everything is read and jobs spend their time opening files.

      Spot itCount files and average size, and run EXPLAIN: the scan should show the filter and projected columns and read a small share of the table.
    • Skewed keys that make a stage hang at 99%

      199 of 200 tasks finish quickly; one runs for an hour, usually on null, "UNKNOWN" or a default code.

      Spot itIn the Spark UI, compare task durations. One far above the median is skew. Count rows per join key to find it.
    • A cluster where one machine would do, or lazy surprises

      A 40 GB table on a 20-node cluster that takes longer to start than DuckDB takes to finish. Or code that "runs" instantly, fails later and recomputes a DataFrame five times.

      Spot itCompare data size with one machine's memory; time a single-node run on a sample. Repeated identical scans in the plan mean a missing cache.
    Part 4

    Self-check

    1. What is the difference between audit lineage and impact analysis, and what graph operation is each?

    Audit asks "what does this figure depend on": search upstream from the figure. Impact asks "what is affected if this changes": search downstream from the source. Same graph, opposite directions.

    2. Why is table-level lineage not enough for a privacy question such as "where does national ID flow"?

    A table may have 80 columns and only one holds the ID. Table-level lineage flags every downstream table. Column-level lineage follows that column and its derivatives, so you can say which reports truly contain it.

    3. A query touches 4 of 40 columns and one day of 30. Why does it read far less on Parquet than on CSV, and which of the savings depends on how the data was written?

    Reading only 4 columns cuts the bytes by roughly 10x, and compression cuts more; both come from the format itself. Skipping 29 of every 30 row blocks depends on the data being sorted or clustered by date when it was written. Without that, the min/max ranges overlap and nothing is skipped.

    4. Why does clustering by date matter for zone maps?

    A block is skipped only if its min/max range excludes the filter value. With dates mixed throughout, every block spans the whole range and none is skipped. Sorted by date, each block covers a narrow range and most are skipped.

    5. Name a transformation that causes a shuffle and one that does not. Why the difference?

    filter and select work on each partition independently, so no shuffle. groupBy and a join on a non-broadcast table need all rows with the same key in the same partition, so rows must be sent across the network to the partition that owns their key hash.

    6. In Spark you write ten lines of transformations and nothing happens. Why, and what is the benefit?

    Transformations are lazy: they add steps to a plan, and only an action runs it. The optimiser sees the whole plan, so it can push filters and columns down to the scan, choose join strategies and fuse narrow steps. The cost: errors appear late and reused results are recomputed unless cached.

    7. With 200 million rows, 64 cores and 20% of rows on one key, why does raising shuffle partitions from 200 to 2,000 barely help?

    Every hot-key row goes to one partition however many exist: 40 million rows, versus about 0.8 million in each other partition at 200. The stage lasts as long as that task. Salt the key, broadcast the smaller side or let adaptive execution split it.

    8. When is DuckDB the better choice than Spark?

    When the working data, after column selection and filters, fits on one machine (often hundreds of GB). It starts instantly, needs no cluster and is easy to debug. Spark wins when data or memory exceed one node, or the platform is already built on it.
